The timing contract hinges on distinguishing the sampled edge from mid-cycle input changes. All inputs are driven before the sampled posedge and are stable at that edge; the checker should evaluate the design using the values present at the posedge, not any values that appear afterward. The phrase "sample after the posedge edge has settled" means the outputs and next-state decisions are observed after the clock edge has propagated through the sequential logic. Thus, for each row, the relevant inputs are those driven before the sampled edge, and the expected outputs are the post-edge settled values.

Mid-input changes are explicitly "after sampling, before the other edge, and carried to the start of the next row." This means a mid-cycle change does not affect the current row's sampled behavior. It becomes the starting input value for the next row. The checker must therefore maintain a notion of "current row inputs" that are latched at the sampled edge, while allowing inputs to change between edges without retroactively altering the previous row's expected outputs. In practice, the testbench should apply the row's inputs, wait for the posedge, sample outputs after settling, then optionally apply mid changes, and only then proceed to the next row's pre-edge inputs.

The branch history register update is the main sequential element. On a prediction request, the predicted direction is computed from the current PHT entry and the current global history, and the history register is updated at the next posedge for the predicted branch. On a training request, the PHT entry is updated at the next posedge, and if the branch was mispredicted, the history register is recovered to the state immediately after the mispredicting branch. The spec gives priority: if training for a misprediction and a prediction occur in the same cycle, training wins for the history register because the predicted instruction will be flushed. The PHT read for prediction must see the pre-edge state even if training targets the same entry in that cycle; training's PHT write is visible only in the following cycle.

A useful checker point is that prediction outputs in a cycle must be computed from the PHT and history state as they exist before that cycle's posedge, regardless of simultaneous training. The training PHT update and any history recovery take effect after the edge. For the history register, the same-cycle conflict rule means the checker should not apply the prediction's history update if a mispredicted training is also valid in that cycle; the training recovery value wins.

Short worked example: suppose at cycle 4 both predict_valid and train_valid are high, training is mispredicted, and both refer to PHT entry 0. The prediction output at cycle 4 must reflect the old PHT entry 0 and the old history. At the cycle-4 posedge, PHT entry 0 is updated per training, and the history register is set to the recovery value from train_history, not advanced for the prediction. In cycle 5, a subsequent prediction sees the new PHT entry and the recovered history. The checker should therefore separate "read state before edge" from "write state after edge" and enforce training precedence only for the history register, while PHT reads remain pre-edge.
