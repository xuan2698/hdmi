## Reset and Power-Up Behavior

The public specification states only that reset is asynchronous and active-high. That single sentence has several consequences the final Python checker should exercise deliberately, because reset interacts with both the prediction and training interfaces and with the two stateful elements (the 7-bit global history register and the 128-entry PHT of 2-bit saturating counters).

First, asynchronous assertion means the checker must not require a clock edge for reset to take effect. If `areset` is driven high between edges, the design is permitted (and expected) to clear the history register and the PHT immediately. The checker should therefore drive `areset=1` at an arbitrary point in the cycle, including while `predict_valid=1` or `train_valid=1` are asserted, and then verify that the post-reset state is the specified reset value rather than a value derived from those simultaneous requests. In particular, a prediction request coincident with reset must not leave a shifted history behind, and a training request coincident with reset must not leave a modified PHT entry behind. The cleanest sampling point is after `areset` is deasserted and the next posedge has settled; sampling during reset is fragile because the design may still be settling combinationally.

Second, power-up behavior without reset is not specified. The checker should not assume any particular initial PHT contents or history value before the first reset. Any directed test that depends on a known counter value (for example, to distinguish a pre-training counter from a post-training counter at the same index) must first apply a reset and then, if the reset value of the PHT is not pinned by the spec, either train the entry to a known state or avoid depending on the absolute counter value. The spec pins the history register width and the PHT organization but does not, in this pass, enumerate the reset encoding of each 2-bit counter; the checker should treat the post-reset PHT as "some defined state" unless a later pass fixes it, and should prefer tests that establish counter state through training rather than through reset.

Third, reset must dominate the same-cycle prediction/training arbitration. The spec says training takes precedence over prediction for the history register when both occur in the same cycle, but reset is a stronger condition: while `areset` is high, neither the prediction shift nor the training recovery should be observable in the post-reset state. A useful probe is to assert `areset` in the same cycle as a mispredicted training request with `train_history` set to a distinctive value, then release reset and confirm the history register reads the reset value, not `train_history`.

A short worked example illustrates the sampling discipline. Suppose the checker has trained the design so that history is `H0` and the PHT entry at index `I = P ^ H0` holds a known counter. In one cycle it drives `areset=1`, `predict_valid=1`, `predict_pc=P`, and `train_valid=1`, `train_mispredicted=1`, `train_history=H1` (with `H1 != H0`). It then deasserts `areset`, waits for the next posedge to settle, and samples. The expected post-reset `predict_history` is the reset value of the history register, and the PHT entry at `I` should reflect the reset state, not a training update derived from `H1`. If the design instead shows `H1` or a shifted `H0`, the checker has caught a reset-arbitration bug.

The key point for the final checker: treat reset as an asynchronous, dominating clear of both stateful structures, sample only after deassertion plus a settled edge, and never rely on unspecified power-up values.
