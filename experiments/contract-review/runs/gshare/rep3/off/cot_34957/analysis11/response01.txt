The most useful distinguishing example for the final checker is a same-cycle collision between a prediction and a training write to the same PHT entry, combined with the history-arbitration rule. This exercises three spec details at once: (1) `predict_history` must be the pre-edge history used to form the index, (2) the prediction must observe the pre-training counter value even when the trained index equals the predicted index, and (3) when `train_mispredicted=1` coincides with `predict_valid=1`, the next history must be `train_history`, discarding the prediction's shift.

Concretely, suppose after reset the history register holds `0000101` and the PHT entry at index `0000101` holds `10` (taken). Drive `predict_valid=1`, `predict_pc=0000000`, so the predicted index is `0000000 ^ 0000101 = 0000101`. The prediction must output `predict_taken=1` and `predict_history=0000101` — the pre-edge value, not the shifted value. In the same cycle, drive `train_valid=1`, `train_taken=0`, `train_mispredicted=1`, `train_history=1100000`, `train_pc=0000000`. The trained index is `0000000 ^ 1100000 = 1100000`, which differs from the predicted index, so this particular case does not test the same-entry collision; to test that, set `train_pc=0000101` so the trained index is `0000101 ^ 1100000 = 1100101`... which again differs. The cleanest same-entry collision is to choose `train_history` such that `train_pc ^ train_history` equals the predicted index. For instance, keep `predict_pc=0000000`, history `0000101`, predicted index `0000101`. Choose `train_pc=0000000` and `train_history=0000101`; then the trained index is also `0000101`. Now the prediction must still output the old counter (`10` → `predict_taken=1`), and the next cycle must show the updated counter after the training write (e.g., `01` if `train_taken=0`). Meanwhile, because `train_mispredicted=1`, the next history must be `train_history=0000101` (which happens to equal the old history here, so to make the arbitration visible, choose `train_history=1100000` and `train_pc=1100101` so the trained index is `0000101` while the next history is clearly `1100000`).

That last variant is the sharpest single test: predicted index `0000101`, trained index `0000101` (same entry), `predict_taken` reflects the pre-training counter, `predict_history=0000101`, and the next-cycle history is `1100000` because mispredicted training wins arbitration. A checker that instead outputs the post-shift history, or that lets the training write affect the same-cycle prediction, or that lets the prediction's shift override `train_history`, will fail this case while passing simpler ones. The checker should also confirm that with `train_mispredicted=0` and `train_valid=1`, history is untouched, and that asserting `predict_valid` or `train_valid` during `areset` leaves the post-reset state unchanged.
