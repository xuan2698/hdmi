One common implementation mistake is to treat the prediction and training interfaces as if they share a single "current" history value, rather than recognizing that the prediction path must expose the pre-edge history register contents while training may asynchronously override what the register becomes at the next edge. In a gshare predictor the history register is both an input to the index hash and a state element updated every cycle. The subtlety is that `predict_history` is an output of the *current* register value (the value used to form the index for this prediction), not the value that will be loaded at the next clock edge. A naive implementation computes the index, then immediately shifts in the predicted direction and drives that shifted value on `predict_history`, or it lets the training write update the register combinationally so that the same-cycle prediction sees the new history. Both are wrong.

The spec is explicit on two points that a checker should probe. First, when `predict_valid=1`, the output `predict_history` must equal the history register value *before* the edge, i.e., the same value that was XORed with `predict_pc` to form the index. The register update (shift in predicted direction) happens at the next positive edge. Second, when `train_valid=1` and `train_mispredicted=1`, the history register must be recovered to `train_history` at the next edge, and this recovery takes precedence over any prediction-driven shift in the same cycle. If both a prediction and a mispredicted training occur in the same cycle, the prediction's shift is discarded; the next-cycle history is `train_history`.

A related mistake is letting the training PHT write affect the same-cycle prediction. The spec says the prediction sees the PHT state *before* training, because training only modifies the PHT at the next positive edge. An implementation that writes the counter combinationally (or that reads the "updated" counter for the prediction) will produce a wrong `predict_taken` when prediction and training hit the same index in the same cycle.

Worked example: suppose the history register holds `0000101` and the PHT entry at index `0000101` holds counter `10`. Drive `predict_valid=1`, `predict_pc=0000000` (index `0000101`), and simultaneously `train_valid=1`, `train_taken=0`, `train_mispredicted=1`, `train_pc=1100101`, `train_history=1100000` (trained index `1100101 ^ 1100000 = 0000101`, same entry). Correct behavior: `predict_taken=1` (old counter `10`), `predict_history=0000101` (pre-edge), and at the next edge the counter becomes `01` while the history register becomes `1100000` (training wins arbitration). A checker that sees `predict_history=0000110` (shifted), or `predict_taken=0` (post-training counter), or next-cycle history `0000110` (prediction shift not overridden), has caught the bug.

The checker should also verify that `train_valid=1` with `train_mispredicted=0` leaves history unchanged, and that asserting `predict_valid` or `train_valid` during `areset` does not perturb the post-reset state.
