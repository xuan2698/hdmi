The timing contract here is best understood as a strict split between what is visible before a rising edge and what changes after it. All inputs in a row are driven before the sampled posedge; the outputs `predict_taken` and `predict_history` are sampled after that edge has settled, but they must reflect the state that existed *before* the edge. In other words, the prediction path is combinational with respect to the pre-edge PHT contents and the pre-edge global history register. The edge itself is where the PHT counter update and the history-register update are committed. Any mid-input changes occur after sampling and before the next edge, so they belong to the following row's pre-edge state and must not retroactively affect the just-sampled outputs.

This ordering matters because the spec allows prediction and training to be valid in the same cycle, possibly touching the same PHT entry. The prediction must read the old counter value; the training write only becomes visible at the next positive edge. A checker that samples outputs after the edge but compares them against post-edge PHT state will flag correct designs as wrong. The correct reference is: `predict_taken` = MSB of PHT[index] as it stood before the edge, where index = `predict_pc ^ history_register_pre_edge`; `predict_history` = that same pre-edge history register.

The history register has two possible next-state sources. If only prediction is valid, the next history is the pre-edge history shifted left with the predicted direction appended (the spec's prediction-side update). If training is valid, training takes precedence regardless of prediction validity, because any simultaneously predicted younger instruction will be flushed. For a mispredicted training request, recovery is not a shift of the live register; it is explicitly `{train_history[5:0], train_taken}`. For a correctly predicted training request, the spec's training interface still supplies `train_history`, and the safe reading is that the history register is restored/updated from the training-provided history plus outcome rather than from the live register. The PHT write address is always `train_pc ^ train_history`, using the training-supplied history, not the live register and not the prediction index.

A compact worked example: pre-edge history = 0; `predict_valid=1`, `predict_pc=1`; `train_valid=1`, `train_mispredicted=1`, `train_taken=1`, `train_history=64`, `train_pc=64`. The sampled outputs must be `predict_history=0` and `predict_taken` = old PHT[1] MSB. The PHT write targets index `64 ^ 64 = 0`, and the next history is `{64[5:0],1} = 1`. A same-cycle bypass from the training write into the prediction read, or using live history 0 for the training index, would produce observably different values.

For the final Python checker, the highest-value points are therefore: capture outputs against pre-edge state; compute the training index as `train_pc ^ train_history`; compute mispredicted recovery as `{train_history[5:0], train_taken}`; and enforce training precedence over prediction for the history register. Also verify two-bit saturation at 0 and 3 and the MSB-as-direction rule across the 1↔2 boundary.
