## Reset and Power-Up Behavior

The specification states that reset is **asynchronous active-high**. This is the single most important fact for the checker's reset model, and it has several consequences that are easy to get subtly wrong.

First, because reset is asynchronous, it takes effect immediately when `areset` is asserted, independent of `clk`. A checker that only samples `areset` at a clock edge will miss the case where reset is asserted and deasserted entirely between edges, or asserted just after an edge and released before the next. The reference model should therefore treat `areset=1` as forcing the architectural state to its reset values at all times, and should treat the first post-reset sampled edge as starting from those values.

Second, the spec does not enumerate explicit reset values for the PHT or the history register. The safe and conventional reading—consistent with "power-up behavior" being grouped with reset here—is that reset clears the global branch history register to 0 and initializes every 2-bit saturating counter in the 128-entry PHT to a defined state. The natural choice, and the one that makes the MSB-as-direction rule well-defined at power-up, is all counters = 0 (i.e., predict not-taken). A checker should not assume any other initialization; if the design leaves the PHT undefined after reset, predictions immediately after reset are not checkable and the checker should either skip them or require the design to define them. The history register, by contrast, must be 0 after reset because `predict_history` is directly observable and the spec's prediction-side update is defined relative to it.

Third, reset interacts with the two next-state sources for the history register. During reset, neither prediction nor training updates should take effect: the register is held at 0 regardless of `predict_valid` or `train_valid`. The checker should confirm that a `predict_valid` or `train_valid` asserted in the same cycle as `areset` does not perturb the post-reset history. Similarly, a training write must not land in the PHT while reset is asserted.

Fourth, the asynchronous nature means the checker's sampling discipline matters. Outputs `predict_taken` and `predict_history` are combinational functions of pre-edge state (PHT read at `predict_pc ^ history`, and the history register itself). After reset deasserts, the very first sampled edge should show `predict_history=0` and `predict_taken` equal to the MSB of the reset-initialized PHT entry. If the design initializes counters to 0, that MSB is 0, so the first prediction is not-taken—but the checker should derive this from the model's initialized PHT rather than hard-coding it, so that a design using a different documented init still passes if the spec is later clarified.

Finally, power-up without reset is not separately specified. The checker should treat the interval before the first `areset` assertion as unconstrained and begin checking only after a reset has been observed. This avoids flagging X-propagation or arbitrary initial PHT contents as errors, which is the correct reading of a spec that only guarantees behavior following asynchronous reset.

In short: model reset as an immediate, edge-independent override that zeroes the history register and defines the PHT; suppress all prediction and training side effects while reset is high; and start formal checking only after the first observed reset.
