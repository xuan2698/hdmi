# Reset and Power-Up Behavior of the Gshare Predictor

The public specification defines reset as **asynchronous active-high** (`areset`). This is the single most important fact for the final Python checker, because it means the checker must not model reset as a synchronous event that only takes effect at a clock edge. Instead, whenever `areset` is asserted, the predictor's sequential state must be forced to its reset value immediately, independent of `clk`. The two pieces of sequential state are the 7-bit global branch history register and the 128-entry table of two-bit saturating counters (the PHT). The spec does not spell out the exact reset value of each PHT counter, but the natural reading—consistent with "two-bit saturating counters" and with the requirement that a freshly reset predictor behave deterministically—is that all counters reset to a defined initial state (typically the weakly-not-taken or weakly-taken encoding, whichever the implementation chooses, but it must be a single fixed value). The checker should treat the post-reset PHT contents as a known constant, not as unconstrained "don't care" values, because the prediction interface can be exercised immediately after reset and its outputs must be predictable.

The global history register resets to all zeros. This is the conventional choice and is implied by the spec's framing: the history register is a 7-bit shift register that accumulates predicted/actual directions, and a reset predictor has no history. After reset deasserts, the first prediction request therefore uses `predict_history = 0` as the index hash input, and the PHT entry selected is `pc[6:0] XOR 0 = pc[6:0]`. The checker can use this to validate the very first prediction after reset without needing to know any prior branch outcomes.

Power-up behavior is the same as reset behavior in the checker's model: the spec provides no separate power-on initialization, so the only defined starting state is the one produced by asserting `areset`. The checker should assume that any test sequence begins with `areset` asserted (or that the initial state equals the reset state), and it should not attempt to model indeterminate X-values. In particular, the checker should not allow a prediction to be "unknown" merely because no reset was seen; the protocol seed and the asynchronous-reset definition together imply the checker drives `areset` at the start.

A subtle point for the checker: because reset is asynchronous, a reset assertion that occurs *between* edges (a "mid" change) must still clear the state before the next sampled edge. The checker's state-update function should therefore apply reset with priority over any pending prediction or training update, and it should do so at the moment reset is observed, not deferred to the posedge. Equivalently, the checker can compute the next state as: if `areset` then reset-state, else apply the edge rules (training PHT write, history recovery on mispredicted training, else prediction history advance). This ordering also resolves any same-cycle conflict between reset and a valid predict/train: reset wins.

Worked example: suppose the predictor has been running, history = `7'b1010101`, and PHT entry 0 holds `2'b11`. Then `areset` is asserted mid-cycle. The checker must immediately set history to `7'b0000000` and all PHT entries to the reset counter value, so that a prediction request sampled at the next posedge (with `areset` now low) outputs the reset-state prediction and `predict_history = 0`, not the pre-reset values. This confirms the checker must separate "state before the sampled edge, after any asynchronous reset" from "state after the edge."
