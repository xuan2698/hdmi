# Reset and Power-Up Behavior

The public specification states that reset is asynchronous and active-high. This is the single most important fact for the checker's reset model, and it has several consequences that are easy to get wrong if one assumes a synchronous or edge-triggered reset.

**Asynchronous assertion.** When `areset` is high, the GHR and every PHT entry are cleared immediately, without waiting for a clock edge. The cleared values are the natural ones: the 7-bit GHR becomes 0, and each of the 128 two-bit saturating counters becomes 0 (the "strongly not-taken" state, since the spec describes two-bit saturating counters and the reset value is the all-zero state). Because the reset is asynchronous, the checker must treat `areset` as a level that forces state, not as a signal sampled only at `posedge clk`. Any sampled output taken while `areset` is high must reflect cleared state regardless of where in the clock period the sample falls.

**Effect on the prediction interface.** While `areset` is high, the PHT is all zeros, so any prediction read returns `predict_taken = 0`. The `predict_history` output reflects the cleared GHR, i.e., 0. The checker should not expect a prediction request to "see" a stale counter or a stale history value during reset; the asynchronous clear wins.

**Effect on the training interface.** Training writes are edge-triggered (the PHT is modified at the next positive clock edge), but reset overrides them. If `train_valid` is asserted while `areset` is high, the asynchronous clear dominates: the PHT entry does not take the trained value, and the GHR does not take `train_history`. The checker should model reset as having priority over both the PHT write and the GHR update, including the misprediction-recovery path.

**Power-up.** The spec does not define a separate power-up sequence beyond reset. The safe checker assumption is that after power-up the state is only well-defined once `areset` has been asserted (asynchronously clearing GHR and PHT) and then deasserted. Before any reset, the checker should not assume specific GHR or PHT contents; it should begin meaningful comparison only after a reset has established the all-zero state. This matters for the seed-based protocol: the first sampled edge after reset deassertion should be checked against the cleared state, not against an arbitrary initial state.

**Interaction with mid-cycle changes.** Because reset is asynchronous, a mid-cycle change of `areset` (after sampling, before the next edge) takes effect immediately on the state, not at the next edge. The checker must apply the clear at the moment `areset` rises, so that the next sampled edge already sees cleared GHR and PHT. This is the one place where the "mid-cycle changes only affect the next sampled edge" rule is superseded: an asynchronous reset asserted mid-cycle clears state before that next edge.

**Worked example.** Suppose at cycle 4 the PHT entry 0 holds 2 and the GHR holds `7'b1010101`, and `areset` is asserted mid-cycle after the cycle-4 sample. The checker must immediately set entry 0 to 0 and the GHR to 0. At the cycle-5 sample, `predict_taken` for a request hashing to entry 0 must be 0, and `predict_history` must be 0 — not the pre-reset values and not any value derived from a training request that was pending at cycle 4. Any `train_valid` at cycle 4 is discarded by the reset.

**Checker takeaway.** Model `areset` as an asynchronous level that clears GHR and all PHT entries with priority over prediction reads, PHT writes, and GHR updates (including misprediction recovery). Only begin state comparison after a reset has established the all-zero state, and apply mid-cycle reset assertions immediately rather than deferring them to the next edge.
