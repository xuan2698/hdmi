# Reset and Power-Up Behavior Analysis

The branch predictor's reset behavior is the first thing the final Python checker must get right, because reset is asynchronous and active-high, and it interacts with the otherwise purely synchronous edge-update logic. The public spec states: "Reset is asynchronous active-high." This means `areset` is not sampled only at the clock edge; whenever `areset` is asserted, the architectural state must be forced to its reset value immediately, independent of `clk`. The two pieces of state are the 7-bit global history register (GHR) and the 128-entry table of two-bit saturating counters (PHT). On reset, the GHR clears to 0 and every PHT counter clears to its reset encoding (the standard 2-bit saturating counter reset is 0, i.e., strongly not-taken, unless the implementation's encoding says otherwise; the checker should use the same encoding the design uses for `predict_taken`).

Power-up is the same event as reset from the checker's perspective: before any clock edge and before reset is released, the model must assume GHR=0 and all counters at their reset value. There is no separate "unknown" power-up state to model; the asynchronous reset defines the initial state. The checker should therefore initialize its state to the reset values and then, on every evaluation, first check `areset`. If `areset` is high, the outputs are computed from the reset state (GHR=0, all counters reset), and the next-state is also the reset state regardless of `predict_valid`, `train_valid`, or any other input. Reset dominates the priority chain completely.

A subtle but important point for the checker: because reset is asynchronous, a reset assertion that occurs between clock edges must still take effect. In a cycle-accurate Python model that samples after the posedge, the practical rule is: evaluate `areset` at the sampling point; if it is high, force state to reset and produce outputs from reset state. Do not let a same-cycle `train_valid` PHT write or a `predict_valid` GHR shift override reset. The spec's priority ordering is explicit: "Asynchronous active-high reset dominates everything: it clears the GHR and PHT regardless of other inputs."

The combinational outputs deserve care around reset. `predict_taken` is the MSB of the counter at index `predict_pc ^ ghr`, and `predict_history` is the unmodified GHR. These are "pure combinational reads of state." So when `areset` is high, the state is the reset state, and the outputs must reflect that: `predict_history = 0`, and `predict_taken` is the MSB of the reset counter (0 if counters reset to 0). The checker should compute outputs from the *pre-edge* state, but when reset is asserted, the pre-edge state is effectively the reset state. A common bug is to compute outputs from stale pre-reset state while reset is high; the checker should flag that.

Worked example: suppose before reset the GHR=127 and PHT[127]=3. Then `areset` goes high while `predict_valid=1`, `predict_pc=0`. The correct outputs are `predict_history=0` and `predict_taken=0` (reset counter MSB), not `predict_history=127`/`predict_taken=1`. At the edge, state remains GHR=0, all counters reset, even if `train_valid=1` with `train_mispredicted=1`. This single case exercises the dominance of reset over both the prediction read and the training write, which is the highest-value check for the final Python model.
