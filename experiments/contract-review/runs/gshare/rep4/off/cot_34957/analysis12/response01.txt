One likely implementation mistake is to let the training request affect the same-cycle prediction output, or to let the prediction shift override the training recovery of the global history register. Both violate the public timing rule that prediction outputs are combinational from the current state, while PHT and GHR updates occur only at the positive clock edge.

The prediction path must compute `predict_taken` from the PHT entry selected by `predict_pc ^ ghr` using the current GHR and the current PHT contents. If `train_valid=1` in the same cycle and the training index equals the prediction index, the prediction must still report the old counter value. The training write is visible only after the edge. Similarly, `predict_history` must be the current GHR, not a value already shifted by the predicted branch.

At the edge, the update priority matters. Reset is asynchronous active-high and dominates. Otherwise, if `train_valid=1` and `train_mispredicted=1`, the GHR must be recovered to the state immediately after the mispredicting branch, using `train_history` and `train_taken`. This recovery takes precedence over any prediction shift. If training is valid but not mispredicted, the GHR should not be recovered; a same-cycle prediction may still shift it. If no training recovery applies and `predict_valid=1`, the GHR shifts in the predicted direction. Otherwise it holds.

A short worked example: suppose GHR = 127, `predict_valid=1`, `predict_pc=0`, so the prediction index is `0 ^ 127 = 127`. Let PHT[127] = 3. Then the prediction must output `predict_taken=1` and `predict_history=127`. In the same cycle, drive `train_valid=1`, `train_pc=0`, `train_history=127`, `train_taken=0`, `train_mispredicted=1`. The training index is also 127. The prediction still reports taken with history 127 because the PHT write has not occurred. At the edge, PHT[127] decrements to 2, and the GHR becomes `(127 << 1) | 0 = 126`, because mispredicted training recovery wins over the prediction shift. A buggy implementation that applies the prediction shift first would produce 127 instead of 126; one that applies the training write before computing the prediction might report not-taken instead of taken.

For the final Python checker, this suggests keeping only the 7-bit GHR and 128 two-bit counters as state, computing all outputs from the pre-edge state, then applying reset, then the PHT write if `train_valid`, then the GHR priority chain: reset, mispredicted training recovery, prediction shift, hold. That ordering directly catches the common mistakes of exposing edge updates combinationally and mishandling GHR priority.
