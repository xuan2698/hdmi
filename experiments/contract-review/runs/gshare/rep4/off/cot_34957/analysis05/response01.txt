The key distinguishing point for the checker is the interaction between the prediction read and the training write on the same PHT entry in the same cycle, combined with the GHR update arbitration. A naive model might apply the training update before computing the prediction, or might let the prediction's GHR shift override a mispredicted training's recovery. The spec is explicit that the prediction must observe the pre-edge counter value, and that a mispredicted training suppresses the prediction's GHR shift.

Consider a concrete scenario that separates these behaviors. Suppose after reset the GHR is 0 and all PHT entries are 0. First, train entry 0 (pc=0, history=0) as taken twice, so entry 0 reaches 2 and predicts taken. Now issue a prediction with pc=0, history=0: index 0, counter 2, so `predict_taken=1` and `predict_history=0`. In the same cycle, issue a training with pc=0, history=0, `train_taken=0`, `train_mispredicted=1`. The prediction must still output `predict_taken=1` (old counter 2), not the post-training value. At the next edge, entry 0 decrements to 1, and because the training is mispredicted, the GHR is recovered to `train_history` shifted with `train_taken`: `(0 << 1) | 0 = 0`. The prediction's own GHR shift (which would have shifted in the predicted taken bit, giving 1) must be suppressed. A checker that lets the prediction shift win would see GHR=1 instead of 0 at the next sample.

A subtler variant: same setup but `train_mispredicted=0`. Then the training still decrements entry 0 to 1 at the edge, but the GHR update is not a recovery; the prediction's shift applies, so GHR becomes 1. This distinguishes "training always wins GHR" from "only mispredicted training wins GHR." The spec says training takes precedence only when the branch being trained is mispredicted; a correct training does not suppress the prediction's shift. So the checker must gate the GHR arbitration on `train_mispredicted`, not merely on `train_valid`.

Also worth probing: a prediction and a training hitting different PHT entries in the same cycle. Here both the prediction's shift and (if mispredicted) the training's recovery compete for the GHR. The spec's rule is that mispredicted training wins regardless of entry aliasing, because the predicted instruction is younger and will be flushed. So even with different indices, `train_mispredicted=1` must override the prediction's shift. A checker that only arbitrates on same-index collisions would miss this.

Finally, asynchronous reset priority: if `areset` asserts mid-cycle after a sample, the next sampled edge must see GHR=0 and all counters 0, and any pending prediction/training effects from that cycle are discarded. The checker should apply reset at assertion time, not wait for the edge, and should not let a same-cycle training write survive the reset.
