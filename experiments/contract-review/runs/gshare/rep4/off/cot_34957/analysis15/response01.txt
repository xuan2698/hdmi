The branch predictor is a gshare design with a 7-bit global history register (GHR) and a 128-entry pattern history table (PHT) of 2-bit saturating counters. The PHT index is `predict_pc ^ ghr` (7 bits), and the prediction is the MSB of the selected counter. The prediction interface is purely combinational: when `predict_valid` is asserted, `predict_taken` reflects the current PHT counter MSB at the XOR index, and `predict_history` reflects the current GHR. These outputs are reads of state and do not themselves depend on `predict_valid` for their value (though the spec frames them as the prediction response). On the next posedge, if `predict_valid` is asserted, the GHR shifts in the predicted direction (the predicted taken bit) — i.e., the GHR is updated for the predicted branch.

The training interface is registered: when `train_valid` is asserted, the PHT counter at `train_pc ^ train_history` is updated at the next posedge according to `train_taken` (increment on taken, decrement on not-taken, saturating at 0 and 3). The `train_history` input is the GHR value that was used when the branch was predicted, so the training index uses that historical value, not the current GHR. If `train_mispredicted` is asserted, the GHR is also recovered at the posedge to the state immediately after the mispredicting branch — which is `train_history` shifted with the actual outcome `train_taken` in the appropriate direction (the spec says "recover the branch history register to the state immediately after the mispredicting branch completes execution"). In practice this means the GHR becomes the value that would have resulted from shifting `train_history` by the actual outcome.

Priority between the two interfaces at a posedge: training takes precedence over prediction for GHR updates. If both `train_valid` (with misprediction) and `predict_valid` occur in the same cycle, the GHR is set from the training recovery, not from the prediction shift. The PHT write from training and the PHT read for prediction are independent in the same cycle: the prediction sees the pre-edge PHT state, and the training write takes effect only after the edge. So a same-cycle predict and train on the same index do not interfere combinationally.

Reset is asynchronous and active-high, and it dominates everything. When `areset` is high, the state is forced to GHR=0 and all PHT counters reset (to 0, so MSB=0). The combinational outputs must reflect this reset state: `predict_history=0` and `predict_taken=0`, regardless of `predict_valid`, `predict_pc`, or any training inputs. At the posedge, the next state remains the reset state even if `train_valid` or `predict_valid` are asserted. The checker should evaluate `areset` at the sampling point and, if high, compute outputs from the reset state and force next-state to reset — never from stale pre-reset state, and never allowing a same-cycle train write or predict shift to override reset.

Worked example: pre-reset GHR=127, PHT[127]=3. `areset` goes high with `predict_valid=1`, `predict_pc=0`. Correct outputs: `predict_history=0`, `predict_taken=0`. At the edge, state stays GHR=0, all counters 0, even with `train_valid=1`, `train_mispredicted=1`. This single case checks reset dominance over both the prediction read and the training write.
