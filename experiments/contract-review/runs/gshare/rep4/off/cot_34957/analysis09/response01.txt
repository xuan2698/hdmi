The key architectural point for the checker is that the branch history register (GHR) has a single commit point at the clock edge, and the priority among its possible next values is: reset (highest), then training recovery, then prediction shift, then hold. The PHT write is independent of the GHR commit and is gated only by `train_valid` (and not by reset, since reset overrides everything). The prediction outputs are combinational functions of the current state and the current `predict_pc`, so they must be evaluated before the edge using the pre-edge GHR and pre-edge PHT contents — training in the same cycle does not affect the prediction output, because the PHT write lands only at the edge.

Concretely, when `areset` is low: the prediction index is `predict_pc ^ ghr` (7-bit XOR), and `predict_taken` is the MSB of the 2-bit counter at that index (taken if the counter is 2 or 3). `predict_history` is simply the current GHR value. These outputs are produced whenever `predict_valid=1`; when `predict_valid=0` the outputs are don't-care for the checker (but the GHR still holds unless training commits). At the edge, if `train_valid=1` and `train_mispredicted=1`, the GHR is overwritten with `(train_history << 1) | train_taken` (the recovered history immediately after the mispredicting branch), regardless of whether `predict_valid` is also high — training wins. If `train_valid=1` and `train_mispredicted=0`, the GHR is not recovered (the branch was correctly predicted, so the speculative shift already applied is correct); only the PHT is updated. If `train_valid=0` and `predict_valid=1`, the GHR shifts in the predicted direction: `(ghr << 1) | predict_taken`. If neither, the GHR holds.

The PHT update at the edge, when `train_valid=1`, uses index `train_pc ^ train_history` and saturates the counter toward `train_taken` (increment if taken and counter<3, decrement if not-taken and counter>0). This write is unconditional on `train_valid` and independent of `train_mispredicted`; the mispredicted flag only affects the GHR recovery. Note the subtlety that the training index uses `train_history` (the history supplied with the training request), not the current GHR, so the checker must not substitute the live GHR there.

Worked example: suppose GHR=0b0000101 (5), and PHT entry at index `3 ^ 5 = 6` holds counter 2 (weakly taken). In a cycle with `predict_valid=1, predict_pc=3`, the outputs are `predict_taken=1, predict_history=5`. If simultaneously `train_valid=1, train_pc=3, train_history=5, train_taken=0, train_mispredicted=1`, then at the edge the PHT entry 6 decrements to 1, and the GHR is recovered to `(5<<1)|0 = 0b0001010` (10), not shifted by the prediction. The prediction output in that cycle still reported the pre-edge counter (taken) and pre-edge history (5).

The checker should therefore keep GHR and the 128 counters as the only state, compute prediction outputs combinationally from pre-edge state, and apply edge updates in the priority order reset > train-recovery > predict-shift > hold for the GHR, with the PHT write applied whenever `train_valid` and not reset.
