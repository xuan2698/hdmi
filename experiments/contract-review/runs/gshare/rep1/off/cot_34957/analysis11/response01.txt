The most useful distinguishing point for the final checker is the exact priority and visibility ordering around a single clock edge, because several plausible-but-wrong implementations differ only there.

Consider a cycle where `predict_valid=1` and `train_valid=1` target the same PHT index, and `train_mispredicted=1`. A naive implementation might let the prediction read the counter after the training write, or let the prediction-driven GHR shift win over recovery. The spec forbids both: the prediction must see the pre-edge PHT value (read-before-write), and at the edge the mispredict recovery must override the prediction shift. A checker that only tests isolated predict-only or train-only cycles will miss this.

A second distinguishing case is same-cycle predict and train on the same index without misprediction. The prediction output must reflect the old counter, while the edge updates the counter. If the checker samples `predict_taken` after the edge, it will wrongly expect the new counter's MSB. The correct expectation is: compute `index = predict_pc ^ ghr` from current state, output `PHT[index][1]` and current `ghr`; then at the edge apply the saturating update. This is exactly the timing diagram's cycle-4/cycle-5 behavior.

A third point is reset dominance. Asynchronous active-high reset must clear GHR and all 128 counters and suppress same-row updates. A checker should drive reset mid-cycle (after a posedge, before the next) and confirm outputs go to zero immediately and that any pending train/predict in that row does not alter state. This catches implementations that treat reset as synchronous or that still apply a training write on the reset edge.

Worked micro-example: after reset, `ghr=0`, all counters 0. Cycle A: `predict_valid=1, predict_pc=0` → `predict_taken=0`, `predict_history=0`; edge shifts in predicted 0, so `ghr` stays 0. Cycle B: `train_valid=1, train_pc=0, train_history=0, train_taken=1, train_mispredicted=0` → counter 0 goes 0→1 at edge; `ghr` unchanged. Cycle C: `predict_valid=1, predict_pc=0` with `ghr=0` → still `predict_taken=0` (counter=1, MSB=0), confirming read-before-write and the 2-bit MSB threshold. Now Cycle D: `predict_valid=1, predict_pc=0` and `train_valid=1, train_pc=0, train_taken=1, train_mispredicted=1, train_history=0`. Prediction must output the pre-edge counter MSB and pre-edge `ghr`; at the edge, recovery sets `ghr = ((0<<1)|train_taken)&0x7F = 1`, overriding the prediction shift, and the counter increments (saturating). A checker that lets the prediction shift win would leave `ghr=0`; one that reads post-write would mispredict the MSB. These three assertions—pre-edge read, recovery-over-shift priority, and reset dominance—are the highest-value checks.
