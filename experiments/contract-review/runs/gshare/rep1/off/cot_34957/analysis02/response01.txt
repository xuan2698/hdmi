# Reset and Power-Up Behavior

The branch predictor has a single asynchronous active-high reset, `areset`. Because it is asynchronous, reset takes effect immediately when asserted, independent of `clk`; the checker must not wait for a posedge to observe its effect. While `areset` is high, the architectural state is forced to its defined initial values, and the outputs are driven from that reset state rather than from whatever the pre-reset state happened to be.

The state elements are: the 128-entry PHT of 2-bit saturating counters, and the 7-bit global branch history register. On reset, the history register is cleared to zero. The PHT entries are also initialized to a defined reset value; the natural choice consistent with a 2-bit saturating counter is all-zero (strongly not-taken), and the checker should treat the post-reset PHT as uniformly zero unless the harness specifies otherwise. The key point for the checker is that after reset deasserts, the very first prediction must be computed from this known initial state: `predict_history` reads 0, and the PHT lookup at `predict_pc ^ 0` returns the reset counter value, so the initial prediction is not-taken for every PC until training changes entries.

Power-up without an explicit reset is not separately modeled. The public spec only defines behavior through `areset`; the checker should assume the harness asserts `areset` before any meaningful prediction or training traffic, and should not attempt to infer state from an un-reset power-up. In other words, there is no "undefined but eventually consistent" warm-up window to emulate—either reset has been applied (state known) or the checker is outside the specified contract.

Two subtleties matter for the final checker. First, because reset is asynchronous, a reset assertion between sampled edges must immediately clobber state; a mid-cycle `areset` is the one exception to the "mid changes are carried to the next edge" rule. The checker should apply reset as an immediate override, then resume edge-sampled behavior once `areset` is low. Second, reset has the highest priority in the next-state assignment. If `areset` is asserted in the same cycle that `predict_valid` or `train_valid` is high, reset wins: no PHT write, no history shift, no training recovery is committed. The checker's next-state function should therefore order priorities as reset > mispredicted-training recovery > prediction update, exactly as the history-register rule states, and should also suppress the PHT write under reset.

A short worked example clarifies the interaction. Suppose the harness asserts `areset` for a few cycles, then deasserts it while driving `predict_valid=1`, `predict_pc=P`, with `train_valid=0`. At the first posedge after deassertion, the pre-edge state is the reset state: history=0, PHT all zero. The prediction output is `predict_taken=0` and `predict_history=0`, computed from the reset PHT entry at index `P^0 = P`. At that same edge the history register shifts in the predicted direction (not-taken, so it remains 0), and no PHT entry changes because training is inactive. The checker should verify outputs against the reset-derived pre-edge state, then apply the single next-state assignment. If instead `areset` were still high at that edge, the checker must ignore the prediction request entirely and hold the reset state, confirming that reset dominates all other inputs.
