The key distinguishing behavior for the checker is the **training index derivation**: the PHT entry selected during training must be computed as `train_pc ^ train_history`, using the supplied `train_history` input, *not* the live GHR. This matters whenever `train_history != ghr` at a training cycle — which is exactly the situation after a misprediction, when the pipeline is flushing younger instructions and the live GHR has already been shifted by speculative predictions that are now being discarded. A checker that accidentally hashes `train_pc` with the current GHR will produce identical results on most cycles (since normally `train_history` equals the GHR snapshot taken when the branch was predicted), but will diverge on any cycle where the two differ. So the short distinguishing input should force `train_history != ghr` while `train_valid=1`, and arrange the two candidate indices to point at PHT entries with different counter states, so the resulting `predict_taken` (or the post-edge PHT contents) differ depending on which index was used.

A compact example: set the live GHR to `0000001` and `train_history` to `1000000`, with `train_pc = 0000000`. Then `train_pc ^ train_history = 1000000` (index 64) while `train_pc ^ ghr = 0000001` (index 1). Preload PHT[64]=`00` and PHT[1]=`11`. Issue `train_valid=1, train_taken=1, train_mispredicted=0`. A correct predictor updates PHT[64] from `00`→`01` and leaves PHT[1]=`11`. A buggy predictor updates PHT[1] from `11`→`11` (saturated) and leaves PHT[64]=`00`. On the next cycle, predict with `predict_pc=0000000` and GHR=`1000000` (index 64): correct gives `predict_taken=0` (counter `01`), buggy gives `predict_taken=0` too — so instead probe index 1: predict with `predict_pc=0000001`, GHR=`0000000` (index 1). Correct reads `11`→taken; buggy reads `11`→taken as well. To separate, use `train_taken=0` instead: correct updates PHT[64] `00`→`00` (saturated), buggy updates PHT[1] `11`→`10`. Then predict index 1: correct sees `11`→taken, buggy sees `10`→taken. Still same MSB. The cleanest separation is to preload PHT[64]=`10` and PHT[1]=`01`, train with `train_taken=1`: correct → PHT[64]=`11`, buggy → PHT[1]=`10`. Then predict index 64 (pc=0, ghr=`1000000`): correct `11`→taken, buggy `10`→taken. Predict index 1 (pc=1, ghr=0): correct `10`→taken, buggy `10`→taken. Hmm — the MSB-only output makes single-cycle separation awkward; the checker should instead observe the PHT state indirectly across two training steps, or simply verify the *next* prediction after a second training that flips the MSB. The robust approach: after the misindexed training, train the *correct* index again with the opposite direction and confirm the counter moves from the expected value, which only matches if the first write landed at index 64.

Also worth exercising: `train_mispredicted=1` with `train_valid=1` and `predict_valid=1` in the same cycle — recovery (`{train_history[5:0], train_taken}`) must win over the prediction shift (`{ghr[5:0], predict_taken}`), and the same-cycle `predict_taken`/`predict_history` outputs must reflect pre-edge state (training does not affect the read). And reset dominance: assert `areset` while `train_valid=1`; post-edge GHR must be 0 and all PHT entries 0, with no leakage from the concurrent train.
