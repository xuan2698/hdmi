The timing analysis hinges on distinguishing combinational read paths from registered state updates at the sampled posedge. On any cycle, `predict_taken` and `predict_history` are pure functions of the current registered state: the PHT entry selected by `predict_pc[6:0] XOR ghr` and the current `ghr` value. Neither output depends on `train_valid`, `train_taken`, or `train_mispredicted` in the same cycle, because training only mutates state at the next edge. This is the "prediction sees pre-edge PHT" rule, and it must hold even when the training request targets the exact same index.

The GHR next-state is priority-encoded. Reset (asynchronous, active-high) forces `ghr` to zero immediately, independent of clock. Otherwise, at a posedge: if `train_valid && train_mispredicted`, the GHR loads `{train_history[5:0], train_taken}`; else if `predict_valid`, it shifts in the predicted direction `{ghr[5:0], predict_taken}`; else it holds. Training precedence over prediction is essential because a mispredicted branch flushes younger instructions, so any prediction issued in the same cycle is architecturally dead. Note the subtlety: the shift-in value for a prediction is `predict_taken`, which is itself derived from the pre-edge PHT read — so the GHR update and the PHT read are consistent snapshots of the same cycle.

The PHT update is independent of the GHR priority logic. Whenever `train_valid`, the counter at `train_pc XOR train_history` is incremented (if `train_taken`) or decremented (if not), saturating at 3 and 0 respectively. This write commits at the posedge and is visible to predictions starting the next cycle. Crucially, the index uses `train_history`, not the current `ghr`, because the training request carries the history that was in effect when the branch was predicted — the pipeline may have advanced the GHR since.

Mid-cycle input changes (after sampling, before the next edge) are carried into the next row's evaluation. A checker should therefore evaluate each row's outputs from the state established at the prior posedge, then apply the row's inputs to compute next-state, then advance. The seed protocol means inputs are stable at the sampled edge; mid changes only matter for the following row.

Worked example: suppose `ghr=0`, PHT[0]=2, and in one cycle `predict_valid=1, predict_pc=0` while `train_valid=1, train_mispredicted=1, train_taken=0, train_history=0, train_pc=0`. The prediction reads PHT[0]=2, so `predict_taken=1` (upper bit set) and `predict_history=0`. At the edge, training wins the GHR: `ghr` becomes `{0,0}=0`. PHT[0] decrements to 1, visible next cycle. A checker that let the prediction shift win, or that exposed the decremented counter to the same-cycle read, would diverge on `predict_taken`/`predict_history`/`ghr`.

Two boundary checks deserve directed coverage: saturation (state 3 with taken stays 3; state 0 with not-taken stays 0, ideally with a coincident prediction confirming the pre-edge read), and the 7-bit mask on the history shift (`ghr=7'b1111111` with a taken prediction yields 127, not 255). Combining the wrap with the collision case gives compact, high-coverage stimulus.
