One likely implementation mistake is to treat the prediction and training interfaces as if they operate on the same cycle’s state, rather than respecting the registered nature of both the PHT and the global history register (GHR). The public spec is explicit that a prediction request returns the PHT state and history value used to make that prediction, and that a training request only modifies the PHT at the next positive clock edge. A common bug is to let a same-cycle training write affect the prediction read, or to let the prediction’s history shift override a mispredicted-training history recovery. Either error changes the observable `predict_taken`, `predict_history`, or subsequent `ghr` behavior.

The key distinction is that the PHT is a registered array with read-before-write semantics for coincident accesses, while the GHR next-state is priority-selected. On a mispredicted training request, the GHR must be recovered to `{train_history[5:0], train_taken}`. If a prediction for a younger instruction also occurs in that cycle, training wins the GHR update because the predicted instruction will be flushed. But the prediction must still report the pre-edge PHT counter and the pre-edge history value it actually used. A checker that models training as combinational, or that applies the prediction shift before the training recovery, will diverge on exactly the collision cases the spec calls out.

A short worked example: suppose `ghr = 7'b0000000`, a prediction for `predict_pc` hashes to PHT index 0 whose counter is 2, and in the same cycle a mispredicted training request arrives with `train_history = 7'b0000000`, `train_taken = 0`, also hashing to index 0. The prediction must output `predict_taken = 1` (counter 2 means taken) and `predict_history = 7'b0000000`, the value before the training write commits. At the posedge, the mispredicted training wins the history update: `ghr` becomes `{train_history[5:0], train_taken} = 7'b0000000`. The PHT entry at index 0 is decremented from 2 to 1, but that new value is only visible to predictions in the next cycle. A checker that instead let the prediction’s shift win, or that let the prediction observe the decremented counter, would produce a different `predict_taken`/`predict_history`/`ghr` triple and be caught here.

This example is valuable because it separates the two state elements. The PHT is a registered array: writes take effect after the sampled edge, so a coincident read returns the pre-edge counter. The GHR is also registered, but its next-state selection is priority-encoded: reset, then mispredicted training, then prediction, then hold. The same-cycle collision forces the checker to implement both the “read old PHT” rule and the “training beats prediction for GHR” rule independently; a naive implementation that applies the prediction shift first and then overwrites with training, or that applies training to the PHT before servicing the read, will diverge.

A second point worth encoding is the saturation boundary. If the same index held state 3 and `train_taken=1`, the update must leave it at 3, not wrap to 0; if it held state 0 and `train_taken=0`, it must stay 0. These edges are easy to get wrong with a modulo-4 increment/decrement, so the checker should include at least one directed case at each boundary, ideally combined with a coincident prediction to confirm the read still returns the saturated pre-edge value.

Finally, the 7-bit masking of the history shift deserves an explicit check. With `ghr=7'b1111111` and a taken prediction, the next `ghr` is `(127<<1 | 1) & 127 = 127`, not 255. Any checker that stores an 8-bit intermediate or forgets the mask will fail on this wrap, and the failure will be visible in `predict_history` on the following cycle. Combining the wrap case with the collision case above gives a compact but high-coverage directed test.
