The reset behavior is the first thing a checker must pin down, because it defines the entire initial state from which every subsequent prediction and training operation is derived. The specification states that reset is asynchronous and active-high. This means the checker must not wait for a clock edge to observe reset effects: asserting `areset` at any time must immediately force the design into its reset state, and deasserting it must allow normal operation to resume from that state. The practical consequence for the checker is that it should treat `areset` as a level-sensitive override that dominates all other inputs, including `predict_valid` and `train_valid`. If reset is asserted while a prediction or training request is also asserted, the reset wins; the request is discarded and produces no state change.

On reset, the global history register (`ghr`) is cleared to 7'b0000000. The pattern history table (PHT) is also cleared, so all 128 two-bit saturating counters start at 0 (strongly not-taken). This initial PHT state matters because the very first predictions after reset will all report not-taken regardless of PC, until training has had a chance to move counters. A checker that seeds the PHT to 2 (weakly taken) or leaves it uninitialized will diverge immediately on the first prediction. The reset value of the outputs follows from this state: with `ghr=0` and all counters at 0, a prediction for any PC yields `predict_taken=0` and `predict_history=0`.

Power-up behavior is the same as reset behavior in this design, since there is no separate initialization sequence described. The checker should assume that before the first reset assertion, the design's state is unspecified, and it should not evaluate outputs until at least one reset has been applied and released. The cleanest approach is to begin every test sequence with an explicit reset pulse, then sample outputs only after the reset has been deasserted and a clock edge has occurred.

A subtle point for the checker is the interaction between reset and the "mid-cycle input changes" convention. Because reset is asynchronous, a mid-cycle assertion of `areset` must take effect before the next sampled edge, not at it. The checker should model reset as an immediate state-clearing event that also cancels any pending next-state computation from the current row's inputs. In other words, if a row's inputs would have updated `ghr` or the PHT at the upcoming edge, but `areset` is asserted mid-cycle, those updates must not occur; the state remains at the reset values.

Worked example: suppose the design has been running with `ghr=5` and PHT[3]=3. Mid-cycle, `areset` is asserted. The checker must immediately expect `ghr=0` and all PHT entries at 0, and any prediction or training request present in that same row must be ignored. If `predict_valid=1, predict_pc=3` were also asserted, the prediction output should reflect the reset state (`predict_taken=0`, `predict_history=0`), not the pre-reset PHT[3]=3. A checker that applied the prediction against the old state, or that deferred the reset to the next edge, would produce a spurious taken prediction and a nonzero history.

The key takeaway for the final checker: reset is an asynchronous, dominant, state-clearing event that must be applied before evaluating any same-row prediction or training, and it must cancel pending next-state updates rather than merely overwrite them at the edge.
