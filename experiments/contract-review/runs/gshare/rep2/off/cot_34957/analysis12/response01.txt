One implementation mistake worth targeting in the checker is conflating the *combinational prediction path* with the *sequential training update path*, especially when both fire in the same cycle. The spec is explicit that a prediction request in cycle N must observe the PHT and GHR as they exist *before* the posedge at the end of cycle N, even if a training request for the same PHT entry is also present in cycle N. Training only mutates the PHT at the next positive clock edge. A model that computes `predict_taken` by first applying the training update (or by sharing a single "next PHT" variable between the read and write paths) will produce a wrong same-cycle output.

A concrete failure mode: suppose the PHT entry indexed by the prediction PC currently holds `2'b10` (weakly not-taken, so `predict_taken=0`), and in the same cycle `train_valid=1`, `train_taken=1` targets that same entry. The correct `predict_taken` for that cycle is `0` — the pre-edge value. A checker that lets the training write leak into the combinational prediction path would wrongly output `predict_taken=1` in that same cycle. This is the "prediction sees pre-edge PHT state" rule.

Now layer the GHR priority on top. Suppose in that same cycle `train_mispredicted=1` with `train_history=H`. The prediction still reports `predict_history=GHR` (pre-edge) and `predict_taken` from the old counter, but the *next-state* GHR must be `H` (the mispredicted-training load), **not** the shifted prediction value. So the checker must independently track: (a) combinational outputs from current state, and (b) next-state GHR = mispredicted-train load if `train_valid && train_mispredicted`, else prediction shift if `predict_valid`, else hold. Ordinary training (`train_valid && !train_mispredicted`) must leave the GHR untouched even though it writes the PHT.

A subtle trap: if `train_valid && train_mispredicted` and `predict_valid` coincide, a naive implementation might shift the GHR by the predicted bit *and then* load `train_history`, or might load `train_history` but also insert the predicted bit. Both are wrong — the load fully overrides the shift. The checker should construct a stimulus where the predicted bit differs from the LSB of `train_history` so the two candidate next-states are distinguishable, then sample the GHR on the following cycle (via `predict_history` on a subsequent prediction, or by observing the index it produces).

Also verify the asynchronous reset path: assert `areset` mid-cycle (not aligned to a posedge) and confirm that `predict_taken`/`predict_history` immediately reflect cleared state (GHR=0, all counters 0) without waiting for a clock edge. A model that only clears on posedge will fail this.

Finally, confirm saturating-counter boundaries: drive a counter to 3 with repeated taken training, then a taken prediction must still output 1 and the counter must stay 3 (no wrap); similarly floor at 0. Combine this with the same-cycle read/write case so the checker exercises both the saturation and the pre-edge-read rule together.
