# Reset and Power-Up Behavior

The public specification defines a single asynchronous active-high reset, `areset`, and says nothing about any separate power-up initialization sequence. For the checker, this means the only legal way to establish a known architectural state is to assert `areset`. There is no "undefined until first clock" window that the checker should try to model: after reset deasserts, the PHT and GHR are fully specified.

**What reset clears.** On assertion of `areset`, the 128-entry PHT of two-bit saturating counters is cleared to 0 (strongly not-taken) and the 7-bit global history register is cleared to 0. Because reset is asynchronous, this clearing must be treated as immediate and independent of `clk`: the checker should not require a posedge to observe the cleared state, and should not assume the reset is sampled only at an edge. In practice the checker should force the model into the reset state whenever `areset` is high, before evaluating any edge-dependent behavior for that row.

**Interaction with the sampled edge.** The timing convention is that inputs are driven before the sampled posedge and outputs are sampled after the edge has settled. Reset is the exception to the "edge-driven" story: if `areset` is high at the sampled edge, the post-edge state is the reset state regardless of `predict_valid`, `train_valid`, or any training fields. The checker should therefore give reset the highest priority in next-state computation — reset overrides both the PHT write and the GHR update/recovery logic. A same-cycle training request while reset is asserted must not leave a counter incremented or a GHR recovered; the reset value wins.

**Power-up.** Since the spec provides no explicit power-up values beyond reset, the checker should treat the pre-reset state as don't-care and require a reset assertion before checking functional behavior. It should not assume the PHT starts at 0 or the GHR starts at 0 without a reset; those values are guaranteed only by `areset`. Equivalently: any test sequence that checks predictions or training effects must first drive `areset=1` (asynchronously) and then release it, after which PHT=0 and GHR=0 are the reference state.

**Worked example.** Suppose the checker begins a sequence with `areset=1` while `train_valid=1, train_pc=0, train_history=0, train_taken=1, train_mispredicted=1`. Because reset dominates, the checker expects PHT[0] to remain 0 (not incremented to 1) and GHR to remain 0 (not recovered). Only after `areset` is released does a subsequent training request at a posedge actually modify PHT[0] and, if mispredicted, recover the GHR.

**Checker takeaway.** Model state as: if `areset` then {PHT all 0, GHR 0} immediately; otherwise apply the clocked PHT write and the conditional GHR recovery/shift at the posedge. Do not invent power-up values, and do not let reset be overridden by same-cycle predict/train activity.
