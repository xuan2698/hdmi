# Reset and Power-Up Analysis for the Gshare Predictor

The public spec states reset is **asynchronous active-high**. This is the single most important fact for the checker, because it means the reset path is *not* a synchronous clear gated by `clk`. A correct implementation must drive the GHR and every PHT counter to zero the instant `areset` is asserted, independent of any clock edge. The checker should therefore assert `areset` at an arbitrary point in the cycle (deliberately off any posedge), then sample the outputs *before* the next posedge and confirm they already reflect cleared state.

Concretely, the observable consequences of reset are:

- `predict_history` must read 0 whenever `areset` is high, because the GHR is cleared. Since `predict_history` is a combinational tap of the GHR (the spec says the prediction interface "produces ... the state of the branch history register used to make the prediction"), a reset that only clears on posedge would leave a stale nonzero GHR visible for the remainder of the cycle — a detectable bug.
- `predict_taken` must reflect a cleared PHT. With all counters at 0 (the "strongly not-taken" encoding under the usual 2-bit saturating convention where 0 = strongly not-taken), a prediction on any PC should output 0. The checker can assert `predict_valid=1` with `areset=1` and confirm `predict_taken=0` and `predict_history=0` without advancing the clock. Note the spec does not pin the counter encoding explicitly, so the checker should treat "all counters cleared" as "prediction on a fresh table yields the not-taken default," and verify that default is 0 by construction (the reset value the design chooses must be the not-taken floor, since the spec's saturating-counter discussion floors at 0 and predicts not-taken there).

Power-up (before any reset) is unspecified by the public spec; the checker should not assume any particular initial state and should always issue an `areset` pulse before beginning functional stimulus. Do not test behavior in the window between time-zero and the first reset assertion.

A second reset subtlety: because reset is asynchronous, deassertion is also asynchronous with respect to the clock in the checker's stimulus. The spec does not require synchronous deassertion, so the checker should deassert `areset` cleanly between edges and then allow one full cycle before trusting state, to avoid racing a posedge. It should *not* demand a particular recovery/removal timing relationship, since the public spec is silent on it.

**Worked example (reset path).** Suppose the design has been running: GHR = 0b1010101, entry 0 counter = 3. The checker drives `areset=1` at, say, 30% into the cycle (no posedge nearby), with `predict_valid=1` and `predict_pc` hashing to entry 0. Expected *immediately*, before any clock edge: `predict_history = 0b0000000` and `predict_taken = 0`. A model that clears only on posedge will instead output `predict_history = 0b1010101` and `predict_taken = 1` for the rest of that cycle — the checker flags this as a reset-path failure. After deasserting `areset` and one clean cycle, a fresh prediction on entry 0 must still yield `predict_taken = 0`, confirming the counter was truly cleared to the floor rather than merely masked.

The key point for the final checker: **sample outputs in the same cycle as an off-edge `areset` assertion, before the next posedge, and require immediate cleared GHR and not-taken prediction.** This isolates asynchronous-reset correctness from all clocked behavior and is the cheapest high-value reset test.
