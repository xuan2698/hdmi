One likely implementation mistake is to let a same-cycle training request affect the prediction outputs, or to let the prediction's GHR shift override the misprediction recovery. The public spec makes these operations simultaneous but ordered by clock-edge semantics: prediction is combinational from the current PHT entry and current GHR, while training changes the PHT only at the next positive edge. If a mispredicted training and a prediction occur in the same cycle, the prediction must still report the old PHT state and old GHR, but the GHR update at the edge must come from training, not from the predicted branch. A design that computes `predict_taken` after applying the training counter update, or that computes `predict_history` after applying the prediction shift, will pass many ordinary cases but fail exactly the collision cases the checker is likely to target.

The subtle part is that there are two different “history” values in play. `predict_history` is an output describing the GHR value used to index the PHT for the prediction request. It is not necessarily the next GHR state. The next GHR state is determined by priority rules: if `train_valid && train_mispredicted`, recover to `{train_history[5:0], train_taken}`; otherwise, if `predict_valid`, shift in the predicted direction; otherwise hold. A common bug is to update the GHR whenever `predict_valid` is high, even when a mispredicted training is also high. That violates the stated precedence rule: training takes precedence because the predicted instruction will be discarded anyway. Another common bug is to shift the GHR on every training request. The spec only says to recover the GHR on mispredicted training; ordinary training updates the PHT but does not shift the GHR.

A related indexing mistake is to use the wrong history for the PHT index. The prediction index is formed by XORing the 7-bit `predict_pc` with the current 7-bit GHR. Training must index the PHT using `train_pc` XOR `train_history`, not the current GHR and not the prediction PC. If the implementation reuses the prediction index path for training, or updates the GHR before computing the training index, it can train the wrong counter. The checker can expose this with a case where `predict_pc` and `train_pc` differ, or where `train_history` differs from the current GHR.

A short worked example: let GHR be 0, PHT[0] be 2, and in one cycle have `predict_valid=1`, `predict_pc=0`, `train_valid=1`, `train_pc=0`, `train_history=0`, `train_taken=0`, `train_mispredicted=1`. Correct outputs are `predict_taken=1` and `predict_history=0`, because the prediction sees the pre-edge counter 2 and pre-edge GHR 0. At the edge, training decrements PHT[0] to 1 and sets GHR to `{000000,0}=0`. If the implementation instead outputs `predict_taken=0`, it applied training too early; if it outputs `predict_history=1`, it let the prediction shift override misprediction recovery. Both are high-value failures for the final checker.
