# Reset and Power-Up Behavior

The public specification defines only an asynchronous active-high reset (`areset`) and does not describe any separate power-up initialization sequence. Consequently, the checker should treat `areset` as the sole mechanism that establishes a known architectural state; any behavior observed before a reset has been applied is not part of the public contract and should not be used to constrain the model.

When `areset` is asserted, the branch predictor must asynchronously clear both stateful structures: the 7-bit global branch history register (GHR) and the 128-entry pattern history table (PHT) of two-bit saturating counters. "Asynchronous" here means the clearing does not wait for a clock edge. The checker should verify that asserting `areset` mid-cycle immediately forces the outputs to their reset values, independent of `clk`. In particular, `predict_history` must read as 0 while reset is high, and `predict_taken` must reflect the reset PHT state for the requested index. Because the spec does not state a nonzero reset value for the counters, the natural reading is that all PHT entries reset to 0, so a prediction during reset yields `predict_taken = 0` (the MSB of a zeroed two-bit counter is clear). The checker should confirm this rather than assume a "weakly not-taken" or "weakly taken" initialization.

Reset also overrides the normal next-state priority. Even if `train_valid && train_mispredicted` is asserted in the same cycle as `areset`, the GHR must remain cleared and the PHT must remain zeroed; the training request must not leak through. Similarly, a `predict_valid` request during reset must not shift the GHR. The checker should include a case where reset and training/prediction coincide to confirm that reset dominates.

After reset is deasserted, the first sampled cycle begins from GHR = 0 and all-zero PHT entries. The prediction interface then reads the PHT entry at `predict_pc ^ GHR` (with GHR = 0, this is just `predict_pc`) and outputs the counter's MSB as `predict_taken`, along with the current GHR as `predict_history`. The GHR updates at the next positive edge according to the priority rules: misprediction recovery first, then prediction shift, else hold. Ordinary training updates only the PHT counter at `train_pc ^ train_history` and does not shift the GHR.

A useful checker point: reset is the only defined initialization, so the checker should not attempt to model an implicit power-up state. Instead, it should drive `areset` high at the start of every test, sample the outputs while reset is asserted to confirm the asynchronous clearing, then deassert reset and begin normal stimulus. This avoids ambiguity about uninitialized PHT contents and ensures the first prediction after reset is evaluated against the all-zero table and zero GHR. Any test that skips the reset phase risks comparing against an undefined initial state and should be rejected as non-conforming to the public spec.

In short: asynchronous active-high reset clears GHR and PHT immediately, dominates all other inputs, and is the sole specified initialization mechanism. The checker should assert reset at test start, verify immediate output clearing, and only then exercise prediction and training.
