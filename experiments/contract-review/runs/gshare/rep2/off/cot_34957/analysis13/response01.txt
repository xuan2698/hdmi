The key timing distinction the checker must encode is that **all outputs are combinational functions of the current (pre-edge) state**, while **all state updates happen at the posedge**. Concretely:

- `predict_taken` and `predict_history` are computed from the *current* GHR and the *current* PHT contents, using the current `predict_pc` (and current `predict_valid`). They do not depend on `train_*` inputs at all in the same cycle — even if training targets the same PHT entry. The spec's timing diagram makes this explicit: a training request in cycle 4 changes the PHT entry only in cycle 5, so a prediction request in cycle 4 must output the cycle-4 PHT state.
- The next-state GHR is a priority mux: if `train_valid && train_mispredicted`, load `train_history`; else if `predict_valid`, shift in the predicted direction; else hold. Ordinary training (`train_valid && !train_mispredicted`) writes the PHT but leaves the GHR alone.
- The next-state PHT entry (indexed by `train_pc` xor `train_history`) is updated by saturating increment/decrement based on `train_taken`, but only when `train_valid`.

A checker that lets the training write leak into the combinational prediction path would wrongly output `predict_taken=1` in the same cycle the counter is being trained up. This is the "prediction sees pre-edge PHT state" rule.

Now layer the GHR priority on top. Suppose in that same cycle `train_mispredicted=1` with `train_history=H`. The prediction still reports `predict_history=GHR` (pre-edge) and `predict_taken` from the old counter, but the *next-state* GHR must be `H` (the mispredicted-training load), **not** the shifted prediction value. So the checker must independently track: (a) combinational outputs from current state, and (b) next-state GHR = mispredicted-train load if `train_valid && train_mispredicted`, else prediction shift if `predict_valid`, else hold. Ordinary training (`train_valid && !train_mispredicted`) must leave the GHR untouched even though it writes the PHT.

A subtle trap: if `train_valid && train_mispredicted` and `predict_valid` coincide, a naive implementation might shift the GHR by the predicted bit *and then* load `train_history`, or might load `train_history` but also insert the predicted bit. Both are wrong — the load fully overrides the shift. The checker should construct a stimulus where the predicted bit differs from the LSB of `train_history` so the two candidate next-states are distinguishable, then sample the GHR on the following cycle (via `predict_history` on a subsequent prediction, or by observing the index it produces).

Also verify the asynchronous reset path: assert `areset` mid-cycle (not aligned to a posedge) and confirm that `predict_taken`/`predict_history` immediately reflect cleared state (GHR=0, all counters 0) without waiting for a clock edge. A model that only clears on posedge will fail this.

Finally, confirm saturating-counter boundaries: drive a counter to 3 with repeated taken training, then a taken prediction must still output 1 and the counter must stay 3 (no wrap); similarly floor at 0. Combine this with the same-cycle read/write case so the checker exercises both the saturation and the pre-edge-read rule together.

**Worked example.** Cycle N: GHR=0b0000101, `predict_valid=1`, `predict_pc` hashes to entry 0 whose counter is 2 (predict taken, `predict_taken=1`, `predict_history=0b0000101`). Same cycle: `train_valid=1`, `train_mispredicted=1`, `train_taken=0`, `train_history=0b1100000`, `train_pc` also hashes to entry 0. Expected outputs this cycle: `predict_taken=1`, `predict_history=0b0000101` (pre-edge). Next cycle: GHR=0b1100000 (load wins over shift), entry 0 counter decremented to 1. A checker that outputs `predict_taken=0` or `predict_history=0b0001010` has leaked training into the combinational path or mishandled priority.
