The public spec defines a gshare predictor whose observable behavior is split cleanly between combinational prediction outputs and edge-committed state. The checker should treat `predict_taken` and `predict_history` as functions of the pre-edge state: the PHT entry selected by `predict_pc` XOR the current GHR, and the current GHR itself. They must not reflect any training update requested in the same cycle, because training only modifies the PHT and GHR at the next positive clock edge. This is the central timing rule and the most likely source of checker false positives if sampling is done carelessly.

Inputs are driven before the sampled posedge. `predict_valid`, `predict_pc`, `train_valid`, `train_taken`, `train_mispredicted`, `train_history`, and `train_pc` all describe the cycle whose edge is about to be sampled. The outputs `predict_taken` and `predict_history` are read after that edge has settled, but they must correspond to the state that existed immediately before the edge. In other words, the edge commits updates; it does not retroactively change what the prediction interface reported for that cycle. A checker that samples outputs only after the edge and compares them to post-edge state will incorrectly reject a correct design.

The mid-input changes occur after sampling and before the next edge. They are carried into the start of the next row. This means the checker should not treat a mid-cycle change as affecting the just-sampled prediction. It only affects the next sampled edge. The practical consequence is that each row's expected outputs are computed from the state at the beginning of that row, while the state for the following row is computed by applying that row's training and prediction-side GHR update at the edge.

Training has priority over prediction for the GHR when both occur in the same cycle. If `train_valid` and `train_mispredicted` are asserted, the next GHR is formed from `train_history` and `train_taken`, not from the current GHR shifted by the predicted outcome. If training is valid but not mispredicted, the PHT is updated but the GHR recovery rule does not apply. If prediction is valid and training is not recovering the GHR, the predicted branch shifts the GHR. If both a prediction and a mispredicted training occur, the training recovery wins and the predicted branch's shift is discarded.

The PHT update is also edge-committed. A same-cycle prediction and training of the same entry must have the prediction observe the old counter value. The training request changes the counter only for subsequent cycles. Saturating counters must pin at `2'b11` and `2'b00`; they must not wrap. The GHR must wrap by shifting out the oldest bit and inserting the new outcome, with seven bits total.

A short worked example captures the collision: PHT entry 0 holds `2'b10`, GHR is `7'h00`, and in one cycle `predict_valid=1, predict_pc=0` coincides with `train_valid=1, train_pc=0, train_history=0, train_taken=1, train_mispredicted=1`. The prediction outputs must be `predict_taken=1` and `predict_history=7'h00`. At the edge, the PHT becomes `2'b11` and the GHR becomes `7'h01`. The next prediction for `pc=0` sees `2'b11` and history `7'h01`. This single case distinguishes pre-edge prediction visibility, training-priority GHR recovery, and correct PHT update ordering.
