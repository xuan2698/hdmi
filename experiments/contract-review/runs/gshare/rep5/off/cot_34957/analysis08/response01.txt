The reset and power-up behavior of this gshare predictor is the first thing the checker must pin down, because every subsequent prediction and training observation depends on a known initial state. The public specification states that reset is asynchronous active-high. That means the checker should not assume the design waits for a rising clock edge before clearing state. Instead, it should drive `areset=1` at an arbitrary point in the cycle — ideally between sampled edges, after one row has been captured and before the next — and then observe that the architectural state has been cleared without requiring a clock transition. The two pieces of state that must clear are the 7-bit global branch history register (GHR) and the 128-entry pattern history table (PHT) of two-bit saturating counters. After reset, the GHR should read as `7'h00`, and every PHT entry should read as `2'b00` (the strongly-not-taken encoding implied by the saturating counter description and the worked example, where a decrement from `2'b11` yields `2'b10`). The checker should confirm this by issuing a prediction immediately after reset release and checking that `predict_history` is zero and that the predicted direction corresponds to the reset PHT contents for the computed index.

Power-up behavior before any reset is less constrained by the public spec, but the checker should treat the post-reset state as the only reliable starting point. It is safest to begin every test sequence with an asynchronous reset assertion, then release reset and sample on subsequent edges. The checker should avoid assuming any particular value of GHR or PHT prior to the first reset, since the spec does not define power-up contents. If the checker needs a deterministic baseline, it should assert `areset` mid-cycle, wait for the state to clear, release, and only then begin driving `predict_valid`/`train_valid`.

A subtle point for the checker is the interaction between asynchronous reset and same-cycle prediction/training requests. Because reset is asynchronous and active-high, if `areset` is asserted while `predict_valid` or `train_valid` is high, the reset should dominate: the GHR and PHT clear, and any pending prediction or training effect is discarded. The checker should verify that a prediction requested in the same cycle as an asynchronous reset assertion does not leave residual state — for example, that the GHR does not shift on that edge and that no PHT entry is modified. After releasing reset, the next sampled edge should show the cleared state, and the first legitimate prediction should use `predict_history=7'h00`.

Worked discriminator for reset: suppose the checker has trained the predictor so that GHR=`7'h2A` and PHT[0x3F]=`2'b11`. It then asserts `areset=1` mid-cycle, before the next rising edge, while also holding `predict_valid=1` with `predict_pc=7'h15`. The checker should observe, without waiting for a clock edge, that the GHR has cleared to `7'h00` and PHT[0x3F] has cleared to `2'b00`. On the next sampled edge after reset release, `predict_history` should be `7'h00`, and the prediction for `predict_pc=7'h15` should reflect the cleared PHT entry (i.e., not-taken, since `2'b00` is the strongly-not-taken state). A design that only clears state on the clock edge, or that lets the same-cycle prediction shift the GHR despite reset, will fail this check. The checker should also confirm that after reset release, a subsequent training request writes the PHT normally, proving the reset did not leave the table in a stuck or partially cleared condition.
