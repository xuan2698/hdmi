The key timing fact for the checker is that this design has two distinct "views" of state in each cycle: the registered state visible at the sampling edge, and the next-state updates that only become visible after the following posedge. The prediction interface is combinational with respect to the current PHT and history register, while training effects are deferred to the next edge. So the checker must sample outputs after the posedge has settled, using the pre-edge registered state, and must not let a same-cycle training request retroactively change the prediction outputs.

At a sampled posedge, the values that matter are the current global history register and the current PHT entry selected by the xor of `predict_pc` and that history. If `predict_valid` is high, `predict_taken` is the current counter's MSB (taken if the 2-bit saturating counter is in the taken half) and `predict_history` is the current 7-bit history register, both computed from state before any edge update. The prediction request also schedules a history update for the next edge: the history register shifts in the predicted direction for the predicted branch. That update is not visible in the same cycle's `predict_history`; it appears only after the next posedge.

Training is similar but has priority rules. When `train_valid` is high, the PHT entry addressed by `train_pc` xor `train_history` is updated at the next posedge according to `train_taken`, using 2-bit saturating arithmetic. If `train_mispredicted` is also high, the history register is recovered at the next posedge to the state immediately after the mispredicting branch, which in this interface is supplied as `train_history` (the history value associated with the branch being trained). The spec says training takes precedence over a simultaneous prediction's history update, because the predicted younger instruction will be flushed. Therefore, if both `predict_valid` and a mispredicted `train_valid` occur in the same cycle, the next-edge history register must reflect the training recovery, not the prediction shift.

The subtle PHT point is the "prediction sees old state" rule. If prediction and training hit the same PHT entry in the same cycle, the prediction output must use the counter value before the training update. The training update changes the entry only after the posedge. This means the checker should evaluate prediction outputs from the current table contents, then apply training writes and history updates as next-state actions. It should not compute prediction after applying the training increment/decrement.

Mid-cycle input changes are changes that occur after the sampled edge and before the next edge. They are carried into the next row's pre-edge values. For the checker, this means the inputs for a row are the values present just before that row's sampled posedge, including any mid changes from the previous row. Outputs are sampled after the posedge settles, so they reflect the registered state that existed before that edge plus any combinational prediction path from the row's inputs. The checker should therefore treat each row as: establish inputs, sample outputs after edge, then compute next state for the following row.

A short worked example: suppose the current history is H, `predict_pc` xor H selects entry E with counter 2'b10 (taken), and `predict_valid` is high. The sampled outputs must be `predict_taken=1` and `predict_history=H`. If in the same cycle `train_valid` is high for the same entry E with `train_taken=0`, the prediction still outputs taken from the old 2'b10; the PHT entry becomes 2'b01 only after the edge. If `train_mispredicted` is also high, the next history register becomes `train_history`, overriding the prediction's shift. This priority and deferred-write behavior is the main thing the final Python checker must encode.
