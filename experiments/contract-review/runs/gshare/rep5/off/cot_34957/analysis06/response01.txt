One implementation mistake worth targeting is conflating the two independent state updates that can occur on the same edge: the PHT counter write and the GHR update. The spec makes them separate: training always updates the PHT entry selected by `train_pc` using `train_taken`, while the GHR update depends on whether a prediction is being made and whether training is recovering from a misprediction. A common bug is to treat `train_valid` as a global "do training instead of prediction" signal, so that when both `predict_valid` and `train_valid` are high the design skips the prediction-side GHR shift entirely, or shifts the GHR by `train_taken` rather than by the predicted direction. Both are wrong for a non-mispredicted training: the prediction still reads the pre-edge PHT entry, still reports the pre-edge `predict_history`, and still shifts the GHR by the predicted direction at the edge. Training only changes the PHT counter; it does not alter the GHR unless `train_mispredicted` is asserted.

The same mistake shows up in the misprediction case in a subtler form. When `train_mispredicted=1`, recovery wins over the prediction shift, so the next GHR is `{train_history[5:0], train_taken}`. A buggy design might apply the prediction shift first and then overwrite with recovery, which happens to give the same final GHR but can corrupt the PHT write if the implementation uses the shifted GHR to compute the training index, or might skip the PHT write because it treats recovery as "no training." The spec requires the PHT write to occur regardless of `train_mispredicted`, using the index derived from `train_pc` and `train_history` (the supplied history, not the live GHR). Another variant reads the PHT entry for prediction after applying the training write in the same cycle, which violates the "prediction sees pre-edge state" rule.

A tight discriminator is a same-cycle predict-and-train on the same index with opposite directions. For example, let `ghr=7'h2A`, `predict_pc=7'h15` (index `0x3F`), and suppose PHT[0x3F]=`2'b11`. With `train_valid=1`, `train_pc=7'h15`, `train_history=7'h2A`, `train_taken=0`, `train_mispredicted=0`, the prediction must output `predict_taken=1` and `predict_history=7'h2A`; after the edge PHT[0x3F] becomes `2'b10` and GHR becomes `{2A[5:0],1}=7'h55`. If `train_mispredicted=1` instead, the prediction outputs are unchanged, PHT still updates to `2'b10`, but next GHR is `{2A[5:0],0}=7'h54`. A design that shifts by `train_taken` would produce `7'h54` in the first case, and a design that suppresses the prediction shift under `train_valid` would leave GHR at `7'h2A`; both fail the first case. The checker should sample `predict_taken`/`predict_history` before the edge and inspect GHR/PHT after the edge, and should include a mid-cycle `areset` assertion to confirm asynchronous clearing without requiring a clock edge.
