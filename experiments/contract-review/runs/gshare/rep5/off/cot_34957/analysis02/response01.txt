**Reset and power-up behavior**

The design has a single asynchronous active-high reset, `areset`. Because it is asynchronous, assertion of `areset` takes effect immediately, independent of `clk`; the checker must not require a clock edge to observe reset behavior. While `areset` is high, the architectural state is forced to its reset values: the 7-bit global branch history register is cleared to zero, and the 128-entry PHT of two-bit saturating counters is initialized to a defined reset state (the public spec fixes the counter width and table size but does not spell out the reset counter encoding, so the checker should treat the reset PHT contents as the implementation's documented reset value rather than inferring one from the prose). All outputs are combinational functions of registered state and current inputs, so during reset the prediction outputs settle to whatever the cleared history and reset PHT imply for the applied `predict_pc`; the checker should sample outputs only after the edge has settled and should not assume `predict_taken` is forced low by reset unless the reset PHT encoding makes it so.

Power-up without a reset assertion is not a specified state. The public spec gives no initialization guarantee for the history register or PHT absent `areset`, so the checker must drive `areset` before relying on any state. It should not attempt to predict behavior from an uninitialized table.

The important reset subtlety for the final checker is the interaction between asynchronous reset and the same-cycle training/prediction rules. Reset dominates all next-state logic: if `areset` is high at the sampling point, the next history register is zero and the PHT returns to its reset contents, regardless of `predict_valid`, `train_valid`, `train_mispredicted`, or the precedence of training over prediction. The checker should model reset as an unconditional override applied to the registered state, evaluated before the normal next-state equations. It should also confirm that reset is level-sensitive and asynchronous: a mid-cycle assertion between edges must clear state without waiting for the next posedge, and a mid-cycle deassertion must not itself create a spurious update.

A short worked example: suppose the history register holds `7'h2A`, the PHT entry selected by `predict_pc ^ history` holds `2'b11`, and in one cycle `predict_valid=1`, `train_valid=1`, `train_taken=0`, `train_mispredicted=1`, with `areset` also asserted. The prediction outputs may still reflect the pre-reset registered state for that sampled edge, but the next-edge state must be the reset state: history `7'h00` and the reset PHT contents. Training's precedence over the prediction shift is irrelevant here because reset overrides both. The checker should encode reset as the highest-priority next-state action, then training recovery, then prediction shift, then hold.
