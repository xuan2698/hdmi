**Reset and power-up behavior**

The design has a single asynchronous active-high reset, `areset`. Because it is asynchronous, assertion takes effect immediately, independent of `clk`; the checker must not require a clock edge to observe reset behavior. While `areset` is high, the architectural state is forced to its reset value: the 7-bit global history register (GHR) is cleared to `7'h00`, and all 128 two-bit PHT counters are cleared to `2'b00`. The outputs are combinational functions of the current state and the current inputs, so during reset the prediction outputs should reflect the cleared state whenever `predict_valid` is asserted: with GHR `0`, the index is `predict_pc ^ 0 = predict_pc`, the selected counter is `2'b00`, so `predict_taken` is 0 and `predict_history` is `7'h00`. If `predict_valid` is low, `predict_taken` and `predict_history` are don't-cares for checking purposes, though a reasonable implementation may still drive them from state.

Power-up without an explicit reset is not part of the public contract. The spec only guarantees behavior after `areset` has been applied. The checker should therefore begin every test by asserting `areset` for at least one cycle (and, because it is asynchronous, it may assert it between edges) and should not attempt to predict state before that. After deassertion, the first sampled edge establishes normal operation. There is no requirement that reset be synchronized to `clk`, and no requirement about output glitches while `areset` is high; only the sampled values at the specified sampling points matter.

A subtle point for the checker is the interaction of reset with the edge-committed updates. Training and prediction updates are applied at the positive clock edge. If `areset` is asserted asynchronously, it overrides those updates: the GHR and PHT return to zero regardless of any `train_valid` or `predict_valid` values present. Thus a row that has `areset=1` should be checked as producing reset-state outputs and leaving reset-state state for the next row, even if training inputs are also high. Conversely, a row with `areset=0` uses the normal priority rules: a mispredicted training request recovers the GHR from `train_history` and `train_taken`; otherwise a valid prediction shifts in the predicted direction; PHT writes are edge-committed and a same-cycle prediction observes the pre-edge counter.

Worked reset example: suppose before an edge the GHR is `7'h2A` and PHT entry 5 is `2'b11`, and in the sampled row `areset=1`, `predict_valid=1`, `predict_pc=7'h05`, `train_valid=1`, `train_pc=7'h05`, `train_taken=1`, `train_mispredicted=1`. The expected outputs are `predict_taken=0`, `predict_history=7'h00` (reset state, not the old GHR). At the edge the state remains GHR `0` and PHT entry 5 `2'b00`; the training request is suppressed by reset. The next row, with `areset=0` and a prediction for `pc=5`, must see counter `2'b00` and history `0`, not the pre-reset values. This case is useful because it distinguishes asynchronous reset override from ordinary training priority and confirms that reset clears both the GHR and the entire PHT, not merely the addressed entry.
