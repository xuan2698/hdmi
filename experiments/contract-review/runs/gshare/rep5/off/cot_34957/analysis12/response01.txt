One likely implementation mistake is to let a same-cycle training request influence the prediction outputs, or to let a same-cycle prediction shift the GHR before training recovery is applied. The public spec is explicit that the prediction interface reports the PHT state and branch history register value used to make the prediction, and that training only modifies the PHT at the next positive clock edge. Therefore, when `predict_valid` and `train_valid` target the same PHT entry in the same cycle, `predict_taken` must reflect the old counter value, not the trained value. Likewise, `predict_history` must be the pre-edge GHR, not a value already shifted for the predicted branch.

A second, closely related mistake is mishandling the GHR update priority. If both a prediction and a misprediction training request occur in the same cycle, training takes precedence because the predicted instruction is younger and will be flushed. The recovered GHR should be formed from `train_history` and `train_taken`, not from the current GHR plus the predicted branch outcome. A design that simply performs the prediction shift and then applies training recovery in the wrong order, or that applies both updates, can produce an incorrect next-cycle history.

A useful worked example: suppose PHT entry 0 has been trained twice taken and currently holds `2'b10`, and the GHR is `7'h00`. In one cycle assert `predict_valid=1, predict_pc=0` and `train_valid=1, train_pc=0, train_history=0, train_taken=1, train_mispredicted=1`. The prediction must output `predict_taken=1` from the old `2'b10` and `predict_history=7'h00`. At the edge, training updates the PHT entry to `2'b11` and recovers the GHR to `{train_history[5:0], train_taken} = 7'h01`. The next prediction for `pc=0` should see `2'b11` and history `7'h01`. A checker should include this exact same-cycle collision because it distinguishes correct pre-edge prediction visibility and training-priority GHR recovery from several plausible but wrong implementations.

The checker should also test counter saturation and GHR wrap behavior independently. Repeated same-direction training must pin the two-bit counter at `2'b11` or `2'b00`; a signed or wrapping counter bug often appears only on the third same-direction update. For the GHR, seven taken predictions should yield `7'h7F`, an eighth taken prediction should leave it at `7'h7F`, and a following not-taken prediction should produce `7'h7E`. These tests catch shift-width and masking errors that a single collision test might miss.

Finally, sampling matters. Outputs should be sampled after the clock edge has settled but interpreted as functions of pre-edge state. A design that commits PHT or GHR updates before the prediction is observed will fail the same-cycle collision case even if its steady-state training behavior looks correct. The minimal distinguishing test is the collision above: prediction must see `2'b10` and `7'h00`, while the edge commits `2'b11` and `7'h01`.
