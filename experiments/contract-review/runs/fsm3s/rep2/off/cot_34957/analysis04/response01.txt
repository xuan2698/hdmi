The public table defines four states, A through D, with a single 1-bit input `in`, a single 1-bit synchronous active-high `reset`, and a single 1-bit Moore output `out`. The state encoding is not specified numerically; the checker should treat the states symbolically and only care about the transition and output mapping. Because the output is Moore, `out` depends solely on the current (post-edge) state: states A, B, and C output 0, while state D outputs 1. There is no input-dependent output term, so the checker must not combine `in` with the state when computing the expected output.

The transition table has a few structural features worth noting for boundary checking. State A with `in=0` self-loops to A, and with `in=1` advances to B. State B with `in=0` goes to C, and with `in=1` self-loops to B. State C with `in=0` returns to A, and with `in=1` advances to D. State D with `in=0` goes to C, and with `in=1` goes to B. Notably, D has no self-loop: every non-reset edge leaves D. This means the output-1 condition is transient in the sense that it lasts exactly one sampled edge after entering D, unless reset re-enters A. The checker should verify that once D is reached, the very next non-reset edge produces C or B and therefore output 0 again.

Reset is synchronous and active high, and it has priority over the transition table. At each rising edge, if `reset` is high, the next state is A independent of `in` and independent of the current state. If `reset` is low, the next state follows the table. The checker should evaluate reset first, then the table, then the Moore output from the resulting state. Comparing output against the pre-edge state would be wrong, especially on edges that enter or leave D.

The specification does not define a power-on state or an asynchronous reset. The checker should not assume the machine begins in A before a reset-sampled edge. A safe approach is to establish a known state by sampling an edge with `reset=1`, then begin meaningful output comparisons from the following settled state. Any expected-state tracking before that first reset edge relies on an initialization convention not present in the public table.

Mid-input changes occur after sampling and before the other edge. They do not trigger a transition and do not retroactively change the just-sampled output. They are carried forward as the starting input for the next row unless that row drives a new value. The checker should therefore separate the sampled input used for a given edge from any later mid-row input value.

Worked example: if the current state is B with output 0 and a row drives `in=0`, `reset=0`, the rising edge moves B to C, and the settled output is 0. A later mid-row change of `in` to 1 is carried to the next row and does not alter the B-to-C transition or produce output 1 at that edge.
