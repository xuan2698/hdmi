**Reset and power-up analysis**

The specification defines a synchronous active-high reset. That means reset is not an asynchronous override: it is sampled at the same rising clock edge as the state transition logic. The checker should therefore evaluate reset as part of the edge behavior, not as a continuous level that forces state A immediately whenever reset is high. If reset is asserted before a rising edge and remains high through that edge, the next state is A regardless of the current state and regardless of the input value. If reset is asserted only between edges, it has no effect until the next sampled rising edge. This distinction is important because a checker that treats reset as asynchronous may compare the output too early, before the edge has settled, or may incorrectly force state A during a row in which reset is high but no rising edge occurs.

Power-up behavior is not specified beyond the reset mechanism. The public table gives no separate initial state for simulation start, and no asynchronous reset path is described. For checking purposes, the safest interpretation is that the machine must be brought to a known state by the synchronous reset at a rising edge. The checker should not assume that state A is present before the first reset-sampled edge unless the testbench explicitly establishes it. In other words, the first meaningful comparison should follow a sampled edge where reset has been applied, or the checker should otherwise track the expected state from a known initialization convention that is outside the public state table. The prose specification does not grant an implicit power-on state, so the final checker should avoid relying on one.

Because the machine is Moore, the output depends only on the current state after the sampled edge has settled. The output is not a function of the row input. A row may drive `in` and `reset` before the edge; at the edge, reset takes priority if high, otherwise the transition table uses `in` to choose the next state. After the edge settles, the checker compares `out` to the Moore output for that resulting state. This ordering prevents the common mistake of using the pre-edge state for the output comparison.

Mid-input changes occur after sampling and before the other edge. They must not retroactively affect the just-sampled transition or output. The checker should carry such a change forward as the starting input for the next row, unless the next row drives a new value. A mid-input change is not an extra clock event and does not itself cause a transition.

Worked example: state B, output 0, row drives `in=0`, `reset=0`. At the rising edge, B with `in=0` goes to C. After settling, state C gives output 0. If `in` later changes to 1 mid-row, that value is carried to the next row; it does not change the B-to-C result or make the output 1 at that edge. The checker should apply reset first at each sampled edge, otherwise use the row input for the transition, then compare the output to the resulting state’s Moore value.
