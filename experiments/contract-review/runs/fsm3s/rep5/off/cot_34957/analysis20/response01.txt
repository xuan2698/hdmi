The most useful thing to pin down for the final checker is the exact ordering of observations within a row, because the public spec's Moore formulation makes output a function of the *pre-edge* state only, while reset and `in` affect only the *post-edge* state. Getting that order wrong produces errors that look like transition-table mistakes but are actually one-row offsets.

Consider the three common failure modes and why each masquerades as a table bug.

First, computing `out` from the next state rather than the current state. In a Moore machine the output is attached to the state the machine is *in* during the row, i.e. the state present before the sampled edge. If an implementation derives `out` from the state it is about to enter, every output is shifted one row later. The symptom is subtle: the output appears correct on the following row because the state has caught up, which can be misread as a transition-table bug.

Second, letting `reset` influence `out` directly. Reset is synchronous and active high; it forces the post-edge state to A. It does not change the output observed for the current row. If the pre-edge state is D and `reset` is high, the row's `out` must still be 1. Gating the output with reset, or computing output from the reset-forced next state, would emit 0 for that row and then appear correct on the next row (state A, output 0). Again, the symptom is a one-row offset that mimics a transition error.

Third, sampling `in` too late. Mid-cycle input changes occur after sampling and are carried to the start of the next row. The transition for a row must use the `in` value present at that row's sampling edge. If the checker reads `in` after a mid-cycle change, it may select a transition the hardware never took. The resulting state mismatch appears one row later and can be misdiagnosed as a next-state table error rather than a sampling error.

Worked example: suppose the pre-edge state is D, `in` is 0, and `reset` is high. The correct row output is 1 because the pre-edge state is D. The post-edge state is A because reset overrides the transition. If an implementation instead computes next state A first and drives `out` from A, it emits 0 for this row and 0 for the next row, which looks like a correct A-row output but is actually shifted by one row.

For the final checker, the useful invariant is row-local and ordered: capture pre-edge state and sampled `in`/`reset`; verify `out` from the pre-edge state via the Moore table; then compute post-edge state as A if reset is high, otherwise the table entry for (pre-edge state, sampled `in`); finally advance. Output verification must occur strictly before reset and transition application, and no mid-cycle `in` value may feed the current row's transition. This structure catches output-from-next-state bugs, reset-gating bugs, and mid-cycle leakage without requiring path reasoning.
