The key timing point for the checker is that this is a Moore machine: the sampled output on any row must be a function of the state *before* that row's clock edge, not the state reached after the transition. The public table lists output alongside each state, so the natural reading is "if the machine is in state S at the sampling edge, `out` equals S's output." A common implementation error is to compute the next state first and then drive `out` from that next state. Because the only state with output 1 is D, this error is invisible on every row except those adjacent to a D visit, which makes it easy to miss in casual testing but easy to localize with a targeted sequence.

A concrete sequence exposes the shift. Starting from reset (state A), apply inputs 1, 1, 0, 1, 1 across successive rows. Row 1: A with in=1 → B, output 0. Row 2: B with in=1 → B, output 0. Row 3: B with in=0 → C, output 0. Row 4: C with in=1 → D, output 0, because the pre-edge state is C. Row 5: D with in=1 → B, output 1, because the pre-edge state is D. The correct output stream is therefore 0,0,0,0,1. An implementation that drives output from the next state emits 1 on row 4 (next state D) and 0 on row 5 (next state B), producing 0,0,0,1,0. That is a clean one-row shift, and it is exactly the signature the checker should attribute to output timing rather than to a transition-table error.

The same sequence also distinguishes a second plausible mistake: conflating C and D on input 1. If C→B is used instead of C→D, row 4 lands in B rather than D, and the expected output 1 on row 5 never appears. Here the first observable divergence is the state on row 5, but the output discrepancy on row 5 is the more diagnostic signal because it directly reflects the missed D visit. The checker should therefore record both the post-transition state and the sampled output per row, so it can report whether the failure is a state error, an output-timing error, or both.

For the final checker, evaluate each row in a fixed order: read the pre-edge state, the input sampled at that edge, and reset; check `out` from the pre-edge state (A/B/C give 0, D gives 1); then apply reset (forcing A) or the table transition; then advance. Mid-cycle input changes must be carried to the next row and must not affect the current row's transition. This ordering catches output-from-next-state errors, reset-gating errors, and input-sampling leakage, and it makes the C/D and A/B distinctions observable at the row where they actually matter.
