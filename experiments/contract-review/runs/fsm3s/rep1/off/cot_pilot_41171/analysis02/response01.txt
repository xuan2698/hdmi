# Moore FSM Implementation — Detailed Reasoning

## 1. Reading the specification literally

The table gives four states A–D, one 1-bit input `in`, one 1-bit output `out`, and a synchronous active-high `reset` that forces state A. The output column is a **Moore** output: it depends only on the current state, not on `in`. Concretely:

- A: `in=0 → A`, `in=1 → B`, output 0
- B: `in=0 → C`, `in=1 → B`, output 0
- C: `in=0 → A`, `in=1 → D`, output 0
- D: `in=0 → C`, `in=1 → B`, output 1

So `out = 1` **iff** the current state is D. Every other state outputs 0. This is the single most important fact to get right: the output must be a pure function of the registered state, not of `next_state` and not of `in`.

## 2. State encoding

Four states need two bits. I choose the natural binary encoding A=00, B=01, C=10, D=11. This is arbitrary but convenient: it makes `out = state[1] & state[0]` (i.e., `state == 2'b11`), and it lets me sanity-check the next-state logic with Boolean algebra. The RTL itself will use a `case` statement, so the encoding is abstracted away and the code reads directly like the table — which is the safest way to avoid transcription errors.

## 3. Deriving the next-state equations (sanity check)

Let `s1 s0` be the state bits and `i = in`. Reading the table row by row:

- **ns1 (MSB of next state):** set when (A and i=1) → B=01, (B and i=0) → C=10, (C and i=1) → D=11, (D and i=0) → C=10. So ns1 = 1 for: A·i, B·ī, C·i, D·ī.
  - A·i = s1' s0' i
  - B·ī = s1' s0 ī
  - C·i = s1 s0' i
  - D·ī = s1 s0 ī
  - Grouping: (s1' s0' + s1 s0') i + (s1' s0 + s1 s0) ī = s0' i + s0 ī = **s0 ⊕ i**.
- **ns0 (LSB):** set when (A and i=1) → B=01, (B and i=1) → B=01, (C and i=1) → D=11, (D and i=1) → B=01. In every case ns0 = 1 exactly when i = 1. So **ns0 = i**.

So the compact form is `next_state = {s0 ^ i, i}`. That is a nice cross-check: it means the LSB of the next state is just the input, and the MSB is the XOR of the current LSB with the input. I will **not** hand-write this in RTL, because a `case` statement is far more readable and directly mirrors the spec; but if the case statement and this equation ever disagree, I know I mistyped a row.

## 4. RTL structure

Three pieces, standard Moore template:

1. **State register** — `always @(posedge clk)` with `if (reset) state <= A; else state <= next_state;`. This is the *synchronous* active-high reset: reset is sampled on the same clock edge as everything else, so it does not create an asynchronous path. On a rising edge with `reset=1`, the state becomes A regardless of `next_state`. On a rising edge with `reset=0`, the state takes the combinational `next_state` value that was stable just before the edge.
2. **Next-state combinational block** — `always @(*)` with a `case (state)` that assigns `next_state` from `in` exactly per the table, plus a `default: next_state = A;` to keep the latch-free / fully-assigned property and to make simulation X-safe if the state ever becomes 2'bxx (it cannot in normal operation, but the default costs nothing).
3. **Output** — `assign out = (state == D);`. Pure Moore output, no dependence on `in`, no dependence on `next_state`. This is critical: if I had written `out = (next_state == D)` I would have created a Mealy-like glitch path and violated the spec.

## 5. Timing / check-cycle reasoning

The protocol says: inputs are driven before the sampled (posedge) edge; the sample happens after the posedge has settled; optional mid-cycle input changes occur after sampling and before the next edge, and are carried into the next row. That is exactly the behavior of a synchronous FSM:

- At posedge *n*, the flop captures the value of `next_state` that was computed from `state` (the value *before* the edge) and `in` (the value *before* the edge). So the state visible *after* edge *n* is the state the table says you should be in given the pre-edge state and pre-edge input.
- The output `out` is a combinational function of the *registered* state, so it settles shortly after the posedge (one gate delay) and is stable for the rest of the cycle. It does **not** change mid-cycle when `in` changes, because `in` does not feed the output. This is the defining property of a Moore machine and matches the spec's "output" column being a function of state only.
- A mid-cycle change on `in` only affects `next_state`; it is latched at the *next* posedge. That is exactly "carried to the start of the next row."

So the check-cycle view is: sample `state` and `in` at the edge → compute next state → register it → output reflects the new state for the whole following cycle.

## 6. Reset / hold / state-update corner cases

- **Reset asserted at a posedge:** state ← A unconditionally. `next_state` is ignored that cycle. Output becomes 0 (since A ≠ D) one gate delay after the edge.
- **Reset released:** the very next posedge uses `next_state` computed from state A and whatever `in` is then. If `in=0`, stay in A; if `in=1`, go to B. No special "reset release" state is needed because reset is synchronous — there is no asynchronous recovery/removal timing to worry about.
- **Hold behavior:** there is no explicit "hold" input; the machine only holds a state if the table says so (e.g., A with `in=0` stays A; B with `in=1` stays B). The state register always updates to `next_state` when reset is low — it never "freezes" on its own. That is correct per the table.
- **Illegal state (2'bxx in simulation):** the `default` in the case sends `next_state` to A, and `out` evaluates `(state==D)` which is false for X, so the output is 0 (or X in four-state sim, but the default recovers the state next edge). In hardware this cannot occur because the encoding is fully covered.
- **Output glitch:** because `out` is a single comparison on the registered state, it can only change right after a posedge that moves into or out of D. No combinational path from `in` reaches `out`, so no input-induced glitches.

## 7. Manual trace of a small counterexample

Start in A, reset low. Drive `in` sequence 1, 0, 1, 1, 0, one value per cycle, sampled at successive posedges.

- Cycle 0 (state A, in=1): next = B. After edge: state B, out 0.
- Cycle 1 (state B, in=0): next = C. After edge: state C, out 0.
- Cycle 2 (state C, in=1): next = D. After edge: state D, **out 1**.
- Cycle 3 (state D, in=1): next = B. After edge: state B, out 0.
- Cycle 4 (state B, in=0): next = C. After edge: state C, out 0.

Check against the table: A→(1)→B ✓, B→(0)→C ✓, C→(1)→D ✓, D→(1)→B ✓, B→(0)→C ✓. Output is 1 only while in D, exactly one cycle here. Good.

Second trace, reset in the middle: state D, `in=0`, reset=1 at the posedge. Table would say D→(0)→C, but reset overrides: state ← A, out ← 0. Next cycle with `in=0` stays A. Correct synchronous-reset behavior.

Third trace, mid-cycle input change: state A, `in` driven 0 before the edge (so next=A), then `in` flips to 1 mid-cycle. At the posedge the sampled `in` was 0, so state stays A; the mid-cycle 1 is "carried to the start of the next row," i.e., it will be the `in` value for the next cycle's evaluation. This matches the protocol description and is exactly what a synchronous FSM does.

## 8. Independent check of weak points

- **Is the output truly Moore?** Yes — `assign out = (state == D)` references only the state register. No `in`, no `next_state`. This is the most common place to slip; verified.
- **Is reset synchronous and active-high?** Yes — it is inside the `posedge clk` block, tested as `if (reset)`, and forces A. It is not in a sensitivity list, so it is not asynchronous.
- **Does the case cover all four states and default?** Yes — A, B, C, D plus `default`. No latch inference because every branch assigns `next_state` and the block is `always @(*)`.
- **Does the encoding match the table?** Cross-checked with the derived equations `ns0 = i`, `ns1 = s0 ^ i`. For each row: A(00),i=1 → {0^1,1}={1,1}=D? Wait — that would be D, but the table says A→B. Let me recheck. `s0` for A is 0, `i=1`, so `s0^i = 1`, `ns0 = i = 1`, giving next = 11 = D. That contradicts the table (A→B=01). So my derived equation is wrong somewhere — good thing I checked. Let me redo ns1.

Recompute ns1 carefully. ns1=1 for: A·i (→B=01, MSB 0!) — no, B is 01 so MSB is 0. I made an error: B=01 has MSB 0. Let me redo with correct MSBs: A=00(0), B=01(0), C=10(1), D=11(1). So ns1=1 only when next is C or D: B·ī (→C), C·i (→D), D·ī (→C). That is ns1 = s1' s0 ī + s1 s0' i + s1 s0 ī = s0 ī (s1'+s1) + s1 s0' i = s0 ī + s1 s0' i. And ns0=1 when next is B or D: A·i, B·i, C·i, D·i → ns0 = i (since B=01, D=11 both have LSB 1, and A·i→B, C·i→D). So ns0 = i still holds. Check A,i=1: ns1 = 0·0 + 0·1·1 = 0, ns0=1 → 01 = B ✓. Check C,i=1: ns1 = 0·0 + 1·1·1 = 1, ns0=1 → 11 = D ✓. Check D,i=0: ns1 = 1·1 + 1·0·0 = 1, ns0=0 → 10 = C ✓. Check B,i=0: ns1 = 1·1 + 0·1·0 = 1, ns0=0 → 10 = C ✓. Good — the corrected equation matches the table. The earlier slip was a reminder to verify, not to trust, hand algebra; the `case` statement in RTL sidesteps this entirely by transcribing the table directly.

- **Any risk of the output being registered one cycle late?** No — `out` is combinational off `state`, so it reflects the state *after* the edge within the same cycle. That is the standard Moore convention and matches "output" being a column of the state table.
- **Reset priority vs. next_state:** reset is checked first in the `if`, so it wins. Correct.
- **Widths:** `in` 1, `reset` 1, `out` 1, state 2 bits. Matches the declared widths.

## 9. Final RTL

```verilog
module fsm (
    input  clk,
    input  reset,
    input  in,
    output out
);

    localparam A = 2'b00,
               B = 2'b01,
               C = 2'b10,
               D = 2'b11;

    reg [1:0] state, next_state;

    // Next-state logic: direct transcription of the table
    always @(*) begin
        case (state)
            A: next_state = in ? B : A;
            B: next_state = in ? B : C;
            C: next_state = in ? D : A;
            D: next_state = in ? B : C;
            default: next_state = A;
        endcase
    end

    // State register: synchronous active-high reset to A
    always @(posedge clk) begin
        if (reset)
            state <= A;
        else
            state <= next_state;
    end

    // Moore output: 1 only in state D
    assign out = (state == D);

endmodule
```

This matches the table row-for-row, uses a synchronous active-high reset to A, produces a pure Moore output that is 1 only in D, and behaves correctly under the stated check-cycle protocol (sample at posedge, mid-cycle input changes carried to the next row).
