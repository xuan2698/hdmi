The reset behavior described in the public specification is a synchronous, active-high reset, and this has a direct consequence for how the final checker must model power-up and reset sequencing. Because the reset is synchronous, asserting `reset` does not combinationally force the state to A. Instead, the state only becomes A at the next sampled positive clock edge. Therefore, between the moment reset is driven high and the next posedge, the machine continues to behave according to its current state: the output remains whatever the current state's Moore output is, and any input changes during that window are not reflected in the state until the edge. The checker should therefore not expect an immediate output transition when `reset` is asserted; it should expect the output to change only after the sampling edge, at which point the state is A and the output is 0.

Power-up behavior is not separately specified beyond the reset mechanism. The public spec does not define an asynchronous initialization or a guaranteed initial state before any reset is applied. The safe interpretation for the checker is that the machine's observable behavior is anchored by the synchronous reset: after a sampled posedge with `reset=1`, the state is A and the output is 0. Any pre-reset state should not be assumed unless the checker's harness explicitly drives reset before sampling. In practice, the checker should apply reset before the first meaningful sample so that the starting state is unambiguously A, rather than relying on an unspecified power-up value.

The row-based timing model reinforces this. Each row's inputs are driven before the sampled edge, and the sample occurs after the posedge has settled. Thus, for a row in which `reset=1`, the checker drives reset, waits for the rising edge to settle, and then samples the output; that sampled output corresponds to state A, i.e., 0. If reset is asserted in a row but the sample is taken before the edge, the checker would incorrectly observe the old state's output. The specification explicitly warns against this: reset between edges does not immediately force the state to A, and the output during the cycle in which reset is asserted but before the edge is still the output of the current state.

A short worked example illustrates the reset timing. Suppose the machine is in state D with output 1. A row drives `reset=1`, `in=0`. Before the posedge, the output is still 1 because the state is still D. At the posedge, the synchronous reset takes effect, the state becomes A, and after the edge settles the output is 0. The checker must sample after the edge to see 0; sampling before the edge would wrongly yield 1. This is the key point for the final checker: associate the sampled output with the state reached at the sampled edge, and treat reset as taking effect only at that edge, not at the moment it is driven. Mid-cycle input changes, including changes to reset, are carried to the next row and do not affect the current sample.
