The key checker point is that `pm` is part of the stored state, not a derived function of `hh`. The public spec defines `pm` as asserted if the clock is PM, and the 12-hour display sequence is `01,02,...,11,12,01,...`. That means the only enabled transition that changes `pm` is `11:59:59` to `12:00:00`: AM becomes PM, or PM becomes AM. Every other enabled tick preserves `pm`, including the `12:59:59` to `01:00:00` rollover, where the hour changes from 12 to 01 but the half-day does not change. Reset forces `12:00:00 AM`, so `pm=0` on any reset row regardless of `ena`.

Power-up behavior is not specified by the public interface. The checker should therefore not assume any particular initial `hh`, `mm`, `ss`, or `pm` before the first sampled row. The first row should be treated as a reset row, or at least the checker should not infer a legal starting state from unspecified power-up values. Once a reset row has been sampled, the state is known: `hh=0x12`, `mm=0x00`, `ss=0x00`, `pm=0`. From that point, each row is a transition from the previous settled state using the inputs latched at that row’s sampled edge.

Reset is synchronous and active high, with priority over enable. So for a row with latched `reset=1`, the expected next state is always `12:00:00 AM`, even if `ena=1`. For `reset=0, ena=0`, the expected next state is exactly the previous settled state, including `pm`. For `reset=0, ena=1`, the checker should increment seconds in BCD, carry to minutes at 60, carry to hours at 60 minutes, and apply the 12-hour hour sequence. The hour increment is not ordinary binary or BCD counting through 13; after `12` comes `01`, and after `11` comes `12`. The `pm` bit is carried forward except on the specific `11:59:59` enabled transition, where it is complemented.

A useful worked example is previous settled state `hh=12`, `mm=59`, `ss=59`, `pm=1`, with latched `reset=0`, `ena=1`. The correct next state is `hh=01`, `mm=00`, `ss=00`, `pm=1`. The hour wraps from 12 to 01, but the half-day remains PM. A checker that recomputes `pm` from the new hour, or that toggles `pm` on every hour wrap, would incorrectly expect `pm=0`. The checker should instead compare against a state machine that stores `pm` and complements it only when the previous time is exactly `11:59:59` and `ena=1`.

Finally, the checker should reject illegal BCD outputs rather than normalizing them. It should also respect the sampling protocol: inputs are latched at the sampled edge, and any mid-row input change belongs to the next row, not the row just sampled.
