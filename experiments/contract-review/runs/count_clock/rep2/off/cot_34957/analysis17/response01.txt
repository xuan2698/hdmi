A useful distinguishing example for the final checker is a reset row issued while the clock is in a non-trivial PM state and `ena` is also high. Suppose the previous settled state is `pm=1, hh=0x11, mm=0x59, ss=0x59` (11:59:59 PM), and the current row samples `reset=1, ena=1`. The correct next settled state is `pm=0, hh=0x12, mm=0x00, ss=0x00` (12:00:00 AM). This single row is highly diagnostic: it confirms that reset has priority over enable, that reset forces the 12-hour representation rather than `00:00:00`, and that no pending increment from the previous state leaks through. A design that gates reset behind enable would instead advance to 12:00:00 AM by incrementing, which happens to look similar here, so the checker should pair this with a `reset=1, ena=0` row from a non-trivial state to separate the two behaviors. The `ena=0` reset row must still produce the reset state; if it holds the old state, reset is incorrectly gated by enable.

The checker should latch `reset` and `ena` at the sampled rising edge and compare the settled outputs after that edge against the transition implied by the previous settled state. Mid-row input changes occur after sampling and before the opposite edge; they belong to the next row and must never be used to justify the current row's outputs. The first row must be a reset row because power-up state is unspecified; without that anchor, a checker cannot distinguish a correct hold from an arbitrary starting point.

Two non-enabled rows are essential. A `reset=0, ena=0` hold row catches free-running counters and designs that increment on every `clk` instead of only on `ena`. A `reset=1, ena=0` row from a non-trivial state catches reset gated behind enable and catches reset to `00:00:00` instead of `12:00:00 AM`. After a reset row, the next row must either hold the reset state (if `reset=0, ena=0`) or advance from it (if `ena=1`).

Enabled increments require BCD carry and the 12-hour wrap. Seconds go 00→…→59→00 and carry into minutes; minutes carry into hours the same way. Hours go 01→…→11→12, then 12→01. The subtle point is `pm`: it toggles only on the 11→12 transition, not on 12→01. So `11:59:59 AM` with `ena=1` becomes `12:00:00 PM`, while `12:59:59 PM` with `ena=1` becomes `01:00:00 PM` with `pm` still 1. A checker that flips `pm` on every hour wrap, or on 12→01, will fail exactly these rows. Illegal BCD outputs should be rejected outright rather than normalized.

The most useful point for the final checker: compare each row only against the previous settled state plus that row's latched inputs, and treat `pm` as part of the state transition rather than deriving it from `hh`.
