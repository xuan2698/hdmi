**Reset and power-up analysis**

The public specification makes reset a synchronous, active-high input with priority over `ena`, and it explicitly requires reset to work even when `ena=0`. For the final Python checker, the most useful consequence is that reset must be evaluated as an unconditional override of the next-state function, not as one branch inside an enable-gated increment path. A row with `reset=1, ena=0` from any legal or even unspecified prior state must drive the next settled outputs to exactly `pm=0, hh=0x12, mm=0x00, ss=0x00`. This is not `00:00:00`; the hour field is BCD `12`, and `pm` is cleared to AM. A checker that only exercises reset while `ena=1` would miss an implementation that accidentally gates reset behind enable, so at least one reset row should have `ena=0`, preferably from a non-trivial state such as `11:59:59 PM` or `12:59:59 PM`.

The complementary hold case is equally important. With `reset=0, ena=0`, all outputs must remain unchanged after the settled edge. This catches free-running counters or any design that increments on every `clk` instead of only on the enable pulse. The row immediately after a reset should also hold the reset state until another reset or an enabled increment arrives; otherwise a design could reset combinationally for one sample and then drift.

Power-up state is unspecified by the public spec. Therefore the first sampled edge should not be judged unless it is a reset edge. A clean checker sequence begins with `reset=1`, verifies the following settled state, and then compares each subsequent row’s settled outputs against the state implied by the previous row plus that row’s latched `reset`/`ena`. Mid-row input changes occur after sampling and before the other edge, so they set up the following row and must not be used to explain the current row’s outputs.

For enabled increments, the checker should follow BCD carry and the 12-hour wrap, with special attention to `pm`. The `pm` bit toggles only on the `11→12` hour transition, not on `12→01`. Thus from `11:59:59 AM` with `ena=1`, the next state is `12:00:00 PM`; from `12:59:59 PM` with `ena=1`, the next state is `01:00:00 PM` with `pm` still 1. A checker that flips `pm` on every hour wrap, or on the 12-to-1 transition, will fail these rows.

The checker should also reject illegal BCD outputs outright: hours must be `01`–`12` (`00` and `13`–`19` invalid), and minutes/seconds must be `00`–`59`, so any nibble above 9 is invalid.

Worked example: settled state `pm=1, hh=0x11, mm=0x59, ss=0x59`; row inputs `reset=1, ena=0`. Expected next settled outputs: `pm=0, hh=0x12, mm=0x00, ss=0x00`. This single row checks reset priority over enable, the correct reset value rather than `00:00`, and suppression of any pending increment.
