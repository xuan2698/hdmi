The clock is a synchronous BCD timekeeper with a single fast `clk` and a one-cycle-wide `ena` pulse marking each second. All state updates occur only at the sampled posedge; between edges the outputs are stable. The state consists of `hh` (two BCD digits, valid 01–12), `mm` and `ss` (two BCD digits each, valid 00–59), and `pm` (0 for AM, 1 for PM). Reset is synchronous, active high, and has priority over `ena`; it forces `hh=0x12, mm=0x00, ss=0x00, pm=0`, i.e. 12:00 AM. Reset may assert regardless of `ena`.

The increment logic is a cascade. When `ena` is high and `reset` is low, `ss` advances by one BCD count: 00→01→…→09→10→…→59→00. Only when `ss` rolls from 59 to 00 does `mm` advance, with the same BCD pattern and 59→00 rollover. Only when `mm` rolls from 59 to 00 does the hour advance. The hour sequence is 01→02→…→11→12→01, never 00. The `pm` bit flips exactly when the hour crosses 11→12 or 12→01; it does not flip on any other hour change. Consequently, going 11:59:59 AM → 12:00:00 PM sets `pm=1`, and 12:59:59 PM → 01:00:00 AM clears `pm=0`. A reset to 12:00 AM also forces `pm=0`.

Because `ena` is a pulse, a row with `ena=0` (and `reset=0`) must hold all outputs unchanged. The checker should treat `ena` as gating the entire cascade: no partial increments, no BCD digit changes, no `pm` change.

Timing discipline is the key correctness point. Inputs are driven before each sampled edge; optional mid-row changes occur after sampling and before the next edge. A mid-row change is not sampled by the current edge — it persists and becomes the effective input for the next sampled edge. The checker should keep a persistent "pending inputs" variable carrying mid-changes forward. For row *i*, effective inputs are whatever was driven before that row's sampled edge, including any carried-over mid-change from row *i-1*. A mid-change must never retroactively alter row *i*'s expected outputs. This matters most for `reset` and `ena`: a mid-row reset assertion does not reset until the next posedge, and a mid-row enable pulse does not increment until the next posedge.

Worked example: row *i* sampled with `reset=0, ena=1`, state 11:59:59 AM. Expected post-edge: `hh=0x12, mm=0x00, ss=0x00, pm=1`. If a mid-change then sets `ena=0` before row *i+1*'s edge, row *i+1* holds that PM 12:00:00 state; the mid-change does not undo the increment already sampled.

For the final Python checker, separate three phases per row: (1) apply carried mid-changes and row inputs, (2) sample at posedge using reset-then-ena priority, (3) compute expected post-edge outputs and compare. Keep a persistent "pending inputs" variable so mid-changes carry forward, and never let a mid-change affect the row already sampled. Also validate BCD digit legality (each nibble 0–9), enforce the hour range 01–12, and confirm `pm` flips only on 11→12 or 12→1 hour transitions.
