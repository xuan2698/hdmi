The public specification defines a synchronous, active-high reset with priority over enable. Because reset is synchronous, it does not act as an asynchronous clear: asserting reset between sampled edges does not immediately force the outputs to “12:00 AM.” Instead, the reset value is observed only at the next sampled posedge, after the edge has settled. The same timing discipline applies to `ena`: an enable pulse is meaningful at a sampled edge, not as a combinational request to increment immediately. A checker should therefore treat `reset` and `ena` as inputs sampled at the active edge, with any mid-row changes carried forward to the next sampled edge rather than applied retroactively.

Reset priority is explicit and should be modeled directly. If `reset` and `ena` are both asserted at the same sampled edge, the next state is the reset state, not an incremented state. The reset state is “12:00 AM,” meaning `hh = 0x12`, `mm = 0x00`, `ss = 0x00`, and `pm = 0`. This priority matters especially near rollover boundaries, where an increment and a reset could otherwise produce different hours or different `pm` values. The checker should evaluate reset first, then enable, then hold.

When reset is not asserted and enable is asserted, the counter advances by one second according to the specified BCD rollovers. Seconds are two BCD digits in 00–59, minutes are two BCD digits in 00–59, and hours are two BCD digits in 01–12. The `pm` indicator is part of the state and changes only on the 11→12 hour transition. It does not toggle on the 12→01 transition, and it does not toggle merely because minutes or seconds roll over. This is a frequent source of checker errors: a naive modulo-12 hour counter may produce the correct hour digits while leaving `pm` wrong, or may toggle `pm` on every hour wrap.

A short worked example illustrates the combined rules. Suppose the sampled state is 11:59:59 AM, with `ena = 1` and `reset = 0`. At the next sampled posedge, seconds become 00, minutes become 00, hours become 12, and `pm` becomes 1, yielding 12:00:00 PM. If instead `reset = 1` and `ena = 1` at that same sampled edge, the result is 12:00:00 AM with `pm = 0`, because reset dominates enable. If reset is asserted only after the 11:59:59 AM row has been sampled, that mid-row assertion does not alter the already-sampled outputs; it is carried to the next sampled edge and applied there.

Power-up behavior should not be invented by the checker. The public specification gives a reset state and synchronous reset semantics, but it does not define an independent asynchronous power-on state. The checker should therefore avoid assuming a particular initial value before the first sampled reset or before the first sampled edge that establishes state under the testbench’s protocol. It should compare outputs only after the sampled edge has settled, using the pending input values that were driven before that edge. It should not normalize malformed BCD digits or out-of-range hours, minutes, or seconds; the specification defines legal ranges and rollover behavior, so deviations should be reported as mismatches rather than silently corrected. The useful checker rule is: latch pending inputs, apply them at the sampled posedge, give reset priority over enable, update `pm` only on 11→12, and compare settled outputs at edge boundaries only.
