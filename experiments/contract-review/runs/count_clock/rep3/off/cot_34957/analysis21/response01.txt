The key state is the full tuple `(hh, mm, ss, pm)`, not just the numeric time. `hh` is BCD 01–12, `mm` and `ss` are BCD 00–59, and `pm` is a separate state bit. The counter advances only when `ena` is high at a sampled posedge, except that `reset` overrides both `ena` and the current state. Reset is synchronous and active high, so a reset asserted mid-row does not change the already-sampled outputs; it is carried to the next sampled edge and applied there. The checker should therefore treat each sampled edge as a single atomic transition from the previous settled state using the pending inputs driven before that edge.

The rollover order is seconds → minutes → hours, with BCD carry. When `ss` is 59 and `ena` is high, `ss` becomes 00 and `mm` increments; when `mm` is 59 and `ss` rolls over, `mm` becomes 00 and `hh` increments. The hour sequence is 01, 02, …, 11, 12, 01, 02, … . The `pm` bit changes only on the 11→12 transition: 11:xx:xx AM becomes 12:xx:xx PM, and 11:xx:xx PM becomes 12:xx:xx AM. It does not toggle on 12→01, and it does not toggle when minutes or seconds roll over. This is the most common checker pitfall: a modulo-12 hour counter can produce correct hour digits while leaving `pm` wrong, or can toggle `pm` on every hour wrap.

A short worked example: suppose the sampled state is 11:59:59 AM, with `ena = 1` and `reset = 0`. At the next sampled posedge, seconds become 00, minutes become 00, hours become 12, and `pm` becomes 1, yielding 12:00:00 PM. If instead `reset = 1` and `ena = 1` at that same sampled edge, the result is 12:00:00 AM with `pm = 0`, because reset dominates enable. If reset is asserted only after the 11:59:59 AM row has been sampled, that mid-row assertion does not alter the already-sampled outputs; it is carried to the next sampled edge and applied there.

The checker should not invent power-up behavior. The public specification defines a reset state and synchronous reset semantics, but it does not define an independent asynchronous power-on state. Compare outputs only after the sampled edge has settled, using the pending input values driven before that edge. Do not normalize malformed BCD digits or out-of-range hours, minutes, or seconds; the specification defines legal ranges and rollover behavior, so deviations should be reported as mismatches rather than silently corrected. The useful checker rule is: latch pending inputs, apply them at the sampled posedge, give reset priority over enable, update `pm` only on 11→12, and compare settled outputs at edge boundaries only.
