The public spec fixes a synchronous 12-hour clock with BCD outputs and an AM/PM flag. The key timing facts for a checker are: all state changes are referenced to the rising edge of `clk`; `reset` is synchronous and active high, with priority over `ena`; and `ena` is a one-cycle pulse that authorizes an increment. Because `clk` is much faster than one second, the checker must not infer seconds from `clk` edges. It must treat `ena` as the sole increment event. A row’s inputs are driven before the sampled edge, and outputs are sampled after the posedge has settled. Mid-row input changes occur after sampling and before the next edge, so they belong to the next row’s pre-edge setup, not to the current row’s result.

The most useful point for the final Python checker is to separate “sampled edge state” from “mid-input changes.” At each sampled posedge, the checker should evaluate the next state from the values that were present before that edge: `reset`, `ena`, and the current registered outputs `pm`, `hh`, `mm`, `ss`. If `reset` is high, the next state is unconditionally 12:00 AM, regardless of `ena`. If `reset` is low and `ena` is high, the clock advances by one second in BCD with the 12-hour wrap rules. If `reset` is low and `ena` is low, the state holds. Any input change that appears after the sampled edge must not retroactively affect that row; it is carried to the start of the next row and used only for the next sampled edge.

This matters because a naive checker might compare outputs immediately after any input transition, or might treat `ena` as a level rather than a pulse. The spec says `ena` is a pulse whenever the clock should increment, so a high `ena` lasting across multiple sampled edges would imply multiple increments unless the protocol guarantees one-cycle pulses. The checker should therefore validate the transition at each sampled edge using the pre-edge inputs, not the post-edge or mid-row values.

A short worked example: suppose the current sampled state is `12:59:59 PM`, `reset=0`, and `ena=1` at the sampled edge. The next state should be `01:00:00 PM` because seconds wrap 59→00, minutes wrap 59→00, and hours wrap 12→01 while `pm` remains asserted. If `ena` changes to 0 shortly after the edge, that mid-input change does not alter the already-sampled transition; it only affects the following row. If instead `reset=1` at the sampled edge, the result is `12:00:00 AM` even if `ena=1`.

For the final Python checker, the practical rule is: capture inputs and outputs at the sampled edge boundary, compute expected next outputs from the pre-edge registered state and pre-edge `reset`/`ena`, then compare after settling. Ignore mid-row changes for the current row except as setup for the next row. Also enforce BCD digit ranges and the 12-hour domain: hours 01–12, minutes and seconds 00–59, with `pm` toggling only on the 11:59:59→12:00:00 boundary in the appropriate direction. This edge-versus-mid-input discipline is the main source of false failures in such checkers.
