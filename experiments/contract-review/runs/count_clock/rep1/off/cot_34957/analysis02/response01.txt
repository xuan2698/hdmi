**Reset and power-up behavior**

The public specification defines `reset` as a synchronous, active-high signal with priority over `ena`. That means the checker should not treat reset as an asynchronous clear that can change outputs between sampled edges. Instead, reset is observed only at the sampled clock edge: if `reset` is high at that edge, the next state is forced to 12:00:00 AM regardless of `ena`, and the `pm` flag is cleared. If `reset` is low at the sampled edge, the normal enabled/inhibited transition applies. Because reset has higher priority than enable, a row with both `reset=1` and `ena=1` must produce the reset state, not an increment. A mid-cycle change to `reset` after sampling must not retroactively alter the transition already committed at that edge; it is carried to the next sampled edge.

Power-up is not specified as a separate input condition in the public interface. The only defined initialization mechanism is the synchronous reset. Therefore the checker should not invent an asynchronous power-on value for `hh`, `mm`, `ss`, or `pm`. Any verification of initial state should either begin from a known reset-sampled state or treat pre-reset outputs as unspecified unless the testbench explicitly drives reset at a sampled edge. In particular, the checker should not require that the first observed row after simulation start is already 12:00 AM unless a reset edge has occurred. This distinction matters because the specification says reset resets the clock to 12:00 AM, but it does not state that power-up automatically asserts reset or that the counters self-initialize.

A useful point for the final Python checker is to model reset as a transition override at the sampled edge, not as a continuous combinational override. The checker should compute the expected next state from the previous state plus the sampled `reset` and `ena` values. If `reset` is sampled high, expected next state is `hh=0x12`, `mm=0x00`, `ss=0x00`, `pm=0`. Otherwise, if `ena` is sampled high, apply one BCD increment with carry and the 12-hour wrap/toggle rule. Otherwise hold state. The `pm` bit must be part of the stored state, because 12:00 AM and 12:00 PM have the same `hh` encoding but different `pm`.

Worked example: previous state 11:59:59 AM (`pm=0`). At the sampled edge, `reset=0`, `ena=1` gives expected 12:00:00 PM (`hh=0x12`, `mm=0x00`, `ss=0x00`, `pm=1`). If `reset=1` at that same edge, expected is 12:00:00 AM (`pm=0`) even though `ena=1`. A later mid-cycle `ena` change does not affect that already-sampled transition.

The checker should also validate BCD ranges after reset and after every enabled transition: seconds and minutes low digits 0–9 and high digits 0–5; hours must encode 01–12, so the pair is not 00 and the tens digit is 0 or 1 with valid ones digit. Reset being synchronous means an asserted reset between edges is irrelevant until the next sampled edge. Finally, because `ena` is a pulse, consecutive enabled rows need not correspond to a fixed real-time spacing; the checker only verifies one increment per enabled sampled edge.
