## Reset and power-up behavior

The waveform begins with `q = x` at time 0, meaning the register has no defined power-up value. There is no explicit reset input in the public interface — only `clk` and `a`. Consequently, the circuit's initial state is indeterminate until the first active clock edge establishes a known value. In this trace, the first rising edge at 5 ns samples `a = 1` and loads `q = 4`, so the unknown state is overwritten immediately. A checker should therefore not assume any particular pre-first-edge value of `q`; it should treat the first sampled posedge as the point where `q` becomes well-defined, and only compare outputs from that edge onward. If a simulation were to start with `a = 0`, the first edge would compute `(x + 1) mod 7`, which is not meaningful — so the specification implicitly relies on the first sampled `a` being 1 (or on the checker ignoring the first edge). The safest interpretation for the final Python checker is: initialize `q` to a don't-care, and begin checking only after the first posedge where the sampled `a` is 1 (which forces `q = 4`), or more generally after the first posedge, using the rule to compute the expected next state from whatever `q` was — but since `q` is unknown before that, the first comparison must be skipped or seeded from the observed value.

There is no asynchronous reset, no synchronous reset, and no enable. Power-up is purely the FPGA/ASIC register's undefined state, resolved by the first clock edge. The circuit does not self-correct to a known state unless `a = 1` at some edge; if `a` remained 0 forever from an unknown `q`, the state would remain unknown modulo 7 arithmetic (undefined). This is a latent robustness issue but not something the public spec asks the checker to model beyond ignoring pre-first-edge `q`.

**Worked example (the critical mid-cycle case):** At 45 ns the row lists `a = 0`, but the prose states mid-cycle input changes occur *after* sampling. The change from 1 to 0 happened after the 45 ns posedge sampled `a`. Thus the edge at 45 ns saw `a = 1` and reloaded `q = 4` (unchanged). The new `a = 0` is carried into the next row, so the 55 ns edge samples `a = 0` and computes `q = (4 + 1) mod 7 = 5`. A naive checker that used the row's printed `a` value at 45 ns would wrongly predict `q = 5` at 45 ns. The final checker must therefore use the *sampled* `a` at each posedge — i.e., the value in effect just before the edge, not the post-edge value shown in the same row when a mid-cycle change is annotated.

**Key point for the final Python checker:** model each posedge as sampling the pre-edge `a`, then apply `q_next = 4 if a_sampled else (q + 1) % 7`. Skip comparison of `q` before the first posedge (or until `q` is first forced to 4). The modulo is 7, not 8 — confirmed by the 6→0 transition at 75 ns.
