# One Likely Implementation Mistake: Misplacing the Mid-Row Input Change

The most instructive mistake for this decade-counter checker is a **timing/ordering error around the mid-row input change**, specifically mishandling the `reset` value that is carried from one row to the next. The public spec says each row's values are driven before the sampled edge, and that optional mid input changes occur *after* sampling, before the other edge, and are carried to the start of the next row. A checker that conflates "the reset value seen at the end of the row" with "the reset value that governs the sampled edge" will produce wrong expectations.

Concretely, suppose a row begins with `reset=0`, the rising edge is sampled, and then `reset` changes to `1` mid-row. That change belongs to the *next* row. The next row therefore begins with `reset=1`, and its rising edge should drive `q` to 0. A checker that reads `reset` at the end of the row, or that applies the mid-row change to the previous edge, would wrongly expect 0 on the first edge. The correct order is: latch the row's starting `reset`, compute the expected post-edge `q`, compare against settled `q`, then adopt any carried input change for the next row.

The checker should maintain an explicit current-count variable rather than inferring state from `q` alone. When the row's starting `reset` is 1, the expected settled `q` is 0 regardless of prior count, and the checker can anchor its current count at 0. When the row's starting `reset` is 0, the expected settled `q` is `(current_count + 1) mod 10`. This modulo-10 behavior is what distinguishes a decade counter from a 4-bit binary counter: at count 8 with `reset=0` the next value is 9, and at count 9 with `reset=0` the next value is 0, not 10 or 15.

Power-up is unspecified. The public spec gives no initial value for `q`, so the checker must not assume the counter starts at 0. If the first sampled edge has `reset=1`, the expected result is 0 and the checker can establish its current count there. If the first sampled edge has `reset=0`, the checker should treat the observed pre-edge `q` as the initial count and expect `(initial + 1) mod 10` after the edge; from then on it has a definite current count. Assuming a zero start would create false failures for any design that powers up elsewhere.

The highest-value protections for the final Python checker are therefore: an explicit current-count variable; edge-local reset semantics using the row's starting `reset`; modulo-10 increment only when that starting `reset` is low; comparison against the settled post-edge `q`; and adoption of carried inputs only after that comparison. The checker should also avoid assuming `q` powers up at 0 unless a reset edge has established it. These guards prevent both false positives from misreading mid-row changes and false negatives from assuming an unspecified initial state.
