One likely implementation mistake is treating the counter as a generic 4-bit modulo-16 counter with a separate “if count == 10 then clear” patch, rather than as a true decade counter whose next-state function is defined modulo 10. That mistake can look almost correct in ordinary counting because the visible sequence 0,1,2,...,9 may appear, but it creates incorrect behavior at the wrap boundary and can interact badly with reset timing. The public specification says the counter counts from 0 through 9 inclusive with period 10, and that reset is active-high synchronous and resets the counter to 0. Therefore the intended next-state relation is: if reset is active at the sampled edge, next state is 0; otherwise, if the previous state is 9, next state is 0; otherwise next state is previous state plus one. A modulo-16 implementation with a conditional clear is not equivalent unless the clear is applied at exactly the right boundary and with the right priority relative to reset.

The subtle failure is not merely “it counts to 15.” A designer might write logic that increments a 4-bit register and then clears it when the incremented value equals 10. That can produce the right visible sequence in some simple simulations, but it makes the wrap depend on an intermediate value rather than on the previous state. It also risks giving reset the wrong priority. For example, if the previous sampled state is 9 and reset is inactive at the sampled edge, the expected next state is 0. If the implementation first increments 9 to 10, then detects 10 and clears, it may still produce 0, so a shallow test can pass. But if reset is asserted at that same sampled edge, the expected result is also 0, and the distinction between “wrap because previous state was 9” and “reset because reset was active” is lost. That matters for checker reasoning because the checker must compute expected output from the reset value at the edge and the previous sampled state, not from an internal intermediate count.

A second related mistake is applying a mid-cycle reset change to the current row. The protocol says each row’s values are driven before the sampled edge, and optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. So if the current row samples reset=0 with previous state 9, the expected q is 0 due to wrap. If reset then changes to 1 after sampling, that change must not be used to explain or alter the current row’s q. It becomes the reset value for the next row. A checker that reads the final reset value of the row, rather than the reset value active at the sampled edge, can falsely flag a correct design or accept an incorrect one.

Worked example: previous sampled state q=9; current row drives reset=0 before the edge. Expected q after the edge is 0. If reset changes to 1 after sampling, the next row samples reset=1 and also expects q=0. The current row’s expected q remains based on reset=0 and previous state 9. The final checker should therefore track previous sampled state, use the edge-sampled reset value, compute expected next state as 0 if reset_at_edge else (prev+1)%10, and carry mid-cycle reset changes only to the next row. It should not model reset as an immediate asynchronous clear, should not use modulo 16, and should not let seed-specific stimulus order affect the functional expectation.
