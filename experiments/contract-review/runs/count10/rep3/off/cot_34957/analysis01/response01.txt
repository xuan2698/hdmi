The public specification defines a synchronous decade counter with a single active-high `reset` input and a 4-bit output `q`. The counter advances on the rising edge of `clk`, counting 0,1,2,…,9 and then wrapping to 0, giving period 10. Because `reset` is synchronous and active high, a high level on `reset` sampled at a rising clock edge forces `q` to 0 at that edge; a low level allows normal counting. The output width is 4 bits, so all ten legal states are representable, and the six unused codes (10–15) should not appear in normal operation.

The timing language is the critical part for the final checker. Each row’s input values are “driven before the sampled edge,” and the sample occurs “after the posedge edge has settled.” That means the checker should treat the row’s `reset` value as the value present at the active clock edge, not as a value that changes after the edge. The phrase “optional mid input changes occur AFTER sampling, before the other edge, and are carried to the start of the next row” means a row may contain a reset value that is valid at the sampled rising edge, and then a mid-cycle change that affects only the next row’s starting condition. In checker terms, the row’s sampled `reset` must be latched at the posedge, while any mid-input change must not retroactively alter the current row’s expected `q`.

A useful point for the final Python checker is to separate three time regions per row: (1) the pre-edge driven values, which determine the sampled edge behavior; (2) the post-edge settled output, which is the row’s expected `q`; and (3) the optional mid-cycle input change, which is carried forward to the next row’s pre-edge values. The checker should not compare the row’s `q` against a reset value that appears only after sampling. Instead, it should compute the next state from the previous state and the `reset` value that was active at the sampled edge. If `reset` is high at that edge, next `q` is 0; otherwise next `q` is `(prev_q + 1) mod 10`, with the caveat that only 0–9 are legal and the modulo behavior should be implemented as wrap from 9 to 0 rather than binary modulo 16.

A short worked example: suppose the previous sampled state is `q=9`, and the next row drives `reset=0` before the rising edge. After the edge settles, expected `q=0`. If that same row then has a mid-cycle change setting `reset=1` after sampling, that change is carried to the start of the following row; it does not make the current row’s `q` become 0 again at the same edge. The following row would then sample `reset=1` and also produce `q=0`. This distinction prevents an off-by-one-row error in the checker.

The checker should also enforce that `q` is always in 0–9 after each sampled edge, including after reset. Since reset is synchronous, an asynchronous reset assertion between edges should not be modeled as immediately clearing `q`; only the sampled edge matters. The protocol seed is irrelevant to the functional contract except for generating stimulus order, so the checker should rely on the row semantics rather than on seed-specific assumptions. Finally, because input widths are given as `{'reset': 1}` and output widths as `{'q': 4}`, the checker should validate bit widths and treat `reset` as a single-bit Boolean at the sampled edge. The main risk is conflating mid-input changes with edge-sampled inputs; the final checker should explicitly carry mid changes to the next row and never apply them to the current row’s expected output.
