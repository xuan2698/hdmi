The key timing distinction for the checker is between the input value that is present at the sampled clock edge and any optional mid-cycle input change that occurs after sampling. The public specification says each row’s values are driven before the sampled edge, and that optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. Therefore, for each row, the functional expectation must be computed from the reset value that is active at the sampled posedge, together with the previous sampled state of the counter. A reset change that happens after that edge must not retroactively affect the row just sampled; it belongs to the next row’s input setup.

This matters because the counter has a synchronous active-high reset. The reset is not an asynchronous clear. The expected next state should be determined as follows: if the reset value at the sampled edge is high, the next state is 0; otherwise, the next state is the previous sampled state incremented by one, wrapping from 9 to 0. The checker should not compute the next state by first incrementing and then conditionally clearing an internal intermediate value, because that can obscure whether the result came from reset or from the decade wrap. It also risks giving reset the wrong priority. For example, if the previous sampled state is 9 and reset is inactive at the sampled edge, the expected next state is 0. If the implementation first increments 9 to 10, then detects 10 and clears, it may still produce 0, so a shallow test can pass. But if reset is asserted at that same sampled edge, the expected result is also 0, and the distinction between “wrap because previous state was 9” and “reset because reset was active” is lost. That matters for checker reasoning because the checker must compute expected output from the reset value at the edge and the previous sampled state, not from an internal intermediate count.

A second related mistake is applying a mid-cycle reset change to the current row. The protocol says each row’s values are driven before the sampled edge, and optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. So if the current row samples reset=0 with previous state 9, the expected q is 0 due to wrap. If reset then changes to 1 after sampling, that change must not be used to explain or alter the current row’s q. It becomes the reset value for the next row. A checker that reads the final reset value of the row, rather than the reset value active at the sampled edge, can falsely flag a correct design or accept an incorrect one.

Worked example: previous sampled state q=9; current row drives reset=0 before the edge. Expected q after the edge is 0. If reset changes to 1 after sampling, the next row samples reset=1 and also expects q=0. The current row’s expected q remains based on reset=0 and previous state 9. The final checker should therefore track previous sampled state, use the edge-sampled reset value, compute expected next state as 0 if reset_at_edge else (prev+1)%10, and carry mid-cycle reset changes only to the next row. It should not model reset as an immediate asynchronous clear, should not use modulo 16, and should not let seed-specific stimulus order affect the functional expectation.
