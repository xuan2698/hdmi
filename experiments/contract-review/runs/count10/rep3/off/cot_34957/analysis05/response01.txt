The key distinction for the checker is between the reset value **sampled at the active edge** and any reset change that arrives **after sampling**. The public spec says each row’s values are driven before the sampled edge; optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. So the expected `q` for a row depends only on the reset value present at that row’s sampled edge, together with the previous sampled state. A mid-cycle reset assertion must not retroactively clear the current row’s output; it becomes the pre-edge reset value for the following row.

Boundary values matter in two places. First, the wrap boundary is 9 to 0: from previous state 9 with reset 0, the expected next state is 0, not 10 and not 9. Second, the reset boundary is the distinction between “reset active at the sampled edge” and “reset changed after the sampled edge.” These are different events even though both involve `reset=1`.

A short worked example: suppose the previous sampled state is `q=9`, and the current row drives `reset=0` before the rising edge. After the edge settles, the expected `q` is 0 because 9 wraps to 0. If that same row then has a mid-cycle change setting `reset=1` after sampling, that change belongs to the start of the next row. It does not make the current row’s `q` become 0 again at the same edge. The following row would then sample `reset=1` and also produce `q=0`. This prevents an off-by-one-row error.

For the final Python checker, the useful focus is to maintain the previous sampled state, read the reset value active at the sampled edge, compute the expected next state as `0 if reset_at_edge else (prev + 1) % 10`, and compare that against the sampled `q`. Carry any mid-cycle reset change forward to the next row’s pre-edge value. Do not model asynchronous reset as an immediate clear, and do not use binary modulo 16. The protocol seed affects only stimulus order, not the functional contract, so the checker should rely on row semantics rather than seed-specific assumptions. The main risk is conflating mid-input changes with edge-sampled inputs; the checker should explicitly carry mid changes to the next row and never apply them to the current row’s expected output.
