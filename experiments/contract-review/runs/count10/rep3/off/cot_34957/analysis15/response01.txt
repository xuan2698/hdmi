The public specification defines a synchronous, active-high decade counter. The only input is a one-bit `reset`; the only output is a four-bit `q`. The clock is `clk`, and all judgments are made on values sampled after the positive edge has settled. Each row's driven values are established before the sampled edge. Optional mid-cycle input changes occur after sampling and before the opposite edge; they are carried forward to the start of the next row and must not affect the current row's expectation.

The functional state is the last sampled output `q`. On any sampled edge, if the sampled `reset` is 1, the next state is 0. If the sampled `reset` is 0, the next state is `(previous_state + 1) % 10`. The previous state is the last sampled `q`, not an internal guess and not a value inferred from mid-cycle activity. A mid-cycle reset change occurring after sampling belongs to the next row; it must not revise the current row's expectation. Treating reset as asynchronous, or letting a later reset value retroactively explain the current sample, is a serious checker error: it can make a row appear correct for the wrong reason and can mask a modulus fault.

Power-up behavior is not separately specified beyond the reset mechanism. The checker should not assume an uninitialized state is 0 unless the stimulus actually establishes that through a sampled reset. The safe approach is to begin from the first sampled output as the reference state, or to require an initial reset assertion before judging counting behavior. In either case, the checker must not invent an asynchronous power-on reset. The public contract gives only the synchronous reset path, so any expectation of automatic zeroing at time zero would be an unsupported assumption.

A short worked example makes the boundary concrete. Suppose the previous sampled state is 9 and the current row drives `reset=0` before the edge. The correct expectation is `q=0`, because the decade counter wraps from 9 to 0. A checker using modulo 16 would instead expect 10, which is illegal here. If reset changes to 1 after sampling, that change must not alter the current row's expectation; it is carried to the next row. A checker that used the later reset value might expect 0 for the wrong reason, masking the modulus error in that row while remaining structurally wrong elsewhere.

For the final Python checker, the useful discipline is: maintain the previous sampled state; use only the edge-sampled reset for the current expectation; reject any observed `q` outside 0–9; and advance with modulo 10. Do not model asynchronous reset, do not use modulo 16, and do not let post-sampling changes or seed-specific ordering rewrite the current row's functional expectation.
