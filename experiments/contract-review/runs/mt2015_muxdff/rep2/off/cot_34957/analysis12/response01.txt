# Implementation Mistake Analysis: Submodule Boundary Confusion

The most likely implementation mistake in a hierarchical version of this design is a **bit-ordering mismatch between the parent's concatenation and the submodule's port mapping**. The public spec defines the recurrence as `q <= {q[1] ^ q[2], q[0], q[2]}`, which is a *positional* statement about the three bits of `q`. When this is decomposed into three instances of a flipflop-plus-mux submodule, each instance owns exactly one bit of `q`, and the parent must wire the submodule's `Q` output to the correct slice of the parent's `q` bus, and wire the submodule's `q_in` input to the correct *source* bit of the parent's `q` bus.

The subtlety is that the three source bits are not in the same order as the three destination bits. Destination bit 0 receives `q[1] ^ q[2]`; destination bit 1 receives `q[0]`; destination bit 2 receives `q[2]`. A natural but wrong implementation wires instance *i*'s `q_in` to `q[i]` for all *i*, i.e. it treats the recurrence as the identity permutation. That produces a design that is stable under `L=0` (every state is a fixed point), which is clearly wrong, but it can still pass a short trace if the checker only loads once and then samples a single `L=0` step where the expected output happens to equal the loaded value.

A second, related mistake is to compute the XOR *outside* the submodule and feed it as `r_in`, while also feeding `q[1]` and `q[2]` as separate `q_in` signals — but the public spec's submodule has only one `q_in` and one `r_in` per bit. If the implementer instead builds a submodule with a wider `q_in` (say, all three bits) and selects internally, the port widths no longer match the spec's `{'L':1,'q_in':1,'r_in':1}` and the checker's per-bit drive model breaks.

A third mistake is **sampling `L` and `r_in` at the wrong time relative to the edge**. Because the submodule is a flipflop, its `D` input is captured at `posedge clk`. If the parent registers `L` or `r_in` through an extra flop before feeding the submodule, the effective load happens one cycle late. The checker drives inputs before the edge and samples `Q` after the edge settles; an extra pipeline stage in the parent will make the first `L=1` row appear to have no effect, and the checker will see the unknown seed persist for one extra row.

Worked example of the bit-order bug: load `r=101` (`L=1`), so `q=101`. Drive `L=0`. Correct next state: `{q[1]^q[2], q[0], q[2]} = {0^1, 1, 1} = 110`. The identity-permutation bug yields `{q[0],q[1],q[2]} = 101`, which differs — but if the checker had loaded `r=000` or `r=111`, both correct and buggy designs agree, so the checker must include a load with `q[1] != q[2]` and at least one `L=0` step, as the spec's guidance already notes.

For the final Python checker: do not infer behavior from the submodule hierarchy; model the three-bit register directly from the public recurrence, keep the seed unknown until a full `L=1` load, and require at least one `L=0` step after a load with `q[1] != q[2]` so the XOR polarity is exercised.
