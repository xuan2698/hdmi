The key point for the final checker is to avoid over-modeling the machine. The public table gives only five present-state rows (`000` through `100`), and the interface exposes only `Y0` and `z`, not the full next-state vector. So the checker should not try to infer behavior for unlisted states such as `101`, `110`, or `111`, and it should not compare `Y[2:1]` at all. It should compute `Y0` as the least significant bit of the next-state entry selected by the sampled present state and sampled `x`, and compute `z` from the present-state row alone.

A second useful point is the timing split. The row values are driven before the sampled posedge; after that edge settles, the checker samples `Y0` and `z`. Optional mid-input changes happen after sampling and before the other edge, and are carried into the next row. Therefore a later change on `x` must not retroactively change the expected `z` for the row just sampled. The checker should latch its expectation at the sample point, not recompute from whatever `x` happens to be later in the cycle.

A short worked example: at present state `y=011`, if the sampled `x=0`, the next state is `001`, so `Y0=1`; the row output is `z=1`. If `x` changes to `1` after sampling, the next-state entry would become `010` and `Y0` would become `0`, but that change belongs to the next row’s setup. The already-sampled `z` remains `1`. This illustrates why the checker must separate the sampled edge values from later combinational settling and must compare only the requested low bit `Y0`.
