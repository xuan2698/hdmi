The public interface has one 1-bit input `x`, a 3-bit present-state input `y`, a clock `clk`, and two 1-bit outputs `Y0` and `z`. The table is a state-assigned next-state/output table: for each present state `y[2:0]` and each value of `x`, it gives the next state `Y[2:0]`; the output `z` is listed once per row. The implementation target is only the low next-state bit `Y[0]` plus `z`, not the full `Y[2:0]` bus.

Boundary values are straightforward because all signals are unsigned bit vectors. `x` ranges over `0` and `1`. `y` ranges over `000` through `111`, but the public table specifies behavior only for `000`, `001`, `010`, `011`, and `100`. States `101`, `110`, and `111` are unspecified by the public specification. A checker should not invent expected behavior for those states from the table alone; it should either avoid them or treat them as outside the specified domain. `Y0` and `z` are single bits, so their only possible values are `0` and `1`.

For the specified rows, the next-state entries are:

- `y=000`: next state `000` for `x=0`, `001` for `x=1`; `z=0`.
- `y=001`: next state `001` for `x=0`, `100` for `x=1`; `z=0`.
- `y=010`: next state `010` for `x=0`, `001` for `x=1`; `z=0`.
- `y=011`: next state `001` for `x=0`, `010` for `x=1`; `z=1`.
- `y=100`: next state `011` for `x=0`, `100` for `x=1`; `z=1`.

Thus `Y[0]` depends on both `y` and `x`, while `z` depends only on `y` in the public table. The final checker should compute expected `z` from the sampled present state row, independent of `x`. It should compute expected `Y0` from the selected next-state entry for the sampled `x`, then take only the least significant bit. It should not compare the full next-state vector, because the interface exposes only `Y0`.

The timing note matters. Each row’s inputs are driven before the sampled posedge. After the posedge has settled, the checker samples `Y0` and `z`. Optional mid-input changes occur after sampling, before the other edge, and are carried to the start of the next row. Those later changes must not alter the values already sampled for the current row. In particular, if `x` changes after the posedge, the sampled `z` for that row remains the row’s listed value.

A short worked example is row `y=011`. For `x=0`, the next state is `001`, so `Y0=1`. For `x=1`, the next state is `010`, so `Y0=0`. The row output is `z=1` for both branches. If the checker samples this row at `x=0`, it should expect `Y0=1` and `z=1`. If `x` later changes to `1` after sampling, the already-sampled `z` must still be treated as `1`; the later change belongs to next-row setup, not to the completed sample.

The useful focus for the final Python checker is therefore: separate sampled edge values from later combinational settling, treat `z` as row-indexed by `y` unless the public table explicitly shows `x` dependence, and compare only the requested low bit `Y0` rather than the full next-state vector. Also restrict expected behavior to the five publicly specified present states.
