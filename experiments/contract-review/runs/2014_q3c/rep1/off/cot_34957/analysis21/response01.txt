The public table defines a five-state Moore-output machine with a single input `x` and a three-bit present state `y[2:0]`. Only the low next-state bit `Y[0]` and the output `z` are specified; `Y[2:1]` are outside the comparison contract. The table rows are:

- `000`: `x=0 → 000`, `x=1 → 001`, `z=0`
- `001`: `x=0 → 001`, `x=1 → 100`, `z=0`
- `010`: `x=0 → 010`, `x=1 → 001`, `z=0`
- `011`: `x=0 → 001`, `x=1 → 010`, `z=1`
- `100`: `x=0 → 011`, `x=1 → 100`, `z=1`

The output `z` depends only on the present state, not on `x`. States `011` and `100` are the only listed states with `z=1`; the other three listed states have `z=0`. For `Y[0]`, the selected next state depends on both the present state and the sampled `x`. Reading the low bit of each next-state entry gives the expected `Y0` for that row and input value.

A key checker point is that the row must be evaluated from the `y` and `x` values sampled at the active edge, not from whatever `x` happens to be later in the cycle. The protocol allows optional mid-cycle input changes after sampling and before the other edge; those changes are carried to the start of the next row. Therefore, a checker should latch the sampled `y` and sampled `x` for each row, look up the expected `Y0` and `z` from that latched pair, and compare only against the design’s sampled `Y0` and `z`. If `x` changes after the sample point, it must not retroactively change the expected `Y0` for the row already checked.

For example, if the sampled pair is `y=011`, `x=0`, the table selects next state `001`, so the expected low bit is `Y0=1`, and the output is `z=1`. If `x` later changes to `1`, the same present state would select next state `010` with `Y0=0`, but that later value belongs to the next row’s sampling, not to the already-sampled row. A checker that recomputes from live `x` after the edge can falsely flag a correct design.

The checker should also respect the limits of the public specification. Reset and power-up behavior are unspecified. Unlisted present states have no required `Y0` or `z`, so they should not be treated as table violations. Only `Y[0]` is specified as an output function; `Y[2:1]` should not be compared. The useful final-checker behavior is: sample after the positive edge settles, latch `y` and `x` for that row, compute expected `Y0` and `z` only for listed states with a known sampled `x`, and let later `x` changes affect only the next row.
