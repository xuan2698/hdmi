The public specification defines a three-bit present-state input `y[2:0]`, a one-bit input `x`, a one-bit next-state bit `Y[0]`, and a one-bit output `z`. The clock is `clk`, and sampling occurs after the positive edge has settled. Values for each row are driven before the sampled edge; optional mid-cycle input changes occur after sampling and before the next edge, and are carried into the next row. The protocol seed is 20261123.

Port widths are therefore: `x` is 1 bit, `y` is 3 bits, `Y0` is 1 bit, and `z` is 1 bit. The state encoding uses only five of the eight possible three-bit values: 000, 001, 010, 011, and 100. The remaining encodings 101, 110, and 111 are don't-cares in the public specification: no next state and no output value are assigned. The checker must not assert any expectation when the driven present state is one of those three encodings, and must not infer a power-up state or reset behavior that the specification does not define.

For the specified rows, `z` is a pure function of `y`: `z=0` for `y=000`, `001`, and `010`; `z=1` for `y=011` and `100`. It does not depend on `x` or on the next-state value. The next-state function does depend on `x`. For `y=000`, both `x=0` and `x=1` return 000, so `Y[0]=0` in both cases. For `y=001`, `x=0` returns 001 (`Y[0]=1`) and `x=1` returns 100 (`Y[0]=0`). For `y=010`, `x=0` returns 010 (`Y[0]=0`) and `x=1` returns 001 (`Y[0]=1`). For `y=011`, `x=0` returns 001 (`Y[0]=1`) and `x=1` returns 010 (`Y[0]=0`). For `y=100`, `x=0` returns 011 (`Y[0]=1`) and `x=1` returns 100 (`Y[0]=0`). Thus `Y[0]` is not a function of `x` alone; it must be evaluated against the specific present state.

The critical checker discipline is temporal. The row's `y` and `x` are driven before the sampled positive edge. The checker should capture `x` at that pre-edge moment and bind it to the row, compute the expected `Y[0]` from the captured `x` and the driven `y`, compute `z` from `y` alone, and compare after the edge has settled. If `x` changes in the mid-cycle window after sampling, that change belongs to the next row and must not alter the current row's expectation. A checker that re-reads `x` after the edge would mis-evaluate rows such as `y=011, x=0`, where the correct next state is 001 (`Y[0]=1`) but a post-edge `x=1` would suggest 010 (`Y[0]=0`).

A short worked example: suppose the checker drives `y=011` and `x=0` before a positive edge. It captures `x=0`, computes expected `Y[0]=1` from the row for `y=011, x=0`, and computes expected `z=1` from `y=011`. After the edge settles, it compares `Y0` and `z` to those expectations. If `x` later changes to 1 in the mid-cycle window, that change is not used for this row.

Finally, the checker should skip expectation checks for unlisted present states and for any cycle before it has explicitly established a legal `y`. The public specification provides no reset or initialization contract, so the first sampled row should be treated as authoritative only after the checker has driven a known legal `y` and `x`.
