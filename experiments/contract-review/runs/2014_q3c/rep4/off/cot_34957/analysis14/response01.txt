**Reset and power-up behavior.** The public specification defines no reset input and no power-up state. It gives only a state-assigned table over present states `y[2:0]` and next states `Y[2:0]`, with output `z` depending solely on the present state. Consequently, the checker must not assume that the design powers up in `000`, nor may it require any particular initialization sequence. Any assertion about reset value, synchronous or asynchronous clearing, or “first state after power-up” would be an extra contract not present in the public spec. The only safe interpretation is that the five listed present states are the specified operating states; behavior outside them is unspecified.

This has a direct consequence for the final Python checker: it should drive only the five specified present states, or at minimum compare only rows whose present state is one of `000`, `001`, `010`, `011`, `100`. If the checker drives an unspecified state such as `101`, `110`, or `111`, the implementation is free to choose any next state and any output consistent with its own don’t-care assignment. Rejecting a correct implementation because it resolved those don’t-cares differently would be a checker bug, not a design bug. The robust approach is therefore to restrict stimulus to the specified states and to use direct table lookup rather than minimized Boolean equations that might implicitly encode a particular don’t-care choice.

**Timing and sampling.** Each row’s values are driven before the sampled positive edge. The next-state entry for that row is selected by the `x` value present before that edge. After the edge has settled, the checker compares observed `Y[0]` and `z` against the row’s expected values. Optional mid-cycle input changes occur after sampling and before the other edge; those changes are carried to the start of the next row. Thus a mid-cycle change on `x` belongs to the next row’s setup and must not retroactively alter the expected `Y[0]` for the row just sampled.

This matters because `z` depends only on the present state, not on `x`. If a checker mistakenly uses the post-sampling `x` value when computing expected `Y[0]`, `z` may still match, and the failure will look like a logic error in `Y[0]` rather than a testbench timing error. The checker should capture the pre-edge `x` value for the current row, compute expected `Y[0]` from that captured value and the present state, then compare after the edge has settled. Mid-cycle `x` changes should be recorded only as setup for the next row.

**Short worked example.** Before the positive edge, drive `y=011` and `x=0`. The table gives next state `001`, so `Y[0]=1`; present state `011` gives `z=1`. After the edge settles, compare against `Y[0]=1` and `z=1`. If `x` then changes to `1` during the mid-cycle window, that change is next-row setup and must not change the expected result for the `011` row.

**Useful point for the final Python checker.** Separate pre-edge capture from post-edge settled comparison. Use direct lookup for the five specified present states rather than minimized Boolean logic. Treat mid-cycle `x` changes as next-row setup, and never let them contaminate the current row’s expected `Y[0]`.
