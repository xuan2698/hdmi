One common implementation mistake is to treat `Y[0]` as a function of the *current* `x` line rather than the `x` value that was present at the sampling edge. In a clocked testbench, inputs may change between edges. If the checker computes the expected next state after a mid-cycle change to `x`, it can compare the DUT’s registered output against the wrong row. The public table is state-assigned and edge-sampled: the row is chosen by the `(y, x)` pair captured at the positive edge, and `Y[0]` is bit 0 of the selected next-state entry. A later `x` transition must not retroactively alter the expected value for the row just sampled.

For example, suppose the sampled pair is `y=011, x=1`. The table row for `011` gives next state `010` when `x=1`, so `Y[0]=0`, and the row output is `z=1`. If `x` changes to `0` after the edge but before the next sampling point, that new value belongs to the next row. A checker that uses the later `x=0` for the current row would instead select next state `001`, predict `Y[0]=1`, and flag a correct DUT as failing. The fix is to latch the sampled `(y, x)` pair at each positive edge and perform the lookup only from that latched pair. The same discipline applies to `z`: it is the row’s output bit and does not depend on `x`, so it should be taken from the row selected by the sampled `y`, not recomputed from any later input activity.

A second, related pitfall is to assume a reset or initial state that the public specification does not define. The checker should only evaluate rows for defined `y` encodings and should not invent expected behavior for undefined states or for the first cycle unless the harness explicitly establishes it. Keeping the expected-value computation as a pure lookup on the captured `(y, x)` pair avoids both mistakes and makes the checker robust to legal mid-cycle input changes.
