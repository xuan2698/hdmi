**Reset and power-up behavior.** The public specification defines no reset input, no reset state, and no power-up sequence. It gives only a state-assigned table over five defined present-state encodings (`000` through `100`) and two input values. Consequently, the checker must not invent a reset expectation, must not assume the machine begins in `000`, and must not require any particular value of `y` before the first sampled edge. Whatever `y` is present at the first sampled edge is simply looked up in the table if it is one of the five defined encodings; if it is `101`, `110`, or `111`, the specification provides no expected `Y[0]` or `z`, so the checker should not fabricate a prediction for that row. The safest interpretation is that the testbench is responsible for driving only defined `(y, x)` pairs at sampling edges, and the checker’s job is to compare against the table for exactly those pairs.

This matters because a common checker mistake is to seed an internal model with `y=000` at time zero and then compare the DUT’s first outputs against that model. The public spec does not license that. There is no stated initial state, no stated reset polarity, and no stated reset synchronization. If the DUT powers up in some other encoding, or if the testbench drives a defined state only after some setup interval, a model that assumes `000` will produce spurious mismatches. The checker should therefore be edge-driven and table-driven: at each sampling edge, read the settled `y` and `x`, and if `(y, x)` is one of the defined pairs, compute the expected `Y[0]` and `z` directly from that row. If the pair is undefined, skip the comparison rather than guessing.

**Worked example.** At a sampling edge, suppose the settled values are `y=011`, `x=1`. The table row for `011` gives next state `010` for `x=1` and output `z=1`. Thus expected `Y[0]` is bit 0 of `010`, which is `0`, and expected `z` is `1`. If `x` later changes to `0` before the next sampled edge, that change belongs to the next row; re-evaluating the current row with `x=0` would give next state `001`, hence `Y[0]=1`, which would be a false failure. Note that `z` remains `1` for both inputs in this row, so a checker that only compares `z` would miss the error; comparing `Y[0]` catches it.

**Key point for the final Python checker.** Capture the settled `(y, x)` at the sampling edge, perform a direct lookup in the five-row table, take `Y[0]` from bit 0 of that row’s next-state entry for the sampled `x`, and take `z` from the same row. Do not let post-sampling input transitions affect the current row’s expected values. Do not assume any reset or power-up state. Do not treat `101`, `110`, or `111` as valid table rows unless the testbench explicitly drives a defined state. The checker should be a pure function of the sampled `(y, x)` pair and the table, with no hidden state initialization.
