The key point for the final checker is that the expected values for a sampled row are determined by the pair `(y, x)` at the sampling edge, not by any later change on `x`. The public table maps each present state `y[2:0]` and input `x` to a next state `Y[2:0]` and output `z`. The checker only needs `Y[0]`, the least significant bit of that next-state field, plus `z`.

A useful distinguishing example is `y=011, x=1`. The table row for `011` says: when `x=0`, next state is `001`; when `x=1`, next state is `010`; and `z=1`. So for the sampled pair `(011, 1)`, the expected `Y[0]` is bit 0 of `010`, which is `0`, and the expected `z` is `1`. If `x` changes to `0` after sampling, that change is carried to the next row and must not alter the expectation for the already-sampled `(011, 1)` row. The next row will use `x=0` with whatever `y` is sampled then.

This example also shows why the checker cannot infer `z` from `Y[0]` alone. For `y=011, x=1`, `Y[0]=0` but `z=1`. Similarly, `y=100, x=0` gives `Y[0]=1` and `z=1`, while other rows with `Y[0]=1` may have `z=0`. The checker must evaluate the full row and input together, then extract bit 0 of the next-state field and compare `z` from the same row.

The timing discipline is therefore: capture the settled post-posedge `y` and `x`, look up that exact pair in the public table, compare the observed `Y[0]` to the least significant bit of the table’s next-state entry, and compare `z` to the table’s output entry. Do not recompute the current row using a mid-cycle `x` that arrived after sampling. That prevents false mismatches when a legal mid-input change occurs.
