**Reset and power-up behavior.** The public specification gives only a synchronous active-high reset, so the checker should treat power-up as an unspecified but benign condition that is resolved by the first sampled reset. In simulation terms, the FSM begins in its initial “no prefix matched” state with `start_shifting = 0`. Because reset is synchronous, asserting `reset = 1` before a posedge does not asynchronously force the state or output; it merely makes the next sampled edge a reset edge. At that edge, the machine returns to the initial state and clears the sticky `start_shifting` flag. If `reset` is already high at time zero and remains high through the first posedge, that first edge establishes the known initial condition. If `reset` is low at power-up, the checker should still assume the documented initial state and zero output, because the specification defines the machine’s behavior from that starting point rather than describing an unpredictable power-on state.

The important subtlety is the distinction between values present before the sampled edge and changes that occur after sampling. A reset driven before the posedge is sampled and takes effect at that edge. A reset asserted only after the posedge is not seen until the following posedge. Therefore the checker must not clear `start_shifting` merely because `reset` becomes high somewhere in the middle of a row. It must carry that high reset value into the next row’s pre-edge phase, and only then apply the synchronous reset transition. The same discipline applies to `data`: a mid-row data change does not affect the transition just sampled; it becomes the input for the next sampled edge unless the next row explicitly drives a different pre-edge value.

Once `start_shifting` becomes 1, it is sticky forever until a sampled synchronous reset. No subsequent data pattern, including zeros or a new partial match, may clear it. The checker should compare the output after the posedge has settled, using the state reached by the sampled inputs. It should also ensure that a reset sampled at an edge clears both the prefix state and the sticky flag, and that the machine then resumes searching from the initial state on later edges.

A short worked example illustrates the timing. Suppose the FSM is in the state for prefix “11” with `start_shifting = 0`. Before a posedge, `data = 0` is driven, so the sampled edge moves the machine to the suffix state for “10” and leaves `start_shifting = 0`. After sampling, `data` changes to 1. That 1 is not part of the current transition; it is carried to the next row. At the next posedge, with `data = 1` present before the edge, the machine completes “1101” and sets `start_shifting = 1`. The checker must not mark the sequence as found in the first row merely because a 1 appeared after the sampled edge.

For the final Python checker, the useful focus is therefore the two-phase row model: compute the next state and output from pre-edge driven values, then propagate any mid-row changes into the next row’s pre-edge inputs. Reset is just another synchronous input under that model. Power-up can be treated as the documented initial state, with the first sampled reset providing the definitive known condition. The pattern detector itself is a small prefix automaton plus a terminal sticky state; the timing discipline around sampling, mid-row changes, and synchronous reset is the part most likely to cause checker errors.
