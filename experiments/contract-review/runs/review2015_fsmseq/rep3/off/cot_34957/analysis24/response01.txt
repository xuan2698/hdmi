The most useful implementation mistake to target is a fallback error in the state that represents having seen `110`. After the prefix `110`, the machine is one bit away from a match. On the next input bit, the two legal outcomes are: a `1` completes `1101` and moves to the accepting state; a `0` produces history `1100`, whose longest suffix that is a prefix of `1101` is empty, so the machine must return to the initial state. A common hand-written table instead sends that `0` to the state representing “seen one `1`,” because the author reasons loosely that the trailing `0` “doesn’t help” and the earlier `1` might. That is wrong: the earlier `1` is not adjacent to the new bit, so it cannot serve as a prefix of a future match. The correct fallback from the `110` state on `0` is the reset-like start state, not the one-`1` state.

This matters because the error is invisible on many short inputs and only appears when a later `1` arrives after the bad fallback. For example, consider the input stream `11001`. The correct machine processes `1`→S1, `1`→S2, `0`→S3, `0`→S0, `1`→S1, and never asserts the output. A buggy machine that sends S3→S1 on `0` would process the first four bits into S1, then the fifth bit `1` into S2, still not accepting—so this particular length does not distinguish them. Extend to `11001101`: the correct machine restarts at S0 after `1100`, then sees `1101` and accepts at the final bit. The buggy machine, after `1100`, is already in S1; it then sees `1`→S2, `1`→S2 (self-loop), `0`→S3, `1`→ACCEPT, so it also accepts, but one state earlier in its internal history. The observable difference appears when the trailing bits after the bad fallback do not themselves form a match. For instance `110010`: correct machine goes S0 after `1100`, then S1, S0, and outputs 0 throughout. The buggy machine goes S1 after `1100`, then S2 on `1`, S3 on `0`, and on the final `0` falls back—still output 0. To expose the bug observably, use `110011`: correct machine after `1100` is S0, then S1, S2, output 0. Buggy machine after `1100` is S1, then S2, S2, output 0. Still no difference. The cleanest distinguishing case is `1101` itself preceded by a spurious `0` that the buggy machine treats as a partial match: input `01101`. Correct: S0 on `0`, S1 on `1`, S2 on `1`, S3 on `0`, ACCEPT on `1`—output 1 at the end. Buggy S3→S1 on `0`: after `0110` it is in S1, then `1`→S2, and the final `1` stays in S2, so output remains 0. That is a direct observable failure.

For the final Python checker, the practical lesson is to encode the `110`-state fallback explicitly and to include an input where a `0` arrives after `110` and is followed by bits that would otherwise complete a match. The checker should also confirm that the accepting state is absorbing: once `start_shifting` is 1, it stays 1 forever until reset, regardless of subsequent data. A short case such as `11010` distinguishes an absorbing accept (outputs 0,0,0,1,1) from a machine that lets the accepting state fall back on `0` (outputs 0,0,0,1,0). Finally, the checker must sample `reset` and `data` at the posedge and read `start_shifting` from the settled post-edge state, applying synchronous reset priority before any transition.
