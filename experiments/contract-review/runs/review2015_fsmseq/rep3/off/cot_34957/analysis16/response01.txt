The interface is deliberately narrow: `reset` and `data` are each one bit, and `start_shifting` is one bit. There are no multi-bit buses, no enable, and no separate done flag. The only meaningful boundary values are 0 and 1 for every port. `clk` is the sampling clock; the specification says to sample after the posedge has settled, so the checker should treat the post-edge settled value of `start_shifting` as the observable result of the transition whose inputs were present before that same posedge.

Reset is active high and synchronous, with priority over data. That means the checker must evaluate reset first at each sampled edge. If the pre-edge `reset` is 1, the next state is S0 and the post-edge `start_shifting` is 0, regardless of current state or `data`. Only when pre-edge `reset` is 0 does `data` control the transition. This priority is a common source of checker error: a model that advances on `data` and then applies reset afterward, or that treats reset as asynchronous, can produce a different state and output at the boundary.

The state progression is: S0 --1--> S1; S1 --1--> S2; S2 --0--> S3; S3 --1--> S4. From S4 the machine stays in S4 and holds `start_shifting` at 1 until reset. The non-advancing edges are equally important: S0 --0--> S0; S1 --0--> S0; S2 --1--> S2; S3 --0--> S0. These reflect longest-suffix matching for the target 1101. In particular, S2 on a 1 remains S2 because the trailing "11" is still a useful prefix, and S3 on a 0 falls all the way to S0 because "1100" has no suffix that begins 1101.

The critical checker point is the sampling boundary described in the prompt. Each row's values are driven before the sampled edge. Optional mid-row input changes occur after sampling and before the other edge, and they are carried to the start of the next row. Therefore the checker must compute the expected next state and expected post-edge `start_shifting` from the pre-edge `reset` and `data`, not from any later value in the same row. It should then compare the settled post-edge output. A final-value sampler that reads `data` or `reset` at the end of the row, or a pattern matcher that ignores reset priority, will diverge exactly at rows containing mid-row changes or reset assertions.

Worked example: suppose the machine is in S2, and before a posedge `reset=0`, `data=0`. The edge moves to S3 and `start_shifting` remains 0. If `data` then changes to 1 after sampling, that 1 belongs to the next row; only at the following posedge does S3 --1--> S4 set `start_shifting` to 1. A checker that used the post-edge 1 for the earlier transition would report the output one cycle early. The final Python checker should therefore latch pre-edge inputs per sampled edge, apply reset priority, update state, and compare the settled output.
