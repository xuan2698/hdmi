The reset behavior is the first thing the final checker must pin down, because it is the easiest place for a superficially correct model to diverge from the public specification. The spec says reset is active high and synchronous. That means the sampled posedge is the only place reset has authority. A high reset value present before the sampled edge forces the machine to its initial state and forces `start_shifting` to 0 at that same edge, regardless of `data`. A reset that appears after the sampled edge, even if it is high for most of the interval before the next posedge, does not retroactively change the previous edge's result. It is an input to the next sampled edge only. The checker should therefore capture the pre-edge values of `reset` and `data`, evaluate the transition using those captured values, and then compare the settled post-edge state and output. It should not read the post-edge input values when judging the edge that just occurred.

Power-up behavior should be treated as the same initial condition the synchronous reset produces: the machine begins in the no-prefix state with `start_shifting` cleared. The public spec does not describe any asynchronous initialization path, so the checker should not assume that an unclocked reset or an undefined power-up can set the sticky output. Until a sampled edge with `reset=1` occurs, or until the sequence completes, the output remains 0. After reset is released, ordinary sequence detection resumes from the initial state.

The sticky nature of `start_shifting` is the second critical point. Once the machine has recognized 1101, the output must remain 1 forever until a synchronous reset clears it. Later input bits, including bits that would normally move the state machine away from the accepting condition, must not clear the output. The checker can model this either with an absorbing accept state or with a separate latched flag, but it must compare the settled post-edge output rather than recomputing the output solely from the current transition. A common mistake is to let a subsequent 0 or 1 after completion drive the output back to 0 because the state machine has moved on. That is wrong under this specification.

Reset priority also matters when the machine is already in the accepting condition. If the pre-edge inputs are `reset=1` and `data=1`, the edge must produce the initial state and `start_shifting=0`, even though `data=1` might otherwise advance a partial match. The checker should apply reset first, then sequence logic only if reset is low. Treating reset as asynchronous, or letting data override reset, will produce false mismatches.

Longest-suffix fallback is the remaining place where a simplified checker tends to fail. From the state representing a matched prefix “11,” a 1 should keep that state because the trailing “11” is still a valid prefix. From the state representing “110,” a 0 should return to the initial state because “1100” has no useful suffix for 1101. A checker that merely counts matched bits without proper fallback will diverge on overlapping prefixes.

Worked example: suppose the machine is in the “11” state, pre-edge `reset=0`, `data=0`. The sampled edge should move to the “110” state and keep `start_shifting=0`. If `data` changes to 1 after sampling, that 1 belongs to the next row; only the following posedge can complete 1101 and set `start_shifting=1`. A checker that uses the post-edge 1 for the earlier transition would flag the output one cycle early. The final checker should latch pre-edge inputs per sampled edge, apply reset priority first, update the absorbing or latched state, and compare the settled post-edge output.
