The key distinction for the checker is that this is a *synchronous* reset with *pre-edge* input sampling, and the output is a registered (post-edge) signal. The public spec says reset is active high synchronous, and that each row's values are driven before the sampled edge. So the expected behavior at a posedge is: read `reset` and `data` as they are just before the edge; if `reset` is 1, force state S0 and `start_shifting` 0; otherwise advance the pattern state using `data` and set `start_shifting` to 1 only once S4 is reached (and keep it 1 thereafter until reset). The output compared is the settled post-edge value.

A subtle but important point is the "forever until reset" latch on `start_shifting`. Once the sequence 1101 has been detected and the machine enters S4, `start_shifting` stays 1 across subsequent edges even if `data` no longer matches anything, and even though the state remains S4. Reset is the only thing that clears it. A checker that recomputes `start_shifting` purely from the current match (e.g., "output 1 only on the edge that completes 1101") will be wrong on every later cycle. Equivalently, the output is sticky: it is the OR of "have we ever completed 1101 since the last reset" and the current completion. Modeling it as a separate latched flag, or as part of the state (S4 absorbing), both work, but the checker must not let a non-matching `data` clear it.

The other common failure is reset priority combined with mid-row changes. Because optional mid input changes occur after sampling and are carried to the start of the next row, the checker must not use the row's final `data`/`reset` values to decide the transition at the sampled edge. Consider a row where the machine is in S3, pre-edge `reset=0`, `data=1`, so the edge should go S3→S4 and set `start_shifting=1`. If `reset` then rises to 1 after sampling (mid-row), that reset affects only the *next* posedge, not this one. A checker that samples inputs at end-of-row would see `reset=1` and wrongly expect S0/0 for this edge. Conversely, if pre-edge `reset=1` and `data=1`, the edge must go to S0 and output 0 even though `data` would otherwise advance the pattern; applying `data` first and reset second, or treating reset as asynchronous, breaks this.

The non-advancing transitions also matter for distinguishing correct longest-suffix behavior from a naive "restart on mismatch" matcher. From S2, a 1 keeps S2 (the trailing "11" is still a valid prefix), not S0 or S1. From S3, a 0 goes to S0 (no useful suffix of "1100" for target 1101). From S1, a 0 goes to S0. These are the edges where a checker that only tracks "how many matched so far" without proper fallback will diverge, especially after overlapping prefixes.

Worked example: state S2, pre-edge `reset=0`, `data=0` → next state S3, `start_shifting` stays 0. If `data` changes to 1 after sampling, that 1 is for the next row; only the following posedge does S3→S4 and sets `start_shifting=1`. A checker using the post-edge 1 for the earlier transition would flag the output one cycle early. So the final checker should latch pre-edge inputs per sampled edge, apply reset priority first, update the absorbing/latched state, and compare the settled post-edge output.
