One common implementation mistake is to treat the terminal “found” condition as if it were just another pattern-matching state that can be left when the next input bit does not continue the sequence. In this specification, once `1101` has been recognized on a sampled rising edge, `start_shifting` must become 1 and remain 1 forever until a sampled synchronous reset. The terminal state is absorbing with respect to `data`: subsequent 0s or 1s must not clear the output or move the machine back into the search states. A checker or reference model that instead keeps matching after the first success, for example by returning to an earlier prefix state on a later mismatch, can appear correct for short streams that stop immediately after the match, but it will fail on any longer stream that continues after `1101`.

The subtle part is that this is not merely an output-latching detail. The state transition itself must be terminal. If the implementation reaches a “matched” state but still allows `data` to drive transitions out of it, then a later bit can silently undo the match. The public behavior requires that only `reset` can leave the terminal condition. This matters especially because the output is specified as “forever, until reset,” not “while the last four bits are 1101.” Those are different machines. The latter is an overlapping sequence detector with a pulse or level output tied to the current window; the former is a one-shot sticky detector.

A useful worked example is a stream containing `1101` followed by `0`. Suppose the machine has already seen `110` and the next sampled bit is `1`. At that edge, the sequence is complete, so the next state is terminal and `start_shifting` becomes 1. After that edge, before the next rising edge, `data` changes to 0. That mid-cycle change is not sampled at the edge that completed the match. It is carried to the start of the next row. On the next sampled rising edge, the machine is already terminal, so the sampled 0 must leave `start_shifting` at 1 and must not move the state back toward the initial search state. Only a sampled `reset=1` can clear it.

For the final Python checker, the important point is to model the post-match state as truly absorbing for `data`, and to compare the settled output after each sampled edge rather than reacting to mid-cycle input changes. A checker that recomputes the output from the most recent four input bits, or that lets a post-sample `data` change affect the just-sampled transition, can produce false mismatches. The reference behavior should separate pre-edge sampled inputs, the resulting state and output, and any later mid-cycle changes that become the next row’s starting inputs. In particular, after a match, the checker should not expect the output to drop merely because the next carried `data` bit is 0; the terminal state ignores it until reset.
