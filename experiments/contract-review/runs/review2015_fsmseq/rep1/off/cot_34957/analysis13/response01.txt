The key timing distinction in this specification is between values present at the sampled (rising) edge and optional mid-cycle changes that occur after sampling but before the next edge. Each row drives its inputs before the sampled edge, so the transition and output for that row are determined solely by the pre-edge state and the pre-edge input values. Any mid-cycle change to `data` is not retroactively applied to the transition just taken; instead it is carried forward as the starting input for the next row. This matters most around the completing edge of `1101`: if the sampled `data` is the final 1, the machine enters the terminal state and asserts `start_shifting=1` on that edge. A subsequent mid-cycle change of `data` to 0 belongs to the next row and must not be interpreted as part of the match-completing transition.

A second important point is that the terminal state is absorbing with respect to `data`. Once `start_shifting` has been set, no later `data` value—whether sampled at an edge or introduced mid-cycle—can clear it. Only a sampled synchronous `reset=1` returns the machine to its initial state and deasserts `start_shifting`. The checker should therefore treat the post-match state as sticky for all `data` inputs, and should require an explicit sampled reset to leave it. It should not infer `start_shifting` from the most recent four input bits, because the output is a latch-like match flag, not a sliding-window detector output.

A short worked example clarifies the edge/mid-input split. Suppose the pre-edge state has already matched `110`, and the sampled `data` at the rising edge is 1. After that edge settles, the machine is terminal and `start_shifting=1`. If `data` then changes to 0 before the next rising edge, that 0 is carried to the start of the next row. On the next sampled edge, the terminal state remains terminal and `start_shifting` remains 1. The mid-cycle 0 does not undo the match and does not participate in the transition that completed `1101`.

For the final Python checker, the useful focus is to model each row as three phases: pre-edge sampled inputs, post-edge settled state and output, and optional mid-cycle changes that become the next row’s starting inputs. The checker should compare the settled output after each sampled edge, apply the absorbing rule for `data` in the terminal state, and require a sampled reset to clear the terminal state. It should not recompute `start_shifting` from the last four bits, and it should not let a post-sample `data` change affect the transition just sampled. Power-up should be treated as unspecified until a synchronous reset has been sampled, so the checker neither rewards nor penalizes an arbitrary pre-reset value. These rules align the checker with the public specification’s synchronous reset, sampled-edge semantics, and truly sticky match behavior.
