The key subtlety for the final checker is the distinction between the sampled edge and mid-cycle input changes. The public spec says each row's values are driven before the sampled edge, and optional mid input changes occur after sampling but before the other edge, carried to the start of the next row. So the checker must not treat a mid-cycle change as if it were sampled at the same edge. It must evaluate the FSM using the pre-edge values, then apply any post-sample mutation only as the starting input for the following row. Output comparison is after the sampled edge has settled.

A useful distinguishing example is a match completed on a rising edge followed by a mid-cycle data change. Suppose the machine is in the “110” state, meaning it has seen 1, then 1, then 0, and is waiting for a final 1. A row drives `reset=0, data=1` before the rising edge. At that sampled edge, the FSM sees the 1, completes 1101, enters the terminal state, and sets `start_shifting=1`. After sampling, before the falling edge, the input changes to `data=0`. That change is not sampled at the same edge. It is carried to the start of the next row. The next row therefore begins with `data=0`, but the machine is already in the terminal state, so the next sampled rising edge keeps `start_shifting=1`. The mid-cycle 0 does not undo the match, and it does not cause a return to the initial state. Only a sampled `reset=1` clears the terminal state and the output.

This example matters because a checker that compares outputs immediately when inputs are driven, or that folds mid-cycle changes into the same edge, can produce a false mismatch. If it sees `data=0` after the match and expects the output to drop or the state to leave the terminal state, it will be wrong. The public behavior is sticky: once 1101 is found, `start_shifting` remains 1 forever until a sampled reset. The terminal state ignores data entirely. The mid-cycle 0 is relevant only as the next row's pre-edge data, and in the terminal state that data has no effect on state or output.

The checker should also be careful with reset timing. A high reset sampled at a rising edge returns the machine to the initial state and clears `start_shifting`. A reset that goes high only after sampling is a mid-cycle change and does not clear anything until the next sampled rising edge. Similarly, a reset that goes low mid-cycle does not release the machine early; release happens only when a sampled edge sees reset low. This is consistent with active-high synchronous reset semantics.

For the final Python checker, the practical rule is: for each row, take the pre-edge `reset` and `data`, compute the next state and settled output, compare the output after the edge has settled, then apply any post-sample input change as the carried input for the next row. Do not let mid-cycle mutations affect the current edge's state transition or output comparison. The worked example above is a compact test of that separation: a match on the sampled 1 must persist despite a later mid-cycle 0, and the next row must begin with that 0 while the output remains high.
