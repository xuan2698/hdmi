One likely implementation mistake is treating `start_shifting` as a combinational “pattern detector” rather than as the output of a sticky state. A candidate might write logic that asserts `start_shifting` whenever the last four sampled bits equal `1101`, or whenever the current state is S4 and the current `data` bit completes `1101`. That looks correct on the first match, but it fails the public requirement that the output stay 1 forever until reset. After a match, the machine must remain in S4 for every subsequent `data` value, including 0. If the checker recomputes the output from a sliding window of recent bits, it will expect `start_shifting=0` after the next 0, even though the specification requires 1.

This mistake is especially easy to make because the state names S0–S3 naturally suggest “remember the longest useful prefix,” while S4 is not a prefix state at all; it is an absorbing “already matched” state. A checker should therefore verify the sticky property directly: once a sampled edge has produced `start_shifting=1`, every later sampled edge with `reset=0` must also produce `start_shifting=1`, regardless of `data`. Only a sampled `reset=1` may clear it.

A second, related mistake is allowing a mid-cycle `data` change to affect the transition that was already sampled. The public protocol says each row’s values are driven before the sampled edge, and optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. So if `data` changes after the posedge that completes `1101`, that change must not retroactively alter the match or the output for that row. The checker should compare the settled output after the sampled edge using the inputs that were present at that edge, then treat the mid-cycle value as the starting input for the next row.

A short worked example: after reset, sampled data `1,1,0,1` moves S0→S1→S2→S3→S4 and sets `start_shifting=1`. If `data` then changes mid-cycle to 0 before the next sampled edge, the next row starts with `data=0`; at that next sampled edge the machine stays in S4 and `start_shifting` remains 1. A checker that instead combines the mid-cycle 0 with the previous three bits and expects no match, or that clears the output because the last four bits are now `1010`, would reject a correct implementation.

For the final Python checker, the useful focus is: model S4 as absorbing under both data values, make reset the only exit from S4, and compare `start_shifting` only after the sampled edge has settled. Do not derive the expected output from the most recent four input bits. Also ensure the checker’s row phasing distinguishes pre-edge driven inputs from post-sampling mid-cycle changes, so a late `data` change is applied to the next row rather than to the transition just checked.
