The public specification defines a small synchronous finite-state machine whose only job is to detect the bit pattern `1101` in a serial `data` stream and then assert `start_shifting` permanently until a synchronous reset occurs. The reset is active high and synchronous, so it is sampled on the same posedge as `data`; when `reset` is high at a sampled posedge, the machine must return to its initial state and drive `start_shifting` low, regardless of the current `data` value or prior history. Power-up behavior is not separately specified beyond this reset discipline. In a checker, the safest interpretation is that the reference model begins in the initial state and that only a sampled synchronous reset can force it back there. Any pre-reset or unknown power-up condition should not be used to justify a different expected output after a valid reset has been sampled.

The detection behavior is sticky. Once the terminal state is reached, `start_shifting` remains `1` forever until reset. From the terminal state, every non-reset input keeps the machine terminal and keeps the output high. This means the checker must not clear the output merely because subsequent data no longer matches `1101`; only reset may clear it.

The state progression should preserve valid overlapping prefixes. From the initial state, a `1` moves to a state representing a trailing `1`; a `0` stays initial. From trailing `1`, another `1` moves to trailing `11`; a `0` returns initial. From trailing `11`, a `0` moves to trailing `110`; a `1` remains trailing `11`, because the final two `1`s still form a valid prefix. From trailing `110`, a `1` enters the terminal state and sets `start_shifting` to `1`; a `0` returns initial. From the terminal state, every non-reset input remains terminal. An implementation that resets to the initial state after a failed partial match, or that fails to preserve trailing `11` on repeated `1`s, can miss valid detections or produce incorrect output timing. The checker should therefore model the expected state explicitly and update it only on sampled posedges, applying synchronous reset first.

Timing discipline is another likely source of error. Each row’s values are driven before the sampled posedge, and the checker samples after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they are carried to the start of the next row. A mid-cycle change on `data` must not affect the transition just sampled; it becomes the input for the following sampled edge. An implementation or checker that treats mid-cycle changes as extra samples, or that lets them perturb the expected state before the next posedge, can produce false mismatches. The final Python checker should maintain an expected state variable updated only at sampled posedges, apply synchronous reset first, compare the DUT output after settling, and enforce terminal-state persistence.

Short worked example: suppose the machine is in trailing `11`. A sampled row with `reset=0, data=0` moves it to trailing `110`, with `start_shifting=0`. If `data` changes to `1` after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters terminal and `start_shifting=1`. Thereafter, with reset low, the output remains `1` for any data.

For the final Python checker, the most useful focus is to avoid recomputing expected output from a recent input window. That approach can mask overlap and sticky-output bugs. Instead, keep a compact reference state machine, update it only on sampled posedges, and record mid-cycle data changes only for the next row’s sampled input.
