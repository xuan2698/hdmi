The key point for the final Python checker is that reset and the sticky flag must be evaluated from the sampled posedge values, not from any mid-cycle activity. At each sampled posedge, the checker should first ask whether `reset` is 1. If so, the expected post-edge `start_shifting` is 0, and the detector state should be treated as cleared regardless of what `data` is on that same edge. This is a synchronous reset: it does not act between edges, and it does not depend on the previous state. A high reset on the sampled edge overrides both the sequence history and the current input bit.

When `reset` is 0, the machine advances only according to the sampled `data` bit. The checker should maintain the usual sequence-detection state for 1101, but it must also maintain the sticky output flag separately. Once the 1101 sequence has been completed on a sampled edge, `start_shifting` becomes 1 and remains 1 on all later sampled edges while reset stays low. The checker should not clear the flag just because the detector state would otherwise move on, and it should not expect a pulse. The output is a latched “found” indicator, not a momentary match signal.

Power-up behavior should be treated as the initial condition before any sampled edge has occurred. The public specification does not describe an asynchronous reset or a special power-on sequence beyond the synchronous reset input. For checker purposes, the safe interpretation is that the machine begins in a non-accepting state with `start_shifting` low, and that the first meaningful expectation is established at the first sampled posedge using the driven `reset` and `data` values for that row. If the first sampled row has `reset=1`, the expected output after that edge is 0 and the detector is cleared. If the first sampled row has `reset=0`, the checker should apply the normal transition from the initial non-accepting state using the sampled `data` bit. It should not assume that power-up alone sets the sticky flag, and it should not assume any hidden history before the first row.

Mid-row input changes should not affect the transition just sampled. The row’s driven values are what the checker uses at the posedge. If `data` or `reset` changes after that sample and before the opposite edge, that change is carried into the next row’s starting condition. The checker should not retroactively reinterpret the previous sampled edge, and it should not require the current row’s output to reflect the mid change. The mid change matters only when it becomes the driven value at the next sampled posedge.

A short worked example: assume the detector has already seen `11` and is waiting for `0` then `1`. At a posedge, `reset=0` and `data=0` are sampled. The expected next detector state is “seen 110,” and `start_shifting` remains 0. If `data` then changes mid-cycle to 1, that change is not part of the current transition. At the next posedge, if `reset=0` and `data=1` are sampled, the 1101 sequence is complete, so `start_shifting` becomes 1. From then on, with `reset=0`, it stays 1 at every sampled edge.

Thus the final checker should sample inputs at posedge, apply synchronous reset first, update the detector state only from the sampled `data`, and make `start_shifting` sticky once set. Mid-input changes belong to the next row, not to the current sampled edge.
