The key point for the final Python checker is that the output is not a function of the current input or even of the last four sampled bits; it is a function of a persistent machine state that, once it reaches the terminal “found” state, never leaves it except on synchronous reset. A checker that models the DUT as “output = 1 iff the most recent four sampled data bits are 1101” will pass many ordinary cases but fail the persistence requirement. For example, after the sequence 1101 is observed, the next sampled bit might be 0, making the last four bits 1010; the correct output is still 1, but a sliding-window checker would drop it to 0. The public specification is explicit: when the sequence is found, `start_shifting` is set to 1 forever until reset. So the checker should carry a sticky flag or a terminal state, and only a sampled `reset=1` should clear it.

A second useful point is that the checker should model the search as a small prefix automaton rather than as a substring search over a growing history. The sequence 1101 has nontrivial overlap behavior. After seeing `11`, a further `1` should keep the machine in the “seen 11” condition, because the last two bits are still `11`; it should not reset to the initial state. After seeing `110`, a `0` should return to the initial state, because the suffix `00` contains no useful prefix of `1101`. After the full match, the terminal state dominates all later data. These transitions are easy to encode explicitly and easy to check against the DUT. A naive checker that scans a buffer for the substring `1101` may accidentally get some of these cases right, but it will not naturally enforce the sticky output and may mishandle reset timing.

Reset handling is another place where the checker must follow the public protocol exactly. Reset is active high and synchronous. At a sampled posedge where `reset=1`, the machine must go to the initial state and clear `start_shifting`, regardless of `data`. The checker should apply reset at the sampled edge, not as an asynchronous clear. It should also respect the sampling discipline described in the specification: each row’s driven values are present before the sampled posedge, and outputs are checked after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they carry into the start of the next row. Therefore a mid-cycle change on `data` must not affect the transition just sampled; it becomes the starting input for the following row.

A short worked example illustrates both persistence and sampling. Suppose the machine is in the “seen 11” state. A sampled row with `reset=0, data=0` moves it to “seen 110” and outputs 0. If `data` changes to 1 after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters the terminal state and outputs 1. Thereafter, with reset low, the output remains 1 for any data. The final checker should therefore compare state-derived outputs and enforce sticky persistence, rather than recomputing from recent input history.
