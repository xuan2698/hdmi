The public interface is narrow and unambiguous: one synchronous active-high `reset`, one serial `data` input, one `start_shifting` output, and a single clock. All ports are one bit wide. Because the specification names only these widths, the checker should not infer multi-bit counters, byte enables, or handshake signals. Boundary values are therefore Boolean: `reset` and `data` are each either 0 or 1, and `start_shifting` is either 0 or 1. The only meaningful “boundary” behavior is the transition between the nonterminal search states and the sticky terminal state, plus the synchronous reset override.

The important modeling point is that this is a Moore-style finite-state machine with a sticky terminal state, not a streaming substring detector. The output should be derived from the current state, not recomputed from a sliding window of recent input bits. That distinction matters after the sequence `1101` has been observed: once the machine reaches the terminal state, `start_shifting` must remain 1 forever until a sampled synchronous reset clears it. A checker that instead recomputes “did the last four bits equal 1101?” would incorrectly drop the output on later bits. The public specification explicitly says the flag is set forever until reset, so the checker should represent that persistence as state.

The overlap structure of `1101` also matters. After seeing `11`, another `1` must not restart the search from the initial state; it must remain in the “seen 11” condition, because the latest two bits are still `11`. After seeing `110`, a `0` must return to the initial state, since the suffix `00` provides no useful prefix of `1101`. After the full match, the terminal state dominates all further data. These details are easy to get wrong if the checker uses a naive substring scan rather than explicit state transitions.

Reset is active high and synchronous. A sampled row with `reset=1` must force the initial state and clear the sticky output regardless of `data`. The checker should apply reset at the sampled edge, not asynchronously. It should also respect the sampling discipline: each row’s driven values are present before the sampled posedge, and outputs are checked after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they carry into the start of the next row. Therefore a mid-cycle `data` change must not affect the transition just sampled; it becomes the starting input for the following row.

A short worked example: from the “seen 11” state, a sampled row with `reset=0, data=0` moves to “seen 110” and outputs 0. If `data` changes to 1 after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters the terminal state and outputs 1. Thereafter, with reset low, the output remains 1 for any data. The final checker should therefore compare state-derived outputs and enforce sticky persistence, rather than recomputing from recent input history.
