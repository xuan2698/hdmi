The public specification defines a synchronous finite-state machine whose only job is to detect the bit pattern `1101` in a serial `data` stream and then assert `start_shifting` permanently until a synchronous active-high `reset` occurs. The input widths are `reset: 1` and `data: 1`; the output width is `start_shifting: 1`. The clock is `clk`, and the checker samples after the positive edge has settled. Each row’s values are driven before the sampled edge. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they are carried to the start of the next row.

The key behavioral point is that `start_shifting` is sticky. Once the machine has observed `1101`, it enters a terminal state in which every non-reset input leaves the output at `1`. Only a synchronous reset returns the machine to its initial state and clears the output. This means the checker cannot simply compare `start_shifting` to a combinational function of the most recent four `data` bits. Such a window-based check would fail to enforce persistence and could also mishandle overlapping prefixes.

The reference state machine should track the longest suffix of the input seen so far that is a prefix of `1101`. From the initial state, a `1` moves to a state representing trailing `1`; a `0` stays initial. From trailing `1`, a `1` moves to trailing `11`, while a `0` returns initial. From trailing `11`, a `0` moves to trailing `110`, while a `1` remains trailing `11`, because the final two `1`s still form a valid prefix. From trailing `110`, a `1` enters the terminal state and sets `start_shifting` to `1`; a `0` returns initial. From the terminal state, every non-reset input remains terminal. An implementation that resets to the initial state after a failed partial match, or that fails to preserve trailing `11` on repeated `1`s, can miss valid detections or produce incorrect output timing. The checker should therefore model the expected state explicitly and update it only on sampled posedges, applying synchronous reset first.

Timing discipline is another likely source of error. Each row’s values are driven before the sampled posedge, and the checker samples after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they are carried to the start of the next row. A mid-cycle change on `data` must not affect the transition just sampled; it becomes the input for the following sampled edge. An implementation or checker that treats mid-cycle changes as extra samples, or that lets them perturb the expected state before the next posedge, can produce false mismatches. The final Python checker should maintain an expected state variable updated only at sampled posedges, apply synchronous reset first, compare the DUT output after settling, and enforce terminal-state persistence.

Short worked example: suppose the machine is in trailing `11`. A sampled row with `reset=0, data=0` moves it to trailing `110`, with `start_shifting=0`. If `data` changes to `1` after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters terminal and `start_shifting=1`. Thereafter, with reset low, the output remains `1` for any data.

For the final Python checker, the most useful focus is to avoid recomputing expected output from a recent input window. That approach can mask overlap and sticky-output bugs. Instead, keep a compact reference state machine, update it only on sampled posedges, and record mid-cycle data changes only for the next row’s sampled input.
