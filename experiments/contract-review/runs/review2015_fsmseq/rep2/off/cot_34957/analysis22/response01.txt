The public interface is narrow and unambiguous: `reset` and `data` are each one bit wide, `start_shifting` is one bit wide, and there is a single clock `clk`. All state changes are synchronous to the rising edge of `clk`, and `reset` is active high synchronous. That means reset is not an asynchronous clear: it is sampled like any other input at the posedge, and when sampled high it forces the machine back to its initial state and forces `start_shifting` low. Because the output is described as sticky once the target sequence is found, the only way to clear `start_shifting` is a sampled reset.

The boundary values are therefore simple: every input and output is binary, so the only legal values are 0 and 1. There are no multi-bit fields, no don’t-care encodings, and no arithmetic ranges to worry about. The meaningful boundary conditions are behavioral rather than numeric: the initial state, the four prefix states for `1101`, and the terminal state. The terminal state is absorbing under `reset=0` regardless of `data`, and the output must remain 1 there forever until reset.

The sequence detector must respect overlaps as described. From the initial state, `data=1` moves to the trailing-`1` state and `data=0` stays initial. From trailing `1`, `data=1` moves to trailing `11` and `data=0` returns initial. From trailing `11`, `data=0` moves to trailing `110`; `data=1` stays trailing `11` because the last two bits are still `11`. From trailing `110`, `data=1` completes `1101` and enters the terminal state; `data=0` returns initial because the suffix has no useful prefix of the target. From the terminal state, any `data` with `reset=0` remains terminal.

Timing discipline is the key point for the final checker. Each row’s values are driven before the sampled posedge, and the checker samples after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge, and they are carried to the start of the next row. Therefore a mid-cycle change on `data` must not affect the transition just sampled. It becomes the input for the following sampled edge. The checker should not treat mid-cycle changes as extra samples, and it should not let them perturb the expected state until the next posedge.

A short worked example: suppose the machine is in trailing `11`. A sampled row with `reset=0, data=0` moves it to trailing `110`, with `start_shifting=0`. If `data` changes to `1` after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters the terminal state and `start_shifting=1`. Thereafter, with reset low, the output remains `1` for any data.

For the final Python checker, the most useful focus is to maintain an expected state variable updated only at sampled posedges, apply synchronous reset first, compare the DUT output after settling, and enforce terminal-state persistence. Avoid recomputing expected output from a recent input window; that approach can mask overlap and sticky-output bugs. Also ensure that mid-cycle data changes are recorded only for the next row’s sampled input, not for the current edge. This gives a compact, protocol-faithful reference model and catches the subtle cases the public specification emphasizes.
