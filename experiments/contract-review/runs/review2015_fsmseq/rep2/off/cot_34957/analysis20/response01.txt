The public specification defines a Moore-style recognizer for the bit pattern `1101` with a sticky success output. The machine has a small set of meaningful states: no useful prefix seen, a trailing `1`, a trailing `11`, a trailing `110`, and a terminal matched state. The output `start_shifting` is `0` in all nonterminal states and `1` in the terminal state. Once the terminal state is entered, it is absorbing under normal operation: for any `data` value with `reset=0`, the machine remains in the terminal state and `start_shifting` stays `1`. This is the “forever, until reset” requirement.

Reset is active high and synchronous. That means the reset input is not an asynchronous clear; it is sampled at the rising clock edge like the other inputs. When a sampled row has `reset=1`, the machine must go to the initial state and drive `start_shifting=0` after that edge has settled, regardless of `data`. Because reset is synchronous, a high reset value that appears only between edges does not by itself reset the machine unless it is present at the sampled posedge. Likewise, a reset pulse that is removed before the next sampled edge has no effect on the state transition for that edge. The checker should therefore apply reset as the highest-priority condition in the next-state function at each sampled posedge.

Power-up behavior is not specified as an independent asynchronous initialization in the public description. The safe interpretation for checking is that the machine begins in the initial nonterminal state, with `start_shifting=0`, and that synchronous reset can always return it to that state. The checker should not assume any particular behavior before the first sampled edge beyond what the reset and initial-state convention imply. In practice, the reference model should initialize its expected state to the initial state and then update only on sampled posedges.

The transition behavior must respect overlaps. From the initial state, `data=1` moves to the trailing-`1` state; `data=0` stays initial. From trailing `1`, `data=1` moves to trailing `11`; `data=0` returns initial. From trailing `11`, `data=0` moves to trailing `110`; `data=1` stays trailing `11`, because the last two bits are still `11`. From trailing `110`, `data=1` completes `1101` and enters the terminal state; `data=0` returns initial, since the suffix has no useful prefix of the target. From the terminal state, any `data` with `reset=0` remains terminal.

Timing discipline is central. Each row’s values are driven before the sampled posedge, and the checker samples after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge; they are carried to the start of the next row. Therefore a mid-cycle change on `data` must not affect the transition just sampled. It becomes the input for the following sampled edge. The checker should not treat mid-cycle changes as extra samples, and it should not let them perturb the expected state until the next posedge.

A short worked example: suppose the machine is in trailing `11`. A sampled row with `reset=0, data=0` moves it to trailing `110`, with `start_shifting=0`. If `data` changes to `1` after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters the terminal state and `start_shifting=1`. Thereafter, with reset low, the output remains `1` for any data.

For the final Python checker, the most useful focus is to maintain an expected state variable updated only at sampled posedges, apply synchronous reset first, compare the DUT output after settling, and enforce terminal-state persistence. Avoid recomputing expected output from a recent input window; that approach can mask overlap and sticky-output bugs. Also ensure that mid-cycle data changes are recorded only for the next row’s sampled input, not for the current edge. This gives a compact, protocol-faithful reference model and catches the subtle cases the public specification emphasizes.
