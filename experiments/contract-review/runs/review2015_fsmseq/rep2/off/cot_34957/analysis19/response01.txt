The key point for the final checker is that the DUT is a state machine, not a substring detector. The checker should model the five meaningful states explicitly: initial, seen `1`, seen `11`, seen `110`, and terminal/match. At each sampled posedge, it should first apply synchronous reset: if `reset=1`, force the initial state and `start_shifting=0` regardless of `data`. Otherwise it should advance according to the current state and sampled `data`, then compare the post-edge `start_shifting` against the state-derived expected value. Once the terminal state is reached, only reset can leave it; all later data must leave `start_shifting=1`.

The overlap cases deserve explicit attention. From seen `1`, a `1` goes to seen `11`; from seen `11`, another `1` stays in seen `11`, because the trailing two bits are still `11`. From seen `110`, a `0` returns to initial, since the suffix `00` has no useful prefix of `1101`. From seen `110`, a `1` completes the match and enters the terminal state. These transitions are the ones a naive buffer scan can accidentally pass while still failing the sticky-output requirement or reset timing.

Timing discipline matters as much as the transition table. Each row’s values are driven before the sampled posedge, and the checker samples after that edge has settled. Optional mid-cycle input changes occur after sampling and before the opposite edge; they are carried to the start of the next row. Therefore a mid-cycle change on `data` must not retroactively affect the transition just sampled. It becomes the input value for the following sampled edge. The checker should not treat mid-cycle changes as extra samples, and it should not let them perturb the expected state until the next posedge.

A short worked example: suppose the machine is in seen `11`. A sampled row with `reset=0, data=0` moves it to seen `110`, with `start_shifting=0`. If `data` changes to `1` after sampling, that change is ignored for this edge. At the next posedge, with `reset=0, data=1`, the machine enters the terminal state and `start_shifting=1`. Thereafter, with reset low, the output remains `1` for any data.

For the final Python checker, the most useful focus is to maintain an expected state variable updated only at sampled posedges, apply synchronous reset first, compare the DUT output after settling, and enforce terminal-state persistence. Avoid recomputing expected output from a recent input window; that approach can mask overlap and sticky-output bugs. Also ensure that mid-cycle data changes are recorded only for the next row’s sampled input, not for the current edge. This gives a compact, protocol-faithful reference model and catches the subtle cases the public specification emphasizes.
