One common implementation mistake is to treat `start_shifting` as a combinational “match now” signal rather than as a latched state bit. That is, the designer may write logic that asserts the output whenever the current state and current `data` together look like the end of `1101`, but does not hold the output after the next input bit arrives. In simulation this can look almost right at the exact detection edge, so a superficial test that only checks the completing row may pass. The error appears on the following sampled rows: after `1101` has been seen, the machine may drop `start_shifting` back to 0 when `data` changes, even though the specification says it must remain 1 forever until reset.

This mistake is especially easy to make because the detector itself must still track prefix progress before detection. A correct implementation has two related but distinct obligations: the state transition logic must recognize the sequence, including overlaps, and the output must be a sticky flag once recognition occurs. If the output is derived directly from “state == MATCH” or from a momentary comparison, then the flag is not truly sticky. The checker should therefore not merely ask whether `start_shifting` is 1 on the row where the final `1` of `1101` is sampled. It should also continue sampling subsequent rows with `reset=0` and arbitrary `data`, and require `start_shifting` to remain 1 on all of them.

A short worked example makes the failure visible. Suppose the sampled stream has just completed `1101`, so on that row `reset=0`, `data=1`, and the correct output is `start_shifting=1`. On the next sampled row, let `reset=0`, `data=0`. The correct output is still `start_shifting=1`, because detection is permanent until reset. A buggy implementation that recomputes the output from the current bit or from a transient match condition may output 0 on this second row. The final checker should include this kind of post-detection persistence check, not just a one-row detection check.

The reset interaction is the other side of the same issue. Because reset is synchronous and active high, a sampled `reset=1` must clear the sticky flag and return the detector to its initial prefix state. The checker should apply reset with priority over `data` on that sampled row, and should not let a mid-row change of `reset` affect the already sampled row. After reset is released, the machine must be able to detect `1101` again from scratch. A checker that only verifies “stays high forever” without also verifying “only reset clears it” would miss an implementation that never clears the flag, while a checker that only verifies detection would miss an implementation that fails to hold it.

So the most useful checker focus is the registered persistence of `start_shifting`: check the 0-to-1 transition on the completing sampled row, check that it remains 1 on later non-reset rows regardless of `data`, and check that a sampled synchronous reset is the only event that returns it to 0.
