One common implementation mistake is to let the sticky `start_shifting` output be derived from the current input pattern rather than from the machine's state. That is, a candidate design might compute `start_shifting = (state == S3 && data == 1)` or otherwise gate the output on the present `data` value, instead of making it a latched property of having reached the found state. Under the public specification, once the sequence `1101` has been detected, `start_shifting` must remain `1` forever until a synchronous reset is sampled. The output is not a one-cycle match pulse, and it must not depend on subsequent `data` bits. A checker should therefore verify that after the completing row, every later row with `reset=0` produces `start_shifting=1` regardless of `data`, including runs of zeros or a new partial pattern.

This mistake is easy to make because the transition into the found state naturally depends on `data`, and a designer may reuse that same combinational condition for the output. It can also appear as an output that is correct on the completing row but drops on the next row when `data` changes. The public spec's phrase "forever, until reset" rules this out. The checker should distinguish the detection event from the persistent output: detection is a transition condition, while `start_shifting` is a state-derived output that remains asserted.

A short worked example: suppose the machine has seen `1`, `1`, `0` and is in the state expecting the final `1`. On the completing row, sampled `reset=0`, `data=1`. The machine transitions to the found state and outputs `start_shifting=1`. On the next row, sampled `reset=0`, `data=0`. A correct implementation still outputs `1`; a mistaken implementation that gates the output on `data==1` would output `0`. The checker should catch that by continuing to sample rows after detection and requiring the output to stay high.

A related but distinct pitfall is reset handling in the found state. Because reset is active high synchronous, a sampled `reset=1` must clear `start_shifting` and return the machine to its initial state, even if `data` would otherwise continue a pattern. A mid-row reset change after sampling must not clear the current row; it is carried to the next row. The checker should apply reset only from the sampled row values, with reset priority over data, and should not treat reset as an asynchronous override. It should also not require the output to drop immediately when reset is driven between edges.

Finally, the checker should evaluate each row using only the sampled `reset` and `data` for that row, compute the next state and output from the entering state, and only then carry any mid-row changes forward. This row-local discipline prevents false failures around the completing edge, around reset assertion or deassertion between edges, and around the persistent nature of `start_shifting`. The most useful focus for the final checker is to separate detection from persistence: verify the transition into the found state on the completing row, then verify that the output remains asserted on all subsequent non-reset rows independent of `data`.
