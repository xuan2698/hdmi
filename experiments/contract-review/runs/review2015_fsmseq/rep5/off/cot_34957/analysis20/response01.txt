Reset and power-up behavior deserve separate attention because they determine the initial state of the sticky flag and the detector's prefix state, and because a synchronous active-high reset has a precise sampling relationship to the clock edge that the checker must respect.

At power-up, before any sampled edge has occurred, the machine has no defined history. The public specification does not state an explicit initial value for `start_shifting`, but the intended behavior is that the flag begins cleared: the detector has not yet seen `1101`, so it must not assert `start_shifting` merely because the simulation started. The checker should therefore treat the pre-first-edge condition as "no detection yet," and should not accept an implementation that powers up with `start_shifting=1`. Equivalently, the first sampled row with `reset=0` must produce `start_shifting=0` unless that single row somehow completes a match, which it cannot, since a match requires four bits. The prefix state at power-up should be the initial state corresponding to "no matching prefix," so that the first `1` of a candidate sequence begins progress toward the match rather than being ignored or misaligned.

Reset is synchronous and active high. That means the reset input is sampled on the same posedge as `data`, and its effect is observed in the outputs after that edge has settled. The checker must drive `reset` before the sampled edge and must evaluate the resulting `start_shifting` on that same sampled row. A sampled `reset=1` must take priority over `data`: regardless of the bit present on `data` during that row, the machine must clear `start_shifting` to 0 and return its prefix state to the initial state. A mid-row change of `reset` that occurs after sampling and before the next edge must not retroactively alter the already sampled row; it is carried forward and only matters at the next sampled edge. This is the key timing point for the checker: reset is not asynchronous, so it does not clear the flag the instant the reset line rises, only at the next sampled posedge.

After reset is released, the machine must be able to detect `1101` again from scratch. The checker should therefore include a sequence in which a detection occurs, the flag is held high across several non-reset rows, then a sampled reset clears it, and then a fresh `1101` is presented and must set the flag again. This distinguishes a correct sticky-flag implementation from one that either never clears or clears asynchronously.

A short worked example illustrates the reset timing. Suppose the flag is currently 1 from an earlier detection. On a sampled row the checker drives `reset=1` and `data=0`. After the posedge settles, the correct output is `start_shifting=0`, and the prefix state is initial. If the checker then drives `reset=0` and `data=1` on the next row, the output must remain 0, because a single `1` is only the first bit of a potential match. Only after the full `1101` is sampled again should the flag return to 1.

The most useful point for the final Python checker is to verify the registered, edge-sampled nature of both the sticky set and the synchronous clear: assert the 0-to-1 transition on the completing sampled row, hold it across later non-reset rows with arbitrary `data`, and confirm that only a sampled `reset=1` returns it to 0, with reset taking priority over `data` on that row.
