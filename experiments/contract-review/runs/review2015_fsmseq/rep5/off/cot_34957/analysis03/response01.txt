The machine has five meaningful states: the initial state (no useful prefix), states representing having matched `1`, `11`, and `110`, and a terminal found state. The output `start_shifting` is 0 in all non-terminal states and 1 in the found state. Because the output is sticky, once the found state is entered it is never left except by a sampled synchronous reset, which returns the machine to the initial state and forces the output to 0 for that row.

Transitions are driven by the sampled `data` bit. From the initial state, `data=1` advances to the `1` state; `data=0` stays initial. From the `1` state, `data=1` advances to `11`; `data=0` returns to initial (the trailing `0` cannot begin `1101`). From the `11` state, `data=0` advances to `110`; `data=1` stays in `11` (the new trailing `1` still leaves a valid `11` prefix). From the `110` state, `data=1` completes `1101` and enters the found state, setting `start_shifting=1`; `data=0` returns to initial, since `1100` contains no useful prefix for `1101`. In the found state, any `data` keeps the machine found and the output 1.

Reset is synchronous and active high. On any sampled row where `reset=1`, the next state is initial and the row’s output is 0, regardless of `data` or prior state. This includes the found state: a sampled reset clears stickiness. If `reset=0`, the normal transition above applies. Initialization before the first row is the initial state with output 0; if the first sampled row asserts reset, the result is still initial with output 0, so the checker can treat that uniformly.

The critical checker discipline is row ordering. Each row’s expected output must be computed from the state entering that row and the sampled inputs for that row, with reset applied first. Mid-row changes to `data` or `reset` occur after sampling and must be carried only into the next row’s sampled tuple. They must never retroactively alter the current row’s transition or output. This matters most when the current sampled `data=1` completes `1101`: a later mid-row change to `data=0` cannot cancel the completion for that row; it only becomes the next row’s input, where the machine is already found and remains found unless reset is sampled high.

Worked example: entering a row in the `110` state with sampled `data=1`, `reset=0`, the row’s output is 1 and the next state is found. If `data` then changes mid-row to 0, the current row still outputs 1; the carried `data=0` applies to the next row, which stays found with output 1 (absent a sampled reset). The final checker should therefore process rows as fixed sampled tuples, apply synchronous reset first, then the sequence transition, then the sticky output, and only afterward update carried inputs for the following row.
