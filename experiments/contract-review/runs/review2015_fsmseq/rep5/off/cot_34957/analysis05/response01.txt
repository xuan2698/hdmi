A useful distinguishing example for the checker is a completing transition followed by a mid-row change on `data`. Suppose the machine has already seen `110` and is in the `110` prefix state. The next row is driven with `reset=0`, `data=1` before the sampled positive edge. At that edge the machine completes `1101`: the row’s output must be `start_shifting=1`, and the next state is the found state. Now suppose that, after sampling and before the next edge, `data` changes to `0`. That change is carried to the start of the following row. It must not retroactively affect the completing row: the completing row still outputs `1`, and the machine still enters the found state. On the following row, the sampled input is `reset=0`, `data=0`; because the machine is already in the found state, the output remains `1` and the state remains found. The carried `0` is simply the next row’s data, not a reason to reinterpret the previous row.

This example matters because a naive checker might combine all input changes within a row and then evaluate the transition once, or it might let a late `data` change influence the row that just completed the pattern. The public specification instead fixes the order: each row’s values are driven before the sampled edge; the sampled edge determines the row’s output and next state; optional mid-row changes occur after sampling and are carried to the start of the next row. Therefore the checker should treat each row as a tuple of sampled `reset` and `data`, compute the transition from the entering state using only those sampled values, apply synchronous reset with priority, and then update the sticky output. Only after that should it carry any mid-row changes forward.

A second useful point is reset priority in the found state. If the machine has already set `start_shifting=1`, a later row with sampled `reset=1` must clear the output to `0` and return to the initial state, regardless of `data`. Conversely, a mid-row `reset` change after sampling does not clear the current row; it is carried to the next row, where it will be sampled and then applied. The checker should therefore not treat reset as an asynchronous override. It should also not treat `start_shifting` as a pulse: once the found state is entered, every subsequent sampled row with `reset=0` outputs `1`, even if the data no longer resembles `1101`.

The key checker discipline is thus row-local evaluation followed by carry-forward. Sampled values determine the current transition and output; mid-row changes affect only the next row’s sampled values. This prevents false failures around the completing edge and around reset deassertion or assertion that occurs between edges.
