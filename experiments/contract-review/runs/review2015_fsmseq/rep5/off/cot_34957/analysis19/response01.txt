The public specification defines a synchronous finite-state machine that scans a one-bit input stream for the pattern `1101`. The key behavioral requirement is not merely recognizing the pattern, but latching a sticky output: once `start_shifting` becomes 1, it must remain 1 on every subsequent sampled row until a synchronous active-high reset clears it. The checker should therefore focus on registered persistence, not just momentary pattern matching.

Timing matters because the interface has both edge-sampled and mid-row inputs. The clock is `clk`; all values are sampled after the positive edge has settled. Each row’s values are driven before the sampled edge. Optional mid-input changes occur after sampling and before the other edge, and are carried into the start of the next row. In practical checker terms, the row’s `reset` and `data` values at the sampled positive edge are the ones that determine the next state and output. A mid-row change to `data` or `reset` must not retroactively alter the result of the row already sampled. This is especially important for reset: a sampled `reset=1` must clear the sticky flag and return the detector to its initial prefix state, with reset taking priority over `data` on that sampled row. A mid-row reset change should only affect the next sampled row.

The transition logic must recognize `1101` including overlaps. For example, after seeing `110`, a `1` completes the match, but the trailing `1` can also serve as the start of a new potential match. The output, however, must not be derived directly from “state == MATCH” or from a momentary comparison. It must be a sticky flag. The checker should not merely ask whether `start_shifting` is 1 on the row where the final `1` of `1101` is sampled. It should also continue sampling subsequent rows with `reset=0` and arbitrary `data`, and require `start_shifting` to remain 1 on all of them.

A short worked example makes the failure visible. Suppose the sampled stream has just completed `1101`, so on that row `reset=0`, `data=1`, and the correct output is `start_shifting=1`. On the next sampled row, let `reset=0`, `data=0`. The correct output is still `start_shifting=1`, because detection is permanent until reset. A buggy implementation that recomputes the output from the current bit or from a transient match condition may output 0 on this second row. The final checker should include this kind of post-detection persistence check, not just a one-row detection check.

The reset interaction is the other side of the same issue. Because reset is synchronous and active high, a sampled `reset=1` must clear the sticky flag and return the detector to its initial prefix state. The checker should apply reset with priority over `data` on that sampled row, and should not let a mid-row change of `reset` affect the already sampled row. After reset is released, the machine must be able to detect `1101` again from scratch. A checker that only verifies “stays high forever” without also verifying “only reset clears it” would miss an implementation that never clears the flag, while a checker that only verifies detection would miss an implementation that fails to hold it.

So the most useful checker focus is the registered persistence of `start_shifting`: check the 0-to-1 transition on the completing sampled row, check that it remains 1 on later non-reset rows regardless of `data`, and check that a sampled synchronous reset is the only event that returns it to 0.
