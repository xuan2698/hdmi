The key modeling point for the final checker is the timing boundary between the sampled posedge and any mid-cycle input changes. The public spec says each row's values are driven before the sampled edge, and optional mid input changes occur after sampling, before the other edge, and are carried to the start of the next row. Therefore the checker should treat the posedge as the only update event for state and output. It should compute the next state from the current state and the sampled `data` at that posedge, then read `start_shifting` from that next state. In particular, on the row where the final `1` of `1101` is sampled, the correct post-edge output is already 1. A checker that instead asks whether the current state plus current data complete the sequence before applying the edge will expect 0 on that row and 1 only on the following row; that is the classic registered-versus-combinational or Moore-versus-Mealy confusion, and it will fail against a correct implementation.

A second point is that the found state must be absorbing. Once `start_shifting` has been set, every later sampled edge with `reset=0` must keep it at 1 regardless of `data`. A checker that implements only the minimal prefix automaton and then resumes suffix matching after detection will incorrectly clear the output on some later bit. The found state should have a self-loop on all data values, with only synchronous reset leaving it.

A third point is reset timing. Reset is active high synchronous, so a mid-cycle `reset=1` must not clear the output until the next sampled posedge. The checker should apply reset only at the sampled edge, with reset priority over data. If it models reset as asynchronous or lets a mid-cycle reset change the expected output for the current row, it will disagree with a correct DUT.

Short worked example: state `110`, sampled posedge with `data=1`, `reset=0` → enter found, post-edge `start_shifting=1`. Then mid-cycle `reset=1` occurs before the next posedge. The correct expectation for the current row remains `start_shifting=1`; only at the next sampled posedge does reset clear the state and output. A checker that reacts to the mid-cycle reset immediately, or that expects detection one cycle late, fails here.

For the final checker: separate sampled-edge updates from mid-cycle input changes, compare only the registered post-edge `start_shifting`, enforce synchronous reset priority at the edge, and make the found state absorbing.
