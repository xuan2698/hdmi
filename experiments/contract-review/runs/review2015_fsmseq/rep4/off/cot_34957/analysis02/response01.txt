The public specification describes a synchronous finite-state machine that scans a one-bit serial input for the pattern `1101`. Once that pattern has been observed, the output `start_shifting` is asserted and remains asserted permanently until a synchronous active-high reset clears the machine. The reset is sampled at the rising edge of `clk`, and the output is registered: it reflects the state after the sampled edge has settled, not any combinational function of the current input. The input and output widths are one bit each, and the only clock is `clk`.

The key behavioral point for the final checker is the distinction between the inputs that are stable at a sampled posedge and any optional mid-cycle changes that occur afterward. Each row of the stimulus has a drive phase before the sampled edge and an optional mid-cycle change phase after sampling but before the opposite edge. The checker must associate the sampled `start_shifting` value with the `reset` and `data` values that were present at the sampled posedge. A mid-cycle change to `data` or `reset` is carried forward to the next row and is consumed only at the next posedge. It must not retroactively alter the just-sampled output or state.

Reset behavior is synchronous and active high. If `reset` is high at a sampled posedge, the machine returns to its initial state and `start_shifting` is cleared after that edge. Reset has priority over any data pattern matching at that same edge. A reset that is asserted mid-cycle does not affect the current sample; it takes effect only at the next posedge. Power-up behavior is not separately specified beyond the synchronous reset, so the checker should treat the initial state as the reset state and should not assume any asynchronous clearing. The sticky found condition is absorbing: once the FSM has entered the found state, `start_shifting` remains 1 at every subsequent sampled posedge unless a sampled reset is high.

A short worked example illustrates the timing. Suppose the machine has already matched `110` and is waiting for the final `1`. Before a posedge, `reset=0` and `data=1`. At the posedge, the FSM consumes that `1`, enters the found state, and `start_shifting` becomes 1 after the edge settles. If `data` then changes mid-cycle to 0, that change is irrelevant to the current sample; `start_shifting` stays 1. At the next posedge, because the machine is already in the sticky found state, `start_shifting` remains 1 regardless of `data`, unless `reset` is high at that edge. If instead `reset` goes high mid-cycle after the found sample, the checker must wait for the next posedge: only then does the synchronous reset take effect and clear `start_shifting`.

The final Python checker should therefore model two phases per row: drive inputs, sample the posedge state and output, then optionally apply mid-cycle input changes for the next row. It should compare `start_shifting` only against the registered state after the sampled edge, enforce reset priority at that edge, and keep the found state absorbing until a sampled reset. This avoids the common error of asserting `start_shifting` one half-cycle early or of letting mid-cycle changes leak into the current sample.
