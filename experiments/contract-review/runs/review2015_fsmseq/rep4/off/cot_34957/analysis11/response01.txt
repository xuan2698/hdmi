The most useful thing to pin down for the final Python checker is the exact meaning of "sample after the posedge edge has settled" combined with "each row's values are driven before the sampled edge" and "optional mid input changes occur AFTER sampling, before the other edge, and are carried to the start of the next row." That phrasing means the checker should treat each row as: inputs are stable at the sampled posedge, the FSM updates, and the registered output is observed post-edge. Any mid-cycle change to `reset` or `data` belongs to the next row's pre-edge setup, not to the current row's expected output.

A short distinguishing example makes the hazard concrete. Suppose the machine is in state `110` (it has seen `110` as a suffix). On a sampled posedge, `reset=0` and `data=1`. The sequence `1101` is now complete, so the next state is the absorbing found state, and the registered `start_shifting` after that edge is 1. A checker that computes the output combinationally from "current state plus current data" and then compares it to the pre-edge registered value will expect 0 on this row and 1 only on the following row. That is the classic Moore-versus-Mealy or registered-versus-combinational mismatch. For this spec, the detection row itself must already expect post-edge `start_shifting=1`.

The same example exposes the reset-timing trap. If a mid-cycle `reset=1` appears after that detection sample but before the next posedge, it must not retroactively change the detection row's expected output. The detection row remains `start_shifting=1`; only the next sampled posedge, where reset has priority over data, clears the state and output. A checker that models reset as asynchronous, or that lets a mid-cycle reset alter the current row's expectation, will disagree with a correct synchronous design.

Persistence is the other place a checker can go wrong. Once the found state is entered, it must self-loop on both `data=0` and `data=1` when `reset=0`. A checker that resumes suffix matching after detection, or treats the found state as transient, may incorrectly clear `start_shifting` on a later bit. The found state is absorbing; only a sampled synchronous reset exits it.

So the final Python checker should: separate sampled-edge updates from mid-cycle input changes; compare only the registered post-edge `start_shifting`; enforce synchronous reset priority at the edge; and make the found state absorbing. That is the narrow, high-value focus for this pass.
