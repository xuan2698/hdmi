One useful implementation mistake to target in the final Python checker is treating `start_shifting` as a combinational “detection now” signal rather than as a registered post-edge output. The public spec says the FSM searches for `1101`, and when the sequence is found it should set `start_shifting` to 1 forever until reset. It also says the clock is `clk`, sampling occurs after the posedge has settled, each row’s values are driven before the sampled edge, and optional mid input changes occur after sampling and before the other edge. That timing language matters: the checker should evaluate the state transition caused by the sampled edge and then observe the registered output after that edge. It should not expect the output to reflect the current row’s `data` combinationally before the edge.

A common mistaken checker computes the expected output from the pre-edge state and the current row’s `data`, then compares that against the DUT output for the same row. That can shift detection by one cycle. For a Moore-style registered output, the row that completes `1101` should already show `start_shifting=1` after the sampled posedge, because the FSM has entered the found state at that edge. A checker that expects the output only on the following row will reject a correct implementation. Conversely, a checker that expects a combinational Mealy assertion on the same row before the edge may accept an implementation whose output is not actually registered as required.

A short worked example: suppose the FSM is in the state representing suffix `110`. On a sampled posedge, `reset=0` and `data=1`. The sequence `1101` is completed, so the next state is the absorbing found state, and the registered `start_shifting` after that edge is 1. The checker should expect 1 for that row’s post-edge output. If it instead computes “current state plus current data” and compares to the pre-edge registered value, it will expect 0 on this row and 1 only on the next row. That is the classic registered-output versus combinational-output mismatch.

The same example also exposes reset timing. If `reset=1` changes mid-cycle after the detection sample but before the next posedge, it must not retroactively alter the detection row’s expected output. The detection row remains `start_shifting=1`; only the next sampled posedge, where synchronous reset has priority, clears the state and output. A checker that models reset as asynchronous, or lets a mid-cycle reset change the current row’s expectation, will disagree with a correct synchronous design.

Persistence is the other related trap. Once the found state is entered, it must self-loop on both `data=0` and `data=1` when `reset=0`. A checker that resumes suffix matching after detection, or treats the found state as transient, may incorrectly clear `start_shifting` on a later bit. The found state is absorbing; only a sampled synchronous reset exits it.

So the final Python checker should separate sampled-edge updates from mid-cycle input changes, compare only the registered post-edge `start_shifting`, enforce synchronous reset priority at the edge, and make the found state absorbing. That is the narrow, high-value focus for this pass.
