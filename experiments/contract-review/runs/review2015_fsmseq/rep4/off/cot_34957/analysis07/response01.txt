The public spec describes a synchronous finite-state machine with a single-bit input `data`, a single-bit active-high synchronous `reset`, a clock `clk`, and a single-bit registered output `start_shifting`. The machine searches the serial input stream for the pattern `1101`. Once that pattern has been observed, `start_shifting` must remain 1 forever until a synchronous reset clears the machine. The key timing phrase is “sample after the posedge edge has settled.” That means the checker should evaluate the DUT’s registered output after the active clock edge has propagated through the state and output registers, not before the edge and not combinationally from the current state plus current input.

The edge/mid-input protocol matters because the spec distinguishes values driven before the sampled edge from optional mid-cycle changes that occur after sampling and before the opposite edge. Inputs present before the sampled posedge determine the next registered state and output. A mid-cycle change does not retroactively alter the just-sampled result; it is carried forward and becomes relevant only at the next sampled edge. Therefore the checker must maintain two notions of time: the sampled-edge update, where reset and data are consumed with reset priority, and the interval between edges, where input changes may occur but must not change the expected post-edge output for the row already sampled.

A common checker error is to compute detection combinationally. Suppose the machine is in state `110` and the sampled posedge sees `data=1` with `reset=0`. The correct registered behavior is that the edge moves the machine into the found state and, after the edge settles, `start_shifting` reads 1. If a checker instead asks “does the current state plus current data complete 1101?” before applying the edge, it will expect `start_shifting=0` for that row and only expect 1 on the following row. That is the classic Mealy-versus-Moore or registered-versus-combinational confusion. The public spec’s wording—“set `start_shifting` to 1” and “sample after the posedge edge has settled”—points to the registered interpretation: the output changes as a consequence of the sampled edge, and the checker should compare the post-edge registered value.

A second related mistake is treating the found state as non-absorbing. Once found, the spec says “forever, until reset.” Every subsequent sampled edge with `reset=0` must keep `start_shifting=1`, regardless of `data`. A checker that implements only the minimal prefix automaton and then falls back on suffix matching after detection will incorrectly clear the output on some later bit. The found state must be a sink for data transitions, with only synchronous reset leaving it.

A third mistake is reset timing. Reset is active high synchronous, so a mid-cycle `reset=1` must not clear the output until the next sampled posedge. The checker should apply reset only at the sampled edge, with reset priority over data. If it models reset as asynchronous or lets a mid-cycle reset change the expected output for the current row, it will disagree with a correct DUT.

Short worked example: state `110`, sampled posedge with `data=1`, `reset=0` → enter found, post-edge `start_shifting=1`. Then mid-cycle `reset=1` occurs before the next posedge. The correct expectation for the current row remains `start_shifting=1`; only at the next sampled posedge does reset clear the state and output. A checker that reacts to the mid-cycle reset immediately, or that expects detection one cycle late, fails here.

For the final checker: separate sampled-edge updates from mid-cycle input changes, compare only the registered post-edge `start_shifting`, enforce synchronous reset priority at the edge, and make the found state absorbing.
