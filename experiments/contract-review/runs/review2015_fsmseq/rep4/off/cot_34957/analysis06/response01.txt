The most useful implementation mistake to flag for the final Python checker is conflating the *registered* `start_shifting` output with a combinational “next-state” or “sequence-detected” signal. The public spec says the machine “should set start_shifting to 1, forever, until reset,” and the timing note says to sample after the posedge has settled. That means `start_shifting` is an output of the state register (or of a register that is updated on the same sampled edge), not a wire that goes high as soon as the last `1` of `1101` appears at the input. A checker that computes detection from the current input and current state, then compares that against the DUT’s registered output, will be off by one cycle at the detection edge and will also mis-handle the reset edge.

Concretely, suppose the machine is in the `110` state and the sampled edge has `data=1`, `reset=0`. At that posedge the machine enters the found state, and after the edge settles `start_shifting` should read 1. If the checker instead evaluates “does the current state plus current data complete 1101?” before applying the edge, it will expect `start_shifting=0` for that row and only expect 1 on the following row. That is the classic Mealy-vs-Moore / registered-vs-combinational confusion. The public spec’s “set start_shifting to 1” plus “sample after the posedge edge has settled” points to the registered interpretation: the output changes as a consequence of the sampled edge, and the checker should compare the post-edge registered value.

A second, related mistake is treating the found state as non-absorbing. Once found, the spec says “forever, until reset.” So every subsequent sampled edge with `reset=0` must keep `start_shifting=1`, regardless of `data`. A checker that implements only the minimal prefix automaton and then falls back on suffix matching after detection will incorrectly clear the output on some later bit. The found state must be a sink for data transitions, with only synchronous reset leaving it.

A third mistake is reset timing. Reset is active high synchronous, so a mid-cycle `reset=1` must not clear the output until the next sampled posedge. The checker should apply reset only at the sampled edge, with reset priority over data. If it models reset as asynchronous or lets a mid-cycle reset change the expected output for the current row, it will disagree with a correct DUT.

Short worked example: state `110`, sampled posedge with `data=1`, `reset=0` → enter found, post-edge `start_shifting=1`. Then mid-cycle `reset=1` occurs before the next posedge. The correct expectation for the current row remains `start_shifting=1`; only at the next sampled posedge does reset clear the state and output. A checker that reacts to the mid-cycle reset immediately, or that expects detection one cycle late, fails here.

For the final checker: separate sampled-edge updates from mid-cycle input changes, compare only the registered post-edge `start_shifting`, enforce synchronous reset priority at the edge, and make the found state absorbing.
