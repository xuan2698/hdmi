## Reset and Power-Up Behavior

The specification defines exactly one reset mechanism: `areset`, a **positive-edge-triggered asynchronous reset** that clears the 32-bit global history register to zero. Two properties of this definition matter for the checker.

First, the reset is *asynchronous*, meaning it takes effect immediately when `areset` asserts, independent of `clk`. The checker must therefore not assume that the register only changes on a clock edge. If `areset` is driven high between edges, the correct DUT output becomes zero without waiting for the next `posedge clk`. A checker that samples only at edges will still see the right value at the next sample point, but a checker that models the register as edge-only internally may mispredict intermediate states if it ever inspects them. The safe rule: treat `areset = 1` as forcing `predict_history = 0` for any sample taken while it is asserted, and treat the first sample after deassertion as starting from zero.

Second, the spec says nothing about power-up state other than through reset. There is no defined initial value for the register before the first `areset`. The checker should therefore **not** compare against an assumed power-up value; it should either drive `areset` at the start of the stimulus (the normal protocol-seed approach) or ignore outputs until the first reset has been observed. Any expected-value model should be initialized to zero only *because* a reset was applied, not because zero is assumed at time zero.

The interaction of `areset` with the other inputs is deliberately underspecified beyond "reset wins." The spec does not say what happens to a simultaneous `predict_valid` or `train_mispredicted` during reset; the only defensible assertion is that the output is zero. The checker should avoid constructing rows where reset and a prediction/training coincide unless it is willing to accept only the zero outcome, and it should not infer any "queued" update that survives reset.

A useful consequence for the final checker: because reset is asynchronous and the only defined power-up path, the cleanest harness is to assert `areset` for at least one sample at the beginning, then release it and begin the directed rows. This guarantees a known starting history of zero and removes any dependence on undefined initial state. It also means the very first post-reset prediction row has a fully determined expected value, which is exactly what the priority/source/LSB discrimination rows need.

Worked example (reset context): if the checker begins with `predict_history` unknown, asserts `areset = 1` for one sample, then deasserts and applies `predict_valid = 1, predict_taken = 1` with no training, the expected next state is `(0 << 1) | 1 = 0x0000_0001`. Without the initial reset, that expectation would be unjustified, since the pre-reset history is undefined. This is why the reset row belongs first in the directed sequence, not merely as an isolated asynchronous test.
