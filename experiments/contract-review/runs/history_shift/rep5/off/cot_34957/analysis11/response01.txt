**Distinguishing input analysis**

The key distinguishing scenario for this 32-bit global history shift register is a simultaneous prediction and misprediction, where the two data sources disagree. The public spec states that `train_mispredicted` has priority over `predict_valid`, and that the loaded value is `{train_history[30:0], train_taken}` — not a shift of the current `predict_history`. A checker must therefore verify three independent things at once in such a row: (1) the training path wins over the prediction path, (2) the shift source is `train_history` rather than the current register, and (3) `predict_taken` is ignored entirely.

Consider a row where the current `predict_history` is some value P, `predict_valid = 1`, `predict_taken = 0`, `train_mispredicted = 1`, `train_taken = 1`, and `train_history = T` with T ≠ P. The correct next value is `((T << 1) | 1) & 0xFFFF_FFFF`. Several plausible-but-wrong implementations diverge here:

- A prediction-first implementation that then applies training would still be correct if training truly overwrites, but an implementation that lets prediction win would produce `((P << 1) | 0) & 0xFFFF_FFFF`, which differs whenever P ≠ T or the low bits differ.
- An implementation that ORs the two paths would produce a value combining bits of both P and T, generally wrong.
- An implementation that shifts the current register on the training path (using `predict_history` instead of `train_history`) would produce `((P << 1) | train_taken) & 0xFFFF_FFFF`, wrong whenever P ≠ T.
- An implementation that uses `predict_taken` instead of `train_taken` on the training path would produce the wrong LSB.

To make all four failure modes observable in a single row, choose P and T with different high bits and set `predict_taken ≠ train_taken`. For example, let `predict_history = 0x8000_0000`, `train_history = 0x0000_0000`, `predict_taken = 0`, `train_taken = 1`, with both `predict_valid` and `train_mispredicted` high. The correct next value is `((0x0000_0000 << 1) | 1) & 0xFFFF_FFFF = 0x0000_0001`. A prediction-wins bug gives `((0x8000_0000 << 1) | 0) & 0xFFFF_FFFF = 0x0000_0000`. A wrong-source bug (shifting P) gives `((0x8000_0000 << 1) | 1) & 0xFFFF_FFFF = 0x0000_0001` — coincidentally equal here, so this particular pair does not separate the wrong-source bug; the checker should pick P and T whose shifted results differ, e.g. `predict_history = 0x4000_0000`, `train_history = 0x0000_0001`, `train_taken = 0`, `predict_taken = 1`. Correct: `((0x0000_0001 << 1) | 0) = 0x0000_0002`. Wrong-source: `((0x4000_0000 << 1) | 0) = 0x8000_0000`. Wrong-LSB: `0x0000_0003`. Prediction-wins: `0x8000_0001`. All four differ, so one row separates every candidate bug.

**Second checker point: masking.** Both update expressions must be truncated to 32 bits. With `predict_history = 0x8000_0000`, `predict_valid = 1`, `predict_taken = 1`, and no misprediction, the correct next value is `0x0000_0001`, not the 33-bit `0x1_0000_0001`. The checker should include high-bit cases on both the prediction and training paths, since an unmasked shift on either path yields a 33-bit intermediate that a naive comparison would flag.

**Reset.** When `areset` is sampled high, force `predict_history = 0` regardless of the other controls; the spec does not define combined behavior, so the checker should not require any particular interaction beyond zeroing.

**Priority summary for the checker.** Evaluate in order: if `areset`, next = 0; else if `train_mispredicted`, next = `((train_history << 1) | train_taken) & 0xFFFF_FFFF`; else if `predict_valid`, next = `((predict_history << 1) | predict_taken) & 0xFFFF_FFFF`; else hold. The single most valuable distinguishing row is the simultaneous predict-and-mispredict case with P, T, and the two taken bits chosen so that all four buggy variants produce distinct values.
