**Reset and power-up behavior**

The public specification defines `areset` as a positive-edge-triggered asynchronous reset that clears the 32-bit global history shift register to zero. For the final Python checker, the important consequence is that reset is not sampled like an ordinary synchronous input. When `areset` is asserted, the reference model should force the history state to zero immediately, without requiring a rising clock edge and without waiting for the next sampled input tuple. The checker should therefore permit `predict_history` to become zero as soon as reset is active, and it should not flag a mismatch merely because the transition to zero did not coincide with a clock edge.

After reset is released, the next sampled rising edge must treat the zero state as the prior history. If neither `predict_valid` nor `train_mispredicted` is asserted at that edge, the history remains zero. If `predict_valid` is asserted, the zero history is shifted and `predict_taken` is inserted at the LSB side. If `train_mispredicted` is asserted, the misprediction load takes precedence and the new history is formed from `train_history` concatenated with `train_taken`, regardless of the zero prior state. The checker should not require an extra idle clock edge after reset before accepting a legitimate prediction or training update; it only needs to ensure that the post-reset state was zero before that update is applied.

Power-up behavior is less explicit than reset behavior. The specification does not define a guaranteed initial value for the history register before any reset or clocked update. A robust checker should therefore avoid assuming a particular power-up history unless the testbench explicitly applies `areset`. In practice, the reference model can initialize to zero for convenience, but comparisons should be gated or synchronized so that an undefined pre-reset state does not cause false failures. Once `areset` has been observed, the zero state is well defined and subsequent behavior can be checked strictly.

The asynchronous nature of reset also interacts with mid-cycle input changes. Because optional mid input changes occur after sampling and before the other edge, a change on `areset` during that window must be handled according to its asynchronous semantics, not deferred to the next rising edge. If `areset` becomes active after a rising edge has been sampled, the checker should immediately force the reference history to zero and expect the output to reflect that reset. Inputs that changed after the sampled edge, such as `predict_taken` or `train_history`, must not retroactively affect the state that was just captured; they become the inputs for the next rising edge.

A short worked example illustrates the priority and reset interaction. Suppose the history is zero and `areset` is released. At the next rising edge, `predict_valid = 1`, `predict_taken = 1`, and `train_mispredicted = 0`. The new history should have only bit 0 set. If instead `train_mispredicted = 1`, `train_taken = 0`, and `train_history` has nonzero upper bits at that same edge, the prediction is ignored and the new history is the concatenation of `train_history` and `train_taken`. The checker should apply the misprediction priority before comparing the registered output, and it should ensure that any asynchronous reset assertion observed in the interim forces the reference state to zero immediately.
