The timing analysis hinges on the distinction between the sampled edge and the mid-cycle interval. Each row drives its inputs before the sampled posedge, and the checker samples after that edge has settled. Any optional mid-input changes occur after sampling and before the opposite edge, then carry into the next row. Consequently, the reference model should treat the values present at the sampled posedge as the sole basis for the next state. Mid-cycle transitions must not retroactively alter the state computed for the just-sampled edge; they only affect the following sampled edge. This is especially important for `train_history`, which is a 32-bit input that may change between edges. The checker must latch or otherwise capture the pre-edge values it intends to use, then compute the next state from those captured values, rather than reading live inputs after the edge when mid-cycle changes may already have occurred.

The public specification's priority rule is strict: when `train_mispredicted=1`, the next state is exactly `{train_history[30:0], train_taken}`, regardless of `predict_valid` and `predict_taken`. The prediction inputs are fully ignored for that edge, not partially applied. This is the highest-value behavior for the final Python checker to encode. A common incorrect implementation might shift in `predict_taken` and then overwrite only some bits, or might combine the two paths. The checker should therefore test the simultaneous case explicitly: `train_mispredicted=1` together with `predict_valid=1` and a `predict_taken` value that differs from `train_taken`. The expected next state must depend only on `train_history` and `train_taken`.

A second key point is that `train_history` is an independent input, not the current register value. The checker must not assume `train_history` equals the pre-edge `predict_history`. The misprediction load uses the supplied 32-bit `train_history`, drops its MSB, shifts left, and appends `train_taken` at bit 0. A testbench can drive `train_history` independently, so the reference must follow the input exactly.

Reset must be checked first. `areset` is asynchronous and positive-edge triggered, and the prose treats a high `areset` at the sampled edge as immediately authoritative: the reference becomes zero and all other inputs are irrelevant. The checker should test `areset` before the priority chain. If the testbench starts with `areset` high, the reference should be zero before the first sampled edge; otherwise initialize the reference to zero and let the first observed reset establish it.

For the non-reset case, the order is: if `train_mispredicted`, load `{train_history[30:0], train_taken}`; else if `predict_valid`, shift in `predict_taken` as `{old_history[30:0], predict_taken}`; else hold. The output `predict_history` is the post-edge register value, so the checker computes the next state from the pre-edge reference and compares all 32 bits after the edge settles.

Worked example: suppose the pre-edge reference is `0x1234_5678`. With `areset=0`, `predict_valid=1`, `predict_taken=1`, and `train_mispredicted=0`, the next state is `0x2468_ACF1`. If instead `train_mispredicted=1` and `predict_valid=1` occur together, the checker must ignore `predict_taken` and use `{train_history[30:0], train_taken}`. This single-edge distinction is the highest-value test for catching an incorrect priority implementation.
