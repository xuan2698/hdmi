The timing model here is a single synchronous update point per rising clock edge, with an asynchronous reset that can override that update. All the interesting behavior is decided by the combination of inputs present at the sampled edge, so the checker should think in terms of "what is the next state given this edge's inputs and the current `predict_history`?" rather than in terms of intermediate combinational values. The inputs `predict_valid`, `predict_taken`, `train_mispredicted`, `train_taken`, and `train_history` are all driven before the edge and are stable across it; `predict_history` is the registered output that settles after the edge. Mid-cycle changes, if any, occur after sampling and before the next edge, and they only matter insofar as they set up the inputs for the following sampled edge. There is no combinational path from inputs to `predict_history` that the checker needs to model; the output only changes on an edge (or on an asynchronous reset assertion).

The priority order at a sampled edge is the crux. Asynchronous reset dominates everything: if `areset` is asserted at the edge, the next `predict_history` is zero regardless of prediction or training inputs. Absent reset, `train_mispredicted` dominates `predict_valid`. When `train_mispredicted` is high, the next state is `(train_history << 1) | train_taken`, i.e., the recorded pre-branch history shifted left with the actual outcome inserted at the LSB. This is a load of a supplied value, not a shift of the current register, so the checker must drive `train_history` to a pattern that differs from `predict_history` in many bits; otherwise a buggy "shift current history" implementation would coincidentally match. When only `predict_valid` is high, the next state is `(predict_history << 1) | predict_taken`. When neither is high, the register holds.

The combined-edge case is the highest-value probe because it exercises both the priority rule and the load semantics simultaneously. Consider `predict_history = 0x0000_0001`, `predict_valid = 1`, `predict_taken = 1`, `train_mispredicted = 1`, `train_history = 0x0000_0003`, `train_taken = 0`, `areset = 0`. The correct next state is `(0x3 << 1) | 0 = 0x0000_0006`. A prediction-first-then-load implementation that shifts the current history would land on `0x0000_0003`; an implementation that ignores `train_history` and shifts `predict_history` would land elsewhere again. Because these candidate values are all distinct, one edge discriminates among the plausible bugs. The checker should also include a variant with `areset = 1` on the same combined edge and expect zero, catching implementations that let training override reset or that only clear the LSB. Finally, note that `predict_history[0]` is the youngest branch direction, so the shift direction is toward higher bit indices with new bits entering at bit 0; a checker that reverses this will fail the shift probes even when priority is correct.
