# Reset and Power-Up Behavior Analysis

The specification defines `areset` as a positive-edge-triggered asynchronous reset that clears the 32-bit global history shift register to zero. This single sentence carries several distinct obligations for the final Python checker, and they interact with the priority logic in ways that are easy to get subtly wrong.

**Asynchronous assertion, edge-triggered semantics.** "Positive edge triggered asynchronous reset" means the reset takes effect immediately when `areset` rises, without waiting for a clock edge, but the *deassertion* is synchronized to the clock (the register only leaves reset on a posedge where `areset` is low). For a checker that samples after each posedge, the practical consequence is that any row where `areset` is high at the sampling point must yield `predict_history == 0`, regardless of what else is happening. The checker should not attempt to model the intra-cycle timing of the asynchronous assertion; it only needs to confirm that the sampled output is zero whenever the sampled `areset` is high.

**Reset has absolute priority.** The next-state function is a strict if/else-if chain: `areset` first, then `train_mispredicted`, then `predict_valid`, then hold. The checker must verify that reset overrides *both* the misprediction load and the prediction shift. A row that asserts `areset`, `train_mispredicted`, and `predict_valid` simultaneously must still produce zero. This is the cleanest priority test and should be included explicitly, because a model that computes the misprediction value and then conditionally zeroes it can pass most rows while failing this one if the ordering is inverted.

**Power-up is unspecified.** The spec says nothing about the register's value before the first reset. The checker must not assume zero at time zero. Either the testbench drives `areset` before any observation, or the checker's reference model is initialized to whatever the testbench assumes. The safest pattern is to require a reset row early and treat all pre-reset outputs as don't-care. If the checker instead hard-codes a zero initial state, it may produce spurious mismatches on the first sampled edge of a testbench that starts from an unknown or nonzero value.

**Sampling discipline.** Because reset is asynchronous, a mid-row change of `areset` after the sampling edge belongs to the next row. The checker should capture all inputs at the sampling point, evaluate the priority chain on those captured values, and compare to the output sampled at that same edge. A glitch on `areset` between edges must not retroactively zero the just-sampled transition, and likewise a late `train_mispredicted` must not alter the prediction that was already committed.

**Worked example.** Suppose the register currently holds `32'h0000_0005`, and at one edge the captured inputs are `areset=1`, `train_mispredicted=1`, `train_taken=0`, `train_history=32'hFFFF_FFFF`, `predict_valid=1`, `predict_taken=1`. The correct next state is `32'h0000_0000` — reset wins over both the misprediction load (which would have produced `32'hFFFF_FFFE`) and the prediction shift (which would have produced `32'h0000_000B`). A checker that applies the misprediction branch first and only then checks reset, or that merges the prediction into the misprediction path, will fail this row.

The key takeaway for the final checker: model the next state as a single priority-ordered selection over captured inputs, with `areset` at the top, and never assume a defined power-up value.
