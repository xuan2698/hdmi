The key point for the final checker is that reset must dominate the capture term on the same sampled edge, and the previous-input register must be updated atomically with the output register. The public spec says the output remains 1 until the register is reset, with reset active-high and synchronous. That means at a sampled positive edge where `reset=1`, the next `out` is 0 regardless of whether the current `in` fell relative to the stored previous input. The fall detector is not a separate asynchronous event; it is a per-edge comparison between the current sampled `in` and the previous sampled `in`, accumulated into `out`.

The subtlety is that the detector has two state elements: `out` and `prev_in`. If an implementation clears `out` on reset but does not also refresh `prev_in` to the current sampled `in`, the next edge can either fabricate a 1→0 transition that actually occurred during the reset edge or suppress a real one. Either way the checker will disagree with a reference that updates both state elements atomically per edge.

The same mistake appears in the opposite direction if the capture term is ORed into `out` before reset is applied. On an edge where `reset=1` and the current `in` has fallen relative to `prev_in`, the spec requires `out=0` because the register is being reset. A naive ordering that computes `out | (prev_in & ~in)` first and then conditionally clears will still produce 0 only if reset is applied last; if reset is applied first and capture second, it produces 1. The final checker should therefore encode a single per-edge update: read `reset` and `in` once, compute the next `out` as reset-dominates, and set `prev_in` to the current `in` in the same step. It should not model asynchronous reset, power-on values, or mid-cycle events, since the spec says mid-cycle changes occur after sampling and are carried to the next row.

A short worked example for one bit: suppose `prev_in=1`, `out=0`, and at a sampled edge `in=0` with `reset=1`. Correct next state is `out=0`, `prev_in=0`. A checker that ORs capture before reset yields `out=1`, which is wrong. A checker that clears `out` but leaves `prev_in=1` is wrong on the following edge if `in` remains 0, because it will report a fall that already occurred during reset. The final checker should make this ordering explicit and include reset-adjacent falling edges in its test traces.
