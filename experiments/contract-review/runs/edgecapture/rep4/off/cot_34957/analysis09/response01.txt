The public specification defines a 32-bit edge detector that captures 1→0 transitions on each bit of `in` and holds them in `out` until a synchronous active-high reset clears them. The clock is `clk`, and all sampling is described as occurring after the positive edge has settled. Inputs are driven before the sampled edge; optional mid-cycle input changes occur after sampling and before the next edge, and are carried forward to the start of the next row. The protocol seed is 20261123. Only `reset` (1 bit) and `in` (32 bits) are inputs; `out` is 32 bits.

The state that matters is the previous sampled input, call it `prev_in`, plus the held output `out`. At each sampled positive edge, the model should treat the edge as one atomic update. The capture condition for bit `i` is `prev_in[i] & ~in[i]`: the previous sampled value was 1 and the current sampled value is 0. A captured bit sets the corresponding `out[i]` to 1 and keeps it there. Reset is synchronous and active-high, so it is evaluated only at the sampled edge. When `reset=1`, `out` must be cleared to 0, and the capture term must not override that clear. At the same edge, `prev_in` should be refreshed with the current sampled `in`, even during reset. That refresh is essential: reset clears the output but must not freeze or skip history.

The subtle failure mode is ordering. If a checker computes `prev_in & ~in` and ORs it into `out` before applying reset, then a reset cycle that coincides with a 1→0 transition will incorrectly leave `out=1`. The correct priority is reset first: `next_out = 0 if reset else (out | (prev_in & ~in))`. A second failure mode is resetting `out` but not updating `prev_in` on that edge. Then history becomes stale: a fall that occurred during reset can be captured spuriously on the following cycle, or a genuine fall can be missed because the checker's history diverges from the sampled input. These bugs are easy to miss in short traces and tend to surface only when reset is adjacent to a transition.

Worked example for one bit: suppose `prev_in=1`, `out=0`, and at a sampled edge `in=0` with `reset=1`. Correct behavior is `out=0` and `prev_in=0`. A checker that ORs capture before reset yields `out=1`, which is wrong. A checker that resets `out` but leaves `prev_in=1` is wrong on the next edge: if `in` stays 0, it captures a fall that already happened during reset and sets `out=1` when the spec expects 0.

For the final Python checker, the highest-value rule is to model each sampled positive edge as one atomic update: read `reset` and `in`, compute `next_out = 0 if reset else (out | (prev_in & ~in))`, then set `prev_in = in`. Compare the full 32-bit `out` after each sampled edge, ignore mid-cycle changes entirely, and do not model asynchronous reset, power-on state, or intermediate event-driven updates. This ordering — reset dominates, history always updates — is the point most likely to be encoded incorrectly, so it should be explicit and tested with reset-adjacent transitions.
