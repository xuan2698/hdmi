The key distinguishing case for the final checker is a reset edge that coincides with a 1→0 input transition, because that is where reset priority and `prev_in` updating interact. Consider a single bit with old state `prev_in=1`, `out=0`, and a sampled edge where `in=0` and `reset=1`. The correct simultaneous update is `out=0` (reset dominates; the fall is not captured) and `prev_in=0` (the new input is loaded even though reset is active). A checker that applies the capture term after clearing reset would produce `out=1`, wrongly recording a fall during reset. A checker that clears `out` but leaves `prev_in` stale at 1 would also be wrong: on the next non-reset edge with `in=0`, it would fabricate a fall from the stale 1, even though the actual 1→0 change happened on the reset edge and should have been discarded. The mirror error appears if `in` rises right after reset: stale `prev_in=1` can suppress a genuine later fall, because the checker thinks the bit was already high.

This shows why the checker must sample `reset` and `in` once per row, compute `next_out = reset ? 0 : (out | (prev_in & ~in))` and `next_prev_in = in` from the old state, then commit both together. Reset is synchronous and evaluated at the same edge as the input sample, not as an asynchronous override between edges. The capture term must never be applied after a reset clear, and `prev_in` must never remain stale across a reset edge.

A useful short trace: start with `prev_in=1`, `out=0`. Edge 1: `reset=1`, `in=0` → next `out=0`, `prev_in=0`. Edge 2: `reset=0`, `in=0` → next `out=0`, `prev_in=0` (no fabricated fall). Edge 3: `reset=0`, `in=1` → next `out=0`, `prev_in=1`. Edge 4: `reset=0`, `in=0` → next `out=1`, `prev_in=0` (genuine fall captured). This trace distinguishes correct reset priority and correct history loading from both common bugs.

For the final Python checker, the practical point is to treat reset-adjacent edges as ordinary sampled transitions with reset priority, and to include traces where a 1→0 change coincides with reset, where reset is followed immediately by another 0, and where reset is followed by a rise then fall. Ignore power-on values, asynchronous reset behavior, and mid-cycle changes, since mid-cycle input changes occur after sampling and are carried to the start of the next row. The invariant to enforce is: at every sampled edge, `prev_in` becomes exactly the sampled `in`, and `out` is cleared if `reset` is high; otherwise it is the old `out` ORed with the old-`prev_in`/new-`in` fall term.
