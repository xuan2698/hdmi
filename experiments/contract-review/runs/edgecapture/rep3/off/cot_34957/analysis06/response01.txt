One plausible implementation mistake is to treat the “previous input” for the falling-edge detector as the most recent value seen anywhere in the cycle, rather than the value that was actually sampled at the preceding clock edge. The public spec defines capture in terms of clock-cycle samples: a bit is captured when the input is 1 in one sampled cycle and 0 in the next sampled cycle. Mid-cycle changes are explicitly after sampling and are carried to the start of the next row; they are not themselves sampled values. A checker that updates its remembered input from a mid-row transition can therefore compare the wrong pair of values and either miss a real 1-to-0 event or invent a spurious one.

A short worked example makes the distinction concrete. Suppose at row N the sampled values are `reset=0`, previous sampled `in[0]=1`, current sampled `in[0]=0`. The capture condition is true, so `out[0]` becomes or remains 1. After sampling, a mid-row change drives `in[0]` back to 1 before row N+1. At row N+1 the sampled values are `reset=0`, `in[0]=1`. The correct previous sampled value for row N+1 is the row-N sampled 0, so there is no 1-to-0 capture at row N+1. If the checker instead used the mid-row 1 as “previous,” it would still see no capture here, but the same error in the reverse direction—using a mid-row 0 as previous when the sampled row was 1—would create a false capture. The safe discipline is to compute capture from the sampled current input and the previously sampled input, then update the remembered input to the sampled current input only.

This matters for the final Python checker because the checker should model the sampled sequence, not every intermediate value. It should keep a per-bit previous sampled input, evaluate `prev & ~curr` at each sampled edge, apply synchronous active-high reset with priority over capture, and then carry the sticky output forward. It should also avoid assuming a defined power-up state for `out` unless the testbench guarantees one; before any reset, outputs may be unspecified. The key useful point is that “previous input” must mean the last sampled input, never a mid-row value.
