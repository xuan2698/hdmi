The public interface is a 32-bit synchronous capture block with a single-bit active-high synchronous reset, a 32-bit input `in`, and a 32-bit output `out`, all sampled on the rising edge of `clk`. The widths are asymmetric in role but symmetric in bit position: bit *i* of `out` is the sticky capture flag for bit *i* of `in`, and the reset is a single scalar that clears all 32 output bits simultaneously. There are no per-bit resets, no enables, and no other control inputs, so the only boundary conditions that matter are the two values each bit can take (0/1) and the two reset states (0/1). The interesting boundary is not numeric range but temporal: the transition 1→0 on a given input bit, the persistence of `out` across cycles where no such transition occurs, and the interaction of reset with the internal history.

The specification defines capture as detecting a 1 in one cycle followed by a 0 in the next, per bit. That is a falling-edge detector on each input bit, with the detected event latched into `out`. "Capture" is explicitly sticky: once a bit of `out` is set, it stays set until reset, regardless of subsequent input activity. This means `out` is not a function of the current input alone; it is an accumulator. A checker that recomputes `out` each cycle from `in` and a stored previous value, without carrying forward the prior `out`, will lose earlier captures and diverge on any sequence with more than one isolated falling edge.

The reset is described as an output-only clear. This is the crux. Reset forces `out` to zero on the sampled edge, but it does not clear the internal previous-input history used to detect transitions. The history update happens unconditionally after the capture decision, independent of reset. Consequently, asserting reset while driving 1s, then deasserting and driving 0s, must still produce a capture on the first post-reset 0, because the 1 was recorded in history during the reset cycle. A checker that treats reset as a full state reset—clearing both `out` and the stored previous input—will expect no capture there and will report a false mismatch against a correct design. This is the single most likely divergence between a hand-written checker and the reference, and it deserves a dedicated directed test: reset high with all-ones input for one edge, reset low with all-zeros input on the next, expecting all 32 output bits to set.

A second trap is power-up. Neither `out` nor the internal previous-input state has a specified initial value. Expectations before the first reset edge are therefore unspecified, and a checker must not assert on them. Assertions should be gated until an initial reset edge has occurred, which establishes `out=0` and a known history equal to the input sampled at that edge. Only after that gate should the checker compare `out` cycle by cycle.

For the final Python checker, the actionable summary is: maintain a persistent per-bit previous-input vector updated on every sampled edge regardless of reset; compute the per-bit capture as previous-input AND NOT current-input before applying reset; apply reset as an output-only clear (zero `out` when reset is high, otherwise OR the capture into the existing `out`); gate all assertions on an initial reset edge; and include the reset-with-ones-then-zeros scenario across all 32 bits to expose history-clearing bugs.
