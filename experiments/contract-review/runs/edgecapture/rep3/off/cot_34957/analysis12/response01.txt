One likely implementation mistake is to treat reset as a full state flush: clearing both the output and the remembered previous input on a reset edge. That looks natural if reset is described as “active high synchronous reset,” and it can pass many simple tests because the output is forced to zero anyway. But it changes the meaning of the next cycle after reset. The public behavior is edge-based: a 1→0 transition is captured when the input was 1 at one sampled edge and 0 at the next. Reset affects the output by clearing it, but the specification does not say that reset erases the input history used to detect the next transition. If the remembered input is cleared on reset, then a 1 at the reset edge followed by a 0 at the next edge is not seen as a transition, because the design believes the previous input was 0. The correct model remembers the reset-edge input value and can therefore capture a transition immediately after reset.

This is especially important for the final Python checker because it determines the expected output on the first non-reset edge after a reset. A checker built around the buggy “reset clears everything” interpretation will expect no capture there, while a correct model will expect a capture on exactly those bits that were 1 during the reset edge and 0 on the following edge. The checker should therefore avoid treating reset as a reinitialization of all internal history. It should model reset as an override on the output only, while still sampling the input into the previous-value state on every edge, including reset edges.

A second, closely related mistake is to apply reset after computing the capture and then also suppress the memory update. For example, a design might compute `capture = prev & ~curr`, set `out = reset ? 0 : out | capture`, and then update `prev` only when reset is low. That produces the same failure mode: the reset-edge input is lost. The public spec’s timing language supports the stricter interpretation: each row’s values are driven before the sampled edge, and the output is sampled after the edge has settled. So the input at a reset edge is a real sampled value and should become the “previous” value for the next edge.

A short worked example makes the distinction clear. Suppose bit 0 is 1 at a reset edge, and 0 at the next edge with reset low. The correct expected behavior is that the next edge captures the 1→0 transition and sets `out[0]` to 1. A model that cleared the remembered input on reset would expect `out[0]` to remain 0. This single-bit case is a high-value checker test because it isolates reset-edge history handling without depending on multi-bit interactions.

The final checker should therefore maintain a previous-input vector updated on every sampled edge, reset or not; compute per-bit capture as previous AND NOT current; apply reset as an overriding clear to the output only; and begin checking only after an initial reset edge so that unspecified power-up state does not cause false failures. It should also include a multi-bit variant of the same scenario to confirm that every bit’s reset-edge input is remembered independently.
