The public interface is a single-clock synchronous design with one 1-bit input `reset`, one 32-bit input `in`, and one 32-bit output `out`. All signal widths are fixed by the specification: `reset` is exactly 1 bit, while `in` and `out` are each exactly 32 bits. The clock is `clk`, and all sampling is described as occurring after the positive edge has settled. Values shown for a row are driven before the sampled edge; optional mid-row input changes occur after sampling and before the other edge, and are carried forward to the start of the next row. The protocol seed is 20261122, which is relevant only as a deterministic stimulus-generation seed and does not alter the functional behavior.

The boundary values follow directly from those widths. `reset` can only be 0 or 1. Each bit of `in` can be 0 or 1, and each bit of `out` can be 0 or 1. There is no multi-bit arithmetic, no signed interpretation, and no truncation or extension: the 32 input bits map positionally to the 32 output bits. The only state beyond `out` is the previous sampled input vector, which must also be treated as 32 bits. Because the specification does not define a power-up value for `out`, the checker should not assume any particular initial output unless an explicit reset has occurred. The safe interpretation is that `out` is only guaranteed after a sampled reset, and any pre-reset comparison should either be avoided or treated as unspecified.

Functionally, when `reset` is sampled high, all 32 bits of `out` are cleared synchronously at that same edge. Reset has priority over capture. When `reset` is sampled low, each bit independently captures a 1-to-0 transition: the previous sampled input bit was 1 and the current sampled input bit is 0. In Boolean form, the per-bit capture condition is `prev_in[i] & ~curr_in[i]`. If that condition holds, `out[i]` becomes 1 and remains 1 until a later reset. If it does not hold, `out[i]` retains its previous value. Captures are sticky and independent per bit: a transition on one bit does not affect another bit, and a row with no transition on a given bit does not clear that bit. Repeated 1-to-0 events on the same bit while `out[i]` is already 1 are idempotent; they do not toggle or clear it.

The critical timing point for the final Python checker is the state-update discipline. After computing the output update for a sampled row, `prev_in` must be updated from the sampled row value, not from any mid-row value. Mid-row input changes occur after sampling and before the other edge, and they are carried to the start of the next row. They must not be used to infer a transition in the current row. In checker terms, a mid-row change can affect the next row’s capture calculation, but it cannot create or suppress a capture in the row where it occurs. Reset is synchronous, not asynchronous: it is applied at the sampled edge together with the capture logic, with reset taking priority.

A short worked example: suppose at row N the sampled values are `reset=0`, `prev_in[0]=1`, `curr_in[0]=0`, and `out[0]=0`. At that edge, `out[0]` becomes 1. If row N+1 samples `curr_in[0]=0` with `reset=0`, `out[0]` remains 1. If row N+2 samples `reset=1`, all `out` bits clear at that edge regardless of input transitions. If a mid-row change occurs between rows N and N+1, it only affects the sampled value used for row N+1; it does not retroactively change row N’s capture.

For the final Python checker, the most useful focus is therefore: maintain `prev_in` updated only from sampled row values; compute capture as `prev_in & ~curr_in` per bit when `reset` is low; apply reset as a synchronous clear at the same sampled edge with priority over capture; keep `out` sticky between captures; and avoid assuming a defined power-up state without an explicit reset. Do not let mid-input changes create or suppress a capture in the row where they occur, and do not treat reset as asynchronous. This timing and state-update discipline is the core of matching the public specification.
