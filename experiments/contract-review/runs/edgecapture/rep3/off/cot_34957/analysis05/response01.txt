The key distinguishing point in this spec is the interaction between **sticky per-bit capture** and **synchronous reset priority**, combined with the rule that `prev_in` is updated only from the *sampled* row value. A naive checker often gets one of these wrong: it may treat reset as asynchronous (clearing `out` immediately when `reset` is high, even between edges), or it may update `prev_in` from a mid-row value, which can fabricate or erase a 1-to-0 transition in the wrong row.

Consider a short scenario that separates these behaviors. Suppose `out[0]` is already 1 from an earlier capture, and at row N the sampled values are `reset=0`, `prev_in[0]=1`, `curr_in[0]=0`. The capture condition `prev_in & ~curr_in` is true, so `out[0]` stays 1 (idempotent). Now suppose a mid-row change drives `in[0]` back to 1 before row N+1 is sampled, and row N+1 samples `reset=0`, `curr_in[0]=1`. A checker that incorrectly used the mid-row value as `prev_in` might think there was no 1-to-0 transition at row N+1, which is fine here, but the same mistake in the opposite direction—using a mid-row 0 as `prev_in` when the sampled row had 1—could create a spurious capture. The correct discipline is: at each sampled edge, compute `capture = prev_in & ~curr_in` using the sampled `curr_in`, then set `prev_in = curr_in` (the sampled value), never the mid-row value.

Reset priority matters in the same example. If row N+2 samples `reset=1` while `curr_in[0]=0` and `prev_in[0]=0`, a checker that applies capture before reset might leave `out[0]` unchanged (no capture anyway), but if `prev_in[0]=1` and `curr_in[0]=0` at that same edge, capture would want to set `out[0]=1` while reset wants to clear it. The spec says reset wins: `out` becomes 0 at that edge. An asynchronous-reset checker would clear `out` as soon as `reset` rises, possibly before the sampled edge, which can differ if `out` was set by a capture at the same edge—synchronous reset with priority means the capture is suppressed, not that the clear happens earlier.

Finally, the checker must not assume a defined power-up state for `out`. Without an explicit reset row, `out` is unspecified; the checker should either start from an unknown/zero convention only if the testbench guarantees it, or treat the first rows as don't-care until a reset is observed. Sticky capture means a single 1-to-0 event sets a bit and it stays set across many rows with no further transitions, so the checker must carry `out` forward row by row rather than recomputing it from the current row alone. These three points—sampled-only `prev_in`, synchronous reset priority, and sticky carry-forward—are the core of matching the public spec.
