The public specification defines a falling-edge capture in terms of **sampled clock-cycle values**, not every value that appears on the input wires. For each bit of the 32-bit input, the detector must recognize the pattern where the bit is 1 in one sampled cycle and 0 in the next sampled cycle. When that pattern occurs, the corresponding output bit is set to 1 and remains 1 until an active-high synchronous reset clears it. The reset is sampled like any other synchronous control: at a rising clock edge, if reset is high, the output register is cleared; otherwise the capture logic is applied.

The timing language in the spec is important. Inputs are driven before the sampled edge, and the sample is taken after the positive edge has settled. Optional mid-cycle input changes occur **after** sampling and before the other edge, and those changes are carried to the start of the next row. That means a mid-cycle transition is not itself a sampled value. It may affect what value is present when the next row begins, but it must not be treated as the “previous input” for edge detection. The previous input for a given sampled edge is the value that was actually sampled at the preceding clock edge.

A common implementation mistake is to update the remembered input from any observed change, including a mid-row change. That makes the detector compare the current sampled value against a value that was never sampled at a clock edge. Such a checker can miss a genuine 1-to-0 event or invent a spurious one. The correct discipline is: at each sampled edge, compute the capture condition from the current sampled input and the previously sampled input; then update the remembered input to the current sampled input only. Mid-row values should not enter the remembered state.

A short worked example clarifies the distinction. Suppose at row N the sampled values are reset=0, previous sampled in[0]=1, current sampled in[0]=0. The capture condition is true, so out[0] becomes or remains 1. After sampling, a mid-row change drives in[0] back to 1 before row N+1. At row N+1 the sampled values are reset=0, in[0]=1. The correct previous sampled value for row N+1 is the row-N sampled 0, so there is no 1-to-0 capture at row N+1. If a checker instead used the mid-row 1 as “previous,” it would still see no capture in this particular case, but the same error in the reverse direction—using a mid-row 0 as previous when the sampled row was 1—would create a false capture. The safe rule is to compute capture from sampled current and previously sampled input, then update the remembered input to the sampled current input only.

For the final Python checker, the useful point is that the model should track the **sampled sequence**, not every intermediate value. It should keep a per-bit previous sampled input, evaluate `prev & ~curr` at each sampled edge, apply synchronous active-high reset with priority over capture, and then carry the sticky output forward. It should also avoid assuming a defined power-up state for `out` unless the testbench guarantees one; before any reset, outputs may be unspecified. The key requirement is that “previous input” means the last sampled input, never a mid-row value.
