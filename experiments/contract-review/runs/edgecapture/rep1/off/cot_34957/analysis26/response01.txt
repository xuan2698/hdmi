Reset and power-up behavior are the two places where a naive checker most often diverges from the public specification, so they deserve separate treatment.

Reset is synchronous and active high. On any sampled row where `reset=1`, the output must be forced to 0 for all 32 bits, and no capture may be credited on that row. The subtle requirement is that the input history must still be updated to the sampled `in` value on that same reset row. If an implementation (or a checker) freezes history during reset, the next non-reset row will compare against a stale pre-reset value and can fabricate a 1→0 capture that never occurred. The checker must therefore treat reset as clearing the output while still advancing the per-bit previous-input state.

A short worked example for one bit: entering a sampled row with history=1, reset=1, and sampled in=0. Correct behavior: out is forced to 0, no capture is credited, and history becomes 0. On the following row with reset=0 and in=0, history=0 and current=0, so no capture occurs and out remains 0. A buggy implementation that leaves history at 1 through the reset row will, on that next row, see history=1 and in=0, falsely credit a 1→0 capture, and drive out=1. The checker catches this by updating history on reset rows.

Power-up is unconstrained for `out`. The checker must not require out=0 before the first reset row. It may begin tracking history from the first sampled input, but output assertions should only begin after a reset row has established a known zero state. Before that, any output value is acceptable.

For the final Python checker, keep history and output as separate state. On each sampled row: if reset is high, force out=0, do not credit capture, but set history to the sampled in. If reset is low, credit capture only where history=1 and sampled in=0, leave other bits unchanged, then set history to the sampled in. Ignore mid-row changes for the current row, and leave output unconstrained until the first reset row.
