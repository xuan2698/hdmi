The public specification defines a 32-bit synchronous capture circuit with active-high synchronous reset. The key timing rule is that the input vector is sampled at the positive clock edge, and the capture decision for a given row must be based on the sampled value at that edge compared with the previously sampled value. Optional mid-row input changes occur after sampling and before the next edge; they are carried forward to the start of the next row and must not influence the current row's capture decision. This distinction matters for the final Python checker: the checker should model the sampled `in` value per row, not any later mid-row value, when deciding whether a 1→0 transition occurred.

Reset is synchronous and active high. When `reset` is sampled high on a row, the output must be forced to zero and no capture may be credited on that row. Crucially, the input history must still be updated to the sampled `in` value on that reset row. If an implementation freezes history during reset, it can invent a capture on the following non-reset row. A short worked example shows the failure. Suppose one bit has history=1 before a sampled row. On that row, `reset=1` and sampled `in=0`. Correct behavior: `out` becomes 0, no capture is credited, and history becomes 0. On the next row, `reset=0` and `in=0`. Since history is 0 and current input is 0, there is no capture, so `out` stays 0. If an implementation instead leaves history at 1 during the reset row, then on the next row it sees history=1 and `in=0`, falsely credits a 1→0 capture, and wrongly drives `out=1`. That is exactly the kind of off-by-one state error the final Python checker should catch.

A related mistake is to let a mid-row input change affect the current row's capture decision. The protocol says optional mid input changes occur after sampling and before the other edge, and are carried to the start of the next row. Therefore the capture comparison for a row must use only the value sampled at the posedge, compared with the previous sampled value. A checker that reads a later mid-row `in` value and compares it to current history would misattribute a transition to the wrong row. The comparison is always previous sampled `in` versus current sampled `in`, both taken at posedges.

Finally, power-up is unconstrained for `out`. The checker should not require `out=0` before the first reset row. It may begin tracking history from the first sampled input, but output assertions should begin only after a reset row has established a known zero state. Before that, any output value is acceptable.

For the final Python checker, the useful implementation point is to keep history and output as separate state. On each sampled row: if `reset` is high, force `out=0`, do not credit capture, but set history to the sampled `in`. If `reset` is low, credit capture only where history=1 and sampled `in`=0, leave other bits unchanged, then set history to the sampled `in`. Ignore mid-row changes for the current row, and leave output unconstrained until the first reset row.
