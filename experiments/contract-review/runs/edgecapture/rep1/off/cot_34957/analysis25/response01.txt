The public spec defines a 32-bit edge detector with synchronous active-high reset. For each bit, the circuit must remember the previous sampled input value and assert the corresponding output bit when that previous value was 1 and the current sampled value is 0. Once asserted, an output bit stays 1 until reset clears it. The checker therefore needs two independent pieces of state: a 32-bit history register holding the last sampled `in`, and a 32-bit output register holding latched captures. These must not be conflated, because reset affects them differently.

Timing is the central issue. The protocol samples after the posedge has settled, and each row's values are driven before the sampled edge. Optional mid-row input changes occur after sampling and before the other edge, and are carried into the start of the next row. Consequently, the 1→0 comparison for a given row must use only the value sampled at that row's posedge against the previous row's sampled value. A mid-row change belongs to the next row's sampled input, not the current one. A checker that reads `in` after a mid-row change and compares it to the current history would credit a transition to the wrong row. The safe rule is: compare previous sampled `in` to current sampled `in`, both taken at posedges; ignore mid-row values for the current row.

Reset handling is the second trap. Reset is synchronous and active high. On a sampled row where `reset=1`, the output must be forced to 0 and no capture may be credited. Crucially, history must still be updated to the sampled `in` on that row. If an implementation freezes history during reset, the next non-reset row compares against a stale pre-reset value and can fabricate a capture. The checker must therefore update history on reset rows even though output is cleared.

A short worked example for one bit: suppose history=1 entering a sampled row with reset=1 and sampled in=0. Correct behavior is out forced to 0, no capture credited, and history becomes 0. On the next row with reset=0 and in=0, history=0 and current=0, so no capture and out stays 0. A buggy implementation that leaves history at 1 during the reset row will, on that next row, see history=1 and in=0, falsely credit a 1→0 capture, and drive out=1. The checker must catch this off-by-one state error by updating history on reset rows.

Power-up is unconstrained for `out`. The checker should not require out=0 before the first reset row. It may begin tracking history from the first sampled input, but output assertions should begin only after a reset row has established a known zero state. Before that, any output value is acceptable.

For the final Python checker, keep history and output as separate state. On each sampled row: if reset is high, force out=0, do not credit capture, but set history to the sampled in. If reset is low, credit capture only where history=1 and sampled in=0, leave other bits unchanged, then set history to the sampled in. Ignore mid-row changes for the current row, and leave output unconstrained until the first reset row.
