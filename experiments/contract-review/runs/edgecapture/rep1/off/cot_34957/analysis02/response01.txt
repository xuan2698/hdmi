**Reset and power-up behavior**

The public specification defines a 32-bit sticky falling-edge detector. For each bit, the output is set when the sampled input bit is 0 in the current cycle and was 1 in the previous sampled cycle. Once set, that output bit remains 1 until an active-high synchronous reset clears it. The reset is synchronous, so it is evaluated at the same sampling edge as the input and output updates. The specification does not describe any asynchronous reset path, so power-up behavior should not be inferred from an asynchronous clear. At power-up, before any reset has been applied, the only defensible checker model is that the state is unspecified unless the testbench drives reset. A final Python checker should therefore avoid assuming a particular initial `out` value or a particular initial "previous input" value unless the test sequence begins with a reset row that establishes both. The cleanest interpretation is that a reset row clears `out` and also establishes the input history used for the next row, so the first post-reset row compares against the input sampled on the reset row.

Because reset is synchronous and active high, a reset row takes effect at that row's sampling edge. The public text says the output remains 1 until the register is reset, which makes reset the clearing event. The safest checker interpretation is that reset dominates the row's update: on a reset row, `out` is cleared, and no capture should be credited on that same row unless the specification explicitly says otherwise. The public specification does not say that a reset row can simultaneously capture a falling edge, so the checker should not combine reset clearing with a new capture in one row. This matters for the final Python checker because a common mistake is to compute the falling-edge condition independently of reset and then OR it into the output after clearing. That would incorrectly allow a reset row to set an output bit. The public spec supports reset as the dominant synchronous action.

The mid-input timing is the other place a checker can go wrong. Optional mid input changes occur after sampling and before the other edge, and are carried to the start of the next row. Therefore, a mid-cycle 1-to-0 change must not set `out` in the current row. It can only affect the next row's sampled input value. The checker should build expected outputs row by row from the row's driven pre-edge `in` and `reset`, using the previous row's sampled `in` as history. It should not scan intra-row waveform events for 1-to-0 edges.

A short worked example: suppose bit 0 of `in` is 1 in row N and 0 in row N+1, with reset low in both rows. At row N+1's sampling edge, the checker sees previous sampled bit 1 and current sampled bit 0, so `out[0]` becomes 1. If instead `in[0]` changes from 1 to 0 only in the middle of row N+1, after that row's sampling edge, then row N+1 still samples 1 and row N+2 samples 0; the capture belongs to row N+2, not row N+1. The sticky behavior then keeps `out[0]` at 1 through later rows until a synchronous reset row clears it.

For the final Python checker, the useful point is to model reset as a synchronous row-level clear that also updates the previous-input history, and to derive captures only from sampled pre-edge values. Power-up should be treated as unspecified unless reset is driven, and mid-row changes should never create a capture in the current row.
