The public specification defines a 32-bit falling-edge detector with sticky capture and active-high synchronous reset. The checker should reason at row granularity: each row supplies the driven values of `reset` and `in` before the sampled posedge, and the expected `out` is the value after that edge has settled. The essential state is the previous sampled input vector, since a capture for bit *i* occurs exactly when the previous sampled bit is 1 and the current sampled bit is 0. The output is sticky: once a bit is captured, it remains 1 across subsequent rows until a reset row clears it.

Reset must be treated as dominant on its row. On a row where `reset` is high, `out` is synchronously cleared to zero. The public specification does not state that a reset row may also capture a falling edge, so the checker should not credit a capture on that same row. This is a common source of checker error: computing the falling-edge condition independently of reset and then OR-ing it into the cleared output would incorrectly allow a reset row to set a bit. The safe interpretation is that reset clears the output and suppresses capture for that row. The previous-input history should still be updated from the row's sampled `in`, because history is about the sampled signal, not about whether a capture was credited.

Mid-row input changes are explicitly outside the current row's capture logic. Optional mid input changes occur after sampling and before the other edge, and are carried to the start of the next row. Therefore, a 1-to-0 transition that happens only in the middle of a row must not set `out` in that row. It can only influence the next row's sampled input value. The checker should not scan intra-row waveform events for falling edges; it should compare consecutive sampled pre-edge input vectors.

A short worked example clarifies the timing. Suppose bit 0 of `in` is 1 in row N and 0 in row N+1, with reset low in both rows. At row N+1's sampling edge, the checker sees previous sampled bit 1 and current sampled bit 0, so `out[0]` becomes 1. If instead `in[0]` changes from 1 to 0 only in the middle of row N+1, after that row's sampling edge, then row N+1 still samples 1 and row N+2 samples 0; the capture belongs to row N+2, not row N+1. The sticky behavior then holds `out[0]` at 1 through later rows until a synchronous reset row clears it.

For the final Python checker, the useful point is to model reset as a synchronous row-level clear that also updates the previous-input history, and to derive captures only from sampled pre-edge values. Power-up should be treated as unspecified unless reset is driven, and mid-row changes should never create a capture in the current row.
