The key modeling point for the final Python checker is to separate three row-level concerns: the sampled input value, the stored previous-input history, and the sticky output state. Each row is evaluated from the values driven before the sampled posedge. The checker should compare the current sampled `in` against the previous sampled `in` to detect 1-to-0 transitions, but it must apply reset semantics and output persistence in the correct order.

Reset is synchronous and active high. On a row where `reset` is sampled high, `out` is cleared to zero at that edge. The public specification does not state that a reset row can simultaneously capture a falling edge, so the checker should treat reset as suppressing capture for that row. This avoids crediting a capture that the specification does not clearly authorize. At the same time, the previous-input history should still be updated from that row’s sampled `in`. History tracks the sampled signal, not whether a capture was credited. If history were frozen on reset rows, a later transition across the reset boundary could be invented or missed.

Power-up is unspecified. The checker should not require `out` to begin at zero, nor should it assume any particular initial output pattern. It may begin tracking previous input from the first sampled row, but it should not enforce output values until a reset row has established a known zero state. After a reset row, `out` is known to be zero synchronously, and subsequent captures set bits sticky until the next reset.

Mid-row input changes must not be used to infer captures in the current row. A mid-row 1-to-0 change occurs after sampling and before the next edge; it affects what the next row samples, not what the current row captured. The checker should therefore derive captures only from the sampled pre-edge values of consecutive rows.

A short worked example: if bit 0 of `in` is 1 in row N and 0 in row N+1, with reset low in both, then at row N+1’s sampling edge the checker sees previous 1 and current 0, so `out[0]` becomes 1 and remains sticky. If instead the 1-to-0 change occurs mid-row N+1 after sampling, then row N+1 still samples 1 and row N+2 samples 0; the capture belongs to row N+2. If row N+1 had reset high, `out` would be cleared and no capture credited on that row, but the sampled 1 would still become history for row N+2.

Thus the final checker should model reset as a synchronous row-level clear that also updates previous-input history, derive captures only from sampled pre-edge values, treat power-up output as unspecified until reset, and never let mid-row changes create a capture in the current row.
