The key distinction for the checker is between **sampled row values** and **intra-row waveform activity**. The public spec says capture is based on the input changing "from 1 in one clock cycle to 0 the next." That phrasing ties detection to consecutive clock-cycle samples, not to arbitrary edges inside a cycle. The mid-row note reinforces this: optional mid input changes occur after sampling and are carried to the start of the next row. So the checker should maintain a previous-sampled-input vector and compare it only against the current row's sampled pre-edge input vector. It should not attempt to infer captures from mid-row transitions.

A second useful point is reset dominance and history update. On a row where `reset` is high, `out` is synchronously cleared to zero. The spec does not say a reset row can also capture a falling edge, so the checker should not credit a capture on that same row. The safe interpretation is that reset clears the output and suppresses capture for that row. However, the previous-input history should still be updated from that row's sampled `in`, because history concerns the sampled signal, not whether a capture was credited. If the checker skipped history updates on reset rows, it could later invent or miss a transition across the reset boundary.

Power-up state is another place to avoid overconstraining. The public specification does not define the initial value of `out`. Therefore, unless a reset row has occurred, the checker should not require any particular initial `out`. It can still track previous input from the first sampled row onward, but it should not assume `out` starts at zero. A reset row establishes a known zero state synchronously.

A short worked example: suppose bit 0 of `in` is 1 in row N and 0 in row N+1, with reset low in both rows. At row N+1's sampling edge, the checker sees previous sampled bit 1 and current sampled bit 0, so `out[0]` becomes 1. If instead `in[0]` changes from 1 to 0 only in the middle of row N+1, after that row's sampling edge, then row N+1 still samples 1 and row N+2 samples 0; the capture belongs to row N+2, not row N+1. The sticky behavior then holds `out[0]` at 1 through later rows until a synchronous reset row clears it.

For the final Python checker, the useful point is to model reset as a synchronous row-level clear that also updates the previous-input history, and to derive captures only from sampled pre-edge values. Power-up should be treated as unspecified unless reset is driven, and mid-row changes should never create a capture in the current row.
