The core state is a 32-bit history register holding the most recently sampled input vector, plus a 32-bit output register. These are distinct: history tracks the previous sampled `in`, while `out` is a sticky capture flag. The transition rule for each bit is: a capture is credited exactly when the previous sampled bit was 1 and the current sampled bit is 0, and that capture sets the corresponding output bit to 1 permanently until reset clears it.

Reset is active-high synchronous. On a sampled row where `reset=1`, the output is forced to 0 for all bits, no capture is credited regardless of any 1→0 transition, and — critically — the history register is updated to the current sampled `in`. This last point is the subtle one: reset does not freeze history at its pre-reset value. It overwrites history with the sampled input of the reset row. The next row's edge detection therefore compares against the reset row's sampled input, not against whatever value preceded the reset.

If an implementation instead freezes history during reset, it can fabricate a capture on the following non-reset row. Consider one bit with history=1 entering a sampled row where reset=1 and sampled in=0. Correct behavior: out is forced to 0, no capture is credited, and history becomes 0. On the next row with reset=0 and in=0, history=0 and current=0, so no capture and out stays 0. A buggy implementation that leaves history at 1 during the reset row will, on that next row, see history=1 and in=0, falsely credit a 1→0 capture, and drive out=1. The checker must catch this off-by-one state error by updating history on reset rows.

A second trap is mid-row input changes. The protocol says optional mid input changes occur after sampling and before the other edge, and are carried to the start of the next row. So the capture comparison for a row must use only the value sampled at the posedge, compared against the previous sampled value. A checker that reads a later mid-row `in` and compares it to current history would misattribute a transition to the wrong row. The comparison is always previous sampled `in` versus current sampled `in`, both taken at posedges; mid-row values are ignored for the current row.

Power-up is unconstrained for `out`. The checker should not require out=0 before the first reset row. It may begin tracking history from the first sampled input, but output assertions should begin only after a reset row has established a known zero state. Before that, any output value is acceptable.

For the final Python checker, keep history and output as separate state. On each sampled row: if reset is high, force out=0, do not credit capture, but set history to the sampled in. If reset is low, credit capture only where history=1 and sampled in=0, leave other bits unchanged, then set history to the sampled in. Ignore mid-row changes for the current row, and leave output unconstrained until the first reset row.
