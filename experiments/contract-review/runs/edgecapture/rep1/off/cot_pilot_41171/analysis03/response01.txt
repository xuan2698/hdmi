# Design Reasoning: Per-Bit 1→0 Transition Detector with Sticky Output

## Restating the problem in my own words

We have a 32-bit input `in` sampled every rising edge of `clk`. For each bit position independently, we want to notice the event "this bit was 1 at the previous sampled edge, and is 0 at the current sampled edge." When such an event occurs, the corresponding bit of `out` must become 1 and *stay* 1 — it is sticky/latching — until a synchronous active-high `reset` clears it. The reset is synchronous, meaning it is only honored at a clock edge, and it has priority over any transition detection happening on that same edge. The output is a 32-bit vector, one sticky flag per input bit.

## What state do we need?

To detect "previous cycle was 1, this cycle is 0," we must remember the previous cycle's input. That is a 32-bit register, call it `prev_in`. We also need the sticky output register `out`, which is the module's output. So the state is `{prev_in, out}`, both 32 bits.

The detection expression for bit *i* at a given edge is:

```
edge_i = prev_in[i] & ~in[i]
```

i.e., previous was 1 AND current is 0. This is a pure combinational function of the *old* `prev_in` and the *current* `in` (which is the value present at the sampling edge). The new sticky value is:

```
out_next[i] = out[i] | edge_i        (when not reset)
out_next[i] = 0                       (when reset)
```

And `prev_in` must be updated to the current `in` so the next edge can compare against it.

## Timing / check-cycle reasoning

The spec says: "sample after the posedge edge has settled. Each row's values are driven before the sampled edge. Optional mid input changes occur AFTER sampling, before the other edge, and are carried to the start of the next row."

This tells me the testbench drives `in` (and `reset`) before the rising edge, holds them stable across the edge, and then may change `in` in the middle of the cycle (after the edge, before the next edge). The mid-cycle change is *not* sampled at this edge; it becomes the value seen at the *next* edge. So my design must only look at `in` at the rising edge — which is exactly what a synchronous `always @(posedge clk)` block does. I do not need any combinational path from `in` to `out`; everything is registered. This also means mid-cycle glitches on `in` are irrelevant, which is the correct behavior.

Because the testbench samples "after the posedge has settled," non-blocking assignments (`<=`) are the right choice: all right-hand sides are evaluated with the pre-edge values, and the updates land after the edge, so the sampled values are the settled new register contents. Using blocking assignments would create a race between `out` and `prev_in` updates within the same edge and could produce order-dependent results; non-blocking avoids that entirely.

## Reset semantics and priority

"Active high synchronous reset" means: when `reset == 1` at a rising edge, the output register is forced to 0 at that edge. Synchronous means it is *not* an asynchronous clear — if `reset` is high between edges but low at the edge, no reset occurs. Active high means `reset == 1` triggers it (not `~reset`).

Priority: the spec says the output remains 1 "until the register is reset." That phrasing makes reset the overriding event. So on an edge where `reset == 1`, `out` must become 0 regardless of whether a 1→0 transition is also occurring on that edge. The clean way to express this is a ternary that selects reset first:

```
out <= reset ? 32'b0 : (out | (prev_in & ~in));
```

If I instead wrote `out <= (out | edge) & ~reset`, the result would be the same for `out`, but the ternary form makes the priority explicit and is less error-prone. Either is functionally equivalent here because both are pure functions of old values; I'll use the ternary for clarity.

## Should `prev_in` be reset?

This is the one genuinely ambiguous point, and I want to reason about it carefully using only the public spec.

The spec says: "the output will remain 1 until the register is reset." Grammatically, "the register" refers to the register that holds the output — i.e., `out`. It does not say "the state is reset" or "all registers are reset." So the literal reading is: only `out` is cleared by reset; `prev_in` continues to track `in` unconditionally.

Does that produce sensible behavior? Consider: during a reset cycle, `in = 1`. At that edge, `out` is cleared to 0, and `prev_in` becomes 1 (because `prev_in <= in` unconditionally). Next cycle, `in = 0`, `reset = 0`. Now `prev_in = 1`, `in = 0`, so `edge = 1`, and `out` becomes 1. Is that correct? The input *did* go from 1 (during reset) to 0 (after reset). That is a genuine 1→0 transition across the sampled edges, so capturing it is consistent with "capture when the input signal changes from 1 in one clock cycle to 0 the next." The reset only cleared the *output*; it did not erase the history of the input. So yes, capturing it is the literal-spec-correct behavior.

Now consider the alternative: if I also reset `prev_in` to 0 on reset, then after a reset cycle with `in = 1`, `prev_in` would be 0, and the subsequent 1→0 would *not* be captured. That would contradict the literal spec, because the input genuinely was 1 in the reset cycle and 0 in the next. So resetting `prev_in` would be an extra, unspecified behavior. I will *not* reset `prev_in`.

There is a second-order concern: what is `prev_in` before the very first clock edge? In simulation, an uninitialized reg is `X`. If the first edge has `reset = 1`, `out` becomes 0 (fine), but `prev_in` becomes `in` (fine, since `prev_in <= in` is unconditional). If the first edge has `reset = 0`, then `out <= out | (prev_in & ~in)` would involve `X` in `prev_in`, potentially producing `X` on `out`. To avoid this, I should initialize `prev_in` to 0 at declaration (or rely on the testbench applying reset first). Initializing `prev_in = 0` is safe and matches the "no prior 1" assumption: before any sample, we have no evidence of a 1, so no edge should be detected. I'll initialize `prev_in` to 0. I will *not* initialize `out` in the declaration if the testbench guarantees a reset; but initializing it to 0 as well is harmless and avoids `X` propagation if reset is somehow not applied first. The spec says "initial values of 0 for both registers (or relying on reset to initialize out, and initializing prev_in to 0 to avoid X)" — so initializing both to 0 is explicitly acceptable. I'll do that.

## Walking through small counterexamples

Let me trace a few cycles by hand to make sure the logic is right. I'll use a 1-bit slice for clarity; the 32-bit case is 32 independent copies.

**Example A: simple 1→0, no reset.**
- Initial: `prev_in = 0`, `out = 0`.
- Cycle 1: `in = 1`, `reset = 0`. Edge: `edge = 0 & ~1 = 0`. `out <= 0 | 0 = 0`. `prev_in <= 1`. State: `prev_in = 1`, `out = 0`.
- Cycle 2: `in = 0`, `reset = 0`. Edge: `edge = 1 & ~0 = 1`. `out <= 0 | 1 = 1`. `prev_in <= 0`. State: `prev_in = 0`, `out = 1`. ✓ Captured.
- Cycle 3: `in = 0`, `reset = 0`. Edge: `edge = 0 & ~0 = 0`. `out <= 1 | 0 = 1`. Sticky. ✓
- Cycle 4: `in = 1`, `reset = 0`. Edge: `edge = 0 & ~1 = 0`. `out <= 1`. Still sticky. ✓ (A 0→1 does not clear it.)
- Cycle 5: `in = 0`, `reset = 0`. Edge: `edge = 1 & ~0 = 1`. `out <= 1 | 1 = 1`. Still 1. ✓ (Re-detection is idempotent.)

**Example B: reset priority.**
- State: `prev_in = 1`, `out = 1`.
- Cycle: `in = 0`, `reset = 1`. Edge: reset wins, `out <= 0`. `prev_in <= 0`. State: `prev_in = 0`, `out = 0`. ✓ The transition is *not* captured because reset overrides. This matches "until the register is reset" — reset is the dominant event.

**Example C: reset with in=1, then 1→0 after reset.**
- State: `prev_in = 0`, `out = 0`.
- Cycle 1: `in = 1`, `reset = 1`. Edge: `out <= 0` (reset). `prev_in <= 1`. State: `prev_in = 1`, `out = 0`.
- Cycle 2: `in = 0`, `reset = 0`. Edge: `edge = 1 & ~0 = 1`. `out <= 0 | 1 = 1`. ✓ Captured. This is the case I argued about above; the literal spec says capture it, and we do.

**Example D: mid-cycle change.**
- State: `prev_in = 0`, `out = 0`.
- Before edge: `in = 1`. Edge samples `in = 1`: `edge = 0`, `out <= 0`, `prev_in <= 1`.
- Mid-cycle: `in` changes to 0 (after the edge). This is *not* sampled now.
- Next edge: `in = 0` (carried). `edge = 1 & ~0 = 1`. `out <= 1`. ✓ The mid-cycle change is correctly attributed to the next edge, exactly as the protocol describes.

**Example E: no transition, just 0→0 or 1→1.**
- `prev_in = 0`, `in = 0`: `edge = 0`. No capture. ✓
- `prev_in = 1`, `in = 1`: `edge = 1 & ~1 = 0`. No capture. ✓ (1→1 is not a 1→0.)

**Example F: 0→1 then 1→0.**
- `prev_in = 0`, `in = 1`: `edge = 0`. `prev_in <= 1`.
- Next: `in = 0`: `edge = 1`. Captured. ✓ The 0→1 itself is not captured (correct — we only want 1→0), but it sets up `prev_in` so the following 1→0 is caught.

## Corner cases and weak points

1. **Reset deassertion timing.** If `reset` goes low mid-cycle, it is only honored at the next edge. My synchronous check handles this. If `reset` is high at the edge, reset wins. No asynchronous path exists, so no glitch sensitivity.

2. **`prev_in` not reset.** As argued, this is the literal-spec behavior. The only way this could be "wrong" is if the hidden testbench expects `prev_in` to be cleared on reset. But the spec's wording ("the output will remain 1 until the register is reset") points only at the output register. I'll note this as the single interpretive risk, but I'm confident in the literal reading.

3. **Initial `X`.** Initializing both registers to 0 avoids `X` propagation if the first edge is not a reset edge. This is explicitly permitted by the spec.

4. **Non-blocking assignment ordering.** Both `out` and `prev_in` are assigned with `<=`, so they see old values. `out` uses old `prev_in` and old `out`; `prev_in` uses old `in`. There is no dependency between the two assignments within the edge, so order is irrelevant. This is the correct way to model "sample, then update."

5. **32-bit independence.** The expression `prev_in & ~in` is bitwise, and `out | (...)` is bitwise, so each bit is handled independently. A transition on bit 5 does not affect bit 6's sticky flag. ✓

6. **Sticky across many cycles.** Because `out` feeds back into itself (`out | edge`), once a bit is 1 it stays 1 until reset, regardless of subsequent input activity. ✓

7. **Reset while a transition is pending.** Covered in Example B: reset wins, and the transition is discarded (not queued). This matches "until the register is reset" — reset is a clear, not a pause.

8. **Multiple transitions before reset.** If bit *i* goes 1→0, then later 1→0 again, `out[i]` is already 1; the OR keeps it 1. No double-counting issue. ✓

## Final form

The implementation is a single synchronous block:

```
always @(posedge clk) begin
    out     <= reset ? 32'b0 : (out | (prev_in & ~in));
    prev_in <= in;
end
```

with `prev_in` (and optionally `out`) initialized to 0. This captures per-bit 1→0 transitions, holds them sticky, honors synchronous active-high reset with priority, tracks `prev_in` unconditionally (per the literal spec), and is immune to mid-cycle input changes because everything is edge-sampled with non-blocking assignments. The only interpretive judgment is not resetting `prev_in`, which I've justified from the spec's wording and from the concrete Example C trace.
