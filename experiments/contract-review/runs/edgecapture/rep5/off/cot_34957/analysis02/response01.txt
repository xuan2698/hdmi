**Reset and power-up behavior**

The specification defines a synchronous, active-high reset. That means reset is not an asynchronous clear: it is sampled at the same posedge as `in`, and its effect is applied to the same row’s expected output. When `reset` is high on a sampled row, `out` must be all zeros for that row, regardless of any 1→0 transition that would otherwise be detected between the previous sampled `in` and the current sampled `in`. Reset therefore has priority over transition capture in the row where it is asserted.

This priority is important for the final Python checker because a naive implementation might compute the transition mask first and then OR it into the output without masking by reset, or might apply reset one row late. The correct row-local ordering is: compute the 1→0 transition mask from the previous sampled input and the current sampled input, OR that mask into the stored output, then clear the result if the current row’s sampled reset is high. Equivalently, the next output state is the accumulated detection state masked by the current reset. The previous-input register should still be updated from the current sampled `in` even on a reset row, because the next row’s transition comparison uses the most recent sampled input, not the last non-reset input.

Power-up behavior is less explicit in the public specification. The output is described as remaining 1 until reset, which implies a stored state, but the initial value of that state and the initial value of the previous-input register are not fully specified. For the checker, the safest interpretation is that the first sampled row should not invent a transition from an unknown prior value. In practice this means the checker should either initialize the previous-input register to the first row’s `in` before evaluating that row, or suppress transition detection on the first row. Otherwise a first row containing zeros could be falsely flagged as detecting 1→0 events from an assumed all-ones prior state. The public spec does not justify assuming an all-ones prior input.

A short worked example: suppose the first sampled row has `in = 32'b...0001`, `reset = 0`. If the checker initializes `prev_in` to that same value, no transition is detected and `out` remains at its initial value. On the next row, if `in = 32'b...0000` and `reset = 0`, the checker sees a 1→0 change in bit 0 and sets that output bit. If the following row asserts `reset = 1`, the output is cleared to zero for that row even though no new transition may be present, and `prev_in` updates to that row’s `in`.

The most useful point for the final Python checker is to keep three things separate and ordered: the row’s sampled `in`, the row’s sampled `reset`, and the single stored `prev_in`. Mid-row input changes must not be treated as additional samples; they only affect what will be sampled at the next posedge. The checker should update `prev_in` exactly once per row, after using it for the transition comparison, and should apply reset as a row-local mask on the accumulated output. It should also avoid assuming an unspecified power-up `prev_in` that could create a spurious first-row detection.
