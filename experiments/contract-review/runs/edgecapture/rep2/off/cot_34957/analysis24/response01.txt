The most useful implementation mistake to target here is **conflating the sampled input with the combinational input when updating the previous-input baseline**. In this spec, the detector is edge-sampled: the comparison that can create a capture is between the `in` value sampled at the current posedge and the `in` value sampled at the previous posedge. Mid-cycle changes to `in` are explicitly irrelevant until the next sampled edge. A common RTL mistake is to write the baseline register from the live `in` signal rather than from the registered/sampled value, or to update it in a way that lets a mid-row transition leak into the next comparison. That can create a capture one row early, suppress a legitimate capture, or make the checker disagree with a correct DUT on rows where `in` changes between edges.

The checker should therefore treat each row as: first apply reset priority using the sampled `reset`; then, if reset is high, clear `out` and set the baseline to the sampled `in`; otherwise compare sampled `in` against the stored baseline to detect 1-to-0 transitions, OR those captures into sticky `out`, and then update the baseline to sampled `in`. The order matters: reset re-baselines the detector, and capture is sticky until reset. A stale baseline after reset is another manifestation of the same class of error: if reset clears `out` but does not update `prev_in` to the sampled post-reset input, the first non-reset row after reset can falsely capture against a pre-reset value. The checker should explicitly verify that reset both clears `out` and establishes the new baseline from the sampled `in` at that reset edge.

A short worked example: suppose at row N the sampled `in[0]=1`, reset low, so baseline becomes 1 and no capture occurs. A mid-row change drives `in[0]=0`, but row N must ignore it. At row N+1, reset is high and sampled `in[0]=0`. Reset wins: `out[0]` becomes 0 and the baseline becomes 0. The mid-row change creates no capture, and reset both clears and re-baselines. If instead row N+1 had reset low, the sampled 0 would compare against baseline 1 and set `out[0]=1`; on the following row, even if `in[0]` stayed 0, `out[0]` must remain 1 because the capture is sticky and no reset has occurred.

Finally, power-up is undefined by the public spec. The checker should not assume a known initial baseline or known-zero initial output before the first sampled edge. If the first sampled edge has reset high, expected output is zero and the baseline is established from sampled `in`. If the first sampled edge has reset low, the checker should establish the baseline without demanding a definite capture from an unknown prior state. Treating initial output as known-zero, or inferring a capture from an unknown prior baseline, would produce false failures. After that first edge, the baseline is known and the normal reset-priority and sticky-capture rules apply.
