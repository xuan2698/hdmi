The public spec defines a 32-bit sticky 1-to-0 detector with active-high synchronous reset. The key timing distinction is between values sampled at the posedge and optional mid-cycle input changes that occur after sampling but before the next edge. The checker must model the sampled values as the only inputs to the state update for that row; mid-row changes are carried forward and only become visible at the next sampled edge. In particular, a mid-row transition from 1 to 0 must not cause a capture in the current row, because the detector compares the sampled `in` at consecutive edges, not arbitrary intra-cycle values.

For each sampled edge, the checker should apply reset priority first. If the sampled `reset` is high, `out` is cleared to zero and the stored baseline (`prev_in`) is set to the sampled `in`. This re-baselining is essential: reset does not merely clear the sticky output, it also resets the detector's memory of the previous input. If reset clears `out` but leaves `prev_in` at its pre-reset value, the first non-reset row after reset can falsely capture a 1-to-0 transition against stale data. The checker should explicitly verify both effects of reset at the same edge: output cleared and baseline established from the sampled `in`.

If the sampled `reset` is low, the checker compares the sampled `in` against the stored baseline. For each bit where the baseline is 1 and the sampled `in` is 0, the corresponding `out` bit is set. Captures are sticky: once set, an `out` bit remains 1 until a reset edge clears it. After the comparison, the baseline is updated to the sampled `in`, regardless of whether any capture occurred. This update is what makes the detector edge-to-edge rather than level-sensitive.

A short worked example illustrates the ordering. Suppose at row N the sampled `in[0]=1` with reset low, so the baseline becomes 1 and no capture occurs. A mid-row change then drives `in[0]=0`, but row N ignores it. At row N+1, reset is high and sampled `in[0]=0`. Reset wins: `out[0]` becomes 0 and the baseline becomes 0. The mid-row change produces no capture, and reset both clears and re-baselines. If instead row N+1 had reset low, the sampled 0 would compare against baseline 1 and set `out[0]=1`; on the following row, even if `in[0]` stayed 0, `out[0]` must remain 1 because the capture is sticky and no reset has occurred.

The most useful point for the final Python checker is the reset re-baselining requirement combined with the undefined power-up state. The checker should not assume a known initial baseline or known-zero initial output before the first sampled edge. If the first sampled edge has reset high, expected output is zero and the baseline is established from sampled `in`. If the first sampled edge has reset low, the checker should establish the baseline without demanding a definite capture from an unknown prior state. Treating initial output as known-zero, or inferring a capture from an unknown prior baseline, would produce false failures. After that first edge, the baseline is known and the normal reset-priority and sticky-capture rules apply. The checker should therefore encode the row update as: reset high → clear `out`, set baseline to sampled `in`; reset low → OR captures from baseline-to-sampled transitions into `out`, then set baseline to sampled `in`. Mid-row changes are never inputs to the current row's update.
