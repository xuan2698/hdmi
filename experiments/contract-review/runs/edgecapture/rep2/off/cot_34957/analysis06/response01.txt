The most likely implementation mistake to guard against is conflating the **driven input** with the **sampled input** when maintaining the falling-edge detector. A naive implementation might update the "previous input" register combinationally from the driven `in` value, or recompute the falling-edge mask whenever `in` changes mid-cycle. Under the public spec, that is wrong: capture is defined only on sampled clock edges, and mid-cycle changes are explicitly carried forward as pre-edge state without triggering capture or reset. The checker should therefore model two distinct notions: the value driven during the row (which may change after sampling) and the value actually sampled at the posedge. Only the latter participates in the falling-edge comparison and in advancing the baseline.

A second, closely related mistake is getting the **per-edge ordering** wrong. On each sampled edge the correct sequence is: (1) apply synchronous reset priority — if `reset` is high, force `out` to zero and re-baseline the previous-sampled input to the current sampled input; (2) only when reset is low, compute the falling-edge mask as `prev_sampled & ~curr_sampled` and OR it into `out`; (3) in both cases, set `prev_sampled = curr_sampled`. If an implementation computes the mask before applying reset, a 1-to-0 transition coinciding with a reset edge could leave a stale capture bit set, or the baseline could fail to advance, causing a spurious capture on the following edge. If it updates the baseline before computing the mask, the mask becomes zero and legitimate captures are lost. The checker should encode this ordering explicitly rather than relying on incidental evaluation order.

A third pitfall worth flagging is **power-up underspecification**. The spec does not define `out` before the first sampled edge, so the checker must not assert any particular value there. Comparison should begin only after the first sampled edge, and at that edge reset priority must still apply: if reset is high, expect zeros and baseline to the sampled input; if reset is low, record the sampled input as baseline and avoid demanding a definite captured output unless the testbench has established one. Treating the initial `out` as known-zero, or inferring a capture from an unknown power-up baseline, would produce false failures.

Worked example: at row N, reset low, bit 0 sampled as 1, `out[0]` unknown — record prev=1, no capture. Mid-row bit 0 drops to 0; ignore for row N. At row N+1, reset high, bit 0 sampled as 0 — reset wins: `out[0]=0`, prev=0. The mid change created no capture, and reset cleared and re-baselined the detector.

For the final checker, the key invariant is: separate driven from sampled input, apply reset first, compute the mask only when reset is low, then advance the baseline in all cases.
