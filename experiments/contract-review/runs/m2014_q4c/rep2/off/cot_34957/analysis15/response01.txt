The D flip flop has one data input `d`, one synchronous reset input `r`, one clock `clk`, and one output `q`. Its behavior is defined only at the sampled positive edge of `clk`. At that edge, if `r` is high, `q` is forced to 0; otherwise `q` takes the value of `d`. Because reset is synchronous, it has effect only when it is high at the sampled edge. A reset value that appears or disappears between edges does not retroactively alter the result already produced for the current row.

The public protocol distinguishes two input phases per row. First, the row’s values are driven before the sampled edge. Those are the values the flip flop sees when the expected output for that row is determined. Second, optional mid-input changes occur after sampling and before the other edge; those changes are carried forward as the starting inputs of the next row. The checker must preserve this ordering. If it applies mid-input changes before computing the current row’s expected output, it can produce an incorrect expectation, especially when reset changes after sampling.

Reset is the most sensitive case. If `r` is high at the sampled edge, `q` becomes 0 for that row regardless of `d`. If `r` then falls after sampling, the current row’s reset result still stands, and the lowered reset is merely the starting condition for the next row. Conversely, if `r` is low at the sampled edge, the flip flop captures `d` normally, even if `r` rises immediately after sampling. The high reset seen after sampling applies only to the next sampled edge.

A short worked example makes the distinction concrete. Suppose a row begins with `d=1`, `r=0`. At the sampled positive edge, expected `q` is 1. After sampling, a mid-input change sets `d=0`, `r=1`. The current row’s expected `q` remains 1. On the next row, the checker starts with `d=0`, `r=1`; at that row’s sampled edge, synchronous reset forces `q` to 0. A checker that applied the mid-input change too early would wrongly expect the first row’s `q` to be 0, and it could also mishandle the following row if it failed to carry the updated inputs forward correctly.

Power-up behavior should not be over-specified. The public specification does not define a power-up value for `q` before the first sampled positive edge. The checker should therefore avoid assuming an initial `q` unless the first row’s expected value can be computed entirely from the specified synchronous behavior and the captured inputs. In particular, it should not invent an asynchronous reset or a known initial state. The first sampled edge is the first point at which the specified reset/data rule applies.

The useful point for the final checker is therefore strict phase separation: capture pre-edge inputs, compute the current expected output using synchronous reset, compare, then apply mid-input changes for the next row. Keeping the mid-input update strictly after the row’s expected-output computation prevents reset and data timing from being conflated.
