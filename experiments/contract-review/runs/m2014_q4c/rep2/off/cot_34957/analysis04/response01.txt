The public specification defines a one-bit D flip-flop with a one-bit active-high synchronous reset. The input ports are `d` and `r`, each one bit wide; the output port is `q`, also one bit wide. The clock is `clk`, and sampling occurs after the positive edge has settled. Values for each row are driven before the sampled edge. Optional mid-input changes occur after sampling and before the other edge, and those changed values are carried to the start of the next row. The protocol seed is 20261121.

Because all data ports are one bit, boundary values are simply 0 and 1. There is no multi-bit truncation, sign extension, or width-mismatch issue to resolve. The meaningful boundary behavior is logical: `r=1` at the sampled positive edge forces `q` to 0 regardless of `d`; `r=0` allows the flip-flop to load `d`. Since reset is synchronous, `r` does not act between edges; it matters only at the sampled positive edge. Since reset is active high, `r=0` is the normal operating condition and `r=1` is the reset condition. The output `q` is one bit and should be compared as a single-bit value, not as an integer with extra width.

The key point for the final Python checker is the ordering of three moments inside each row: the driven values before the sampled positive edge, the sampled positive edge itself, and the optional mid-input update after sampling. The expected `q` for the row must be computed from the driven `d` and `r` at the sampled edge, not from any mid-input value. After computing that expected `q`, the checker should advance the carried input state using the mid-input changes, if present, so that the next row begins with those updated values. This ordering matters especially when `r` is high: a synchronous reset at the sampled edge forces `q` to 0 regardless of `d`, and a later mid-input change cannot undo that already-sampled reset for the current row.

A short worked example illustrates the ordering. Suppose a row drives `d=1`, `r=0` before the positive edge. At the sampled edge, `q` becomes 1. After sampling, an optional mid-input change sets `d=0`, `r=1`. That change does not affect the current row’s `q`; it is carried to the start of the next row. At the next sampled positive edge, the checker sees `d=0`, `r=1`, so synchronous reset forces `q` to 0. If the checker incorrectly applied the mid-input change to the current row, it would wrongly expect the current `q` to be reset. Thus the final checker should latch from the pre-mid values at the positive edge, then update the carried inputs for the next row from the mid-input window. This preserves the specified edge and mid-input timing without conflating them.

For the final Python checker, the most useful discipline is therefore: read the row’s pre-edge inputs, compute expected `q` from those inputs and the previous sampled `q` using the synchronous-reset rule, compare that expected `q` to the observed output for the row, and only then apply any mid-input changes to the carried input state for the next row. The checker should also avoid asserting any particular value of `q` before the first sampled positive edge, because the public specification does not define power-up state.
