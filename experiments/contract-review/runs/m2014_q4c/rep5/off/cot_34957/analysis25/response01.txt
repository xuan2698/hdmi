The key distinction in this specification is between the **pre-edge sampled snapshot** and the **post-sampling mid-input changes**. The public spec says each row's values are driven before the sampled edge, and optional mid input changes occur *after* sampling, before the other edge, and are carried to the start of the next row. That ordering is the whole game: the settled output for a row is determined by the inputs present at the positive clock edge, not by whatever the inputs become later in the same row.

For a synchronous D flip-flop with active-high synchronous reset, the next-state rule is simple: if the sampled `r` is 1, the next `q` is 0; otherwise the next `q` is the sampled `d`. The word "synchronous" matters. Reset is not an asynchronous clear. It only takes effect when `r = 1` is part of the pre-edge snapshot at a positive clock edge. Holding `r` high between edges, or seeing `r` change after the edge, does not retroactively clear `q`. Similarly, `d` changes after the edge are not visible to the current row's settled output; they are inputs for the next row.

A useful point for the final Python checker is to maintain two separate carried values per row: the pre-edge input snapshot used to compute the current expected output, and the post-sampling input values that seed the next row. The expected next state should be computed only from the sampled snapshot and the previous expected state. After comparing the settled observed `q` against that expectation, the checker updates its expected state and carries the post-sampling inputs forward. It must not recompute the current row from the row's final input values, and it must not apply reset or data changes before the sampled edge.

Short worked example: suppose the state entering a row is `q_prev = 1`. Before the sampled rising edge, the driven inputs are `d = 0`, `r = 0`. After sampling, before the next edge, the inputs change to `d = 1`, `r = 0`. The correct settled output for this row is `q = 0`, because the sampled edge saw `d = 0`. The later `d = 1` is carried to the start of the next row and may affect the next sampled edge, but it must not change this row's expected `q`. A checker using the row's final input values would incorrectly expect `q = 1`.

One more subtlety: the spec does not define an asynchronous power-up reset value. Any initial `q` assumed by the checker is a checker convention, not part of the reset behavior. The first row should be evaluated from that convention plus the pre-edge sampled inputs, not from an assumption that reset has already cleared the state. The checker should therefore make its initial-state convention explicit and apply the same synchronous next-state rule from row one onward.
