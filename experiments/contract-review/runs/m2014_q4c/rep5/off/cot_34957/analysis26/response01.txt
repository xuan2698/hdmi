The key distinction for the final Python checker is that this is a **synchronous** reset, not an asynchronous clear. Reset only has effect when `r = 1` is present in the pre-edge input snapshot at a positive clock edge. Between edges, `r` is just another input; changing it does not retroactively alter `q`. Likewise, `d` changes after the sampled edge belong to the next row, not the current one.

A useful implementation point is to carry two separate values per row: the pre-edge input snapshot used to compute the current expected output, and the post-sampling input values that seed the next row. The expected next state must be computed only from the sampled snapshot and the previous expected state. After comparing the settled observed `q` against that expectation, the checker updates its expected state and carries the post-sampling inputs forward. It must not recompute the current row from the row's final input values, and it must not apply reset or data changes before the sampled edge.

Short worked example: suppose the state entering a row is `q_prev = 1`. Before the sampled rising edge, the driven inputs are `d = 0`, `r = 0`. After sampling, before the next edge, the inputs change to `d = 1`, `r = 0`. The correct settled output for this row is `q = 0`, because the sampled edge saw `d = 0`. The later `d = 1` is carried to the start of the next row and may affect the next sampled edge, but it must not change this row's expected `q`. A checker using the row's final input values would incorrectly expect `q = 1`.

One more subtlety: the spec does not define an asynchronous power-up reset value. Any initial `q` assumed by the checker is a checker convention, not part of the reset behavior. The first row should be evaluated from that convention plus the pre-edge sampled inputs, not from an assumption that reset has already cleared the state. The checker should therefore make its initial-state convention explicit and apply the same synchronous next-state rule from row one onward.
