One likely implementation mistake is to collapse the protocol into a single “current inputs” value and sample it at the edge, without distinguishing pre-edge drives from mid-row changes. The public spec says each row’s values are driven before the sampled edge, while optional mid input changes occur after sampling and before the other edge, and are carried to the start of the next row. That ordering matters. A checker that simply records the last value seen for `d` and `r` before the next rising edge can accidentally let a mid-row `r=1` reset the current sample, even though the reset was not present at the sampled edge. The correct behavior is: resolve the pre-edge inputs from the carried baseline plus any pre-edge drives, sample once after the posedge has settled, apply reset priority to that resolved pre-edge `r`, and only then apply mid-row changes to the carry for the next row.

A second useful point is that “no drive before the edge” is not the same as “input is 0.” The carried value is the baseline. If the previous row ended with carried `d=1`, then a row that drives nothing before its edge still samples `d=1` unless a pre-edge drive overrides it. The checker should therefore model carried `d` and carried `r` explicitly and merge pre-edge drives onto them, rather than defaulting missing drives to zero. The same caution applies at the very start: the public spec does not define power-up `q` or initial carried inputs. If the harness or seed establishes them, use that; otherwise the checker should not silently invent undocumented history beyond a clearly stated convention.

A short worked example shows the ordering. Suppose a row starts with carried `d=0`, `r=0`, and current `q=0`. Before the edge the row drives `d=1`, `r=0`. The resolved pre-edge inputs are `d=1`, `r=0`, so at the settled rising edge `q` becomes 1. After sampling, a mid-row change sets `r=1`. That does not alter the just-sampled `q=1`; it only makes the next row begin with carried `r=1` (and carried `d=1` if unchanged). If the next row drives nothing before its edge, the resolved inputs are `d=1`, `r=1`, so reset priority forces `q=0`.

For the final Python checker, keep `q`, carried `d`, and carried `r` as separate state. Build pre-edge inputs from carry plus pre-edge drives, sample once at the settled rising edge, apply reset priority, then apply mid-row changes to the carry for the next row. Do not let mid-row changes affect the sampled output, and do not drop them from the next row’s baseline. Make the initial-state convention explicit and consistent, and avoid treating absent drives as implicit zeros when a carried value already exists.
