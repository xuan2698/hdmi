The public interface is deliberately narrow: one data input `d` and one reset input `r`, each one bit wide, plus a clock `clk`; the only output is `q`, also one bit. There are no enable, preset, or clear-asynchronous pins, and no multi-bit packing to worry about. Boundary values are therefore just 0 and 1 for every signal. The meaningful boundary cases are the reset-priority case (`r=1` with either `d` value), the normal capture case (`r=0`, `d=0` or `d=1`), and the carry boundary where a mid-row change to `d` or `r` affects only the next row, not the edge just sampled.

The specification distinguishes three state-like things that the final checker should not conflate. First, the current output `q`, which is the value visible after the most recent settled rising edge (or the chosen initial value before any edge). Second, the carried `d`, which is the data value that will be used at the next rising edge unless the current row drives a new `d` before that edge. Third, the carried `r`, the reset value carried into the next row in the same way. For each row, the pre-edge inputs are the combination of carried values and values driven in the current row before the sampled edge. At the settled rising edge, reset has priority: if the resolved `r` is 1, `q` becomes 0 regardless of resolved `d`; otherwise `q` takes the resolved `d`. Only after that edge decision are mid-row changes processed, and those changes update only the carried `d` and `r` for the next row. They must not retroactively change `q` or the inputs already used at the edge.

A useful point for the final Python checker is that power-up behavior of `q` is not defined by the public specification. The checker must choose an explicit initial convention for `q` at time zero and use it consistently in the reference model and expected-output generation. It should not silently infer an initial value from reset, from the first row’s driven inputs, or from an assumed zero state. Otherwise the first sampled edge can produce a spurious mismatch even when the edge and carry logic are otherwise correct.

Worked example: suppose a row begins with carried `d=1`, `r=0`, and current `q=0`. Before the rising edge the row drives `d=0`, `r=1`. The resolved pre-edge inputs are therefore `d=0`, `r=1`. At the settled edge, reset wins and `q` becomes 0. After sampling, a mid-row change sets `r=0` and leaves `d=0`. That change does not alter the just-computed `q`; it only means the next row begins with `d=0`, `r=0`. If the next row drives nothing before its edge, the next sampled inputs are `d=0`, `r=0`, so `q` remains 0. If the mid change had instead set `d=1`, the next row would begin with `d=1`, and a later rising edge with `r=0` would capture 1.

For the final checker, keep current `q`, carried `d`, and carried `r` separate. Resolve pre-edge inputs, apply reset priority at the settled edge, update `q` only from those resolved inputs, then process mid-row changes as carry for the next row. Make the initial `q` convention explicit and consistent, because the public specification does not define power-up behavior.
