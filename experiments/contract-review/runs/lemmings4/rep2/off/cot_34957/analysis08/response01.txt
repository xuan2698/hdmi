The reset behavior is the cleanest place to separate the Moore machine’s state from its combinational output decoding. The public specification says `areset` is positive-edge-triggered asynchronous and resets the Lemming to walk left. For the final Python checker, the important consequence is that reset is not merely another input sampled at the clock edge; it is an override that can change the state between sampled rows. When `areset` is asserted, the machine must enter the walk-left state and clear any fall counter, digging progress, and splatter latch. The Moore outputs for that reset state are `walk_left=1`, `walk_right=0`, `aaah=0`, and `digging=0`.

This matters most near the splatter boundary. A Lemming that has been falling for many cycles has accumulated fall duration in the state. If reset arrives, that accumulated duration must be erased, not merely frozen or carried forward. Otherwise a later ground contact could incorrectly trigger splatter even though the Lemming was reset to walking left. Similarly, a splattered Lemming must be revived by reset; the “forever until reset” clause means the splatter condition is persistent only in the absence of reset. The checker should therefore treat reset as clearing the splatter memory as well as the fall count.

For ordinary operation, the checker should keep the state categories distinct: walking, falling, digging, and splattered. The Moore outputs are determined by the current state, not by the raw inputs in the same row. Falling has higher precedence than digging, and digging has higher precedence than direction switching. A walking Lemming on ground can begin digging when `dig=1`; otherwise bumps may switch direction. If ground disappears, the Lemming falls and asserts `aaah`. While falling, bumps and dig requests are ignored. When ground reappears, the Lemming resumes walking in the same direction as before the fall. Digging continues until ground disappears, at which point the Lemming falls and later resumes walking in its original direction. If the fall lasts more than 20 clock cycles and then hits ground, the Lemming splatters and all outputs become zero forever until reset.

A short worked example: suppose the Lemming is falling with a large fall count and `areset` asserts asynchronously. The correct next sampled row is the walk-left pattern, with fall count and splatter memory cleared. The checker should not require an ordinary clocked transition first, and it should not carry the old fall count forward.

The useful point for the final Python checker is to separate reset handling from the ordinary precedence rules. Reset should directly set the state to walk-left and clear fall/splatter memory, then Moore outputs should be derived from that state. Ordinary sampled-edge transitions should apply the fall/dig/direction precedence only when reset is not active. Mid-cycle input changes should be carried to the next sampled edge but should not rewrite the current output row. This structure prevents the checker from incorrectly preserving a pre-reset fall count or splatter flag across reset.
