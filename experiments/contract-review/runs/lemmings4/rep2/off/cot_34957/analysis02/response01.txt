**Reset and power-up behavior**

The public specification defines `areset` as a positive-edge-triggered asynchronous reset that returns the Lemming machine to the walk-left state. For the final Python checker, the important consequence is that reset is a state-forcing event, not merely another input sampled in the ordinary transition relation. When a reset edge occurs, the machine must be placed in the walking-left state regardless of the current state, the current values of `bump_left`, `bump_right`, `ground`, or `dig`, and regardless of whether the machine was walking, falling, digging, or splattered. In particular, reset must clear any accumulated fall counter and must clear the splattered condition. After reset, the Lemming is again an ordinary walking-left Lemming with `walk_left=1` and the other three outputs zero.

The checker should not require `areset` to be synchronized to `clk`. The specification says the reset is asynchronous, so a reset edge may occur between clock edges. The checker should therefore treat reset as an immediate override: once the reset edge has occurred, the machine's state is the walk-left state, and the next sampled row must show the walk-left outputs. The row following a reset edge should show `walk_left=1`, `walk_right=0`, `aaah=0`, and `digging=0`. The checker should not demand that reset coincide with a rising clock edge, and it should not let ordinary input changes during the reset interval produce a different post-reset state.

Power-up behavior is best treated as the same initial condition: before any reset or clock activity, the machine is in the walk-left state. The first meaningful sampled row should therefore be consistent with walking left unless a reset edge or other specified transition has occurred. The checker should not invent an unknown or don't-care initial state, because the public specification gives a definite initial direction: walk left.

A short worked example clarifies the reset point. Suppose the machine has been falling for several cycles and has accumulated a fall count near the splatter threshold. Then `areset` goes high asynchronously. The reset must immediately force the walk-left state and clear the fall count. The next sampled row must show `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`. If the machine had instead been allowed to continue falling, it might later splatter; reset prevents that by restoring the initial walking-left condition. The checker should therefore apply reset before evaluating the ordinary transition and should verify the post-reset output row directly.

The useful point for the final Python checker is that reset is an override with a definite observable output, not a transition that depends on the other inputs. The checker should model reset as setting the state to walk-left and clearing fall/splatter memory, then derive the Moore outputs from that state. It should allow reset to be asynchronous relative to `clk`, but it should require the row following a reset edge to show the walk-left outputs. This separates reset handling from the ordinary precedence rules for fall, dig, and direction switching, and it prevents the checker from incorrectly carrying a pre-reset fall count or splatter flag across the reset.
