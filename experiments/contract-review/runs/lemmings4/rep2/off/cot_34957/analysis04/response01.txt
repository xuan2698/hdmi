The port widths are all one bit, so every input and output is a Boolean sampled signal. `areset`, `bump_left`, `bump_right`, `ground`, and `dig` are inputs; `walk_left`, `walk_right`, `aaah`, and `digging` are Moore outputs. Because the outputs are Moore outputs, they depend only on the current state, not directly on the current input row. The checker should therefore compare the sampled output row against the outputs implied by the state after applying any reset and the previous transition, not against a combinational function of the current inputs alone.

Boundary values matter in two places. First, the fall counter has a threshold: falling for more than 20 clock cycles and then hitting ground causes splatter. The checker must distinguish “20 or fewer” from “more than 20,” and must only splatter on the cycle where ground returns, not while still airborne. Second, reset is asynchronous and positive-edge triggered. A reset event can occur between sampled rows, so the checker should not require reset to align with the ordinary clocked transition. After reset, the state must be walking left with fall/splatter memory cleared, and the next sampled row must show `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`.

For ordinary operation, the checker should separate reset handling from the precedence rules. When not reset, the Lemming is walking, falling, digging, or splattered. Falling has higher precedence than digging, and digging has higher precedence than direction switching. A walking Lemming on ground can dig when `dig=1`; otherwise bumps can switch direction. If ground disappears, the Lemming falls and says `aaah!`. While falling, bumps and dig requests are ignored. When ground reappears, the Lemming resumes walking in the same direction as before the fall. Digging continues until ground disappears, at which point the Lemming falls and later resumes walking in its original direction. If the fall lasts more than 20 clock cycles and then hits ground, the Lemming splatters and all outputs become zero forever until reset.

A short worked example: suppose the machine has been falling for several cycles and has accumulated a fall count near the splatter threshold. Then `areset` goes high asynchronously. Reset must immediately force the walk-left state and clear the fall count. The next sampled row must show `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`. If the machine had been allowed to continue falling, it might later splatter; reset prevents that by restoring the initial walking-left condition. The checker should apply reset before evaluating the ordinary transition and should verify the post-reset output row directly.

Thus the final Python checker should model reset as setting the state to walk-left and clearing fall/splatter memory, then derive Moore outputs from that state. It should allow reset to be asynchronous relative to `clk`, but require the row following a reset edge to show the walk-left outputs. This prevents the checker from incorrectly carrying a pre-reset fall count or splatter flag across reset, and it keeps reset handling distinct from the ordinary precedence rules for fall, dig, and direction switching.
