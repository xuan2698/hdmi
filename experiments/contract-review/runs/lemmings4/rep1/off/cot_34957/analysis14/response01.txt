The reset and power-up behavior of this Lemming FSM is the natural place to anchor the checker, because it determines the machine's initial state and the only way to escape the absorbing splattered state. The spec states that `areset` is positive-edge triggered and asynchronous, and that it resets the machine to walk left. For the checker this means two things. First, the reference model must treat `areset` as a level-sensitive override that takes effect immediately on the rising edge of `areset`, independent of `clk`; the sampled outputs after that edge must be `walk_left=1` and all other outputs 0. Second, because the reset is asynchronous, the checker should not require the reset to be synchronized to a clock edge, and it should tolerate `areset` being asserted between sampled edges. The cleanest way to model this in Python is to evaluate `areset` before the clocked transition on every sample: if `areset` is high at the sampling instant, force the state to walk-left and clear the fall counter, then skip the normal transition logic for that sample.

Power-up is the degenerate case of reset. Before any reset has occurred, the machine's state is unspecified by the public spec, so the checker should not assert any particular output on the very first sample unless `areset` is driven high first. A robust testbench drives `areset=1` for at least one sample at the start, then releases it, and only begins checking the Moore-output invariant from the first post-reset sample. This avoids false failures caused by an uninitialized state encoding.

The absorbing nature of splatter interacts with reset in a way the checker must verify explicitly. Once a Lemming has splattered, all four outputs must remain 0 on every subsequent sample regardless of `bump_left`, `bump_right`, `ground`, or `dig`, until `areset` is asserted. The checker should drive a splatter sequence, then apply a variety of inputs (including `ground=1`, `dig=1`, and both bumps) for several cycles and confirm the outputs stay at zero, then assert `areset` and confirm the machine returns to `walk_left=1` with the fall counter cleared. This also confirms that reset is the only exit from the splattered state, matching the spec's "forever (Or until the FSM gets reset)."

A short worked example illustrates the reset timing the checker should enforce. Suppose the machine is in the splattered state with all outputs 0, and the testbench asserts `areset=1` on a sample where `clk` has just risen. The reference model must output `walk_left=1, walk_right=0, aaah=0, digging=0` on that same sample, not one cycle later. If the checker instead waits for the next clock edge to apply reset, it will flag a spurious mismatch. Conversely, if `areset` is asserted and then deasserted between two sampled edges, the machine must already be in walk-left at the next sample, and any inputs present at that sample (such as `bump_right=1`) should be processed as a normal walking transition from walk-left, potentially switching to walk-right. The checker should include this "reset then immediate bump" sequence to confirm that reset does not leave residual direction or fall-count state that would corrupt the first post-reset transition.

Finally, the checker should confirm that reset clears the fall counter, not just the direction. A sequence that falls for, say, 15 cycles, then resets, then falls again for 15 cycles and lands must not splatter, because the counter restarted at zero. This distinguishes a correct reset from one that only rewrites the direction bits.
