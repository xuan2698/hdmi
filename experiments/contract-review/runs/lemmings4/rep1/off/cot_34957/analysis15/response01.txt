The key verification point is that the Moore outputs are a pure function of the current state, and the state must encode three things simultaneously: direction (left/right), activity (walking/falling/digging/splattered), and a fall-duration counter. The checker should treat the fall counter as part of the state, not as an output, and should confirm that the counter only increments while `aaah=1` and only resets on landing or on `areset`.

For the walking state, the transition priority is: fall (if `ground=0`) beats dig (if `dig=1` and `ground=1`) beats bump-switching. So a walking-left Lemming with `ground=0, dig=1, bump_left=1` must enter the falling state with `aaah=1` and must not change direction. A walking-left Lemming with `ground=1, dig=1, bump_right=1` must enter digging, not switch to walking right. Only when `ground=1` and `dig=0` do the bump inputs matter; if both bumps are asserted, the direction still flips (left becomes right, right becomes left), which the checker should test explicitly because a naive XOR or priority encoder can get this wrong.

While falling, bumps and dig are ignored, and the direction is latched. The fall counter increments each sampled cycle in the falling state. On the cycle where `ground` returns to 1, the machine must leave the falling state and resume walking in the latched direction, and the counter must be compared against the splatter threshold at that landing edge. The spec says "more than 20 clock cycles" causes splatter, so the checker should test the boundary: 20 cycles of falling then landing must survive, while 21 cycles must splatter. Because the counter is sampled, the checker must count carefully which sample corresponds to the landing edge.

While digging, the machine stays in digging with `digging=1` until `ground=0`, at which point it falls with `aaah=1` and the latched direction preserved. Bumps during digging are ignored. Digging cannot be entered from falling or from a no-ground condition; a `dig=1` pulse while `ground=0` must be ignored entirely.

The splattered state is absorbing: all four outputs are 0 and remain 0 for any input combination until `areset`. The checker should drive a long fall, land, confirm splatter, then apply `ground=1, dig=1, bump_left=1, bump_right=1` for several cycles and confirm all outputs stay 0. Then assert `areset` and confirm the very next sample shows `walk_left=1` with the fall counter cleared. A subsequent 15-cycle fall and landing must not splatter, proving reset cleared the counter rather than only the direction.

The reset timing is asynchronous and positive-edge triggered, so the checker must apply `areset` such that the reference model's post-reset sample already reflects walk-left. If the testbench asserts reset after the sampled edge, the checker will see a one-cycle lag and produce false mismatches. The checker should also test "reset then immediate bump": assert reset, deassert it before the next sampled edge, and present `bump_right=1` at that next sample; the machine must transition from walk-left to walk-right, confirming no residual direction or counter state survived reset.

One subtlety: the spec says being bumped in the same cycle that ground disappears, or when ground reappears while still falling, does not affect direction. The checker should include a case where `ground` falls to 0 on the same sample as `bump_left=1` while walking right; the machine must enter falling with direction still right, not left. Similarly, on the landing sample with `bump_right=1`, the resumed direction must be the pre-fall direction, not flipped. These cases catch implementations that apply bump logic unconditionally rather than gating it on the walking-and-grounded condition.
