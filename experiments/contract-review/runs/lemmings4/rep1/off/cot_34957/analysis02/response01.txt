# Reset and Power-Up Behavior

The specification states that `areset` is a **positive-edge-triggered asynchronous reset** that returns the Lemming machine to the "walk left" state. Two properties matter for the checker: the reset is *asynchronous*, so it takes effect immediately when `areset` rises rather than waiting for a clock edge; and it is *positive-edge triggered*, so the relevant event is the 0→1 transition of `areset`, not its level. Once asserted, the machine is forced into the initial walking-left configuration: `walk_left=1`, and `walk_right=aaah=digging=0`. The direction memory is set to "left," the fall counter is cleared, and any digging or splattered condition is abandoned. Because the reset is asynchronous, this override must be applied before the normal edge-triggered transition logic is considered; a rising `areset` wins over whatever the clock edge would otherwise have done.

Power-up is the subtler point. The public specification does not describe a separate power-on state distinct from reset; it only defines the reset behavior. The safe interpretation for the checker is that the machine begins in the same walking-left state that reset produces, and that the checker should not rely on any unspecified "unknown" or "don't-care" initial outputs. In other words, before any clock edge and absent an explicit reset pulse, the model should already present the walking-left outputs. This matters because the protocol samples outputs after each positive edge has settled; if the checker instead started from an undefined state, the first sampled row could disagree with a reference model that assumes walking-left initialization.

A second point concerns the interaction of reset with the history-dependent states. The splatter condition depends on accumulated fall duration, and the resume-after-fall behavior depends on stored direction. Reset must clear both: a Lemming that had splattered becomes a normal walking-left Lemming again, and a Lemming that was mid-fall loses its fall count and its remembered direction, restarting as walking left. The checker should therefore treat reset as a full state initialization, not merely as an output override. If reset is asserted while the machine is falling, the fall counter must not survive; otherwise a later ground contact could incorrectly trigger splatter.

A short worked example illustrates the timing. Suppose the machine is walking right and has been falling for several cycles. Then `areset` rises. Immediately—without waiting for `clk`—the outputs become `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`, and the internal direction is left with fall count zero. If a clock edge then occurs while `areset` is still high, the machine remains in this reset state; the edge does not advance it. Only after `areset` returns low does the next edge begin normal transitions from the walking-left state.

For the final Python checker, the useful focus is this: model reset as an asynchronous, edge-triggered override that fully reinitializes state (direction = left, fall counter = 0, mode = walking), and treat power-up as equivalent to that initialized state. Apply the reset check before computing the normal transition, and ensure that mid-input changes occurring after sampling cannot retroactively alter the outputs already sampled for that edge. Keep direction and fall-duration inside the state so that reset genuinely clears them rather than leaving stale history that could corrupt later resume or splatter decisions.
