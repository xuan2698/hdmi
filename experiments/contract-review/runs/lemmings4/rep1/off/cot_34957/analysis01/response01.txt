The key timing point for the checker is that this is a Moore machine sampled after the posedge settles, so every row’s outputs must be a pure function of the state reached by that edge, not of the row’s inputs directly. Inputs listed for a row are the values present before the sampled edge; optional mid-input changes happen after sampling and before the next edge, so they affect only the next row’s transition, never the current row’s outputs.

Because `areset` is positive-edge-triggered asynchronous, a rising edge on `areset` forces the machine to the walk-left state independently of `clk`. The checker should therefore treat reset as an immediate state override: after reset is asserted, outputs must reflect walk-left (`walk_left=1`, others 0), and any mid-input changes while reset is high must not create a different visible state until reset is released and a clock edge is sampled. If reset is released between edges, the next sampled edge starts from the reset state.

For normal operation, the row inputs drive the transition into the state whose outputs are sampled. The precedence rules matter for the transition function: falling dominates digging, and digging dominates direction switching. Thus if `ground=0`, the Lemming enters or remains in the falling state regardless of `dig` or bumps; `aaah=1` and walking/digging outputs are 0. If `ground=1` and the Lemming is walking, `dig=1` starts digging rather than switching direction. Bumps only change direction when the Lemming is walking on ground and not digging. While falling or digging, bumps are ignored for direction. When ground reappears after a fall, the Lemming resumes the direction it had before falling; the checker must preserve that direction across the fall state rather than infer it from the reappearance row’s bumps.

The splatter condition is also state-history dependent: falling for more than 20 clock cycles and then hitting ground produces the terminal all-zero output state forever until reset. The checker should count falling cycles in the state, not from row inputs alone. A bump in the same cycle that ground disappears, or when ground reappears while still falling, does not alter walking direction. Digging continues until `ground=0`, at which point the machine falls and later resumes the original walking direction.

A short worked example: suppose the machine is walking left on ground. A row has `ground=0`, `dig=1`, `bump_left=1`. Because fall has highest precedence, the sampled outputs after that edge are `aaah=1`, with `walk_left=walk_right=digging=0`; the bump and dig are ignored for this transition. If a mid-input change then sets `ground=1` before the next edge, the next sampled state resumes walking left, not right, because the bump during the fall/disappearance cycle did not affect direction.

For the final Python checker, the useful focus is to separate “inputs before the sampled edge” from “mid-input changes after sampling.” Compute outputs only from the stored state after applying reset and the edge transition. Do not let mid-input changes retroactively affect the just-sampled outputs. Also keep direction memory and fall-duration memory inside the state so that resume-after-fall and splatter are handled correctly.
