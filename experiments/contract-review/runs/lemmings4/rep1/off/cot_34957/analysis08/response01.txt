The reset and power-up behavior is the cleanest place to anchor the final checker, because it exposes the two most common implementation mistakes: stale fall history and premature counter clearing.

On power-up, before any clock edge or reset pulse, the machine has no defined history. The public spec says `areset` is positive-edge-triggered asynchronous and resets the Lemming to walk left. The natural reading for a checker is that power-up is equivalent to that reset state: `walk_left=1`, all other outputs 0, fall counter zero, not digging, not splattered. A checker should not assume the simulator's initial register values happen to match; it should either drive `areset` at the start or treat the first sampled state as the reset state. If the design relies on an implicit initial block, that is a simulation convenience, not a spec guarantee.

Asynchronous reset means the reset takes effect without waiting for a clock edge. In a sampled checker, the practical consequence is that a reset asserted before a sampled edge must be reflected in that sample, and a reset asserted between edges must be reflected by the next sample. The checker should apply reset with higher priority than any bump, dig, or ground input in the same cycle. If `areset` and `ground=0` arrive together, the machine is walking left, not falling. If `areset` arrives during a fall, the fall counter must be cleared; otherwise a later, unrelated fall can inherit stale duration and splatter too early.

The subtler reset-adjacent bug is counter clearing on landing. The fall duration must be accumulated while falling, and the landing transition must consult that accumulated value before returning to a walking state. A checker should include a fall of exactly 20 cycles followed by ground (no splatter, resume walking in the prior direction) and a fall of 21 cycles followed by ground (splatter, all outputs 0 forever). It should also test reset during a fall: the machine returns to walking left with zero fall history, and the later landing is irrelevant because it is no longer falling.

Once splattered, no later bump, dig, or ground change may revive the machine; only reset does. The checker should verify persistence across several cycles after splatter, including cycles where `ground=1` and `dig=1` are asserted. Finally, the checker should confirm the fall counter is not shared with digging or walking state, since digging also ends when `ground=0` and then transitions into falling.
