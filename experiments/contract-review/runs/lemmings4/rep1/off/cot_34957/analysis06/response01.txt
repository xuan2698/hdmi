One likely implementation mistake is treating the fall-duration counter as a transient “falling only” signal rather than as state that must be explicitly cleared on reset and on landing. The public spec says a Lemming splatters if it falls for more than 20 clock cycles and then hits the ground. That means the checker must distinguish three things: not falling, falling with a duration of 0 through 20, and falling with a duration greater than 20. If the counter is only incremented while `ground=0` and is not preserved carefully across the transition where `ground` returns to 1, the landing cycle can be misclassified. A common bug is to clear the counter as soon as `ground=1` is seen, before deciding whether the accumulated fall was too long. In that case a fall of 21 cycles followed by ground would look like a normal landing and the machine would resume walking instead of splattering forever.

The reset interaction is another place this mistake shows up. If `areset` occurs during a fall, the machine must return to walking left with no fall history. If the fall counter is not cleared by reset, a later unrelated fall can inherit stale duration and splatter too early. Conversely, if the counter is cleared on every cycle where the machine is not currently in the falling state, then the landing edge itself may erase the evidence needed to detect splatter. The safe interpretation is that the fall duration is accumulated while falling, and the landing transition uses the accumulated value before returning to a walking state. Once splattered, all outputs are 0 forever until reset, so the checker should also ensure that no later bump, dig, or ground change revives the machine.

A short worked example: walking right, then `ground=0` for 21 sampled cycles, then `ground=1` with no bump. The fall duration is 21, so on landing the Lemming splatters: `walk_left=0`, `walk_right=0`, `aaah=0`, `digging=0`, and it stays that way. If the implementation clears the counter when `ground` returns, it will incorrectly resume walking right. If `areset` pulses during the fall, the machine becomes walking left with fall count zero, and the later landing is irrelevant because it is no longer falling.

This matters for the final Python checker because it should test boundary cases around 20 and 21 fall cycles, reset during fall, and splatter persistence. It should also verify that the fall counter is not accidentally shared with digging or walking state. The checker should sample after the positive edge has settled, apply asynchronous reset before the normal transition, and treat power-up as the same initialized state as reset: walking left, fall count zero, not digging, not splattered.
