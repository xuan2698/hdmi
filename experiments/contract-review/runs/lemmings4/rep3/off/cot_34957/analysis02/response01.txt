**Reset and power-up behavior**

The specification makes `areset` a positive-edge-triggered asynchronous reset. That means the reset is not merely another input sampled at the clock edge; it has priority over the normal transition and forces the machine into the initial “walk left” state whenever it is asserted. For the final checker, the cleanest interpretation is: at each sampled edge, first test `areset`. If it is asserted, the post-edge state is the walk-left state, with `walk_left=1` and `walk_right=0`, `aaah=0`, `digging=0`. Only if `areset` is not asserted should the checker evaluate the ordinary transition from the current state using the pre-edge inputs.

Power-up is the same initial condition: before any meaningful history, the Lemming is walking left on ground. The fall counter is zero, the remembered walking direction is left, and the machine is not digging, not falling, and not splattered. This matters because the spec says a falling Lemming resumes “the same direction as before the fall.” If power-up or reset left the remembered direction undefined, the first landing after a reset-induced fall would be ambiguous. The checker should therefore treat reset as restoring both the visible walking-left state and the internal memory needed for later landings.

A subtle point is that reset must also clear any accumulated fall duration and any splattered condition. A splattered Lemming has all four outputs zero forever “until the FSM gets reset.” Thus reset is the only escape from splatter. The checker should not let a long fall counter survive reset, and should not let a prior splatter flag suppress the walk-left outputs after reset.

The mid-input protocol does not change reset behavior. Mid-cycle changes occur after the sampled edge and are carried to the start of the next row; they are not sampled. If `areset` changes mid-cycle, the checker should still use only the value present at the sampled edge for that row’s transition. The asynchronous nature of reset is a hardware description detail; for this row-based checker, the practical rule is simply that an asserted `areset` at the sampled edge overrides everything else.

A short worked example: suppose the machine is splattered with all outputs zero, and at the next sampled edge `areset=1`. The post-edge state is walking left, so the row’s outputs are `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`. Any simultaneous `ground`, `dig`, or bump values are irrelevant because reset has highest priority. If `areset` is instead 0 at that edge, the splattered state persists and all outputs remain zero.

For the final Python checker, the useful rule is: decode outputs from the post-edge state; apply `areset` first with top priority; otherwise apply the normal transition using only pre-edge inputs; ignore mid-inputs entirely for state changes; and enforce fall over dig over bump precedence.
