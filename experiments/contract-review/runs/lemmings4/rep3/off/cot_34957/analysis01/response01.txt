The key timing point for the checker is that this is a Moore machine sampled on the rising edge, so every output row must be a pure function of the state *after* the edge, not of the inputs that were present just before it. The inputs (`bump_left`, `bump_right`, `ground`, `dig`) are driven before the sampled edge and are therefore the inputs that the transition function consumes at that edge. The outputs (`walk_left`, `walk_right`, `aaah`, `digging`) are decoded from the resulting state and must be reported for that same row. In other words: row *n* shows the state reached by applying row *n*'s pre-edge inputs to the state carried out of row *n−1*. A checker that instead decodes outputs from the pre-edge state will be off by one cycle on every transition, which is the single most common failure mode for this problem.

`areset` is positive-edge-triggered and asynchronous. That means it is not merely another input sampled at the clock edge; it can force the machine to the walk-left state between edges. For the checker, the practical consequence is that a row whose pre-edge `areset` is 1 must produce the reset outputs (`walk_left=1`, everything else 0) regardless of prior state, and the reset must be treated as taking effect before the sampled edge settles. Because the reset is asynchronous, a mid-cycle assertion of `areset` (the optional mid-input changes that occur after sampling and before the next edge) must also be honored: the state seen at the next sampled edge is the reset state unless further pre-edge inputs move it. The safest checker model is to apply `areset` with highest priority at the edge, then evaluate the normal transition.

The mid-input changes are explicitly *not* sampled. They occur after the sampling edge and are carried to the start of the next row. This matters because the spec says bumping during a fall, bumping in the same cycle ground disappears, and bumping when ground reappears while still falling do not affect direction. Those are all statements about which inputs are visible at the sampled edge. A mid-cycle bump that is gone by the next sampled edge must have no effect at all; it should not be latched. The checker should therefore ignore mid-input values for state transition purposes and use only the values present at the sampled edge. The mid-inputs exist to test that the design does not accidentally respond to glitches between edges.

Precedence is also a timing concern. At a sampled edge, the transition function must resolve fall over dig over direction-switch. If `ground=0` at the edge, the machine enters or remains in the falling state and increments the fall counter; `dig` and bumps are ignored for direction. If `ground=1` and the machine was falling, it lands: if the accumulated fall exceeded 20 cycles it splatters permanently, otherwise it resumes the remembered direction. Only when walking on ground does `dig=1` start digging, and only then do bumps flip direction. The checker must apply this ordering to the pre-edge inputs and then decode the post-edge state.

Worked example: suppose row *n−1* ends walking left on ground, and row *n*'s pre-edge inputs are `ground=0, dig=1, bump_left=1`. Fall wins, so row *n* outputs `aaah=1` with both walk outputs 0 and `digging=0`; the bump and dig are discarded. If a mid-cycle change then sets `ground=1` before row *n+1*'s edge, row *n+1* lands and resumes walking left, because the remembered direction was never altered.

For the final Python checker: decode outputs from the post-edge state, apply `areset` with top priority at the edge, ignore mid-inputs for transitions, and enforce fall > dig > bump precedence on the pre-edge inputs.
