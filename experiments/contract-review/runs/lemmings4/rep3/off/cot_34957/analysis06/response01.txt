One likely implementation mistake is to treat the fall counter as a simple “currently falling” flag or to reset it too early, rather than as a count of consecutive cycles spent in the falling state that is preserved until the landing edge. The public spec makes the splatter rule depend on duration: a Lemming splatters only if it “falls for more than 20 clock cycles then hits the ground.” That means the checker must distinguish three moments: the edge where `ground=0` causes the Lemming to begin falling, each subsequent edge while `ground=0` and the Lemming remains falling, and the edge where `ground=1` causes landing. The landing test must use the accumulated fall duration as of that landing edge, not a value cleared when ground reappears and not a value incremented after the landing decision.

A common bug is to clear the fall counter on the same edge that ground returns, before deciding whether the fall was too long. Another is to count only cycles where `aaah=1` is observed, which can be off by one depending on whether the first falling cycle is included. The spec’s wording “falls for more than 20 clock cycles then hits the ground” implies that the checker should model the number of cycles spent falling before the landing edge, and then compare that count against the threshold. If the count exceeds 20, the post-edge outputs must all be zero and the machine must remain splattered until reset. If the count is 20 or less, the Lemming resumes walking in its remembered direction.

A short worked example: suppose the Lemming is walking left on ground, then `ground=0` occurs. That edge starts falling; the remembered direction remains left. If ground stays 0 for exactly 20 further sampled edges and then `ground=1` appears, the landing edge should not splatter if the implementation interprets “more than 20” strictly. But if the implementation increments the counter on the landing edge before testing, it may incorrectly splatter. Conversely, if it clears the counter when `ground=1` is seen and then tests, it may never splatter at all. The final checker should therefore make the fall-duration semantics explicit and consistent with the threshold, and should verify that the landing edge uses the accumulated count before any reset of fall state. This is especially important because bumps on the landing edge are ignored for direction, so the landing transition must be handled as a single prioritized event: test splatter using the accumulated fall count, then either splatter or resume walking in the remembered direction, without letting bump inputs alter that direction on the same edge.
