The timing model matters most at the boundary between a sampled edge and the optional mid-cycle input changes. Each row’s inputs are driven before the sampled edge; the machine’s next state and outputs are evaluated after that edge has settled. Any mid-cycle changes occur after sampling and before the opposite edge, and they are carried forward to the start of the next row. For the final Python checker, this means the checker should treat the sampled edge as the decision point for state transitions and Moore outputs, while mid-cycle changes should only affect the inputs seen at the next sampled edge. In particular, a mid-cycle `ground=0` or `ground=1` should not retroactively alter the fall counter or landing decision of the edge that has already been sampled.

The critical timing point is the fall counter around landing. The Lemming begins falling on the sampled edge where it was walking on ground and `ground=0` is observed. While `ground=0`, each subsequent sampled edge while still falling extends the fall duration. The landing edge is the sampled edge where `ground=1` is observed while the machine is in the falling state. At that edge, the splatter decision must use the accumulated fall duration as of that landing edge, before any clearing or resetting of fall state. If the accumulated duration is more than 20 clock cycles, the post-edge outputs must all be zero and the machine must remain splattered until `areset`. If the duration is 20 or less, the Lemming resumes walking in the direction remembered from before the fall.

A common checker mistake is to clear the fall counter on the same edge that `ground=1` is seen, before deciding whether the fall was too long. Another is to count only cycles where `aaah=1` is observed, which can be off by one depending on whether the first falling cycle is included. The spec’s phrase “falls for more than 20 clock cycles then hits the ground” implies that the checker should model the number of cycles spent falling before the landing edge, then compare that count against the threshold. If the count exceeds 20, the post-edge outputs must all be zero and the machine must remain splattered until reset. If the count is 20 or less, the Lemming resumes walking in its remembered direction.

A short worked example: suppose the Lemming is walking left on ground, then `ground=0` occurs. That edge starts falling; the remembered direction remains left. If ground stays 0 for exactly 20 further sampled edges and then `ground=1` appears, the landing edge should not splatter if the implementation interprets “more than 20” strictly. But if the implementation increments the counter on the landing edge before testing, it may incorrectly splatter. Conversely, if it clears the counter when `ground=1` is seen and then tests, it may never splatter at all. The final checker should therefore make the fall-duration semantics explicit and consistent with the threshold, and should verify that the landing edge uses the accumulated count before any reset of fall state. This is especially important because bumps on the landing edge are ignored for direction, so the landing transition must be handled as a single prioritized event: test splatter using the accumulated fall count, then either splatter or resume walking in the remembered direction, without letting bump inputs alter that direction on the same edge.
