The interface is five one-bit inputs and four one-bit outputs, so every port is a scalar logic value rather than a bus. `areset`, `bump_left`, `bump_right`, `ground`, and `dig` are each 1 bit wide; `walk_left`, `walk_right`, `aaah`, and `digging` are likewise 1 bit wide. There are no multi-bit fields, no signed quantities, and no arithmetic ports. The only internal numeric quantity implied by the specification is the fall-duration counter, which is not a port and therefore does not appear in the interface widths. Its boundary is the threshold “more than 20 clock cycles,” so the relevant comparison is against 20, not 19 or 21; a fall of exactly 20 cycles is not splattering, while 21 or more is.

The output encoding is one-hot in intent but not guaranteed one-hot in every state: walking left asserts only `walk_left`; walking right asserts only `walk_right`; falling asserts only `aaah`; digging asserts only `digging`; splattered asserts none of the four. Reset forces the walking-left state, so immediately after reset the outputs are `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`. Because this is a Moore machine, outputs are a function of the post-edge state alone, not of the current input values. That matters for the checker: inputs sampled at an edge determine the next state, and the outputs reported for that row must correspond to the state after the edge has settled.

Boundary behavior around reset is important. Reset is positive-edge-triggered and asynchronous, and it has highest priority. It must clear both the remembered walking direction and any accumulated fall duration, and it must clear splatter. A splattered Lemming has all four outputs zero and remains that way forever unless reset occurs. Thus a row with `areset=1` must never retain splatter, fall count, or prior direction; all other inputs in that row are irrelevant for the state transition.

For non-reset rows, precedence is fall, then dig, then bump/direction change. If walking on ground and `ground=0`, falling begins immediately and simultaneous `dig` or bumps do not alter remembered direction. While falling, bumps and `dig` are ignored. The fall counter increments per cycle spent falling. When ground returns, landing occurs: if the fall duration exceeded 20, the machine splatters; otherwise it resumes walking in the remembered direction. A bump in the same cycle ground disappears, or in the same cycle ground reappears while still falling, does not affect direction memory. A walking Lemming on ground may begin digging when `dig=1`; digging continues until `ground=0`, then it falls and later resumes walking in the original direction. Bumps while digging are ignored. If `dig=1` while falling or with no ground, it is ignored. If digging and bumping coincide on ground, digging wins.

A short worked example: if the machine is splattered and the next sampled edge has `areset=1`, the post-edge state is walking left, so the row outputs are `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`, regardless of `ground`, `dig`, or bump values. If `areset=0`, splatter persists and all four outputs remain zero.

For the final Python checker, the useful point is to decode outputs from the post-edge state, apply `areset` first with top priority, otherwise transition using only pre-edge inputs, ignore mid-input changes for state updates, and enforce fall over dig over bump precedence.
