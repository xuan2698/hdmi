**Reset and power-up analysis**

The machine has one asynchronous reset input, `areset`, and the public spec makes it positive-edge triggered. That means the checker should not model reset as a level-sensitive clear that holds the state down for as long as `areset` is high. Instead, the meaningful event is the rising edge of `areset`. When that edge occurs, the Lemming machine is forced immediately—independently of `clk`—into the walk-left state. In output terms, after reset has settled, the Moore outputs must be `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`.

Power-up behavior is not separately specified beyond this reset. The safe checker interpretation is that the machine begins in the same walk-left state that reset produces, with the fall counter cleared and no splatter condition pending. Any test that starts without an explicit reset should therefore expect walk-left outputs, not an unknown or don't-care state. If the checker wants to be strict, it can require an initial reset edge before trusting any row, but it should not invent a different power-up state.

The reset must clear more than the visible walking direction. It must also clear the internal fall-duration counter and any internal flag that records that the Lemming has splattered or is doomed to splatter on landing. A common bug is to reset the walking state but leave a stale fall counter or a stale splatter latch. If that happens, a Lemming that was reset in mid-fall could later land and splatter even though the fall count should have been discarded. The checker should therefore include reset-during-fall and reset-after-long-fall scenarios, then verify that the Lemming walks left normally and can fall for a short duration without splattering.

Because reset is asynchronous, a reset edge between sampling edges can change the state before the next sampled row. The checker should apply the reset event at the point the protocol says it occurs, then evaluate the next row from the reset state. It should not require the reset to wait for a clock edge, and it should not let a mid-cycle reset be ignored until the following clock.

**Worked example.** Suppose the Lemming is walking right and has been falling for 15 cycles when `areset` rises. The reset immediately forces walk-left and clears the fall counter. On the next sampled row, even if `ground=0`, the machine is in walk-left with a fresh counter; it is not still carrying the old 15-cycle fall. If it then falls for 20 cycles and lands, it must survive, because the pre-reset fall history was erased.

The key point for the final Python checker: treat `areset` as an asynchronous positive-edge event that reinitializes the entire machine state, including hidden counters and splatter latches, and verify that no pre-reset fall history leaks across that event.
