**Reset and power-up behavior**

The machine has a single asynchronous reset, `areset`, which is positive-edge triggered. That means the reset is not sampled relative to `clk`; whenever `areset` makes a 0→1 transition, the Lemming machine is forced immediately into its initial state, independent of the clock. The initial state is "walking left": `walk_left=1`, and `walk_right=0`, `aaah=0`, `digging=0`. Because this is a Moore machine, those outputs are a function of state alone, so the reset state fully determines the outputs until the next state transition.

For the checker, the important consequence is that reset is an event, not a level to be evaluated only at rising edges. If the testbench drives `areset` high between sampled edges, the machine must already be in the walk-left state by the time the next row is sampled. The row-by-row protocol described in the prompt says each row's inputs are driven before the sampled edge and optional mid-cycle changes occur after sampling; a reset pulse is one such mid-cycle event. Therefore the checker should treat an asserted `areset` as overriding whatever transition would otherwise have occurred, and the next sampled row should observe the walk-left outputs. If `areset` is held high across multiple rows, the machine remains in walk-left for all of them, and any bumps, ground loss, or dig commands during that interval are irrelevant.

Power-up is the weaker case. The specification only defines behavior after `areset`; it does not promise a particular state if the simulation begins without a reset pulse. A robust checker should therefore either begin with an explicit reset assertion or treat the first sampled row as following a reset. It should not assume that an un-reset machine starts in walk-left, because only the asynchronous reset guarantees that. In practice, the seed-based stimulus should include an initial `areset` pulse so that the first meaningful row is well-defined.

One more point matters for the checker: reset is asynchronous, so it can interrupt a fall, a dig, or a splattered state. A splattered Lemming stays splattered "forever (or until the FSM gets reset)" — so `areset` is the only escape from splatter. The checker must allow reset to clear splatter and return to walk-left, and must not require any particular number of cycles before that happens.

**Worked example.** Suppose the machine is walking left and a row has `ground=0`, `dig=1`, `bump_left=1`. Fall wins, so the next state is falling with `aaah=1` and the old left direction retained. If `areset` pulses before the following sampled edge, the next row must instead show `walk_left=1` with all other outputs 0, regardless of the fall count.

The useful takeaway for the final Python checker: model `areset` as an immediate state override applied between rows, not as an input bit folded into the normal transition function, and never infer a power-up state without reset.
