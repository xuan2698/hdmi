The key distinguishing scenario for the final checker is the interaction between an over-long fall and a reset that arrives while the machine is still airborne. Consider a Lemming that has been falling for, say, 25 cycles. At this point the fall counter is already past the splatter threshold, but the machine has not yet splattered because it has not touched ground. The outputs are `aaah=1`, everything else 0, and the retained walking direction is whatever it was before the fall began. Now two things can happen on the next sampled edge.

First, if `ground=1` arrives with no reset, the Lemming lands. Because the fall exceeded 20 cycles, it splatters: all four outputs become 0 permanently, and the retained direction is irrelevant. This is the only way to reach the splatter state, and it must be distinguished from a normal landing where the Lemming resumes walking in its retained direction with `aaah` cleared.

Second, if `areset` pulses instead (or simultaneously), the asynchronous reset overrides everything. The next sampled row must show `walk_left=1` and all other outputs 0, with the fall counter cleared. Crucially, the checker must not let the pending "over-long fall" flag survive the reset and cause a spurious splatter on a later landing. A naive implementation that keeps a separate "doomed" latch set once the counter passes 20, without clearing it on reset, would fail here: after reset the Lemming walks left, then later falls briefly and lands, and the stale doomed flag would wrongly zero the outputs. So reset must clear the fall counter and any derived splatter-pending condition together.

A second useful point is the same-cycle precedence at the moment ground disappears while digging. Suppose the machine is digging with `ground=1`. A row arrives with `ground=0` and `dig=1`. Digging cannot continue without ground, so the machine transitions to falling, sets `aaah=1`, clears `digging`, and retains the original walking direction. If `bump_left=1` also appears in that same row, the bump is ignored for direction purposes because the fall transition takes precedence and bumps do not affect the retained direction during the ground-disappearance cycle. The checker should verify that the retained direction after this fall matches the direction the Lemming had before it started digging, not some direction implied by the bump.

A third point: reset during digging must clear `digging` and force `walk_left`, even if the Lemming had been walking right before digging. The retained direction is overwritten by reset, so a subsequent fall-and-land resumes leftward, not rightward. This is easy to get wrong if the checker stores direction separately from the reset override.

The worked example above (walking left, `ground=0`, `dig=1`, `bump_left=1`, then a reset before the next edge) captures the essential discipline: fall precedence sets `aaah` and retains left, but the reset between rows must wipe the fall state and produce a clean `walk_left` row. The final checker should apply `areset` as an immediate override between sampled rows, clear the fall counter and any splatter-pending latch, and never carry fall history across a reset.
