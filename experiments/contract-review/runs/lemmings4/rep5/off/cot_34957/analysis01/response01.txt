The timing question that matters most for the checker is this: the machine is a Moore FSM, so the four outputs are a pure function of the current state, and the state is updated only on the rising edge of `clk`. Therefore every sampled row must be interpreted as "state after the edge that ends this row," and the inputs listed in that row are the inputs that were present *before* that edge (the values driven during the preceding interval). The prose "sample after the posedge edge has settled" confirms this: the row's outputs are read after the edge, while the row's inputs are the settled pre-edge values that the transition consumed.

Concretely, for row *n* the checker should (1) take the inputs of row *n*, (2) apply the transition function to the state that was in force during row *n* (i.e., the state produced by row *n-1*'s edge, or the reset state for the first row), and (3) compare the resulting next state's outputs against row *n*'s outputs. Equivalently, outputs of row *n* are the Moore outputs of the state *after* consuming row *n*'s inputs. This is the standard "inputs and outputs on the same row describe one edge" convention, and it is the one that makes the reset row consistent: `areset` is asynchronous and positive-edge triggered, so a row with `areset=1` forces the state to walk-left regardless of prior state, and that row's outputs must be `walk_left=1`, everything else 0.

The "mid-input changes occur AFTER sampling, before the other edge, and are carried to the start of the next row" clause is the second key point. It means the checker must not treat a mid-cycle change as belonging to the current row. The current row's inputs are frozen at the sampling instant; any change that happens between the sampling edge and the next rising edge is simply the input value that will be seen at the *next* rising edge, i.e., it becomes the next row's input. So the checker should build the input sequence row-by-row from the sampled values only, and ignore mid-cycle toggles except insofar as they define the next row's driven values. In practice: read row *n*'s inputs, compute transition, compare outputs; then read row *n+1*'s inputs (which already incorporate any mid-cycle change), compute transition from the new state, compare. No special "mid" handling is needed beyond using each row's own input vector exactly once.

A short worked example clarifies precedence. Suppose the state is walking-left on ground, and in one row `ground=0`, `dig=1`, `bump_left=1`. Fall has highest precedence, so the Lemming enters falling (`aaah=1`, others 0) and the dig and bump are ignored. The next row, if `ground=1` and the fall lasted only one cycle, the Lemming resumes walking left (original direction preserved), so `walk_left=1`. If instead the fall had persisted for more than 20 cycles before that `ground=1` row, the transition on the landing edge yields the splattered state, and all four outputs are 0 forever until `areset`. Note the splatter decision is made on the landing edge using the accumulated fall count, not on any mid-air row; mid-air rows only increment the counter and output `aaah=1`.

The subtle trap for the checker is the "bumped in the same cycle as ground disappears, or when ground reappears while still falling, does not affect direction" rule. Because the transition is a single function of (state, inputs), the checker must encode this as: direction changes only when the Lemming is in a walking state and not transitioning to fall/dig on that same edge. If `ground=0` and a bump arrive together while walking, the next state is falling with the *old* direction retained; the bump is discarded. Likewise on the landing edge, a bump is discarded and the pre-fall direction is restored. Encoding this as precedence (fall > dig > bump) inside one combinational next-state function, evaluated once per row, is exactly what the row-by-row checker needs.
