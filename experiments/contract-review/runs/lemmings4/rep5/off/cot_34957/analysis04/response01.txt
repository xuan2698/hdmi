The interface is narrow and entirely one-bit: five inputs (`areset`, `bump_left`, `bump_right`, `ground`, `dig`) and four outputs (`walk_left`, `walk_right`, `aaah`, `digging`). Because every port is width 1, there are no multi-bit boundary values to worry about; the only meaningful values are 0 and 1. The checker should therefore treat each sampled row as a five-bit input vector and compare against a four-bit output vector, with no masking or truncation concerns. The one subtlety is that `areset` is asynchronous and positive-edge triggered, so it is not an ordinary synchronous input: it can override the state between sampled edges, and the checker must apply it as an immediate reset rather than as a bit participating in the normal transition function.

The boundary conditions that matter are temporal, not numeric. The fall counter is the only internal quantity with a threshold: a fall of more than 20 clock cycles followed by landing causes splatter, after which all four outputs are 0 forever until reset. Exactly 20 cycles is safe; 21 or more splatters. The checker must count cycles spent in the falling state, reset that count when ground returns, and must not splatter in mid-air — only on the cycle where ground reappears after an over-long fall. Reset during a fall must clear both the fall counter and `aaah`; reset during digging must clear `digging`; reset during walking must force leftward walking even if the Lemming had been walking right.

Power-up is the weaker case. The public specification defines behavior after `areset` but does not promise a particular state if simulation begins without a reset pulse. A robust checker should either begin with an explicit reset assertion or treat the first sampled row as following a reset. It should not assume an un-reset machine starts in walk-left, because only the asynchronous reset guarantees that. In practice, the seed-based stimulus should include an initial `areset` pulse so that the first meaningful row is well-defined.

For the normal transition function, the checker should preserve the precedence rules: falling has higher precedence than digging, which has higher precedence than direction switching. A walking Lemming on ground can dig when `dig=1`; a falling Lemming ignores `dig`; a digging Lemming continues until `ground=0`, then falls while retaining its original walking direction. Bumps do not affect direction while falling or digging, and bumps in the same cycle as ground disappearance or reappearance do not affect the retained direction. The fall counter increments only while falling and resets when ground returns; if the fall lasted more than 20 cycles before landing, the machine enters splatter and all outputs become zero until reset.

**Worked example.** Suppose the machine is walking left and a row has `ground=0`, `dig=1`, `bump_left=1`. Fall wins, so the next state is falling with `aaah=1` and the old left direction retained. If `areset` pulses before the following sampled edge, the next row must instead show `walk_left=1` with all other outputs 0, regardless of the fall count.

The useful takeaway for the final Python checker: model `areset` as an immediate state override applied between rows, not as an input bit folded into the normal transition function, and never infer a power-up state without reset.
