# Reset and Power-Up Analysis

The asynchronous reset (`areset`, positive-edge triggered) is the only mechanism that returns the Lemming machine to a known state. On assertion, the machine must be forced to the walking-left state: `walk_left=1`, and `walk_right=aaah=digging=0`. Crucially, reset must also clear any internal bookkeeping that the Moore outputs do not directly expose — specifically the fall-duration counter and the latched walking-direction memory. If reset only cleared the visible outputs but left the fall counter or direction latch intact, a subsequent short fall could inherit a stale count and splatter incorrectly, or the Lemming could resume walking in the wrong direction after reset. The checker should therefore treat reset as a full state wipe, not merely an output override.

Power-up behavior is the same as reset behavior: before any clock edge, the machine is assumed to be in the walk-left state with a zero fall counter and no latched direction. The first sampled edge after power-up (absent reset) should behave as if the Lemming has been walking left indefinitely. This matters because the fall counter must start at zero, not at some arbitrary value; a power-up that begins mid-fall is not a legal scenario under this spec, so the checker need not model it, but it should confirm that the very first post-power-up edge does not spuriously splatter.

The most useful point for the final Python checker is the separation of the fall counter from the walking-direction latch, and the fact that both are reset-cleared but only the counter is landing-cleared. The counter increments once per sampled edge while the machine is in the falling state, and is evaluated only on the transition where `ground=1` arrives while falling. A count of exactly 20 at landing is safe; 21 splatters. Mid-air cycles never splatter, and the counter must not be incremented on the same edge that ground disappears (that edge enters falling but does not yet count as a fall cycle) nor on the landing edge itself. The checker should drive a fall of exactly 20 cycles, land, and confirm `walk_*` resumes; then drive 21 cycles, land, and confirm all four outputs go to zero permanently until reset.

A second checker-relevant point: the direction latch is written when ground disappears (capturing the current walking direction) and read on landing. Bumps on the disappearance edge, during the fall, and on the reappearance edge must all be ignored for direction purposes. The checker can verify this by asserting `bump_left` and `bump_right` on those specific edges and confirming the resumed direction matches the pre-fall direction.

Worked example: walking right, `ground=1`, `dig=1`, `bump_left=1` on one edge. Dig outranks bump, so the machine enters digging with right-direction memory and discards the bump. Next edge `ground=0`: digging ends, machine falls (`aaah=1`), direction memory still right. Falling edges with `bump_right=1` change nothing. Then `ground=1` with fall count ≤20: machine resumes `walk_right=1`. The checker should confirm the direction never flipped and that exactly one of the four outputs is asserted throughout, with all zero only after a genuine >20-cycle landing splatter.
