# Reset and Power-Up Analysis

The specification defines `areset` as positive-edge triggered and asynchronous. That single sentence carries most of the reset burden for the checker, and it is worth separating what it does and does not imply.

**Asynchronous assertion.** A rising edge on `areset` must force the Lemming machine into the walk-left state without waiting for `clk`. The canonical post-reset output vector is `walk_left=1`, `walk_right=0`, `aaah=0`, `digging=0`. The checker should accept this as the state the machine occupies the instant `areset` rises, and should treat any sampled row with `areset=1` as requiring exactly that vector. Because the reset is asynchronous, the checker must not insist that the reset transition be aligned to a `clk` edge; a reset that arrives between edges is still valid and still forces the walk-left state.

**Reset clears history.** Reset is not merely a direction override. It must also clear the fall counter, the digging flag, and the splattered flag. A Lemming that had splattered, or that was mid-fall with a large accumulated fall count, must come out of reset as a fresh walker. The checker should therefore reject any trace in which a post-reset row shows residual `aaah`, residual `digging`, or a splattered (all-zero) output vector that persists after `areset` has been asserted. Equivalently: after reset deasserts, the machine must behave as if it had just been created walking left on ground, with no memory of prior bumps, digs, or falls.

**Deassertion and resumption.** Once `areset` returns low, ordinary synchronous sampling resumes on the next rising `clk` edge. The first non-reset sampled row should reflect the walk-left state acted on by whatever inputs are present at that edge, following the normal precedence (fall > dig > bump). The checker should not require an extra "settling" cycle after reset; the very next sampled edge is a normal edge.

**Power-up.** The spec does not describe a separate power-up state distinct from reset. The safe reading for the checker is that the machine begins in the walk-left state, identical to the post-reset state, and that any ambiguity about initial conditions is resolved by the first `areset`. Traces that begin without an explicit reset should still be checked against walk-left as the initial state, but the checker should not penalize a design that relies on reset to establish it.

**Interaction with mid-cycle changes.** The asynchronous reset is the one input whose effect is not deferred to the next sampling edge. A mid-cycle `areset` rise changes the state immediately, so outputs observed after that rise (even before the next `clk` edge) must reflect walk-left. This is the exception to the general rule that mid-cycle input changes only affect the following edge. The checker should treat `areset` as taking effect at the moment it rises, while all other inputs (`bump_left`, `bump_right`, `ground`, `dig`) take effect only at the next sampled edge.

**Worked example.** Suppose the machine is walking right, has been falling for 25 cycles, and `areset` rises mid-cycle. The outputs must immediately become `walk_left=1`, others 0, and the fall counter must be cleared. If `ground=1` at the next `clk` edge with no bumps and no dig, the sampled outputs remain walk-left; the long fall must not cause splatter, because reset erased the fall history.

The key point for the final checker: reset is both asynchronous in timing and total in effect—it forces walk-left and wipes fall/dig/splatter memory—so no pre-reset history may leak into any post-reset sampled row.
