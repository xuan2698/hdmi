The public interface is a 16-bit BCD counter with a single 1-bit synchronous active-high reset input and two outputs: a 16-bit `q` and a 3-bit `ena`. The 16-bit `q` is partitioned into four 4-bit BCD digits: `q[3:0]` is the ones digit, `q[7:4]` the tens, `q[11:8]` the hundreds, and `q[15:12]` the thousands. Each digit is nominally in the range 0–9, so the legal encoding space of `q` is far smaller than 2^16; the checker should treat each nibble as a decimal digit and reason about carries at the 9→0 boundary rather than as a plain binary increment. The 3-bit `ena` output corresponds to the upper three digits: `ena[0]` for the tens digit, `ena[1]` for the hundreds, and `ena[2]` for the thousands. There is no enable for the ones digit, since the ones digit increments every clock when not reset.

Boundary values matter. The ones digit increments on every enabled edge and wraps 9→0, passing a carry to the tens digit on that same edge. The tens digit increments only when the ones digit is 9 (so `ena[0]` is high), wraps 9→0, and passes a carry to the hundreds. Likewise the hundreds increments only when both lower digits are 9, and the thousands only when the lower three are 9. Thus the maximum state is `16'h9999`; the next enabled edge wraps all four digits to `16'h0000`. The enables are purely combinational functions of the pre-edge `q`: `ena[0] = (q[3:0] == 9)`, `ena[1] = (q[7:4] == 9) && (q[3:0] == 9)`, and `ena[2] = (q[11:8] == 9) && (q[7:4] == 9) && (q[3:0] == 9)`. They are not gated by reset in the public description; they reflect the pre-edge digits regardless of the sampled reset value.

Reset is synchronous and active-high and is reset-dominant for the next state: if the sampled `reset` is 1 at the posedge, the next `q` is forced to 0. The enables, however, still derive from the pre-edge `q`, so a reset edge can show nonzero enables while forcing `q` to zero on the following state. The checker must compute enables from the captured pre-edge `q` independently of the captured reset, and compute next `q` with reset taking priority over the normal BCD increment.

The protocol ordering is the key correctness point. Each row drives its inputs before the sampled posedge; optional mid-cycle changes occur after sampling and before the other edge and are carried into the next row. Therefore a row's outputs are determined solely by the `reset` and `q` values present at that row's posedge. A mid-cycle reset assertion does not affect the current row; it only changes the reset value the next row samples. The checker should capture `reset` and `q` at the posedge, compute `ena` and next `q` from those captured values, then apply mid changes only to the following row's inputs. Applying an end-of-row reset to the same row would reset one cycle early.

Worked example: pre-edge `q = 16'h0099`, sampled `reset = 0`. Ones and tens are 9, so `ena[0]=1`, `ena[1]=1`; hundreds is 0, so `ena[2]=0`. Next state wraps ones and tens to 0 and increments hundreds to 1: `q = 16'h0100`. A mid-cycle reset rise afterward leaves this row's `q=0100` intact; the next row samples `reset=1` and forces `q=0`.
