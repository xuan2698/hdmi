The public interface is a 16-bit BCD counter with a single 1-bit synchronous active-high reset input and two outputs: a 16-bit `q` and a 3-bit `ena`. The `q` output is partitioned into four 4-bit BCD nibbles: `q[3:0]` is the ones digit, `q[7:4]` the tens, `q[11:8]` the hundreds, and `q[15:12]` the thousands. Each nibble is constrained to the legal BCD range 0–9; values 10–15 are not valid counter states and should not appear in a correct trace. The `ena` output is 3 bits wide, with `ena[0]` corresponding to the tens digit, `ena[1]` to the hundreds digit, and `ena[2]` to the thousands digit. There is no enable bit for the ones digit, since the ones digit increments on every non-reset clock edge.

The boundary behavior of `ena` is the most error-prone part of the specification. An upper digit's enable is asserted only when all lower digits are simultaneously 9, not merely the immediately adjacent digit. Concretely, `ena[0]` (tens enable) is high exactly when `q[3:0] == 9`. `ena[1]` (hundreds enable) is high exactly when `q[3:0] == 9` and `q[7:4] == 9`. `ena[2]` (thousands enable) is high exactly when `q[3:0] == 9`, `q[7:4] == 9`, and `q[11:8] == 9`. This cumulative condition means that for `q = 16'h0099`, `ena = 3'b011`; for `q = 16'h0999`, `ena = 3'b111`; and for `q = 16'h9999`, `ena = 3'b111`. A checker that tests only the next-lower digit would incorrectly produce `3'b001` for `0099` and `3'b010` for `0999`, so the final Python checker must implement the full cumulative conjunction rather than a per-digit local test.

The next-state `q` is computed from the captured `q` with reset priority. If `reset` is high at the sampled edge, the next `q` is `16'h0000` regardless of the current digits. Otherwise each digit increments according to the same cumulative carry condition, with BCD wrap 9→0 and the full word wrapping `9999`→`0000`. The critical distinction is that `reset` overrides only the state update, never the enable outputs. Enables are computed from the captured `q` unconditionally. A common bug is to gate `ena` with `reset` (forcing `3'b000` when reset is high) or to derive `ena` from the post-reset next state; both are wrong.

Worked example: captured `q = 16'h0009`, `reset = 1`. The ones digit is 9, so `ena[0] = 1`; tens is 0, so `ena[1] = 0`; hundreds is 0, so `ena[2] = 0`. Correct outputs are `ena = 3'b001` and next `q = 16'h0000` (reset wins over the normal increment to `16'h0010`). A checker that zeroes enables under reset would expect `ena = 3'b000` and fail.

Mid-cycle input changes occur after sampling and before the other edge, and are carried to the start of the next row. They must not affect the current row's captured `q`, `ena`, or next-state computation. In particular, a mid-cycle reset assertion applies to the following sampled edge, not the one just processed; applying it early creates an off-by-one-cycle mismatch exactly where reset first appears. The checker should treat each row as: drive inputs, sample at posedge, compute outputs from the sampled values, then allow mid changes to seed the next row. Finally, compare `q` digit-by-digit as four BCD nibbles rather than as a binary integer, and include boundary cases such as `0099`, `0999`, `9999`, and reset-high-with-trailing-9 states.
