**Reset and power-up behavior**

The specification defines a synchronous, active-high reset. This means `reset` is sampled on the same clock edge as `q` and `ena`; it is not an asynchronous clear. Consequently, the checker must not expect `q` or `ena` to change merely because `reset` is high between edges. Only the value of `reset` present at the sampled edge governs the row's behavior. If `reset` is asserted after a row has been sampled (a mid-cycle change), that assertion affects only the next sampled row, not the row already captured. The checker should therefore treat each row as a self-contained snapshot: the `ena` bits observed in a row are a function of the `q` bits observed in that same row (gated by that row's `reset`), and the `q` observed in the next row is the BCD increment of the current `q` under those same enables. There is no cross-row enable derivation.

The most useful point for the final checker is to enforce this row-local pairing explicitly and to gate enables on reset. A lagging implementation that registers the "all nines" condition will present enables one cycle late: at `q = 0099` it might show `ena = 000` and only at `q = 0100` show `ena = 011`. A checker that derives expected enables from the next state, or compares enables to the previous row's digits, would accept that lag. The correct check is: for the sampled row, compute expected `ena` from the sampled `q` (and force `000` if `reset = 1`), compare directly; then independently compute the expected next `q` as the BCD increment of the sampled `q` under those enables (or `0000` if `reset = 1`) and compare against the next row's sampled `q`.

Worked example: suppose row A samples `q = 0099`, `reset = 0`. Expected `ena = 011` (ones is 9, tens is 9, hundreds is 0). Expected next `q = 0100`. If the DUT instead shows `ena = 000` at row A and `ena = 011` at row B where `q = 0100`, the row-local enable check fails at row A even though the `q` sequence is correct. Conversely, if row A samples `reset = 1` with `q = 0099`, expected `ena = 000` and expected next `q = 0000`; a checker that ignores reset gating would wrongly demand `011`.

Power-up is unspecified, so the checker should not assume any `q` or `ena` before the first reset row or first defined counting row. Begin enforcing the row-local relationship from the first row whose behavior is determined by sampled inputs and synchronous reset, typically the first `reset = 1` row, and continue thereafter. Mid-cycle reset changes after sampling apply only to the next row and must not retroactively alter the current row's expected enables or next-state prediction.
