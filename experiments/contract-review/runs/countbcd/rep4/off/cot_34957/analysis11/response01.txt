The most useful point for the final checker is that the enable outputs are **combinational functions of the current sampled `q`**, not registered outputs that describe the *next* increment. This distinction is what makes the row-local invariant so sharp, and it is also the easiest place for a plausible-looking implementation to be subtly wrong.

Consider the natural mental model of a BCD counter: "when the ones digit is 9, the tens digit should increment on the next clock." A designer might therefore register the enables alongside the digits, so that `ena[0]` (tens enable) is high during the cycle *after* the ones digit has reached 9 — i.e., the enable is asserted in the same row where the tens digit is about to change. That is a one-cycle-late enable. The public spec instead ties enables to the *current* digits: `ena[0] = (ones == 9)`, `ena[1] = (ones == 9 && tens == 9)`, `ena[2] = (ones == 9 && tens == 9 && hundreds == 9)`. So in the row where `q = 0099`, the enables are `011` (tens and hundreds enabled), and the *next* row shows `q = 0100` with enables `000`. The enable and the digit that will change are in the same sampled row.

This matters for the checker because it must compare `ena` against the digits latched **in that same row**, and separately compare the next row's `q` against the BCD increment of those same latched digits. If the checker instead derived expected enables from the *next* state, or compared enables to the previous row's digits, it would accept a lagging implementation. The worked example in the spec makes the failure concrete: at `q = 0099`, a lagging design might present `ena = 111` (because it is still reacting to `q = 0009`-style conditions one cycle back, or because it registered the "all nines" pulse), and the row-local check flags it immediately even if the subsequent `q` sequence is correct.

A second, related trap is the reset row. Because reset is synchronous and active-high, the sampled row with `reset = 1` must show `ena = 000` and next `q = 0000`. A checker that computes enables purely from the latched digits would wrongly expect `011` at `q = 0099` even under reset. The reset must gate the enable computation, not just the state update. Equally, a mid-cycle reset change after sampling belongs to the next row and must not retroactively rewrite the current row's expected enables.

Finally, power-up is unspecified: before the first reset or the first valid counting row, the checker must not assume any particular `q` or `ena`. It should only begin enforcing the row-local relationship once a row's behavior is determined by sampled inputs and synchronous reset — typically from the first reset row onward. This avoids false failures on uninitialized state while still catching misalignment as soon as a defined row appears.
