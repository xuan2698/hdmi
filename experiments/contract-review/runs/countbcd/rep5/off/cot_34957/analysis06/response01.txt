One common implementation mistake is to derive the three enable outputs from the post-edge counter value rather than from the pre-edge value that was present when the clock edge was sampled. The public specification says the enables indicate when each of the upper three digits *should be incremented* at that edge. That is a combinational function of the state immediately before the edge, not of the state after the edge has already updated. A checker that samples `q` after the posedge and then computes `ena` from that new `q` will disagree with correct hardware on every carry row.

The reason is that a carry changes the very digits that justify the enable. For example, consider a pre-edge state where the ones digit is 9 and the tens digit is 9, with reset low. The tens digit should increment because the ones digit is 9, and the hundreds digit should increment because both the ones and tens digits are 9. At the edge, the ones and tens digits wrap to 0 and the hundreds digit increments. If the checker looks only at the post-edge `q`, it sees ones = 0 and tens = 0, so it would conclude that neither the tens nor the hundreds enable should have been asserted. But those enables were correct for that edge. The mistake is not in the BCD arithmetic; it is in the temporal ordering used to evaluate the enable conditions.

A useful short worked example is the transition from `q = 0x0099` to `q = 0x0100` with reset low. The pre-edge digits are ones = 9, tens = 9, hundreds = 0, thousands = 0. The correct enables are therefore asserted for the tens and hundreds digits, and not for the thousands digit: `ena = 3'b011` under the natural mapping where the three bits correspond to the upper three digits. After the edge, `q = 0x0100`. If a checker instead computes enables from `0x0100`, it sees ones = 0, tens = 0, hundreds = 1, and would produce `ena = 3'b000`, which is wrong for the sampled row.

For the final Python checker, the important modeling point is to capture the pre-edge `q` for each sampled row, compute the expected `ena` from that captured value, and only then apply the synchronous update to obtain the next state. Reset must be handled with priority: when reset is high at the sampled edge, all digits become zero and the enable comparison should still be based on the pre-edge state as specified by the enable semantics, unless the checker’s reference model explicitly defines enables as don’t-care under reset. Mid-cycle input changes after sampling must not affect the current row; they belong to the next sampled edge. Separating pre-edge enable evaluation from post-edge state update is the key to avoiding carry-row mismatches.
