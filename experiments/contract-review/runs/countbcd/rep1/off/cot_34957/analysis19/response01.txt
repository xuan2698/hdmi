The key edge/mid-input distinction for the checker is that every row is classified by the values sampled at its own active clock edge, not by any later transition. The public spec says each row’s values are driven before the sampled edge, and optional mid-input changes occur after sampling and before the other edge. Therefore a mid-row change to `reset` (or to any input) belongs to the next row’s setup, not to the row just sampled. The checker should latch the sampled `reset` together with the sampled `q` and `ena` for that row, then validate the row using that latched reset. Re-reading a later `reset` while checking an earlier row is the classic failure mode: it can make a normal row look like a reset row, or vice versa, and it can corrupt the normal-to-normal progression chain.

For normal rows, enables must be decoded from the current sampled `q`, not from the next row’s `q` and not from a carry computed during the transition. The upper-digit enables are “increment this digit now” signals: `ena[0]` corresponds to the tens digit and is high when the ones digit is 9; `ena[1]` corresponds to the hundreds digit and is high when both ones and tens are 9; `ena[2]` corresponds to the thousands digit and is high when ones, tens, and hundreds are all 9. This is a lower-digit-all-9 condition, not “any lower digit is 9.” At `q = 0x0099`, `ena[0]` and `ena[1]` are high and `ena[2]` is low. At `q = 0x0999`, all three enables are high. At `q = 0x9999`, all three enables are high, and the next normal row should wrap to `0x0000`.

Reset rows are simpler: if the sampled `reset` is high, expected `q` and `ena` are zero regardless of the previous count. A mid-row change to `reset` must not retroactively alter the already-sampled row; it only affects the next sampled row. The checker should store the sampled `reset` alongside the sampled outputs for each row and use that stored value to classify the row. It should not re-read a later `reset` when validating an earlier row.

The checker should also avoid assuming any particular power-up state. The first sampled row is validated by its own sampled `reset`: high means expect zeros; low means treat it as a normal count row and decode enables from its `q`. There is no requirement that the first normal row be `0x0000` unless a reset row preceded it.

Finally, validate count progression only on normal rows. From a normal row with `q != 0x9999`, the next normal row should be the BCD increment of `q`; from `0x9999`, the next normal row is `0x0000`. Reset rows interrupt progression, and the public spec only fixes reset-row outputs to zero—it does not require the post-reset normal row to be `0x0000` unless normal counting from reset is also specified. The safest checker focus is: sampled reset forces zero outputs; normal rows have enables decoded from current `q`; normal-to-normal transitions follow BCD increment with wrap at `0x9999`.

Worked example: rows `q = 0x0009` (normal, `ena = 001`), then `q = 0x0010` (normal, `ena = 000`). The enable on the first row reflects the current ones digit being 9; the second row’s enables reflect its own digits, not the prior carry.
