The key checker insight is to separate three independent obligations and never let one mask another: reset-row output forcing, per-row enable decoding, and normal-to-normal BCD progression. Each sampled row should be classified using the `reset` value sampled at that same edge. A row with sampled reset high must have `q == 0x0000` and `ena == 000`; its predecessor and successor are irrelevant to that row’s output check. A row with sampled reset low is a normal row and must satisfy the enable equations derived from its own `q`, regardless of what happened before it.

For normal rows, decode enables directly from the sampled 16-bit value. Split it into four nibbles: ones `q[3:0]`, tens `q[7:4]`, hundreds `q[11:8]`, thousands `q[15:12]`. Each nibble must be a legal BCD digit, 0 through 9; values 10 through 15 are not valid counter states under the public specification. Then `ena[0]` is true exactly when ones equals 9. `ena[1]` is true exactly when ones equals 9 and tens equals 9. `ena[2]` is true exactly when ones, tens, and hundreds all equal 9. These are conjunctions of lower-digit conditions, not disjunctions and not “any lower digit equals 9.” A checker that computes `ena[1]` as “tens is 9” will fail at states such as `0x0019`, where tens is 1 and `ena[1]` must be low even though the ones digit is 9. Likewise `ena[2]` must not fire merely because hundreds is 9; it requires the two lower digits to be 9 as well.

Progression is a separate check between consecutive normal rows. If row A is normal and row B is the next normal row, then B must equal the BCD increment of A, with `0x9999` wrapping to `0x0000`. Reset rows break the chain: do not compare a normal row to a reset row, and do not compare a reset row to its successor as if counting continued. The public specification fixes reset-row outputs to zero but does not require the first normal row after reset to be zero unless normal counting from reset is also specified. Therefore a checker should not assume that a reset row forces the following normal row to `0x0000`; it should only require that following normal rows obey BCD increment among themselves. Similarly, the first normal row of a trace need not be zero. A legal trace can begin at `0x0042` with no preceding reset, and the checker must accept it by decoding enables from `0x0042` and then validating subsequent normal-to-normal transitions.

A useful worked example is a normal row at `0x0009` followed by a normal row at `0x0010`. At `0x0009`, ones is 9, so `ena[0]` is high; tens is 0, so `ena[1]` is low; hundreds is 0, so `ena[2]` is low. The next normal row must be the BCD increment, `0x0010`. At `0x0010`, no lower digit is 9, so all enables are low. The carry has already occurred in `q`; the enables on the second row describe the second row’s digits, not the prior row’s carry condition.

The final Python checker should therefore store, per sampled row, the sampled `q`, sampled `ena`, and sampled `reset`. It should validate reset rows first, then validate normal-row enable decoding, then validate normal-to-normal progression across adjacent normal rows only. It should reject illegal BCD nibbles in normal rows. It should not re-read `reset` after sampling, should not assume an initial zero state, and should not require a post-reset normal row to be zero. This structure directly matches the public specification and avoids the common false failures around mid-cycle reset changes and carry-derived enables.
