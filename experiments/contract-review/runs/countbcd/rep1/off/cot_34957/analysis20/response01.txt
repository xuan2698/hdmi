The public specification defines a 4-digit BCD counter with a 16-bit output `q` and a 3-bit enable output `ena`. The reset input is synchronous and active-high. The key behavioral points for a checker are: reset forces zero outputs on the sampled row; normal rows must have enables decoded from the current `q`; and normal-to-normal transitions must follow BCD increment with wrap at `0x9999`.

On reset and power-up: the specification does not define a power-up state. The first sampled row must be validated using its own sampled `reset` value. If that sampled reset is high, `q` and `ena` must both be zero. If it is low, the row is a normal count row, and the checker must decode `ena` from the sampled `q` rather than assuming any particular starting value. There is no requirement that the first normal row be `0x0000` unless a reset row preceded it. This matters because a checker that assumes the counter starts at zero would incorrectly reject a legal first normal row such as `0x0042`.

Reset is synchronous, so a mid-row change to `reset` must not retroactively affect the already-sampled row. The checker should store the sampled `reset` alongside the sampled outputs for each row and use that stored value to classify the row. It should not re-read a later `reset` when validating an earlier row. This is a common source of false failures: if the checker samples outputs at one edge and then reads `reset` after a mid-cycle change, it may misclassify a normal row as a reset row or vice versa.

The enable signals are lower-digit-all-9 conditions, not “any lower digit is 9.” `ena[0]` is high when the ones digit is 9. `ena[1]` is high when both ones and tens are 9. `ena[2]` is high when ones, tens, and hundreds are all 9. For example, at `q = 0x0099`, `ena[0]` and `ena[1]` are high and `ena[2]` is low. At `q = 0x0999`, all three enables are high. At `q = 0x9999`, all three enables are high, and the next normal row should wrap to `0x0000`.

Count progression should be validated only on normal rows. From a normal row with `q != 0x9999`, the next normal row should be the BCD increment of `q`; from `0x9999`, the next normal row is `0x0000`. Reset rows interrupt progression. The public spec only fixes reset-row outputs to zero; it does not require the post-reset normal row to be `0x0000` unless normal counting from reset is also specified. Therefore the safest checker focus is: sampled reset forces zero outputs; normal rows have enables decoded from current `q`; normal-to-normal transitions follow BCD increment with wrap at `0x9999`.

Worked example: rows `q = 0x0009` (normal, `ena = 001`), then `q = 0x0010` (normal, `ena = 000`). The enable on the first row reflects the current ones digit being 9; the second row’s enables reflect its own digits, not the prior carry.
