The distinguishing point is that `ena` is a *function of the current row's `q`*, not a prediction of the next row. A common checker bug is to compute enables from the previous row or to treat `ena` as "will increment next cycle." The spec ties `ena` to the sampled `q` on the same edge: for a row with `q = 0x0009`, `ena = 001` because the ones digit is 9; for `q = 0x0010`, `ena = 000` because no lower digit is 9. So the checker must decode enables from the row it is validating, independently of progression.

A second useful point: reset rows are terminal for progression but not for enable decoding. On a reset row, `q` and `ena` are both forced to zero, so the normal-row enable formula would coincidentally also give `ena = 000` at `q = 0`. That coincidence must not tempt the checker to treat reset rows as ordinary normal rows. Reset rows must be validated only as `q == 0` and `ena == 0`, and they must break the adjacent-normal-row chain in both directions. Do not compare a normal row to a preceding reset row, and do not compare a reset row to its successor as if counting continued.

A third point concerns trace boundaries. The spec does not require the first normal row to be zero, nor the first normal row after reset to be zero. A trace may legally begin at `0x0042`, and after a reset the counter may resume at any valid BCD value. Therefore the checker must not infer an initial state or a post-reset state. It should only enforce: reset-row outputs, per-row BCD validity and enable decoding, and normal-to-normal increment across adjacent normal rows with no reset between them.

Worked example: suppose a normal row has `q = 0x0099`. Ones=9 so `ena[0]=1`; tens=9 and ones=9 so `ena[1]=1`; hundreds=0 so `ena[2]=0`. Thus `ena = 011`. The next normal row must be `0x0100`. At `0x0100`, all enables are 0. If instead the next sampled row were a reset row, the checker must not require `0x0100`; it validates the reset row as `q=0, ena=0` and starts a fresh normal chain afterward.

Finally, sampling discipline matters: `q`, `ena`, and `reset` are read together at the rising edge after settling. The checker must not re-read `reset` later in the cycle, because mid-cycle changes occur after sampling and belong to the next row. This prevents false failures when reset is asserted or deasserted between edges.
