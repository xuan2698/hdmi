The key checker hazard is the Moore output timing on the transition row. Because `z` is a function of the installed state, the row that samples the first `1` while in S0 must report `z=1`, not `z=0`. A checker that computes `z` from the pre-transition state will be correct only while the machine remains in S0 (all-zero inputs) and will be wrong from the first `1` onward. This is the single most useful invariant for the final Python checker: emit `z` after installing the next state, not before.

The reset boundary is the other place where a naive checker drifts. `areset` is positive-edge triggered and asynchronous, but the checker samples it only after the posedge has settled. A sampled-high `areset` forces S0 with `z=0` for that row and must not consume the `x` bit on that row; conversion begins on the first row where `areset` is sampled low. A reset asserted after the sampled edge takes effect on the next row. Mid-row `x` changes are staged and carried to the start of the next row, so they never affect the current row's sampled value. The reference should therefore be anchored at the first sampled-high reset row, not at time zero, and the input index should advance only on rows where `areset` is sampled low.

Worked example: LSB-first `x = 0,1,0,1` represents value 10; its two's complement is 0110, so the LSB-first output is `0,1,1,0`. Row 1: S0, `x=0` → S0, `z=0`. Row 2: S0, `x=1` → S1, `z=1` (the distinguishing row). Row 3: S1, `x=0` → S1, `z=1`. Row 4: S1, `x=1` → S1, `z=0`. A pre-state checker instead yields `0,0,1,1`, which is wrong from row 2 onward. Note also that S1 is absorbing until reset, so once the first `1` is seen, every subsequent row outputs `z=1` regardless of `x`; the checker must not "recompute" the complement per bit.
