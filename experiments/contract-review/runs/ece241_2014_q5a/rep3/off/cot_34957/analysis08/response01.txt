The reset behavior is the first thing the final checker must pin down, because it determines what "pre-edge state" even means on the very first sampled row. `areset` is positive-edge-triggered and asynchronous, so a row with `areset=1` does not merely schedule a reset for the next edge — it forces the machine into the reset state and forces the reset output for that row. The checker should treat reset as dominant over `x`: on any row where `areset=1`, `x` is ignored, the state is the reset state, and `z` is the reset output. There is no "half-reset" row where the state is reset but the output still reflects the previous conversion, nor a row where `x` is allowed to advance the state while reset is asserted. This matters because a common implementation bug is to let the state update logic run unconditionally and only gate the output, or vice versa; the checker's reset-dominance rule catches both.

Power-up is the second point. Before the first sampled edge, the machine has no defined history, so the checker must not assume any particular pre-edge state on row 1 unless `areset=1` on that row. The public spec says conversion begins when Reset is released, which means the checker should expect the first meaningful row to be the one where `areset` transitions from 1 to 0, and the state on that row should be the reset state carried forward from the prior reset row. If the trace begins with `areset=0` and no prior reset row, the checker has no basis to predict `z` or the next state from the public spec alone; it should either require an initial reset row or treat the first row as unconstrained for state, while still enforcing Moore alignment (output from whatever pre-edge state the design reports) on subsequent rows.

The Moore alignment rule is the core of the timing discipline. The checker samples `x`, `areset`, and the current state at the posedge, computes `z` from the pre-edge state, then updates the state from `x`. Mid-row input changes occur after sampling and belong to the next row; they must not retroactively alter the just-sampled `z` or the state transition. This ordering — reset dominance, then output from pre-edge state, then state update from `x`, then carry mid-row changes forward — is the single evaluation order the checker should implement.

The worked example above (`0100` LSB-first, output `0011`) illustrates why the first-`1` boundary is the highest-value assertion: on the row where `x=1` first appears in COPY, `z` must be `1`, and a post-transition-output bug produces `0` there. Because the following row also outputs `1` on this trace, a checker that skips the boundary row would pass a broken design. The final checker should therefore assert the boundary explicitly, enforce reset dominance, and reject any retroactive mid-row effect.
