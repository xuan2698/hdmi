The most useful implementation mistake to target in the final checker is an off-by-one in the state/output relationship at the first `1` bit. The spec's machine is a Moore machine: `z` is a function of the *current* (pre-edge) state, not the next state. A common buggy implementation computes the output after deciding the transition, so on the row where `x = 1` first appears while the machine is still in `COPY`, it emits the inverted value (`~1 = 0`) instead of the copied value (`1`). The state then correctly moves to `INVERT`, and all subsequent rows look right. The trace is wrong only at that single boundary row.

A short worked example makes the failure concrete. Suppose the input bit stream (LSB first) is `0, 1, 0, 0`, representing the number `2`. The correct 2's complement is `...1110`, so the output stream should be `0, 1, 1, 1` (the leading `0` is the copy of the low bit, then inversion). Row 1: `areset` released, state `COPY`, `x = 0`, so `z = 0`, next state `COPY`. Row 2: state `COPY`, `x = 1`, so `z = 1`, next state `INVERT`. Row 3: state `INVERT`, `x = 0`, so `z = 1`, state stays `INVERT`. Row 4: `z = 1`. Correct output `0,1,1,1`. A post-transition-output design instead emits `0,0,1,1` — it transitions to `INVERT` before computing `z` on row 2. A checker that only compares the final accumulated value, or that only checks that "some" later rows are `1`, will pass this buggy design. The checker must assert the boundary row explicitly: whenever the sampled pre-edge state is `COPY` and `x = 1`, require `z = 1` and require the next state to be `INVERT`.

Two related traps deserve mention because they interact with the same sampling discipline. First, reset dominance: on any row where `areset` is sampled high, the state must be forced to `COPY` and the output must be the `COPY` output for that row (here `z = 0`). A design that gates only `z` while still advancing state, or that advances state unconditionally, diverges even though its output on the reset row may look correct. Second, mid-row changes: the protocol says optional mid input changes occur after sampling and are carried to the start of the next row. They must not retroactively alter the just-sampled `z` or the transition taken on that row. A checker that reads `x` or `areset` at the wrong moment — for example, after a mid-row change — can misclassify a correct design as failing at the boundary row, or mask the post-transition-output bug.

So the final checker should: leave the first state unconstrained or require an initial reset row; enforce reset dominance on every `areset = 1` row; compute `z` from the pre-edge state before applying the `x`-driven transition; carry mid-row changes forward only; and explicitly assert the first-`1` boundary row (`COPY` with `x = 1` gives `z = 1` and next state `INVERT`). That single boundary assertion is the highest-value check, because it is exactly where the most plausible implementation mistake hides.
