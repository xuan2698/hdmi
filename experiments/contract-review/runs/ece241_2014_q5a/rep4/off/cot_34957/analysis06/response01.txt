One common implementation mistake is to treat the 2's complement conversion as a combinational function of the current input bit rather than as a state-dependent serial process. The specification says the input arrives least-significant bit first, and the output is the 2's complement of the whole number. A naive implementation might try to output `x` directly, or invert `x`, or use a rule like "output the input until the first 1, then invert everything after." That last rule is actually the right intuition for a serial 2's complementer, but it must be encoded as a Moore state machine: the output depends only on the current state, and the state records whether a 1 has already been seen in the input stream.

The key state distinction is between "no 1 seen yet" and "a 1 has been seen." In the first state, the output is the same as the input bit, because the trailing zeros of the original number remain zeros in the 2's complement. Once the first 1 is encountered, the machine moves to the second state, and from then on the output is the complement of the input bit. The transition is: from the initial state, if `x=0`, stay in the initial state; if `x=1`, go to the "seen a 1" state. From the "seen a 1" state, stay there regardless of `x`. The output in the initial state is 0, and the output in the "seen a 1" state is 1. Wait—that is not quite right, because the output must depend on the state only, not on `x`. Let me correct that: the Moore output is associated with the state, but the state must encode enough information to produce the correct output for the current bit. Actually, for a serial 2's complementer, the output at each cycle is the current input bit if no 1 has been seen yet, and the complement of the current input bit once a 1 has been seen. That means the output cannot be a pure function of the state alone unless the state also incorporates the current input bit, which is not allowed in a Moore machine. The standard solution is to use a Mealy machine, or to delay the output by one cycle. But the specification explicitly says Moore state machine. Therefore the correct Moore design must have states that represent the combination of "whether a 1 has been seen" and "the current input bit," or equivalently, the output is registered and corresponds to the previous input bit. This is a subtle point: a Moore machine cannot output a function of the current input, so the output must be based on the state, which can only reflect past inputs. The conversion therefore produces the 2's complement with a one-cycle delay, or the state must be defined so that the output is the correct bit for the current position given the history. The checker must follow the actual state/output table implied by the Moore requirement, not the intuitive combinational rule.

A short worked example: suppose the input stream is `0, 1, 0` (LSB first). The number is binary `010` = 2. Its 2's complement in 3 bits is `110` = 6, so the output stream should be `0, 1, 1` if aligned with the input, or shifted if the Moore output is delayed. A checker that computes `z` from `x` directly would produce `0, 1, 0` or `0, 0, 1` depending on the rule, and would fail. The correct checker must use the state transition table and the state-only output, and must account for the reset behavior and the sampling edge as described.
