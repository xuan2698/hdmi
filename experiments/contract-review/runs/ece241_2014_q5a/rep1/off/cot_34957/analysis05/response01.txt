The key point for the final checker is Moore latency: `z` is a function of state alone, so the value sampled after a posedge reflects the state entered from the `x` history up to and including that edge, not a combinational transform of the current `x`. The checker should therefore maintain the expected Moore state from sampled `x` since reset release and compare sampled `z` against that state's output. Equivalently, the observable output stream is the 2's-complement bit stream delayed by one Moore step, with the initial state contributing `z=0`.

Reset is an asynchronous boundary: asserting `areset` must clear state and drive `z=0` without waiting for a posedge. Releasing `areset` does not itself emit a conversion result; the first meaningful sample is the next posedge after release. Mid-cycle `x` changes occur after sampling and belong to the next row, so they must not retroactively alter an already-sampled `z`.

Worked example: after reset release, suppose sampled `x` is `0, 0, 1` LSB-first. Before the first `1`, the machine stays in its initial region and sampled `z` is `0`. At the edge where sampled `x=1`, it enters the first-one state and sampled `z` becomes `1`. A mid-cycle `x` change after that sample is carried to the next row only; the captured `z=1` for the first-one edge remains valid.

Thus the checker should sample after the posedge settles, treat `areset` as an asynchronous override, derive expected `z` from the Moore state implied by prior sampled `x` rather than current `x`, and allow the inherent one-cycle output latency. It should not over-constrain internal state count or encoding; verify only the public input/output relation and reset semantics.
