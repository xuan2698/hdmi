**Reset and power-up behavior**

The specification defines eight D flip-flops sharing a single clock, `clk`, and a single active-high synchronous reset, `reset`. The data input is an 8-bit bus `d`, and the output is an 8-bit bus `q`. All eight flip-flops are triggered by the positive edge of `clk`. Because the reset is synchronous and active high, asserting `reset=1` does not immediately force `q` to zero; the clearing action occurs only at a rising clock edge, and only if `reset` is high at that sampled edge. When `reset=1` at a positive edge, every flip-flop loads zero regardless of `d`. When `reset=0` at a positive edge, each flip-flop loads its corresponding bit of `d`. Between edges, `q` holds its last loaded value.

Power-up is the subtle part. The public specification does not state an initial value for `q`. It says the flip-flops have synchronous reset, but it does not promise that power-up clears them, nor does it give a reset pulse at time zero. Therefore a checker must not assume `q=0` before the first sampled positive edge. The only values of `q` that the specification constrains are those produced by a sampled edge: either a reset edge that loads zero, or a normal edge that loads `d`. Before any such edge has been observed, `q` is unspecified from the checker’s point of view. A robust checker should either wait for an explicit initialization event in the testbench or begin comparing only after the first sampled edge whose behavior is defined by the stimulus. Inventing an initial zero is a common but unsupported assumption.

The timing protocol adds a second discipline. Inputs are driven before the sampled edge. Optional mid-cycle input changes occur after sampling and before the other edge, and those changes are carried to the start of the next row. This means the checker must distinguish the inputs present at the sampled edge from the inputs that will be present at the next sampled edge. A mid-cycle `reset=1` must not clear `q` immediately; it only affects the next positive edge. Likewise, a mid-cycle change on `d` must not retroactively alter the value just loaded. The settled output after an edge reflects the pre-edge inputs, while any post-edge changes are pending for the following row.

A short worked example: suppose before a rising edge `reset=0`, `d=8'hA5`, and the current settled `q` is `8'h00`. After the edge settles, expected `q` is `8'hA5`. If a mid-cycle change then asserts `reset=1`, `q` remains `8'hA5` until the next sampled rising edge; at that next edge, with `reset=1`, `q` becomes `8'h00`. If instead the mid change sets `d=8'h3C` while `reset` stays 0, the next edge loads `8'h3C`, and `8'hA5` remains valid until then.

For the final Python checker, the useful point is to model one 8-bit state, sample only at positive edges after settling, and apply mid-cycle updates only to the next row. That ordering rule prevents asynchronous reset handling, late `d` changes affecting the previous edge, and unsupported power-up assumptions.
